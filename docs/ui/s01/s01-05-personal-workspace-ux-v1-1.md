## 1. 产品定位与设计原则

### 1.1 产品定位

Personal Workspace 是用户登录 smark-pm 后的默认工作入口。

它以人为中心，跨项目汇总当前用户有权访问的工作信息，帮助用户快速判断：

1. 今天有哪些事情需要我处理？
2. 有哪些事情需要我做出决定？
3. 哪些项目需要我关注？
4. 我可以从哪里快速开始新的工作？

### 1.2 核心原则

| 原则 | 设计要求 |
| --- | --- |
| Human-centric | 以人的工作为组织中心 |
| Cross-project | 支持跨项目工作汇总 |
| Action-oriented | 优先展示需要采取行动的事项 |
| Non-duplicative | 不重复建设项目内业务管理功能 |
| AI-assisted | AI 是全局辅助能力，不抢占首页主体 |
| Permission-aware | 只展示当前用户有权访问的数据 |

### 1.3 产品结构

```text
Personal Workspace（默认登录入口）
├── My Workspace       个人工作概览与快捷入口
│   ├── My Overview
│   ├── My Projects
│   ├── Watchlist
│   ├── Recent Activity
│   └── Quick Actions
├── My Inbox           独立工作处理页面
│   ├── Human Actions
│   ├── Assigned Tasks
│   └── Completed / History
└── Project Workspace  具体项目管理与执行
```

说明：My Inbox 与 My Workspace 是同一层级的个人工作区域，不是某个项目的子页面。

## 2. 全局导航设计

个人工作台采用全局 Shell，不创建独立的导航体系。

### 2.1 一级导航

| 导航项 | 功能 | 页面类型 |
| --- | --- | --- |
| My Workspace | 个人工作首页 | 传统 Page |
| My Inbox | 个人待处理中心 | 传统 Page |
| My Projects | 我的项目 | 传统 Page |
| Activity | 跨项目动态 | 传统 Page |

其中 My Projects 与 Activity 可以先采用首页区域和筛选视图实现，是否独立成为一级路由不作为 V1.1 的强制要求。

### 2.2 全局功能

- 全局搜索。
- 全局 AI 助手入口。
- 通知中心。
- 用户个人设置。
- 当前项目上下文（进入项目后显示）。

全局 AI 入口不能被误认为当前项目 AI Agent 的执行入口。两者需要明确作用范围。

### 3.2 首屏区域优先级

| 区域 | 优先级 | 首屏要求 |
| --- | --- | --- |
| 页面标题及快捷操作 | P0 | 必须 |
| 工作摘要 | P0 | 必须 |
| My Inbox 摘要 | P0 | 必须 |
| My Projects | P0 | 必须 |
| Watchlist | P1 | 可根据屏幕空间显示 |
| Recent Activity | P1 | 可向下滚动 |
| 最近访问 | P2 | 可以合并至项目入口 |

### 3.3 快捷操作：Create Project

新增用户裁决要求：首页必须提供明显的 Create Project 快捷入口。

交互流程：

1. 用户点击 Create Project。
2. 进入 S01-02 Project Creation UX 定义的项目创建流程。
3. 用户填写项目必要信息。
4. 提交创建。
5. 创建成功后进入对应 Project Workspace。
6. 返回个人工作台时，该项目出现在 My Projects 的 Active 分组。

两个重要约束：

- 不在个人工作台重新实现项目创建表单。
- 创建项目后不要求用户先配置 Repository 才能拥有项目；沿用 S01-02 已确认的项目创建规则。

快捷入口应当在首页保持可发现性，但不需要制作成占据大量空间的独立面板。

## 4. My Inbox 独立页面设计

### 4.1 页面定位

My Inbox 是用户跨项目的统一工作处理中心。

它不仅仅是通知中心，也不是简单的个人任务列表。

它负责把不同业务领域中需要当前用户采取行动的事项，聚合为统一的个人工作队列。

### 4.2 双分区结构

根据 Q2 裁决，采用两个相互独立的分区。

```text
My Inbox
All projects · Personal action queue

┌────────────────────────────┐  ┌────────────────────────────┐
│ 06                         │  │ 04                         │
│ Human Actions              │  │ Assigned Tasks             │
│ 决策、审批、验收、补充信息、异常 │  │ 分配给我的普通工作任务       │
└────────────────────────────┘  └────────────────────────────┘

Human Actions
 [Overdue]  Project A   Confirm architecture decision
            需要人类确认后继续推进
 [Approval] Project B   Approve document proposal

Assigned Tasks
 [In Progress] Project A   Review module implementation
```

### 4.3 Human Actions 分类

| 分类 | 说明 | 示例 |
| --- | --- | --- |
| Decisions | 待决策 | 需求变更确认、架构方案确认 |
| Approvals | 待审批 | 知识提案审批、权限审批 |
| Reviews | 待验收 | 任务交付验收、成果审查 |
| Needs Input | 待补充 | 需求澄清、AI 请求补充信息 |
| Attention | 需要关注 | 阻塞、执行异常、重要风险 |

注意：Attention 不代表所有风险都必须转化成待办。只有存在明确的人类处理责任时，才进入 Human Actions。

### 4.4 Assigned Tasks 分类

只纳入符合以下条件的普通任务：

- 有明确的当前用户负责人或有效分配关系。
- 任务仍处于需要处理的状态。
- 当前用户具有查看权限。
- 不是仅供参考的 AI 执行事件。

普通任务不与 Human Actions 混在一起排序。

### 4.5 待办排序规则

Q3 裁决：采用紧急程度优先。

建议排序逻辑：

1. 已逾期事项。
2. 高紧急程度且仍待处理的事项。
3. 即将到期事项。
4. 普通待处理事项。
5. 无明确期限的其他事项。

同等紧急程度下，优先展示具有明确人工阻塞影响的事项。

重要约束：

- 不能凭 AI 自行推断一个事项已经逾期。
- 不能把更新时间直接当成紧急程度。
- 没有截止时间时，不得虚构期限。
- 不允许因为某事项来自 AI，就自动提升其优先级。

### 4.6 Inbox 的筛选能力

建议支持：

- 按项目筛选。
- 按行动类型筛选。
- 按优先级筛选。
- 按逾期状态筛选。
- 按创建时间筛选。

默认展示全部活动事项。

### 4.7 操作规则

Inbox 是聚合入口，不是业务操作的替代实现。

例如：

- 决策：跳转至对应决策对象，执行正式确认。
- 审批：进入原审批流程。
- 验收：进入对应交付验收页面。
- 补充信息：进入相关业务上下文。
- 普通任务：进入任务详情。

所有正式操作继续遵守所属领域的权限、状态机和审计要求。

## 5. My Projects 设计

### 5.1 项目展示范围

Q4 裁决：采用分组展示。

默认结构：

- Active Projects
- Archived Projects

默认进入 Active Projects。

### 5.2 项目卡片信息

| 字段 | 展示要求 |
| --- | --- |
| Project Name | 必须 |
| Project Role | 必须 |
| Project Status | 必须 |
| My Pending | 建议 |
| Last Activity | 建议 |
| Attention Indicator | 有真实关注事项时显示 |

不建议展示每个项目的完整任务数量、需求数量、Agent 数量等统计信息。

这些内容属于项目总控台。

### 5.3 项目操作

- 打开项目。
- 创建新项目。
- 查看归档项目。
- 从最近访问恢复工作。
- 在权限允许的情况下执行项目切换。

项目卡片点击进入项目总控台，具体页面遵循 S01-02 及 S01-03 已确认的 UX。

### 5.4 多项目和空状态

| 场景 | 行为 |
| --- | --- |
| 没有项目 | 展示 Create Project 和 Join Project 入口（后者需有对应能力） |
| 只有 Active 项目 | 只显示 Active 分组 |
| 有归档项目 | 展示 Archived 分组 |
| 项目数量较多 | 支持搜索、筛选和分页或渐进加载 |
| 项目权限失效 | 不继续展示已无权访问的项目内容 |

## 6. Watchlist 设计

### 6.1 产品定位

Watchlist 是用户主动关注的跨项目业务对象集合。

与 Inbox 的区别：

| 维度 | Inbox | Watchlist |
| --- | --- | --- |
| 产生方式 | 系统或业务责任分配 | 用户主动关注 |
| 目的 | 采取行动 | 持续跟踪 |
| 是否要求操作 | 通常需要 | 不一定 |
| 生命周期 | 业务事项处理完成后退出 | 用户取消关注或对象不可访问时退出 |

### 6.2 关注对象

UX 允许展示：

- Project
- Task
- Requirement
- Repository
- Agent Run
- Risk / Blocker

但具体支持哪些对象类型，需要以实际领域能力核验。

V1.1 不擅自要求增加新的 Watchlist 数据实体。

## 7. Recent Activity 设计

### 7.1 产品定位

展示用户参与项目中的近期重要动态。

来源分为：

| 类型 | 标识 |
| --- | --- |
| Human | 人类操作 |
| AI Agent | AI 执行 |
| System | 系统事件 |

### 7.2 展示规则

动态记录应具备：

- 来源项目。
- 发生时间。
- 事件类型。
- 事件摘要。
- 关联业务对象。
- 详情入口。

默认只展示重要动态，避免把所有系统事件都推送到个人首页。

### 7.3 AI 信息表达

需要严格区分：

- AI 已完成执行。
- AI 已提交提案。
- 人类已经确认。
- 系统已经正式提交。

不能将 AI 提案描述成已经批准的正式结果。

这与整个 smark-pm 的 Human-led 设计原则保持一致。

## 8. 全局 AI 助手设计

Q5 裁决：A。不在首页设置独立 AI 面板。

具体规则：

1. 保留全局 AI 助手入口。
2. 不在个人首页放置 AI 聊天卡片。
3. 不将 AI 工作简报强制插入首页。
4. 用户从全局入口进入 AI 能力时，明确当前上下文。
5. 进入项目后，可以根据当前项目切换到对应的项目 AI 能力。

个人工作台负责人的工作，AI 助手负责辅助人的工作，两者不应该争夺首页的主要视觉空间。

## 9. 页面状态与异常处理

### 9.1 首次登录

```text
        ┌──────────────────────────────────────────────┐
        │                                              │
        │        Welcome to smark-pm                   │
        │        Your personal workspace starts here.  │
        │                                              │
        │            [ 文件夹+图标 ]                    │
        │                                              │
        │        You don't have any projects yet.      │
        │   Create your first project to start         │
        │   organizing your development work.          │
        │                                              │
        │            [   Create Project   ]            │
        │                                              │
        └──────────────────────────────────────────────┘
```

首次登录不能用虚构任务、动态或项目数量填充页面。

### 9.2 无待办状态

显示：

- All caught up.
- 当前没有需要处理的人工事项。
- 可以继续查看项目和最近动态。

不能显示错误警告来制造紧张感。

### 9.3 数据加载失败

必须区分：

- 真正没有数据。
- 正在加载。
- 加载失败。
- 当前用户无权访问。

不能把 API 失败误认为用户没有待办。

### 9.4 权限变化

如果用户退出某个项目或项目成员权限发生变化：

- 后续聚合不再展示其无权访问的数据。
- 个人待办需要重新校验可访问性。
- 已打开的对象如果权限失效，应展示明确的无权限反馈。
- 不允许通过个人工作台的聚合接口绕过项目权限。

## 11. 数据与技术实现约束

本设计是 UX 基线，不等于已确认后端接口。

实施前需要对现有数据能力进行核验。

| 功能 | 需要核验的能力 | 设计要求 |
| --- | --- | --- |
| 我的项目 | 项目成员及权限查询 | 只查询授权项目 |
| Human Actions | 决策、审批、验收等待处理记录 | 统一聚合 |
| Assigned Tasks | 任务负责人及状态 | 与人工介入事项分区 |
| 优先级排序 | 截止时间、优先级、逾期状态 | 不虚构排序依据 |
| Watchlist | 用户关注关系 | 不擅自新增实体 |
| Activity Feed | 项目事件和执行事件 | 区分来源 |
| Create Project | 已有项目创建流程 | 复用 S01-02 |
| 全局 AI 入口 | 现有 AI 调用及上下文能力 | 明确作用范围 |

### 11.1 聚合一致性原则

个人工作台属于跨领域读模型的消费端。

因此建议遵守：

1. 不在前端通过多个业务表拼装正式业务状态。
2. 不在前端自行推断待办是否完成。
3. Inbox 中的事项必须可以追溯到原始业务对象。
4. 每一条事项必须保留来源项目和权限上下文。
5. 聚合失败时不能伪装成空结果。
6. 同一业务事项不能因多条事件而重复出现。

如果现有 API 不具备完整的跨项目聚合能力，应在技术设计阶段评估项目级聚合读模型或专门的个人工作台读模型。

不能在 UX 阶段直接假定接口已经存在。

本设计完成后，至少需要通过以下验收。

| 编号 | 验收条件 |

| AC-01 | 用户登录后默认进入个人工作台 |

## 16. 最终设计结论

V1.1 裁决收编完成。

**Personal Workspace：一个人的工作入口，而不是所有项目的统计报表。**

最终产品结构：

1. My Workspace：我的工作概览。
2. My Inbox：我的人工介入事项和分配任务。
3. My Projects：我参与的所有项目。
4. Watchlist：我主动关注的事项。
5. Recent Activity：近期重要动态。
6. Create Project：随时开始一个新项目。
7. Global AI：全局 AI 辅助入口。

核心设计原则：

> 用户进入系统，第一眼看到的是自己需要做的工作，而不是系统拥有多少数据、多少 Agent、多少任务。
