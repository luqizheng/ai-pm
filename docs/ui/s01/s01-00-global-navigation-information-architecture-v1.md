## 1. 设计目标

建立统一、稳定、可扩展的产品导航体系，为后续所有业务模块提供一致的入口组织方式。

本设计需要解决：

1. 用户如何从全局进入个人工作台、项目和系统管理功能。
2. 用户如何在一个项目内部找到不同业务阶段的功能。
3. 如何区分个人级、项目级和系统级功能。
4. 如何提前展示规划中的功能，同时明确区分已开放与未开放能力。
5. 如何避免随着 S01～S08 的推进，不断修改主菜单结构。

### 1.1 核心设计原则

- 全局导航与项目内部导航分离。
- 不引入 Workspace 业务概念。
- AI 能力融入项目业务流程，不设独立的全局 AI 协作中心。
- 项目内部以业务阶段组织，而不是以技术模块或数据库实体组织。
- 未来规划中的功能可以提前展示，必须明确标记开放状态。
- 项目设置与全局系统设置严格区分。
- 导航名称使用业务语言，避免暴露内部技术实现。

## 2. 用户裁决记录

| 问题 | 裁决 | 最终决定 |
|---|---|---|
| Q1：是否保留全局 AI 协作中心 | A | 不保留，AI 融入项目和个人工作台 |
| Q2：项目内部导航组织方式 | B | 按业务阶段分组 |
| Q3：未来功能展示方式 | B | 显示未实现菜单，并标记即将开放 |

以上为 V1.0 的强制设计约束，不得在后续视觉设计中自行改变。

## 3. 产品导航总体结构

产品采用两层主要导航体系：

- Global Navigation：全局主导航
- Project Navigation：项目内部导航

用户从全局导航进入项目后，切换到对应项目的内部导航。

### 3.1 导航结构

```text
Application
│
├── Global Navigation
│   │
│   ├── 工作台
│   ├── 项目
│   ├── 开发环境
│   ├── 组织管理
│   ├── 审计与安全
│   └── 系统设置
│
└── Project Context
    │
    ├── 项目总控台
    │
    ├── 规划与需求
    │   ├── 目标与计划
    │   ├── 需求管理
    │   └── 任务管理
    │
    ├── 分析与设计
    │   ├── 需求分析
    │   ├── 技术设计
    │   ├── 架构决策
    │   └── 实施准备
    │
    ├── 执行与交付
    │   ├── AI 执行
    │   ├── 异常处理
    │   └── 交付验收
    │
    ├── 项目知识

        └── 项目配置
```

说明：

Project Context 不是 Workspace，也不是独立业务实体，而是用户当前进入的项目上下文。

## 4. Global Navigation 详细定义

### 4.1 工作台（Personal Workbench）

**定位：个人工作入口。**

聚合用户跨项目的工作事项，不承担具体项目业务管理职责。

主要内容：

- 个人待办
- Inbox
- 待处理事项
- 跨项目任务
- 我的项目
- 最近访问项目

AI 助手采用工作台内部的辅助交互形态，不建立独立 AI 协作中心。

工作台不拥有项目，不管理项目生命周期。

### 4.2 项目（Projects）

**定位：项目发现、创建和进入入口。**

主要功能：

- 项目列表
- 创建项目
- 项目搜索
- 项目筛选
- 项目状态
- 最近访问项目
- 项目归档入口（按照实际权限开放）

项目列表是项目的全局入口。

进入某个项目后，切换到该项目的 Project Navigation。

### 4.3 开发环境（Development Environment）

**定位：用户开发能力与开发环境接入管理。**

主要内容：

- 开发设备
- Codex 接入
- MCP 配置
- 开发工具接入
- 环境连接状态
- 环境健康状态

注意：

全局开发环境与项目内部 AI 执行环境不是同一个概念。

全局层负责开发环境及其接入能力，项目层负责项目所需的执行配置与关联。

### 4.4 组织管理（Organization）

**定位：组织级身份和权限管理。**

主要内容：

- 组织成员
- 邀请成员
- 成员角色
- 权限管理
- 授权管理

不在这里管理具体项目的需求、任务和项目成员工作。

### 4.5 审计与安全（Audit & Security）

**定位：组织级安全治理和行为追踪。**

主要内容：

- 操作审计
- 用户行为记录
- AI 操作记录
- 权限变更记录
- 授权记录
- 安全事件

项目内具体业务的决策记录仍属于项目业务上下文，不应全部搬入全局审计中心。

### 4.6 系统设置（System Settings）

**定位：全局系统配置与个人偏好。**

主要内容：

- 个人资料
- 个人偏好
- 通知设置
- 界面设置
- 系统配置
- 集成配置（全局级）

系统设置与项目设置严格区分。

## 5. Project Navigation 详细定义

项目内部按照业务阶段分组。

### 5.1 项目总控台（Project Overview）

项目进入后的默认首页。

主要展示：

- 项目整体状态
- 项目目标与进度
- 当前阶段
- 需求和任务总体情况
- AI 执行状态
- 交付状态
- 阻塞与异常
- 需要人类处理的重要事项

项目总控台是项目状态的聚合视图，不是所有业务功能的替代入口。

### 5.2 规划与需求（Planning & Requirements）

| 菜单 | 主要职责 |
|---|---|
| 目标与计划 | 项目目标、里程碑和阶段规划 |
| 需求管理 | 原始需求、正式需求、需求治理、确认和追踪 |
| 任务管理 | 任务规划、分配、依赖与执行准备 |

重要边界：

需求管理负责需求生命周期，不等同于任务管理。

任务是需求实现和项目交付过程中的执行单元。

### 5.3 分析与设计（Analysis & Design）

| 菜单 | 主要职责 |
|---|---|
| 需求分析 | 需求分析、澄清、问题识别和分析结果 |
| 技术设计 | 技术方案、详细设计、设计修订 |
| 架构决策 | ADR、技术决策及决策记录 |
| 实施准备 | 实施基线、技术准备和实施约束 |

说明：

S03 的设计切片是内部设计与治理工作单元，不直接映射为一级导航。

分析与设计是一个完整业务区域，保持统一入口。

### 5.4 执行与交付（Execution & Delivery）

| 菜单 | 主要职责 |
|---|---|
| AI 执行 | Agent 执行、执行进度、执行结果 |
| 异常处理 | 执行异常、冲突、阻塞和人工介入 |
| 交付验收 | 交付清单、交付状态、验收与确认 |

重要边界：

AI 执行不等于人类确认。

人类决策和正式确认必须通过对应业务流程完成。

### 5.5 项目知识（Project Knowledge）

| 菜单 | 主要职责 |
|---|---|
| 项目认知 | AI-PM 对项目的理解、发现与认知状态 |
| 知识库 | 项目正式知识、文档、知识沉淀和发布 |

项目认知与知识库必须保持概念区分：

- 项目认知：系统对项目的理解。
- 知识库：经过治理的项目知识资产。

AI 的认知结果不能自动等同于已经确认的正式知识。

### 5.6 项目设置（Project Settings）

| 菜单 | 主要职责 |
|---|---|
| 仓库管理 | 仓库关联、Primary Repository、仓库接入 |
| 项目成员 | 项目成员和项目级权限 |
| 项目配置 | 项目属性、项目集成和项目级配置 |

仓库管理属于项目配置能力，不作为项目主导航中的独立一级菜单。

项目初始化过程也不作为长期独立菜单，而作为项目总控台中的状态和操作入口。

## 6. 菜单开放状态管理

采用三种状态：

| 状态 | 展示方式 | 用户行为 |
|---|---|---|
| 已开放 | 正常菜单 | 可以进入 |
| 即将开放 | 菜单可见，显示 Coming Soon | 不进入未实现页面 |
| 无权限 | 根据权限策略隐藏或显示受限状态 | 不允许访问 |

### 6.1 未来功能展示规则

用户已裁决：选择 B。

因此：

- 规划中的菜单可以提前出现。
- 未实现菜单显示 Coming Soon 标签。
- Coming Soon 不代表功能已经具备。
- 点击未开放菜单时，不进入空白页面。
- 不允许使用虚假数据模拟已经完成的功能。
- 功能进入实际实施阶段后，移除 Coming Soon 标签。

菜单开放状态应由功能实施状态驱动，不由页面设计人员自行判断。

### 6.2 阶段映射

| 菜单 | 规划阶段 | 初始状态建议 |
|---|---|---|
| 工作台 | S01 | 已开放 / 实施中 |
| 项目 | S01 | 已开放 / 实施中 |
| 开发环境 | S01 | 已开放 / 实施中 |
| 组织管理 | 基础能力 | 按实际能力开放 |
| 审计与安全 | 基础治理 | 按实际能力开放 |
| 系统设置 | S01 基础 UI | 已开放 / 实施中 |
| 项目总控台 | S01 | 已开放 / 实施中 |
| 目标与计划 | 后续项目规划能力 | 即将开放 |
| 需求管理 | S02 | 按 S02 实施状态开放 |
| 需求分析 | S03 | 按 S03 实施状态开放 |
| 技术设计 | S03 | 按 S03 实施状态开放 |
| 架构决策 | S03 | 按 S03 实施状态开放 |
| 实施准备 | S03 | 按 S03 实施状态开放 |
| 任务管理 | S04 | 即将开放 |
| AI 执行 | S05 | 即将开放 |
| 异常处理 | S06 | 即将开放 |
| 交付验收 | S07 | 即将开放 |
| 项目认知 | S01 | 按实际能力开放 |
| 知识库 | S08 | 即将开放 |

注意：上表是导航规划状态建议，不是代码实现完成度的核验报告。后续应以正式阶段验收和实际能力为准。

## 7. 导航交互规范

### 7.1 全局与项目上下文切换

- 全局导航始终提供返回项目列表和工作台的能力。
- 进入项目后，显示当前项目名称。
- 提供项目切换入口。
- 项目切换后进入目标项目的总控台。
- 项目内部导航不得与全局导航混淆。

### 7.2 页面状态

每个菜单页面需要支持：

- 默认状态
- 加载状态
- 空状态
- 错误状态
- 无权限状态
- Coming Soon 状态（仅适用于未开放功能）

### 7.3 导航状态保持

- 当前选中的菜单需要清晰高亮。
- 当前分组需要反映展开状态。
- 页面刷新后尽可能恢复有效路由。
- 浏览器前进、后退应正常工作。
- 项目内部页面应保持项目上下文。
- 不应因菜单折叠而丢失当前页面状态。

### 7.4 响应式设计

桌面端：

- 全局导航与项目导航具有清晰的层级。
- 支持导航折叠。
- 折叠后使用图标和 Tooltip。

小屏幕：

- 导航转为抽屉式或其他适合小屏的交互方式。
- 不得简单压缩桌面端菜单导致内容拥挤。

## 8. 菜单设计与业务实体的边界

以下内容明确不作为一级主菜单：

| 内容 | 原因 |
|---|---|
| AI 协作中心 | AI 是项目流程中的参与者 |
| Workspace | 产品没有 Workspace 业务实体 |
| 仓库管理 | 项目设置下的功能 |
| 项目初始化 | 项目生命周期中的阶段状态 |
| ADR 各类子流程 | 归属于架构决策 |
| S03 各个设计切片 | 归属于分析与设计 |
| AI Agent 列表 | 归属于项目 AI 执行上下文 |
| 单个需求、任务、文档 | 业务对象，不是一级菜单 |

## 9. 视觉设计要求

### 9.1 整体风格

- 专业的 AI 项目管理 SaaS。
- 信息密度适中。
- 强调清晰的信息层级。
- 避免过度装饰。
- 导航具有长期扩展能力。
- 统一使用设计系统中的颜色、间距、字体和图标规范。

### 9.2 视觉层级

必须区分：

1. 全局导航。
2. 当前项目上下文。
3. 项目内部业务分组。
4. 当前选中页面。
5. 未开放功能状态。

Coming Soon 标签应弱化显示，不得比正常菜单更醒目。

### 9.3 菜单图标

图标应保持一致的视觉语言：

- 使用统一图标库。
- 同一级菜单使用相同尺寸。
- 不混用不同风格的图标。
- 图标必须帮助识别功能，不能仅作装饰。

## 10. 前端实现约束

建议将导航配置与页面组件解耦。

导航配置至少应支持：

- 菜单唯一 ID
- 菜单名称
- 图标
- 路由
- 菜单层级
- 分组
- 开放状态
- 权限要求
- 排序
- 项目上下文要求

要求：

1. Global Navigation 与 Project Navigation 分离。
2. 菜单不能直接决定业务权限，后端仍然负责授权校验。
3. Coming Soon 不能被误认为权限控制。
4. 路由和导航配置保持一致。
5. 菜单状态支持未来阶段逐步开放。
6. 不为每个 S 阶段单独创建一套导航体系。
7. 业务页面可以独立迭代，但必须遵循统一信息架构。

## 11. V1.0 冻结范围

本次冻结：

- 全局主菜单的六个一级入口。
- 项目内部导航的业务分组。
- 项目内部各菜单的职责边界。
- 不设置全局 AI 协作中心。
- 不引入 Workspace 概念。
- 未来菜单展示规则。
- 项目初始化和仓库管理的导航归属。
- 全局设置与项目设置的边界。

不在本次冻结范围：

- 每个业务页面的具体布局。
- 每个页面的交互细节。
- 后端导航 API。
- 具体权限矩阵。
- 各业务模块的完整数据模型。
- 每个菜单对应的最终 URL。

以上内容由后续业务 UX 和技术设计分别确定，但不得违反本基线。

3. S01-00-C：Navigation Interaction & Routing
