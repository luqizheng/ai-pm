## 一、核心设计结论

建议将「人工审核中心」设计为：

**独立一级导航入口 + 全局待处理数量徽标 + 指挥中心快捷入口 + 全页工作台。**

它不是简单地把指挥中心的「需关注事项」扩大，而是把系统中所有需要人类作出判断、确认或验收的事项，统一纳入一个 Human-in-the-loop 工作流。

产品定位：
- 指挥中心：回答「项目当前发生了什么，有什么需要关注？」
- 人工审核中心：回答「哪些事情需要我作出决定，我应该如何处理？」
- AI Chat：回答「我可以如何帮助理解、分析和完成这项审核？」

三者职责不同，不应该相互替代。

### 1.1 七项核心决策

| 设计问题 | 推荐方案 |
|---|---|
| 信息架构 | 独立一级页面，全局徽标入口 |
| 页面形态 | 全页审核工作台 |
| 列表形态 | 混排的任务队列 + 可展开详情 |
| 分类方式 | 默认统一混排，提供类型筛选 |
| 决策交互 | 先看上下文，再执行决策 |
| 批量操作 | V1 不允许批量确认、拒绝、验收 |
| 处理后行为 | 从待处理队列移除，支持短暂撤销窗口（仅在后端支持时） |

最重要的设计原则：

> 审核事项可以统一派发，但不能因为统一收件箱而牺牲各业务领域原有的决策规则。

例如，Finding 确认、Document Proposal 确认和 Delivery 验收虽然都出现在同一个收件箱中，但它们的上下文、风险和决策权限不同。

## 二、信息架构设计

### 2.1 三种方案比较

| 方案 | 优点 | 问题 | 结论 |
|---|---|---|---|
| 独立一级页面 | 完整工作流、可扩展、可筛选 | 增加一个导航入口 | **推荐** |
| 指挥中心面板展开 | 入口自然 | 不适合大量事项与复杂审核 | 保留快捷入口 |
| 全局徽标 + 收件箱抽屉 | 随时访问 | 详情和证据空间不足 | 仅做快捷入口 |

### 2.2 推荐的信息架构

```
AI PM 全局导航
├── 个人工作台
├── 项目
├── 人工审核中心  ⑫ 待处理
├── 知识与认知
└── 系统设置
```

统一接收发现、知识提案、交付验收等人工决策事项。数量徽标由聚合接口返回的当前待处理事项数量计算，不额外创造后端字段。

入口同时出现在三个地方：
1. 全局一级导航：人工审核中心。
2. 指挥中心：需关注事项面板，点击后进入对应审核事项。
3. 全局导航徽标：显示当前待处理数量。

不建议再增加一个独立的全局抽屉作为完整审核入口，否则会出现两套审核交互。

### 2.3 路由建议

```
/review
/review?kind=finding_pending
/review?kind=proposal_pending
/review?kind=delivery_pending
/review?item=<id>
```

- `/review`：全部待处理事项。
- `kind`：用于类型筛选。
- `item`：定位并打开对应事项。
- 通过 link.kind + link.params 跳转至业务对象。
- 页面刷新后应能恢复筛选和当前选中事项。

注意：id 是否全局唯一尚不能仅从当前契约确认。如果不是全局唯一，选中项需要使用 kind + id 组合标识，而不是单独依赖 id。

## 三、页面整体结构

### 3.1 推荐：混排队列 + 详情工作区

不推荐传统后台表格作为主要交互——审核不是纯粹的信息浏览，用户需要阅读上下文、理解 AI 提议、查看证据、作出决定。

也不推荐一次只展示一条的纯队列模式——用户往往需要先判断事项的优先级，再决定处理顺序。

最合适的是：**左侧待办列表 + 右侧审核详情，形成双栏工作区。**

### 3.2 页面文字线框

```
┌─────────────────────────────────────────────────────────────┐
│ 人工审核中心                                                 │
│ 处理系统中等待人工确认、决策和验收的事项                     │
├─────────────────────────────────────────────────────────────┤
│ [全部 12] [发现 5] [知识提案 4] [交付验收 3]                 │
├─────────────────────────────────────────────────────────────┤
│ [搜索事项...]  [领域 ▼] [时间 ▼] [排序 ▼]                    │
├──────────────────────┬──────────────────────────────────────┤
│ 待处理事项           │ 审核详情                               │
│                      │                                       │
│ ● 发现待确认         │ 事项标题                               │
│   Discovery          │                                       │
│   2 小时前           │ 类型 / 来源状态 / 更新时间             │
│                      │ ───────────────────────────────────── │
│ ● 文档提案待确认     │ 事项描述                               │
│   Knowledge          │                                       │
│   5 小时前           │ 原始来源 / 关联对象                     │
│                      │ ───────────────────────────────────── │
│ ● 交付待验收         │ 上下文 / 证据 / 差异                    │
│   Delivery           │                                       │
│   昨天               │ ───────────────────────────────────── │
│                      │ 审核操作                               │
│                      │ [查看业务对象]                         │
│                      │ [拒绝] [确认]                          │
└──────────────────────┴──────────────────────────────────────┘
```

### 3.3 列表区域字段布局

每个 ActionItem 展示：title（事项标题）、kind（类型标识）、domain（业务领域）、detail（简短说明）、source_state（来源状态）、updated_at（最近更新时间）、action_hint（操作提示）。

建议列表卡片：

```
┌──────────────────────────────────┐
│ [发现待确认]           [待处理]  │
│ 用户提交的架构发现               │
│ 发现事项需要人工确认……           │
│ Discovery · 2 小时前             │
│ 确认或拒绝该发现                  │
└──────────────────────────────────┘
```

**不要在列表中直接展示确认、拒绝按钮**——用户尚未看到上下文，容易产生误操作。

### 3.4 详情区域布局

详情区域采用统一框架，内部根据 kind 渲染不同的业务组件。

```
┌──────────────────────────────────────┐
│ 发现事项                              │
│ 用户提交的架构发现                    │
│ 类型：发现待处理 / 状态：PENDING / 更新时间：…  │
├──────────────────────────────────────┤
│ 事项说明（detail 完整展示，不超过接口已有长度）│
├──────────────────────────────────────┤
│ 业务上下文                            │
│ [发现内容 / 原始来源 / 关联信息]       │
│ [查看完整业务对象]                    │
├──────────────────────────────────────┤
│ 人工决策                              │
│ [拒绝]                  [确认]        │
└──────────────────────────────────────┘
```

**数据边界**：当前聚合接口的 detail 最多截断到 160 字，不能把它当作完整审核内容。详情页需要通过 link 定位业务对象，使用已有的领域读取接口加载上下文。不能假设聚合接口提供了完整正文、diff、证据文件或责任人字段。

## 四、列表形态与分类策略

### 4.1 不同 kind 是否分 Tab？

建议：**默认混排，分类 Tab 作为快捷筛选**，不把不同业务领域隔离成独立页面。好处：
1. 用户可以从整体上理解当前待处理工作量。
2. 不需要切换页面就能连续处理不同领域事项。
3. 新增 kind 时不需要重新设计导航结构。
4. 后续可以增加优先级、项目、来源等筛选条件。

### 4.2 建议的筛选项

| 筛选维度 | V1 | 数据依据 |
|---|---|---|
| 事项类型 | 支持 | kind |
| 业务领域 | 支持 | domain |
| 更新时间 | 支持 | updated_at |
| 来源状态 | 支持 | source_state |
| 项目 | 需验证 | 现有 link 是否能可靠解析项目 |
| 紧急程度 | 暂不支持 | 当前无 priority 字段 |
| 责任人 | 暂不支持 | 当前无 assignee 字段 |

特别说明：不要根据 kind 自行推断紧急程度。若未来要支持紧急程度，应由业务领域提供明确的优先级规则，并扩展数据契约。

### 4.3 排序建议

V1 提供：最近更新优先（默认）、最早更新优先。
暂不提供：AI 紧急程度排序、业务风险排序、责任人排序。

## 五、三类事项的审核交互设计

**三类事项不能共用一套确认按钮逻辑。**

### 5.1 Finding：发现待处理（V1 可实现完整审核）

业务对象：`discovery.discovery_finding`，当前状态 PENDING，已有决策端点。

交互原则：必须查看发现内容和相关上下文之后才能确认或拒绝。

```
待处理 PENDING → 打开审核详情 → 加载 Finding 完整内容
  ├── 查看发现内容 / 查看原始来源 / 查看关联上下文
  → 用户作出决定 → 确认（提交决策端点）/ 拒绝（提交决策端点）
  → 已处理 → 从待处理列表移除
```

界面操作：查看完整发现内容、查看来源和上下文、确认、拒绝。

拒绝时建议要求填写理由，但要先确认现有决策端点是否支持理由参数。如果不支持，不应在 UI 中收集一个无法持久化的理由。

特别处理 `finding_revision_requested`：与普通 Finding Pending 不应混淆，使用独立类型文案（「发现待确认」/「发现修订后待重新确认」），但必须使用实际业务对象状态和现有端点定义来驱动按钮，不能仅凭名称推断具体决策动作。

### 5.2 Document Proposal：文档提案待确认（V1 可实现完整审核）

业务对象：`ai.document_proposal`，活跃待确认状态，已有确认/否决端点。

交互原则：必须展示提案内容及其对知识库的影响，不能只根据标题确认。

推荐详情布局：

```
文档提案审核
├── 提案基本信息（标题 / 当前状态 / 更新时间）
├── 提案内容（提案正文 / 关联知识对象）
├── 变更影响（新增内容 / 修改内容 / 关联关系变化）
└── 审核决策（查看原始业务对象 / 否决提案 / 确认提案）
```

注意：新增、修改、关联关系变化是详情组件可以呈现的内容类型，不意味着现有接口已经提供这些字段。若当前提案读取接口没有完整 diff，先展示实际可获取的提案内容，不要伪造前后对比。

建议增加二次确认弹窗：确认提案说明业务影响；否决提案若端点支持则填写理由。因为知识提案的确认可能改变项目正式知识，误操作成本高。

### 5.3 Delivery：交付待验收（V1 只读预留，等待 T-070）

业务对象：`delivery.task`，状态 submitted / reviewing。已具备证据读取能力，但验收工作台还在规划中。

**有证据读取能力，不等于已经具备交付验收能力。**

V1 不应：
- 展示可点击的虚假验收按钮。
- 用前端模拟验收成功。
- 直接把 submitted 或 reviewing 当作验收完成。
- 在没有验收端点的情况下从待处理队列删除任务。

交付事项应当在 V1 中支持打开、查看证据、跳转业务对象，但保留明确的「验收工作台尚未开放」状态。

### 5.4 三类事项能力矩阵

| 能力 | Finding | Proposal | Delivery |
|---|---|---|---|
| 查看详情 | 支持 | 支持 | 支持 |
| 查看上下文 | 必须 | 必须 | 必须 |
| 查看证据 | 视来源而定 | 视提案内容而定 | 支持读取 |
| 确认/验收 | 支持 | 支持 | 暂不支持 |
| 拒绝/否决 | 支持 | 支持 | 暂不支持 |
| 二次确认 | 建议 | 必须 | 未来 |
| V1 完整闭环 | 是 | 是 | 否 |

## 六、处理状态与列表去留

区分业务状态和前端交互状态。当前聚合接口没有独立的 processing_status 字段，不能擅自向 ActionItem 增加 processing / approved / rejected / archived——这些状态应该来自对应业务领域，审核中心不自己维护一套状态权威。

### 6.1 三阶段交互状态机

```
待处理 Pending（事项存在于聚合列表中）
  → 用户打开详情 / 发起操作
处理中 Processing（前端临时状态：加载、提交、等待接口响应）
  → 领域决策端点成功，重新获取聚合列表
已处理 Completed（领域状态已更新，事项不再属于待处理集合）
```

### 6.2 重要的异常分支

| 场景 | UI 行为 |
|---|---|
| 用户正在提交 | 禁用当前事项的决策按钮 |
| 请求失败 | 保留事项，展示失败原因 |
| 403 无权限 | 显示无权处理，保留事项 |
| 409 状态冲突 | 重新加载业务对象，提示状态已变化 |
| 事项已被他人处理 | 刷新聚合列表，移除已不再待处理的事项 |
| 网络中断 | 不改变事项业务状态，允许重试 |
| 接口超时 | 查询业务对象当前状态后再决定是否重试 |

尤其注意：接口超时并不等于操作失败。可能服务端已经成功，只是响应未能返回。不要盲目重复提交。

### 6.3 处理后的去留策略

- 已处理事项立即从「待处理」列表消失。
- 当前选中详情显示短暂的处理成功反馈。
- 自动选择下一条待处理事项。
- 如果没有剩余事项，进入空态。
- 不在 V1 中构建历史审核记录页面，除非已有历史数据接口。

撤销窗口不建议在 V1 实现——确认、拒绝、否决是否可逆取决于领域业务规则，不能假设所有决策都支持撤销。

未来可以增加「已处理」视图，但必须有相应的后端历史查询能力。

## 七、批量操作与效率设计

**V1 不开放批量确认、批量拒绝、批量验收。**

原因：三类事项决策含义不同；决策后果不同；Delivery 需要独立证据验收；现有接口未提供批量决策契约；批量误操作的风险远高于节省的点击成本。

| 功能 | 建议 |
|---|---|
| 连续处理 | 支持 |
| 上一条/下一条 | 支持 |
| 自动定位下一条 | 支持 |
| 类型/领域/时间筛选 | 支持 |
| 批量确认/拒绝/验收 | 不支持 |
| 批量标记已读 | 暂不支持，缺少对应契约 |

推荐的连续审核体验：打开事项 A → 查看上下文 → 确认/拒绝 → 成功反馈 → 自动定位事项 B → 继续审核。

## 八、权限设计

现有 ActionItem 没有 assignee / reviewer / owner / permission / can_approve 字段，前端不能通过事项字段判断当前用户是否有权处理。

### 8.1 V1 权限建议

采用：**后端授权优先 + 前端能力反馈 + 无责任人字段时不自行分配。**

| 角色 | V1 建议 |
|---|---|
| Team Owner | 遵循领域权限，可以审核 |
| Team Admin | 遵循领域权限，可以审核 |
| 普通成员 | 根据领域权限判断 |
| 事项提交人 | 不自动获得审核权限，也不自动禁止审核 |
| 项目负责人 | 不能仅凭负责人身份推断有审核权 |

注意：这是产品权限策略建议，不代表当前后端已经实现上述角色授权。真正的权限判断必须由领域端点执行。

### 8.2 无权限时的 UI

展示「当前账号无权处理此事项，你仍然可以查看相关内容」+ [查看业务对象]。

不要让没有权限的用户看到可正常执行的确认按钮再依靠接口失败来反馈；但在没有权限查询能力的情况下，也不能凭角色在前端预先隐藏按钮。

V1 可以：展示操作入口 → 请求时由后端进行权限验证 → 收到 403 后展示无权处理状态 → 保留只读查看能力（如果业务读取权限允许）。

后续建议由后端提供统一的操作能力信息（例如 available_actions），但这属于未来数据契约扩展，不是当前实现前提。

## 九、与四栏壳布局的融合

建议人工审核中心不要另建一套独立壳，而是复用现有四栏结构。推荐职责：

| 宽度 | 页面职责 |
|---|---|
| 188px | 全局导航 |
| 518px | 待审核事项队列 |
| 446px | 审核详情与上下文 |
| 288px | 常驻 AI Chat |

### 9.2 AI Chat 在审核中心的作用

AI Chat 不应该只是普通聊天窗口，而应该支持围绕当前审核事项提供辅助：解释该 Finding 为什么需要确认、总结 Document Proposal 的主要变化、分析交付证据是否完整、解释拒绝某项提案可能产生的影响、帮助理解相关业务上下文。

但必须坚持：**AI 可以建议，不可以替代人工决策。** AI Chat 不能直接把 AI 的分析结果当作已确认、已拒绝或已验收的操作。

建议在 AI Chat 中明确区分：AI 分析建议 / 原始业务事实 / 用户最终决策。AI Chat 的建议必须与当前选中 ActionItem 绑定，避免在连续审核时上下文串项。

### 9.3 上下文切换规则

当用户选择不同事项：
1. 更新当前选中 ActionItem。
2. 更新详情区域。
3. 更新 AI Chat 的当前业务上下文。
4. 保持原有对话历史的隔离策略，不把上一事项的结论自动带入下一事项。

建议将当前事项标识作为上下文绑定依据，但不因此新增后端业务字段。

## 十、组件清单与前端架构

建议拆分四层：
1. 页面容器层：负责路由、数据获取、状态管理。
2. 统一审核组件层：负责队列、详情框架、操作反馈。
3. 领域展示组件层：负责 Finding、Proposal、Delivery 的业务上下文。
4. AI 辅助层：负责当前审核事项的上下文协作。

重要：**组件纯展示化**。所有用户可见文案由调用方通过 vue-i18n 翻译后经 props 传入。

```ts
interface ReviewQueueItemProps {
  title: string
  detail: string
  typeLabel: string
  domainLabel: string
  statusLabel: string
  updatedAtLabel: string
  actionHint: string
  selected: boolean
}
```

组件不应该：内部直接依赖全局 i18n（`const { t } = useI18n()`）；内部判断领域业务规则（`if (item.kind === 'finding_pending') { … }`）。

应该由页面容器负责：

```ts
const viewModel = computed(() =>
  items.value.map(item => ({
    title: item.title,
    detail: item.detail,
    typeLabel: t(`review.kind.${item.kind}`),
    domainLabel: t(`domain.${item.domain}`),
    statusLabel: t(`review.sourceState.${item.source_state}`),
    updatedAtLabel: formatDate(item.updated_at),
    actionHint: item.action_hint,
  }))
)
```

## 十一、ActionItem 数据映射表

### 11.1 后端字段 → UI 元素

| 后端字段 | UI 位置 | 处理方式 | 是否转换 |
|---|---|---|---|
| kind | 类型标签、详情组件分发 | 映射类型 | 是 |
| domain | 领域标签、筛选器 | 映射领域名称 | 是 |
| id | 事项唯一标识 | 原样使用 | 否 |
| title | 卡片标题、详情标题 | 原样展示 | 否 |
| detail | 卡片摘要、详情描述 | 原样展示 | 否 |
| source_state | 来源状态标签 | 映射展示文案 | 是 |
| updated_at | 更新时间 | 格式化 | 是 |
| action_hint | 操作提示 | 原样展示或按 i18n 语义映射 | 视情况 |
| link.kind | 跳转分发 | 映射业务路由 | 是 |
| link.params | 业务对象定位参数 | 原样传递给对应路由适配器 | 否 |

### 11.2 不得从现有字段推导的内容

| 不存在的字段 | 不允许的做法 |
|---|---|
| priority | 根据 kind 伪造紧急程度 |
| assignee | 自动显示当前用户为负责人 |
| reviewer | 假设提交人就是审核人 |
| can_approve | 假设所有用户都能确认 |
| processing_status | 自行维护持久化审核状态 |
| completed_at | 用更新时间冒充处理时间 |
| project_id | 假设每个 link 都包含项目 ID |
| evidence_count | 通过固定数字制造证据数量 |
| diff | 虚构文档前后差异 |

### 11.3 前端内部 ViewModel

允许建立纯前端展示模型，但要与后端 ActionItem 分离。

```ts
type ReviewKind =
  | 'finding_pending'
  | 'finding_revision_requested'
  | 'proposal_pending'
  | 'delivery_pending'

interface ReviewQueueViewModel {
  key: string          // 前端稳定标识，建议 kind:id
  kind: ReviewKind
  title: string
  detail: string
  domainLabel: string  // 均由调用方翻译
  kindLabel: string
  sourceStateLabel: string
  updatedAtLabel: string
  actionHint: string
  selected: boolean    // UI 状态，不是后端业务字段
}
```

不增加伪造的业务属性。

## 十二、Pinia 状态管理建议

建议新建 `stores/reviewCenter.ts`，只管理审核中心页面状态，不把 Finding、Proposal、Delivery 的领域业务状态搬到这里。

```ts
interface ReviewCenterState {
  items: ActionItem[]
  selectedKey: string | null
  filters: {
    kind: string | null
    domain: string | null
    updatedAfter: string | null
    updatedBefore: string | null
  }
  sortBy: 'updated_desc' | 'updated_asc'
  loading: boolean
  submittingKey: string | null
  error: string | null
}
```

| 操作 | 负责位置 |
|---|---|
| 获取聚合事项 | Review API |
| 筛选和排序 | Pinia / 页面容器 |
| 当前选中项 | Pinia |
| 加载状态 | Pinia |
| 提交中的事项 | Pinia |
| Finding 决策 | Finding 领域 API |
| Proposal 决策 | Proposal 领域 API |
| Delivery 证据读取 | Delivery 领域 API |
| 审核成功后的刷新 | Review Store |

不要在 Review Store 中实现 Finding 或 Proposal 的业务决策规则。

## 十三、空态、异常态与状态反馈

空态四类：全部处理完成 / 没有匹配结果（调整筛选条件后重新查看）/ 正在加载 / 加载失败（无法获取审核事项，请重试）。

### 13.1 特殊空态：Delivery 功能未开放

如果当前列表中有 Delivery 事项，不能将其隐藏，也不能将其误判为已处理。应展示「交付待验收——交付证据已准备就绪。当前版本支持查看交付内容，完整验收工作台将在后续版本开放」+ [查看交付任务]。这是功能成熟度的透明表达。

### 13.2 i18n 组织建议

建议增加 `locales/zh-CN/review.json` 与 `locales/en-US/review.json`。

推荐文案键：

### 14.1 仓库导入提案的处理

仓库导入提案的 apply → 提案 → 基线确认链路尚未进入聚合接口。V1 可以预留一个领域扩展位置，但不能：
- 创建假数据填充列表。
- 将仓库导入提案伪装成现有 Finding。
- 通过前端构造 ActionItem 补足后端缺口。
- 在没有正式 API 的情况下实现确认按钮。

未来接入时只需要扩展 kind、领域组件和领域 API 适配，不需要推翻整个审核中心。

## 十五、最终设计裁决建议（建议冻结的设计基线）

- **D1 产品定位**：独立的人工决策收件箱，统一接收需要人类介入的业务事项。
- **D2 信息架构**：独立一级导航 + 全局待处理数量徽标 + 指挥中心快捷入口。
- **D3 页面布局**：左侧待办队列、右侧审核详情，复用现有四栏壳布局，保留 AI Chat 常驻列。
- **D4 审核交互**：先看上下文，再作出决策。禁止未经上下文阅读的一键确认。
- **D5 领域边界**：Finding、Proposal、Delivery 保留各自的业务决策规则和 API。
- **D6 操作权限**：后端负责最终授权，前端不根据不存在的责任人或权限字段自行推断。
- **D7 状态管理**：领域状态是业务事实，前端 Processing 只是临时交互状态，成功后刷新聚合接口。
- **D8 组件架构**：展示组件纯展示化，所有文案由调用方翻译后通过 Props 传入。
- **D9 数据真实性**：只消费已有聚合接口和真实领域读取接口；缺失数据、接口和能力不得用 Mock 补齐。
- **D10 功能范围**：Finding、Proposal 完整审核；Delivery 只读预留；仓库导入提案二期接入。

特别建议坚持的三个设计原则：

1. **审核中心不是一个新的业务领域**。它是跨领域的人工任务聚合与交互入口。Finding 仍归 Discovery，Document Proposal 仍归 Knowledge，Delivery 仍归 Delivery。不能让审核中心成为这些业务对象的第二个状态权威。
2. **AI Chat 是审核助手，不是自动审批者**。AI 可以帮助阅读、分析、解释和提出建议。最终确认、否决、验收仍然由有权限的人执行。
3. **统一队列不代表统一决策**。统一的是待办入口、列表、筛选、导航、状态反馈和交互框架；不统一的是领域决策规则、证据要求和权限判断。

建议的下一步实施顺序：
1. 冻结本设计基线。
2. 先完成 Review Center 页面和四栏壳布局融合。
3. 接入现有聚合接口，实现混排队列。
4. 完成 Finding 和 Proposal 两套真实审核闭环。
5. 接入 Delivery 证据只读工作区。
6. 完成异常处理、权限反馈和空态。
7. 对接 T-070，补全 Delivery 验收。
