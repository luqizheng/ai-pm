### 1.1 修正后的页面路由

```
/project/review-center
/project/review-center?kind=finding_pending
/project/review-center?kind=proposal_pending
/project/review-center?kind=delivery_pending
/project/review-center?kind=finding_pending&item=<id>
```

item 定位时仍采用 kind + id 复合标识。

详情 Drawer 打开、关闭时，应同步 URL 查询参数，确保：

- 分享 URL 能够定位具体事项。
- 浏览器前进、后退可以恢复选中状态。
- Drawer 关闭时清理 item，保留 kind。

### 1.2 修正后的数据边界

人工审核中心是项目级功能。

```
Project
├── Project Command Center
├── Project Review Center
│     └── 项目级聚合接口
│           ├── Finding
│           ├── Document Proposal
│           └── Delivery
```

不再设计 V1 全局跨项目收件箱。全局待处理徽标作为未来能力挂账，不在 V1 伪造跨项目数字。

### 1.3 Finding 决策链：后端先行

直接利用现有表中的 session_id，不增加数据库迁移。建议列为实施第 1 步，前端不得通过其他接口反查或猜测 session_id。

## 二、Q1：474px 队列卡片与详情 Drawer

**裁决：采用紧凑队列卡片 + 右侧覆盖式 Drawer。**

474px 队列只承担识别与排序，不承担审核阅读。

### 2.1 474px 队列卡片字段取舍

保留六项信息：

| 字段 | 展示方式 | 优先级 |
|---|---|---|
| kind | 类型标签 | 必须 |
| title | 主标题 | 必须 |
| detail | 最多两行摘要 | 必须 |
| domain | 次级标签 | 必须 |
| updated_at | 相对时间 | 必须 |
| source_state | 紧凑状态标签 | 建议 |

action_hint 不建议每条卡片完整展示——它与 kind 语义重复度高，挤占标题和摘要空间。选中事项后在 Drawer 展示完整 action_hint；队列卡片通过类型标签表达事项类别；不增加责任人、优先级、项目名称等当前没有的数据。

### 2.2 卡片文字线框

```
┌────────────────────────────────────────────┐
│ [发现待确认]                    [PENDING]  │
│ 项目架构发现需要人工确认                   │
│ 发现内容摘要，最多两行……                   │
│ Discovery                    2 小时前      │
└────────────────────────────────────────────┘
```

- 左右 padding：16px；上下 padding：12px。
- 标题：单行优先，必要时两行；摘要最多两行，超出截断。
- 类型和状态标签不使用紫色；选中态采用 V2 雾蓝青 accent。
- 不出现确认、拒绝、验收按钮。

### 2.3 Drawer 宽度与层级

**推荐 720px。**

- 不建议只覆盖 474px 主区——不适合完整展示 Finding 内容、Proposal 正文及交付证据。
- 不建议默认全屏——破坏四栏壳的空间连续性。
- Drawer 宽度：720px；最大宽度：视口可用内容区域的 90%。
- 锚定：主工作区右侧；覆盖：主内容区 + 右侧上下文区域；保留：左侧全局导航和右侧 AI Chat 常驻列。
- 层级：高于项目主内容，低于全局模态确认框。

```
┌───────────────┬───────────────────────────────┐
│  事项队列     │       审核详情 Drawer         │
│  发现 A       │  发现事项标题             [×] │
│  提案 B       │  类型 / 状态 / 更新时间       │
│  交付 C       │  事项说明 / 完整业务上下文    │
│               │  来源 / 证据 / 变更内容       │
│               │  理由输入框                   │
│               │  [拒绝]          [确认]       │
└───────────────┴───────────────────────────────┘
```

注意：Drawer 内的 AI 分析仍然通过现有 AI Chat 列完成，不在 Drawer 内再创造一个 Chat。

## 三、Q2：专注模式双栏是否纳入 V1？

**裁决：V1 不做，挂 V1.1。**

专注模式值得做，但不值得成为 V1 的交付阻塞项。它涉及主区宽度扩展、队列与详情重新分配、AI Chat 显示与上下文保持、Drawer 与详情区选中状态协调、退出专注模式后的状态恢复，都需要额外交互验证。

V1.1 预留布局模式 `ReviewCenterLayoutMode`：
- NORMAL：474px 队列 + 720px Drawer。
- FOCUS（未来）：扩展主工作区，队列 360–420px + 详情占剩余空间；AI Chat 默认保留可由现有壳布局控制收起；退出时恢复之前的事项选择和筛选条件。

V1 只实现 NORMAL。不要提前做一个没有实际用途的布局切换按钮。

## 四、Q3：Finding 必填理由，Proposal 可选理由

**裁决：统一理由输入组件，领域配置必填规则。**

不建议为两种事项分别开发两套理由输入组件。交互结构基本相同，差异放在调用方传入的配置，而不是组件内部的业务判断。

### 4.1 理由输入规则

| 项目 | Finding | Proposal |
|---|---|---|
| 字段 | answer | note |
| 是否必填 | 是 | 否 |
| 确认操作 | 必须填写 | 可以不填写 |
| 拒绝操作 | 必须填写 | 可以不填写 |
| 最大长度 | 按端点约束 | 按端点约束 |
| 请求参数 | answer | note |
| 版本控制 | 按现有端点规则 | expected_version_no 必须携带 |

容易遗漏的细节：**Finding 的 answer 不只是拒绝理由，而是确认和拒绝都必须填写的决策说明**，不能命名成「拒绝原因」。

### 4.2 统一组件设计

`ReviewDecisionReasonInput.vue` 纯展示组件：

```ts
interface ReviewDecisionReasonInputProps {
  label: string
  placeholder: string
  required: boolean
  value: string
  maxLength?: number
  errorMessage?: string
  disabled?: boolean
}
```

由调用方控制：是否必填、输入内容、校验错误、提交按钮可用状态、具体 API 参数映射。

### 4.3 两种领域的提交契约

Finding：

```json
{ "status": "CONFIRMED | REJECTED", "answer": "string" }
```

提交前必须验证 answer 非空。

Proposal：

```json
{ "action": "approve | reject", "note": "string?", "expected_version_no": 0 }
```

提交前必须读取当前提案版本，并在请求中携带 expected_version_no。

### 4.4 Proposal 的 409 特殊处理

409 作为独立业务异常，不使用普通网络错误提示。

```
用户打开 Proposal → 加载提案及版本号 → 用户阅读、填写备注
→ 提交时携带 expected_version_no
   ├── 成功 → 刷新聚合列表
   └── 409 → 提案版本已变化 → 暂停本次决策
        → 重新加载提案内容 → 展示版本变化提示 → 用户重新阅读并决策
```

提示文案建议：「该提案在你打开后发生了更新。为避免基于旧版本作出决定，请重新查看最新内容。」

**不要自动使用新版本号重试旧决策**——这会破坏 CAS 的意义，也可能让用户在没有阅读新内容的情况下确认。

## 五、Q4：Delivery 空态 CTA 指向任务详情

**裁决：有条件采纳。**

同意采用 `/project/tasks/:taskId` 作为 V1 Delivery 的查看落点。当前已具备：项目级交付聚合读取、delivery.task 业务对象、交付证据读取能力。虽然前端尚无独立交付页，但任务详情比无法执行操作的占位页面更有实际价值。

### 5.1 推荐交互

```
人工审核中心 → 选择 Delivery 事项 → 打开审核 Drawer
→ 查看交付基本信息 → 读取交付证据
→ 提示：验收工作台尚未开放 → [查看交付任务] → /project/tasks/:taskId
```

### 5.2 必须验证的前置条件

不能假设 link.params 一定包含 task_id。需检查实际返回结构确认可从现有 link 参数可靠获得任务 ID。如果可以，直接构造任务详情路由；如果不可以：通过已有业务对象定位能力获取 taskId；没有可靠映射则 CTA 暂不启用。**绝不能用 id 猜测 taskId。**

### 5.3 Delivery 详情的文案修正

不要使用「验收工作台尚未开放」作为整个详情页面的主要状态（易误以为交付内容无法查看）。改为：

> 交付证据可查看，验收操作暂未开放。

清晰区分已具备能力与未具备能力。

## 六、Q5：项目导航徽标与指挥中心计数

**裁决：两处均显示，但语义不同。**

1. 项目导航条目显示待处理数量。
2. 指挥中心「需关注事项」面板标题显示同一数量。
3. 不在每条事项卡片上重复显示计数。

```
项目
├── 指挥中心
├── 需求管理
├── 项目知识
├── 任务管理
└── 人工审核中心  [5]
```

指挥中心面板：标题右侧显示总数，底部 [进入人工审核中心 →]。

两处使用目的不同：导航徽标 = 切换页面时提醒还有待办；指挥中心计数 = 理解项目当前需人工介入的规模。但：
- 两处必须来自同一个项目级聚合结果。
- 不额外创建两套统计逻辑。
- 计数只统计当前聚合接口返回的事项。
- 数据加载失败不显示伪造的 0。
- 数据过期按现有数据刷新策略更新。

另外：只在审核中心导航项显示数字徽标，指挥中心保留面板总数即可，不增加全局壳的额外徽标。全局跨项目数字徽标继续挂账。
