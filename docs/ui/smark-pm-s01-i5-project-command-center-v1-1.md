## 0.2 工作包定位

I5 是项目负责人进入 Project 后的默认工作入口。

它负责将项目各领域的权威数据组织为统一的项目工作视图，使负责人能够快速理解：

1. 项目目标是什么；
2. 当前项目进展如何；
3. 有哪些事项需要人工处理；
4. 哪些 Agent 正在执行什么工作；
5. 当前有哪些风险与阻塞；
6. 项目接入和初始化还缺少什么；
7. 最近发生了哪些重要业务活动。

I5 不负责重新实现上述领域的业务能力。

## 0.3 设计事实标注

本文使用以下口径：

- **已知代码事实**：已有代码结构或数据模型依据。
- **设计裁决**：本设计稿明确规定的目标行为。
- **实施前核验**：必须通过代码检查确认实际实现情况。
- **需新增**：当前没有证据证明已存在，实施时根据核验结果决定是否新增。

不得将设计候选 API、DTO、字段或数据库视图描述为现有实现。

# §1. 设计目标与边界

## 1.1 设计目标

建立项目级聚合工作台，满足以下要求：

- 一个 Project 对应一个清晰的项目工作入口。
- 项目负责人能够优先看到需要自己处理的事情。
- 支持多个 Agent 并行执行的状态展示。
- 同时展示项目运行状态和初始化接入进度。
- 能够发现跨领域的风险与阻塞。
- 重要活动能够追溯到真实业务记录。
- 允许各领域独立演进，不要求所有领域共用一个状态机。
- 所有业务写操作仍由原领域服务负责。

## 1.2 不负责的事情

I5 不负责：

- Project 生命周期和归档机制（I1）。
- Finding 人工确认、拒绝和补充机制（I2）。
- 仓库 Git 读写授权（I3）。
- Project Goal 的创建、修改、确认和生命周期（I4）。
- 仓库接入、代码分析和分析结果写入（I6）。
- Task、Run、Delivery、Knowledge 等领域状态机。
- 建立新的全项目统一状态机。
- 建立新的通用百分比进度系统。
- 直接执行其他领域的写操作。
- 将所有审计记录或系统日志直接展示为项目活动。

## 1.3 领域职责划分

| 领域 | 职责 | I5 使用方式 |
|---|---|---|
| I1 | Project 归档生命周期 | 展示生命周期及归档清理情况 |
| I2 | Finding 人工确认 | 展示待确认、待补充、已确认、已拒绝 |
| I3 | 仓库执行权限 | 展示必要的授权事实，不重新定义权限 |
| I4 | Project Goal | 展示目标摘要和确认状态 |
| I6 | 仓库接入与代码分析 | 展示仓库接入和分析进度 |
| I5 | 项目级聚合 | 统一展示以上领域的权威事实 |

I5 不得反向成为 I1～I6 的业务依赖。

# §2. 项目工作空间信息架构

## 2.1 总控台定位

总控台是 Project 工作空间的默认首页。

项目工作空间继续采用既有 AI R&D Workspace 信息架构：

1. 总控台
2. 目标与计划
3. AI 执行
4. 决策中心
5. 项目认知
6. 产物验收

仓库管理、开发环境和项目设置根据现有导航结构组织，不在总控台重复创建业务菜单。

## 2.2 总控台不等于 Dashboard

总控台的主要目的不是显示统计数字，而是帮助人类负责人采取行动。

页面首先回答：

- 我现在需要处理什么？
- Agent 正在做什么？
- 项目哪里出了问题？
- 接下来最重要的工作是什么？

因此，待人工处理、当前执行和风险区域的优先级高于普通统计卡片。

## 2.3 全局布局基线

沿用 AI R&D Workspace V1.0 设计系统：

| 区域 | 设计基线 | 职责 |
|---|---|---|
| 顶部栏 | 52px | 租户、项目切换、全局操作 |
| 左侧导航 | 232px，可折叠 | 项目工作区导航 |
| 中央区域 | 自适应 | 当前工作区 |
| 底部 AI 命令栏 | 72～120px | 面向当前项目的 AI 交互 |
| 右侧上下文面板 | 320px，可隐藏/固定 | 当前页面上下文来源 |

AI 上下文展示应使用户知道 Agent 正在依据哪些项目资料工作。

上下文展示不等于权限授权，也不能替代后端鉴权。

# §3. 总控台首页结构与优先级

## 3.1 首屏优先级

正式裁决：

**第一优先级：待人工处理。**

**第二优先级：当前执行。**

**第三优先级：风险与阻塞。**

其后依次为：

4. 项目目标与进展；
5. 项目初始化进度；
6. 最近活动。

首屏优先级依据人的决策和管理需要，而不是数据量大小。

## 3.2 项目头部

展示：

- Project 名称；
- Project 标识；
- Project 生命周期状态；
- Goal 摘要；
- 关联仓库数量；
- 最近活动时间。

Project 生命周期状态必须来自 Project 权威数据。

当前已知代码事实：`core.project.status` 实际存在的状态为 `planning` 和 `initializing`，没有 `active`、`archived`。I1 的归档设计尚未实施。

因此页面实施时必须依据 I1 最终实施后的真实状态定义，不得提前假设某个状态已存在。

## 3.3 待人工处理

<badge>首屏第一优先级</badge>

待人工处理区是总控台的核心工作区域。

展示需要人类负责人采取行动的业务事项，包括：

- 待确认 Finding；
- 待补充信息的 Finding；
- 待审批 Proposal；
- 待决策事项；
- 待验收 Delivery；
- 其他明确要求 human approval 的事项。

每条记录应提供：

- 标题和简要说明；
- 来源领域；
- 来源记录 ID；
- 创建或最近更新时间；
- 处理状态；
- 需要执行的动作；
- 下钻页面；
- 负责人或处理角色（如果来源领域提供）。

不得把 Agent 建议直接当作待审批事项，也不得把 Agent 的自述当作人类批准。

总控台负责聚合和导航，不重新实现 Finding 决定、Proposal 审批或 Delivery 验收。

## 3.4 当前执行

展示当前 Project 下有效的执行工作：

- 当前 Task；
- 当前 Agent；
- 当前 Run；
- Run 状态；
- 运行时间；
- 最近状态变化；
- 绑定的 Repository（如果存在）；
- 失败或异常信息。

项目支持多个 Agent 并行执行，因此不能假设一个 Project 只有一个 Agent 或一个有效 Run。

同一个 Task 可能存在多个历史 Run。

展示时必须区分：

- 当前有效 Run；
- 已完成 Run；
- 已失败 Run；
- 取消的 Run；
- 历史重新执行记录。

重新执行不能覆盖历史 Run。

Run 是否完成必须依据执行领域权威状态，不能依据心跳、聊天内容或 Agent 自述推断。

## 3.5 风险与阻塞

风险区域展示跨领域的异常和阻塞：

- 失败或异常 Run；
- 阻塞 Task；
- 仓库分析失败；
- 关键人工决定长期未处理；
- Delivery 验收异常；
- Project 归档后的进程清理异常（I1 提供相关事实时）。

每条风险展示：

- 风险标题；
- 严重程度；
- 来源；
- 发生时间；
- 当前状态；
- 处理建议或入口。

不同领域的原始状态不能直接视为统一严重程度。

如果各领域没有统一严重程度枚举，I5 可以定义展示层映射，但必须保留来源领域的原始状态和来源记录。

同一业务问题被多个领域引用时，不得未经去重就重复计入独立风险数量。

## 3.6 项目目标与进展

展示：

- Project Goal 摘要；
- Goal 当前状态；
- 最近一次人工确认时间（如果有）；
- 当前关键任务；
- 近期重要成果；
- 目标与计划页面入口。

Goal 的权威内容和生命周期归 I4。

I5 不复制 Goal 内容到专用存储，也不自行推导 Goal 是否已经确认。

项目没有 Goal 时显示空状态和创建入口，不自动生成空 Goal。

# §4. 初始化进度设计

## 4.1 正式裁决

**初始化进度始终保留在总控台中。**

初始化事项全部完成后，自动收缩为简要状态；当出现新的适用初始化事项时，重新展示详细进度。

初始化进度是项目接入情况的动态投影，不是 Project 生命周期状态。

## 4.2 为什么不能把初始化设计成固定流程

项目可以：

- 没有任何 Repository；
- 已关联 Repository，但分析尚未开始；
- 已完成分析，但开发环境尚未准备；
- 已有项目认知，但尚未建立 Goal；
- 已开始正常研发，同时继续完善项目认知；
- 后续新增 Repository，重新触发接入和分析。

因此初始化不能被建模为：

`创建项目 → 关联仓库 → 代码分析 → 建立知识库 → 环境准备 → 初始化完成`

这样的强制线性状态机。

不同初始化事项可以并行进行，也可以根据项目实际情况不适用。

## 4.3 初始化事项分组

总控台展示以下事项：

| 初始化事项 | 展示内容 | 权威数据来源 |
|---|---|---|
| 项目基本信息 | Project 基本信息是否建立 | `core.project` |
| 项目目标 | Goal 是否存在、是否确认 | I4 Goal 数据 |
| 仓库接入 | 已关联仓库及连接状态 | `project_repository` |
| 代码分析 | 分析作业和分析结果 | `repo_import`、`repo_import_source` |
| 项目认知 | Discovery、Finding、知识提案情况 | Discovery / Knowledge |
| 开发环境 | 设备连接和环境准备情况 | 相关开发环境数据 |
| 人工处理 | 待确认、待审批、待验收事项 | 各领域权威数据 |

以上是页面分组，不意味着必须新增七张表或七个独立状态机。

## 4.4 初始化事项展示状态

统一采用 I5 展示层状态：

- 未开始；
- 进行中；
- 已完成；
- 存在阻塞；
- 不适用；
- 尚无法判断。

这些状态仅用于总控台展示，不作为领域数据库状态。

每类事项必须定义自身计算规则。

例如：

| 事项 | 展示状态 | 判定原则 |
|---|---|---|
| 仓库接入 | 未开始 | 无仓库关联且无进行中的接入作业 |
| 仓库接入 | 已完成 | 已关联仓库，且连接状态符合成功条件 |
| 代码分析 | 进行中 | 存在正在执行的分析作业 |
| 代码分析 | 存在阻塞 | 最新有效分析结果失败，且没有更新的成功结果 |
| 开发环境 | 尚无法判断 | 真实就绪条件尚未完成核验 |

具体判定必须依据 I6 及对应领域的真实状态定义。

不能仅凭一条历史失败记录，将项目永久判为失败。

## 4.5 初始化完成判定

初始化完成不是 Project 生命周期状态。

只有同时满足以下条件，才可以显示“基础初始化已完成”：

1. 所有适用且被定义为必需的初始化事项均已完成；
2. 没有必需事项处于进行中；
3. 没有必需事项存在阻塞；
4. 没有必需事项尚未开始；
5. 不适用事项不参与未完成计算。

如果尚无项目类型或初始化要求配置，不能擅自把 Goal、仓库、开发环境全部定义为必需项。

在这种情况下，页面展示“项目接入概况”，不宣称项目已经完成全部初始化。

## 4.6 初始化进度收缩规则

| 情况 | 展示方式 |
|---|---|
| 尚未开始 | 展开，显示下一步 |
| 正在初始化 | 展开，显示进行中的事项 |
| 存在阻塞 | 展开，突出阻塞原因 |
| 首次初始化完成 | 自动收缩为简要状态 |
| 后续新增仓库 | 重新展示新增事项 |
| 出现新的必需事项 | 重新展开 |
| 某事项不适用 | 标记不适用，不计为未完成 |

收缩不能隐藏新的阻塞或人工处理事项。

## 4.7 零仓库 Project

零仓库项目是合法项目状态。

不能因为 `project_repository` 数量为 0，就认定 Project 初始化失败或 Project 无效。

页面应展示：

- 当前尚未关联仓库；
- 代码分析尚未开始；
- 仓库接入是可选的下一步；
- 不依赖仓库的项目工作仍然可以继续。

如果项目不需要代码仓库，仓库接入事项可以标记为不适用。

## 4.8 不展示无依据的初始化百分比

第一版不展示“初始化完成度 73%”之类的百分比。

原因：

- 各初始化事项不是等权重；
- 部分事项可能不适用；
- 多项事项可以并行完成；
- 项目可以在初始化尚未全部完成时开始工作；
- 没有权重依据的百分比会制造错误的精确感。

第一版展示事项数量和具体状态：

- 已完成；
- 进行中；
- 存在阻塞；
- 未开始；
- 不适用。

未来如果确实需要百分比，必须先制定明确的业务权重和完成标准。

# §5. 最近活动设计

## 5.1 正式裁决

**第一版不新增独立的项目活动事实表。**

先核验和复用现有：

- 领域业务记录；
- 审计记录；
- 已持久化且可可靠查询的领域事件。

只有现有数据无法满足统一查询、稳定排序、分页、去重和权限过滤时，才新增项目活动读模型。

## 5.2 三种数据的区别

必须区分：

### A. 审计记录

审计记录回答：

- 谁执行了操作；
- 什么时候执行；
- 操作了什么对象；
- 执行了什么动作；
- 操作结果是什么。

当前已知：

- `governance.audit_log` 是审计记录权威来源；
- `pm_write/audit.rs:44,76` 已有审计 helper；
- 审计记录包含 actor 相关字段和 after_data。

审计记录不等于用户活动流。

内部重试、技术维护或普通查询可能需要审计，但不一定值得展示给项目负责人。

### B. 领域事件

领域事件表达业务变化，例如：

- Run 完成；
- Delivery 提交；
- Finding 确认；
- 仓库分析完成。

使用前必须核验：

- 是否持久化；
- 是否具有稳定事件类型；
- 是否包含 Project 归属；
- 是否可查询历史；
- 是否存在重复投递；
- 是否有明确保留期限；
- 是否能够可靠排序。

Outbox 是可靠投递机制，不应未经核验就当作长期活动历史数据库。

### C. 项目活动

项目活动是面向人的展示概念。

它从审计和领域事实中筛选、归一化、去重后形成。

项目活动不是新的业务事实，也不能替代领域记录。

## 5.3 第一版活动白名单

| 活动 | 优先事实来源 |
|---|---|
| Project 创建、归档 | Project 生命周期记录及审计 |
| Goal 创建、确认、修改 | I4 Goal 记录及审计 |
| Finding 确认、拒绝、要求补充 | I2 决定记录及审计 |
| 仓库接入、分析完成、分析失败 | I6 仓库和导入记录 |
| Agent Run 开始、完成、失败 | Run 权威状态和相关事件 |
| Delivery 提交、验收、拒绝 | Delivery 权威记录和审计 |

以下内容不进入第一版项目活动流：

- 普通心跳；
- 内部重试；
- 技术性日志；
- 普通查询；
- 无业务意义的系统操作；
- Agent 自述但尚未形成业务事实的内容。

## 5.4 活动来源优先级

活动展示应优先使用能够准确表达业务结果的权威领域记录。

审计记录用于补充操作者和操作上下文。

领域事件可以作为活动发生的可靠触发来源，但必须核验其持久化和查询能力。

如果多个来源表达同一个业务动作，需要去重。

去重必须基于稳定的业务对象和动作标识，不能只依靠标题和时间相似度。

## 5.5 必要时新增可重建读模型

如果现有数据无法满足活动流查询要求，可以增加 `project_activity` 一类读模型。

其逻辑字段候选：

| 字段 | 含义 |
|---|---|
| project_id | 所属 Project |
| activity_type | 归一化活动类型 |
| source_type | 来源领域 |
| source_id | 来源记录 ID |
| occurred_at | 业务发生时间 |
| actor_type | human / agent / system 等 |
| actor_id | 操作者标识 |
| summary | 活动摘要 |
| metadata | 必要展示信息 |

这些字段是读模型候选，不代表当前已经存在对应表。

如果新增：

- 必须能够从权威事实重建；
- 不得成为业务写操作的权威来源；
- 必须具备去重机制；
- 必须支持 Project 权限过滤；
- 必须支持稳定排序和分页；
- 必须明确数据刷新和修复机制；
- 不得依赖 Outbox 永久保留全部历史的假设。

# §6. 数据来源与聚合边界

## 6.1 已知数据来源

| 数据对象 | 已知用途 | I5 使用方式 |
|---|---|---|
| `core.project` | Project 基本信息和生命周期 | 项目头部 |
| `project_member` | 项目成员关系 | 权限控制、成员展示 |
| `project_repository` | Project 与 Repository 关联 | 仓库接入 |
| `repo_import` | 项目级仓库分析作业 | 分析进度 |
| `repo_import_source` | 分析作业与仓库关联、Commit SHA | 分析结果 |
| `discovery_session` | Discovery 过程记录 | 项目认知进度 |
| `ai.document_proposal` | 知识文档提案八态管线 | 知识处理进度 |
| `devenv.device` | 开发环境设备信息 | 环境准备 |
| `project_ssh_key` | 项目 SSH Key 相关数据 | 仓库接入辅助信息 |

具体查询路径和权限过滤仍须 I5-A 核验。

## 6.2 必须分开的 Proposal 状态

`ai.document_proposal` 的状态管线：

`draft → quality_gates_passed → redline_pending → confirmed → commit_pending → committed / rejected / rolled_back`

`discovery.discovery_proposal` 的状态：

`pending / approved / rejected / conflict`

两者不是同一个状态机。

I5 必须分开读取、分开展示，不能合并成一个通用 Proposal 状态。

## 6.3 尚需核验的数据来源

实施前核验：

- Project Goal 的正式存储和状态；
- Task 统计查询；
- Run 当前状态及历史记录查询；
- Delivery 待验收查询；
- Finding 待确认和待补充查询；
- Discovery Proposal 查询；
- 项目决策记录查询；
- 审计活动查询；
- Agent 与 Run 的关联关系；
- 环境准备的真实就绪条件；
- 各来源的权限过滤规则；
- 领域事件的持久化与查询能力。

不得因为页面需要某个数字，就假设对应 API 或聚合 SQL 已经存在。

## 6.4 数据权威原则

| 展示内容 | 权威来源 | 不允许的替代方式 |
|---|---|---|
| Project 是否归档 | Project 生命周期 | 根据任务数量推断 |
| Finding 是否确认 | I2 Finding 决定状态 | 根据聊天内容推断 |
| Goal 是否确认 | I4 Goal 状态 | 根据文档是否存在推断 |
| Run 是否完成 | Run 状态机 | 根据 Agent 最后一次发言推断 |
| 仓库分析是否完成 | I6 分析结果 | 根据仓库是否关联推断 |
| Delivery 是否验收 | Delivery 验收状态 | 根据是否存在 Commit 推断 |

每个指标都必须能够追溯到权威来源。

## 6.5 不建立第二套事实存储

I5 优先采用查询组合和投影读模型。

不得复制领域表中的业务状态并长期维护另一套权威状态。

如果需要缓存或物化视图：

- 必须能从权威数据重建；
- 必须有明确数据新鲜度；
- 必须有刷新和失效机制；
- 不得成为领域写操作的权威来源。

# §7. 聚合查询与 API 设计

## 7.1 设计原则

先确定查询契约，再确定 API 形态。

不预设必须新增一个巨大接口。

实施前先检查现有端点能否满足页面需求。

## 7.2 逻辑聚合结构

总控台逻辑上包含六个数据块：

| 数据块 | 内容 |
|---|---|
| `project_summary` | 项目身份、生命周期、Goal 摘要 |
| `initialization_progress` | 初始化事项及展示状态 |
| `work_summary` | Task、Run 汇总 |
| `human_action_summary` | 待确认、待审批、待验收 |
| `risk_summary` | 风险事项 |
| `recent_activity` | 最近关键活动 |

以上是建议的读模型结构，不代表当前已经存在对应 DTO、API 或数据库视图。

## 7.3 API 方案

推荐评估项目级总览入口：

`GET /projects/{project_id}/command-center`

这是设计候选，不是已存在端点。

响应按六个数据块组织。

如果单一接口造成查询过重、权限边界混乱或加载延迟过高，可以拆成：

- 项目摘要；
- 初始化进度；
- 工作与执行摘要；
- 待人工处理；
- 风险事项；
- 最近活动。

是否采用单一接口或拆分接口，由 I5-A 核验和性能评估决定。

## 7.4 查询一致性

总控台是聚合读视图，不保证所有数据来自同一个事务快照。

因此：

- 每个数据块应能表达自己的更新时间或数据新鲜度；
- 不同数据块短暂不一致时，不得组合成错误结论；
- 用户进入详情页后，必须重新读取对应领域权威数据；
- 写操作仍由原领域端点完成；
- 不允许通过总控台绕过领域服务更新业务状态。

## 7.5 部分失败处理

某个可选数据源暂时不可用时：

- 其他可用区块仍应正常展示；
- 失败区块明确显示数据暂不可用；
- 不得将数据加载失败显示成 0；
- 不得将数据缺失显示成“没有待处理事项”；
- 应提供必要的重试入口或错误说明。

## 7.6 权限控制

读取聚合数据时：

1. 确认调用者对目标 Project 有读取权限；
2. 每个数据来源继续遵守原领域 Tenant / Project 数据边界；
3. 每条聚合记录必须能够证明其属于当前 Project；
4. 不允许通过传入 Project ID 拼接其他项目的数据；
5. 不允许聚合查询绕过原领域权限检查；
6. 不能因为用户可以查看总控台，就默认其拥有所有领域的写权限。

# §8. 前端交互规则

## 8.1 总控台只做轻量操作

总控台允许：

- 进入详细页面；
- 展开摘要；
- 查看记录详情；
- 执行导航；
- 调用原领域提供且已经授权的快捷操作。

总控台不重新实现：

- Finding 决定；
- Proposal 审批；
- Goal 确认；
- Task 状态变更；
- Run 取消或重新执行；
- Delivery 验收；
- 仓库接入写操作。

## 8.2 空状态

每个区块必须定义空状态。

例如：

| 区块 | 空状态 |
|---|---|
| Goal | 尚未建立项目目标 |
| 仓库 | 尚未关联仓库 |
| Task | 当前没有任务 |
| Agent Run | 当前没有执行中的 Agent |
| 待人工处理 | 当前没有待处理事项 |
| 风险 | 当前没有已识别风险 |
| 最近活动 | 暂无可展示的项目活动 |

必须区分：

- 确实没有记录；
- 尚未接入数据源；
- 数据加载失败；
- 当前用户无权读取；
- 数据尚无法判断。

不能把这些情况全部显示为数字 0。

## 8.3 页面布局

总控台建议结构：

```text
┌──────────────────────────────────────────────────────────────┐
│ 顶部栏：租户 / Project 切换 / 全局操作                         │
├──────────────┬───────────────────────────────────────────────┤
│              │ Project 名称                                  │
│              │ 生命周期状态 / Goal 摘要 / 仓库数量            │
│              ├───────────────────────────────────────────────┤
│              │ 需要你处理                                    │
│              │ Finding / Proposal / 决策 / Delivery           │
│              ├───────────────────────────────┬───────────────┤
│ 项目导航     │ 当前执行                      │ 风险与阻塞     │
│              │ Agent / Task / Run             │               │
│ 总控台       ├───────────────────────────────┴───────────────┤
│ 目标与计划   │ 项目目标与进展                                │
│ AI 执行      ├───────────────────────────────────────────────┤
│ 决策中心     │ 项目初始化进度                                │
│ 项目认知     │ 项目 / Goal / 仓库 / 分析 / 认知 / 环境         │
│ 产物验收     ├───────────────────────────────────────────────┤
│              │ 最近项目活动                                  │

│ AI 命令栏：当前 Project 上下文与 AI 交互                       │
└──────────────────────────────────────────────────────────────┘
```

## 8.4 首屏动态布局

待人工处理、当前执行、风险与阻塞的优先级固定。

初始化进度根据当前状态决定展开或收缩，但不得因为收缩而隐藏新出现的阻塞或待人工事项。

最近活动位于首屏下部，不应抢占人类处理事项的主要空间。

## 8.5 响应式行为

- 左侧导航可折叠；
- 右侧上下文面板可隐藏；
- 中央卡片允许换行；
- 小屏优先显示待人工处理、风险和当前执行；
- 初始化进度可折叠；
- 不因屏幕尺寸变化隐藏关键风险状态。

## 8.6 Project 归档后的展示

Project 归档后：

- 总控台仍可读取项目历史和归档状态；
- 不显示创建新任务或新 Run 的入口；
- 不允许触发会产生新项目活动的操作；
- 可以查看历史 Run、审计和交付记录；
- 如果 I1 的进程清理尚未完成，应展示清理状态。

归档不等于所有执行进程已经完成清理。

# §11. 与其他工作包的依赖

| 工作包 | I5 依赖内容 | 依赖性质 |
|---|---|---|
| I1 | Project 归档、入口关闭、Run 清理状态 | 展示依赖 |
| I2 | Finding 确认、拒绝、待补充语义 | 展示依赖 |
| I3 | 仓库读写授权事实（如需展示） | 展示依赖 |
| I4 | Goal 权威存储和生命周期 | 展示依赖 |
| I6 | 仓库接入、分析作业、Commit 基准和结果 | 初始化进度依赖 |

I5 不反向决定上述领域的数据模型或业务状态。

如果 I5 发现领域缺少必要的权威读能力，应回到对应领域工作包补充，而不是在 I5 中复制一套业务规则。

## 11.1 I6 与 I5 的实施关系

I6 必须先于 I5 完成设计和数据契约核验。

I6 负责：

- 仓库接入；
- 多仓库关联；
- 仓库连接状态；
- 项目级分析作业；
- 仓库级分析来源；
- Commit 基准；
- 分析失败与恢复；
- 分析结果回写。

I5 负责消费 I6 提供的权威事实，并展示：

- 已关联仓库；
- 仓库连接状态；
- 正在分析的仓库；
- 分析失败的仓库；
- 最近分析使用的 Commit SHA；
- 项目代码认知进度。

I5 不得自行重新实现仓库接入或分析状态机。

当前已知代码事实：

- `repo_import` 是项目级作业表；
- 仓库关联在 `repo_import_source(import_id, repository_id)`；
- Commit SHA 在 `repo_import_source.head_commit_sha`；
- `repo_import_one_in_progress` 唯一索引限制同一项目同时最多一个 in-flight 分析；
- `project_repository.status/head_commit_sha/last_verified_at/last_error_code` 表示仓库连接事实；
- 分析作业结果属于 `repo_import/repo_import_source`，两类模型必须分开。

因此 I5 的仓库接入展示必须遵循 I6 最终确认的数据契约，不能把仓库连接成功等同于代码分析完成。

## 11.2 实施顺序

S01 工作包顺序保持：

`I1 → I2 → I3 → I4 → I6 → I5`

I5 虽然设计先行定稿，但实际代码实施排在 I6 之后。

建议在 I6 完成后，对 I5 的数据契约进行一次一致性核验。

该核验不重新打开本设计稿已裁决的产品原则，只确认数据来源、字段和查询方式是否与实际实现一致。

# §12. 最终设计裁决

以下条款为 I5 V1.1 正式裁决：

1. I5 是 Project 默认工作入口，不是单纯的数据统计 Dashboard。
2. 首页首屏以待人工处理为第一优先级。
3. 当前执行排在第二优先级，风险与阻塞排在第三优先级。
4. 统计数字不占据首屏中心。
5. 初始化进度始终保留。
6. 初始化完成后自动收缩；出现新事项时重新展示。
7. 初始化进度是展示层动态投影，不是 Project 生命周期状态机。
8. 初始化完成必须基于适用且必需事项的明确规则。
9. 零仓库 Project 是合法状态。
10. 第一版不展示没有业务权重依据的初始化百分比。
11. 最近活动第一版不新增独立事件事实表。
12. 最近活动先复用审计记录和领域权威事实。
13. Outbox 不得未经核验就作为长期活动历史库。
14. 如确有必要，只能新增可重建的活动读模型。
15. Finding、Goal、Run、Delivery、仓库分析状态必须以各自领域权威数据为准。
16. `ai.document_proposal` 与 `discovery.discovery_proposal` 状态必须分开处理。
17. 聚合读模型不得成为业务事实权威来源。
18. 所有写操作回到原领域服务。
19. 各区块允许独立加载和表达数据新鲜度。
20. Project 归档后保留历史查看能力，但禁止新增项目活动。
21. I6 必须先于 I5 实施，I5 消费 I6 最终数据契约。
22. I5 实施前必须完成代码事实核验和读模型契约。

# §13. 定稿结论

I5 的核心不是把项目所有数据集中到一张页面，而是建立一个可信的项目管理入口。

人类负责人打开 Project 后，首先看到需要自己处理的事情，其次看到 Agent 正在做什么、项目哪里存在风险，然后理解项目目标、初始化情况和最近发生的重要活动。

总控台中的每一个状态、数字和结论，都必须能够追溯到对应领域的权威事实。

I5 不创建第二套项目业务状态，不取代各领域工作页面，不把 Agent 的建议伪装成业务事实，也不把技术日志伪装成项目进展。

**最终目标：让人类负责人管理项目，让 AI Agent 协助执行，让总控台提供可信、可追溯、可行动的项目全局视图。**
