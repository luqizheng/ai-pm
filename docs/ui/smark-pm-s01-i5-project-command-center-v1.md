## §0. 设计目标与边界

### 0.1 设计目标

I5 建立项目负责人进入某个 Project 后看到的第一个工作页面。

它需要回答六个问题：

1. 这个项目要达成什么目标？
2. 项目目前处于什么阶段？
3. 当前有哪些重要工作正在执行？
4. 哪些事情阻塞了项目推进？
5. 哪些事情需要人类负责人决定或批准？
6. 项目接入和初始化还缺少什么？

总控台是项目级读视图，不是新的业务流程引擎。

### 0.2 不负责的事情

I5 不负责：

- 创建、修改或确认 Project Goal（归 I4）。
- 实现 Finding 的确认、拒绝和补充机制（归 I2）。
- 实现仓库 Git 读写授权（归 I3）。
- 实现仓库导入、代码分析及其结果写入（归 I6）。
- 实现 Project 归档和 Run 清理（归 I1）。
- 重新定义 Task、Run、Delivery、Knowledge 等领域状态机。
- 把所有领域状态统一改造成一个 Project 状态字段。
- 建立一个覆盖全项目的通用百分比进度系统。

I5 只消费上述领域的权威事实，并将它们组织成项目负责人可理解的视图。

### 0.3 设计边界

| 范围 | 归属 |
|---|---|
| 项目生命周期 | I1 |
| Finding 人工确认 | I2 |
| 仓库读写授权 | I3 |
| Project Goal | I4 |
| 仓库接入和代码分析结果 | I6 |
| 项目级汇总、风险提示、待办入口 | I5 |
| 页面布局和交互 | I5 |
| 聚合查询和必要读模型 | I5 |

## §1. 产品定位与信息架构

### 1.1 总控台是项目工作入口

总控台不是独立于项目工作空间之外的第二套系统。

它是进入 Project 后默认展示的首页。

用户可以从总控台进入具体业务页面，但不应在总控台直接实现所有领域操作。

例如：

- 发现有待确认 Finding，点击后进入项目认知/决策页面处理。
- 发现某个 Run 失败，点击后进入 AI 执行页面查看。
- 发现某个 Delivery 待验收，点击后进入产物验收页面。
- 发现仓库尚未完成接入，点击后进入仓库管理或初始化流程。

### 1.2 沿用 AI R&D Workspace V1.0 信息架构

项目工作空间继续使用以下主要工作区：

1. 总控台
2. 目标与计划
3. AI 执行
4. 决策中心
5. 项目认知
6. 产物验收

I5 负责第一个工作区，不新增一个与其并列的“初始化中心”。

仓库管理、开发环境、项目设置等具体入口，按既有工作空间导航和页面层级组织，不因为总控台聚合而复制一套菜单。

### 1.3 全局布局基线

沿用此前确认的高保真设计系统：

| 区域 | 尺寸/行为 | 职责 |
|---|---|---|
| 顶部栏 | 52px | 租户、项目切换、全局操作 |
| 左侧导航 | 232px，可折叠 | 项目工作空间导航 |
| 中央区域 | 自适应 | 当前工作区主要内容 |
| 底部 AI 命令栏 | 72～120px | 面向当前项目的 AI 交互入口 |
| 右侧上下文面板 | 320px，可隐藏/固定 | 展示当前页面的上下文来源 |

AI 上下文必须可见，让用户知道 Agent 正在依据哪些材料工作。

但上下文展示不构成权限授权，也不能替代后端鉴权。

## §2. 总控台页面结构

建议采用以下结构：

### 2.1 页面顶部：项目身份与生命周期

展示：

- Project 名称
- Project 标识
- Project 当前生命周期状态
- 项目 Goal 摘要（如果已经建立）
- 项目关联仓库数量
- 最近活动时间

Project 生命周期状态必须来自权威 Project 数据，不能由总控台自行推导出一套新的生命周期。

当前已知代码事实：`core.project.status` 目前实际只有 `planning` 和 `initializing`，没有 `active`、`archived`。I1 归档设计尚未实施，因此不能提前把 `active/archived` 当作现有状态使用。

### 2.2 第一行：项目核心指标

建议展示四个指标：

| 指标 | 展示内容 | 口径 |
|---|---|---|
| 当前任务 | 进行中 / 待处理 | Task 权威状态 |
| Agent 执行 | 运行中 / 异常 | Run 权威状态 |
| 待人工处理 | 待确认 / 待审批 / 待验收 | 对应领域权威状态 |
| 项目风险 | 阻塞 / 异常数量 | 从已知风险来源聚合 |

注意：

- 这些指标不是新的状态存储。
- 数字必须来自真实业务记录。
- 不得把同一个问题在多个领域重复计数后当作多个独立风险。
- 各指标必须提供可点击的下钻入口。
- 如果某类数据尚未接入，显示“尚未接入”或不展示该指标，不得显示伪造的 0。

### 2.3 中央区域：项目进展

建议包含三个区块。

**A. 项目目标**

展示：

- 当前 Project Goal 摘要
- 目标状态
- 最近一次人工确认时间（如果有）
- 目标与当前计划的入口

Goal 的具体内容和权威性归 I4。I5 不复制一份 Goal 内容到总控台专用存储。

如果项目尚未建立 Goal，应展示明确的空状态和创建入口，而不是生成一个空 Goal。

**B. 当前工作**

展示：

- 当前进行中的 Task
- 当前运行中的 Agent / Run
- 最近完成的关键工作
- 当前失败或异常的执行

每条记录应能下钻到对应 Task 或 Run。

不在总控台重新定义 Task 或 Run 的状态。

**C. 近期活动**

展示最近发生的关键项目事件，例如：

- Goal 确认或修改
- Finding 确认或拒绝
- 仓库分析完成
- Agent Run 完成或失败
- Delivery 提交或验收
- Project 归档

活动事件需要有来源和时间，不能将 AI 自述当作已经发生的业务事件。

## §3. 项目初始化进度视图

### 3.1 设计原则

项目初始化进度是总控台的重要组成部分。

但初始化不是一个必须按固定顺序完成的线性流程。

例如，一个项目可以：

- 暂时没有关联任何仓库；
- 已关联仓库，但尚未完成代码分析；
- 已完成代码分析，但尚未准备开发环境；
- 已经有项目认知，但还没有正式 Goal；
- 已经开始任务执行，同时仍在完善项目认知。

因此不能简单采用：

`创建项目 → 关联仓库 → 代码分析 → 建立知识库 → 环境准备 → 初始化完成`

这样的硬编码状态机。

### 3.2 初始化事项分组

总控台展示以下初始化事项：

| 初始化事项 | 展示内容 | 权威数据来源 |
|---|---|---|
| 项目基本信息 | 项目是否已建立、基本信息是否完整 | `core.project` |
| 项目目标 | Goal 是否存在、是否已确认 | I4 的 Goal 权威数据 |
| 仓库接入 | 已关联仓库及连接状态 | `project_repository` |
| 代码分析 | 导入作业、分析结果、失败原因 | `repo_import`、`repo_import_source` |
| 项目认知 | Discovery 会话、Finding、知识提案等 | Discovery / Knowledge 领域 |
| 开发环境 | 设备连接和环境准备情况 | `devenv.device` 等相关数据 |
| 人工处理 | 待确认、待审批、待验收事项 | 对应领域权威数据 |

以上是页面分组，不代表必须创建七张新表或七个新状态机。

### 3.3 初始化事项状态

统一采用总控台展示层状态：

- 未开始
- 进行中
- 已完成
- 存在阻塞
- 不适用
- 尚无法判断

这些是 I5 的展示状态，不是各领域的数据库状态。

每个事项都必须定义自己的计算规则。

示例：

| 事项 | 展示状态 | 判定原则 |
|---|---|---|
| 仓库接入 | 未开始 | 项目没有关联仓库，且没有正在执行的仓库接入作业 |
| 仓库接入 | 已完成 | 已关联仓库，并且连接状态符合已核验的成功条件 |
| 代码分析 | 进行中 | 存在正在执行的导入分析作业 |
| 代码分析 | 存在阻塞 | 最近一次有效分析结果失败，且没有更新的成功结果 |
| 开发环境 | 尚无法判断 | 尚未完成相关数据源和判定规则核验 |

具体条件必须在实施前根据 I6 及其他领域的真实状态定义。

不能仅凭一个历史失败记录，就把当前项目永远判为失败。

### 3.4 零仓库项目

零仓库项目必须是合法状态。

不能因为 `project_repository` 数量为 0，就认定项目初始化失败或项目无效。

页面应展示：

- 当前尚未关联仓库；
- 代码分析尚未开始；
- 仓库接入是可选的下一步操作；
- 其他不依赖仓库的项目工作仍可继续。

如果项目本身的工作方式不需要代码仓库，仓库接入事项可以展示为“不适用”。

不能把仓库数量大于零作为 Project 进入正常工作的唯一条件。

### 3.5 初始化进度不能伪造百分比

不建议第一版展示“项目初始化完成度 73%”这样的百分比。

原因：

1. 各初始化事项不是等权重。
2. 某些事项可能不适用。
3. 某些事项可以并行完成。
4. 项目可以在初始化事项尚未全部完成时开始工作。
5. 没有明确的权重定义，百分比会产生错误的精确感。

第一版展示：

- 已完成事项数量；
- 进行中事项数量；
- 存在阻塞事项数量；
- 尚未开始事项数量；
- 不适用事项数量。

同时展示具体事项和下一步操作。

如果未来确实需要百分比，必须先定义业务权重和完成标准，不能直接按事项数量计算。

## §4. 待人工处理与风险聚合

### 4.1 待人工处理是总控台的优先区域

项目负责人最需要看到的不是所有 Agent 活动，而是哪些事情必须由人类介入。

建议将待人工处理区放在总控台较靠前的位置。

包含：

- 待确认 Finding；
- 待补充信息的 Finding；
- 待人工批准的 Proposal；
- 待决策事项；
- 待验收 Delivery；
- 其他明确要求 human approval 的业务事项。

每一条必须保留来源：

- 来源领域；
- 来源记录 ID；
- 创建时间；
- 当前负责人或处理角色（如果领域有此信息）；
- 需要执行的动作；
- 下钻页面。

不能把“Agent 建议”与“等待人类批准”混成一种状态。

### 4.2 Finding 的展示规则

Finding 的真实决定状态由 I2 负责。

I5 只消费 I2 的最终状态。

至少区分：

- 待确认；
- 待补充；
- 已确认；
- 已拒绝。

特别注意：

- 不能仅凭 Finding 为 PENDING 且存在 open question，就判定为待补充。
- 待补充应遵循 I2 规定的最近一次有效人工决定审计推导规则。
- 不得从 Discovery Session 状态推导 Finding 是否已经确认。
- 人工确认和拒绝必须来自可信 human 操作，不能把 Agent 的转述当作人类确认。

### 4.3 风险聚合

风险不是新的独立业务对象。

第一版从以下来源聚合：

- 失败或异常的 Run；
- 阻塞的 Task；
- 仓库分析失败；
- 待处理的关键人工决定；
- Delivery 验收异常；
- 项目归档后的残留清理异常（如果 I1 提供相应事实）。

风险展示至少包含：

- 风险标题；
- 严重程度；
- 来源；
- 发生时间；
- 当前状态；
- 推荐处理入口。

风险严重程度需要使用领域已有的级别，或者在 I5 明确制定统一的展示映射规则。

不能把不同领域的原始状态直接当成同一套严重程度。

## §5. AI Agent 与人类协作视图

### 5.1 展示 Agent 当前工作

总控台可以展示：

- 当前运行的 Agent；
- 对应 Task；
- 当前 Run；
- 运行时间；
- 最近一次状态变化；
- 是否存在异常；
- 对应仓库（如果该 Run 绑定仓库）。

Run 的执行权威状态由执行领域提供。

总控台不得自行通过心跳、聊天内容或 Agent 自述判断 Run 已完成。

### 5.2 多 Agent 并行

项目允许多个 Agent 并行执行。

总控台必须能够展示多个 Run，而不是假设一个 Project 只有一个 Agent 或一个执行实例。

同一个 Task 可能有多个历史 Run，展示时必须区分：

- 当前有效 Run；
- 历史 Run；
- 失败后重新执行的 Run。

重新执行不会覆盖历史 Run。

### 5.3 AI 建议与业务事实分离

页面应区分：

- 业务事实；
- Agent 观察；
- Agent 建议；
- 等待人类决定的事项。

例如：

“代码分析发现可能存在模块边界问题”属于 Agent 发现或建议。

“模块边界问题已被项目负责人确认”才属于经过人类确认的业务事实。

总控台不能把建议自动提升为已确认事实。

## §6. 数据来源与聚合边界

### 6.1 已知数据来源

| 数据对象 | 已知用途 | I5 使用方式 |
|---|---|---|
| `core.project` | Project 基本信息和生命周期 | 项目头部 |
| `project_member` | 项目成员关系 | 权限控制、成员展示 |
| `project_repository` | Project 与 Repository 关联 | 仓库接入 |
| `repo_import` | 项目级仓库分析作业 | 分析进度 |
| `repo_import_source` | 分析作业与仓库关联、Commit SHA | 仓库分析结果 |
| `discovery_session` | Discovery 过程记录 | 项目认知进度 |
| `ai.document_proposal` | 知识文档提案八态管线 | 知识处理进度 |
| `devenv.device` | 开发环境设备信息 | 环境准备 |
| `project_ssh_key` | 项目 SSH Key 相关数据 | 仓库接入辅助信息 |

注意：

`ai.document_proposal` 的状态管线是：

`draft → quality_gates_passed → redline_pending → confirmed → commit_pending → committed / rejected / rolled_back`

它与 `discovery.discovery_proposal` 的：

`pending / approved / rejected / conflict`

不是同一个状态机。

I5 必须分开读取、分开展示，不得合并成一个通用 Proposal 状态。

### 6.2 尚需核验的数据来源

以下数据需要在 I5-A 阶段核验实际查询路径：

- Project Goal 的正式存储和状态；
- Task 统计查询；
- Run 当前状态及历史记录查询；
- Delivery 待验收查询；
- Finding 待确认和待补充查询；
- Discovery Proposal 查询；
- 项目决策记录查询；
- 审计活动记录查询；
- Agent 与 Run 的关联关系；
- 环境准备的实际成功条件；
- 各来源的权限过滤规则。

不能因为页面需要某个数字，就假设对应的聚合 SQL 或 API 已存在。

### 6.3 数据权威原则

每个展示指标都必须有一个明确权威来源。

例如：

| 展示内容 | 权威来源 | 不允许的替代方式 |
|---|---|---|
| Project 是否归档 | Project 生命周期 | 根据任务数量推断 |
| Finding 是否确认 | I2 Finding 决定状态 | 根据聊天内容推断 |
| Goal 是否确认 | I4 Goal 状态 | 根据文档是否存在推断 |
| Run 是否完成 | Run 状态机 | 根据 Agent 最后一次发言推断 |
| 仓库分析是否完成 | I6 分析结果 | 根据仓库是否关联推断 |
| Delivery 是否验收 | Delivery 验收状态 | 根据是否存在 Commit 推断 |

### 6.4 聚合不应成为第二套事实存储

I5 优先采用查询组合和投影读模型。

不复制业务表中的状态，不维护一套独立的“总控台状态”。

如果需要缓存或物化视图：

- 必须能够从权威数据重建；
- 必须有明确的数据新鲜度；
- 必须有失效或刷新机制；
- 不得成为领域写操作的权威来源。

## §7. 聚合查询与 API 设计

### 7.1 先确定查询契约，再决定 API 形态

I5 不预设必须新增一个巨大接口。

先梳理页面真正需要的数据，再评估：

- 现有端点能否满足；
- 是否需要新增项目级聚合读端点；
- 是否需要拆成多个按需加载的端点；
- 是否需要数据库视图或物化视图。

### 7.2 推荐的逻辑聚合结构

总控台逻辑上需要以下数据块：

| 数据块 | 内容 |
|---|---|
| `project_summary` | 项目身份、生命周期、Goal 摘要 |
| `initialization_progress` | 初始化事项及展示状态 |
| `work_summary` | Task、Run 汇总 |
| `human_action_summary` | 待确认、待审批、待验收 |
| `risk_summary` | 风险事项 |
| `recent_activity` | 最近关键事件 |

以上是建议的读模型结构，不代表现有代码已经存在这些 DTO、API 或数据库视图。

### 7.3 端点方案

建议先评估一个项目级总览读取入口，例如：

`GET /projects/{project_id}/command-center`

但该路径只是设计候选，不是现有端点。

响应可按上述六个数据块组织。

如果单个接口导致查询过重、权限边界混乱或加载延迟过高，可以拆分为：

- 项目摘要；
- 初始化进度；
- 工作与执行摘要；
- 待人工处理；
- 最近活动。

第一版不应为了减少 HTTP 请求而把所有业务查询强行塞进一个超大 SQL。

### 7.4 查询一致性

总控台是聚合读视图，不保证所有数据来自同一个事务快照。

因此：

- 每个数据块应能表达自己的更新时间或数据新鲜度；
- 不同数据块短暂不一致时，不得把它们组合成错误结论；
- 对可能发生并发变化的记录，用户进入详情页后应重新读取权威数据；
- 所有写操作仍由原领域端点完成；
- 总控台不直接绕过领域服务更新业务状态。

### 7.5 权限

总控台必须沿用项目级访问控制。

读取聚合数据时：

- 先确认调用者对目标 Project 有读取权限；
- 每个数据来源继续遵守原领域的 Tenant / Project 数据边界；
- 不允许通过聚合查询泄露其他 Project 的 Finding、Run、Proposal 或 Delivery；
- 聚合结果中的每条记录都应能够证明其归属当前 Project；
- 不允许仅根据前端传入的 Project ID 拼接其他项目的数据。

## §8. 页面交互规则

### 8.1 总控台只做轻量操作

总控台允许：

- 进入详细页面；
- 展开摘要；
- 查看记录详情；
- 触发明确的导航；
- 对某个事项执行已有领域提供的快捷操作（前提是权限和领域规则不变）。

总控台不重新实现：

- Finding 决定；
- Proposal 审批；
- Goal 确认；
- Task 状态变更；
- Run 取消或重新执行；
- Delivery 验收。

### 8.2 空状态

每个区块必须有合理空状态。

例如：

- 尚未关联仓库：展示仓库接入入口。
- 尚无 Goal：展示建立项目目标的入口。
- 尚无 Task：展示当前没有任务。
- 尚无 Agent Run：展示当前没有执行中的 Agent。
- 尚无待人工处理：展示当前没有待处理事项。
- 尚无活动记录：展示项目尚无可展示的活动。

空状态不能统一显示为“0”，因为“没有数据”“尚未接入数据源”和“确实为零”含义不同。

### 8.3 Project 归档后的展示

Project 归档后：

- 总控台仍可读取项目历史和归档状态；
- 不能显示可创建新任务或新 Run 的入口；
- 不能触发会产生新项目活动的操作；
- 可以继续查看历史 Run、审计和交付记录；
- 如果 I1 的进程清理尚未完成，应明确展示清理状态。

归档不等于所有执行进程已经完成清理。

### 9.1 页面线框

### 9.2 首屏优先级

首屏按以下顺序安排：

1. 项目身份与生命周期；
2. 待人工处理；
3. 当前执行和风险；
4. 项目目标与进展；
5. 初始化进度；
6. 最近活动。

如果项目尚处于初始化阶段，可以将初始化进度上移，但不能改变其数据语义。

### 9.3 响应式行为

- 左侧导航可折叠；
- 右侧上下文面板可隐藏；
- 中央区域卡片允许换行；
- 小屏下优先显示待人工处理、风险和当前执行；
- 初始化进度可折叠；
- 不因屏幕尺寸变化而隐藏关键风险状态。

## §10. I5 实施前代码核验

### I5-A：现状核验

实施前必须完成：

1. 核验 Project 查询与权限路径。
2. 核验 `project_repository` 关联查询。
3. 核验 `repo_import` 与 `repo_import_source` 的结果查询。
4. 核验 Discovery Finding 和 Proposal 的查询入口。
5. 核验 `ai.document_proposal` 与 `discovery.discovery_proposal` 的独立状态。
6. 核验 Goal 的正式数据结构和状态。
7. 核验 Task、Run、Delivery 的项目级统计查询。
8. 核验最近活动和审计事件的查询方式。
9. 核验设备和开发环境的真实就绪判定。
10. 核验聚合读取时所有领域的 Project / Tenant 权限边界。

交付建议：

`docs/s01-i5-code-facts.md`

文档必须将结果标注为：

- 已证实；
- 待核验；
- 需新增。

不能将设计候选 API 或字段标记为已存在。

### I5-B：读模型契约

根据 I5-A 结果确定：

- 各数据块字段；
- 每个指标的权威来源；
- 各展示状态的计算规则；
- 空状态规则；
- 数据更新时间；
- 权限过滤方式；
- 错误和部分数据不可用时的处理方式。

### I5-C：聚合查询实现

实现已裁定的查询方案。

要求：

- 不写入领域业务状态；
- 不重复维护领域状态；
- 不跨 Project 泄露数据；
- 不因为某个可选数据源缺失而使整个总控台无法展示；
- 对部分数据失败提供可识别的错误状态。

### I5-D：前端总控台

按 V1.0 设计系统实现：

- 项目头部；
- 指标区；
- 待人工处理；
- 当前工作；
- 风险区；
- 初始化进度；
- 最近活动；
- 空状态；
- 归档只读状态。

### I5-E：验收与性能

验证聚合查询、权限、并发变化、空状态、归档状态和页面性能。

| 编号 | 验收内容 | 预期结果 |
|---|---|---|

| I5-002 | 零仓库 Project | 合法展示，不判定初始化失败 |
| I5-003 | 多仓库 Project | 能区分各仓库的接入和分析结果 |
| I5-004 | 分析作业进行中 | 能展示真实进行状态 |
| I5-005 | 分析作业失败 | 展示失败来源和下钻入口 |

| I5-014 | Delivery 待验收 | 展示待验收入口 |
| I5-015 | 没有待人工处理 | 正确显示空状态 |
| I5-016 | 数据源部分失败 | 其他可用区块仍可展示 |

## §12. 与其他工作包的依赖

| 工作包 | I5 依赖内容 | 依赖性质 |
|---|---|---|
| I1 Project 归档 | 归档状态、入口关闭、Run 清理状态 | 展示依赖 |
| I2 Finding 确认 | 确认、拒绝、待补充的权威语义 | 展示依赖 |
| I3 Git 权限 | 仓库写权限和执行授权事实（如需展示） | 展示依赖 |
| I4 Project Goal | Goal 权威存储和生命周期 | 展示依赖 |
| I6 仓库分析 | 导入作业、仓库分析结果、Commit 基准 | 初始化进度依赖 |
| I5 | 汇总上述领域事实 | 最后实施 |

I5 不应反向成为 I1～I6 的业务依赖。

如果 I5 发现领域数据不足，应回到对应工作包补充权威读能力，而不是在 I5 中复制一套业务规则。

## §13. 最终设计裁决建议

1. I5 是项目负责人默认进入的总控台，不是新增一个初始化菜单。
2. 总控台同时呈现项目运行总览和初始化进度。
3. 初始化进度是展示层投影，不建立新的 Project 初始化状态机。
4. 零仓库 Project 是合法项目。
5. 第一版不展示没有业务权重依据的初始化百分比。
6. 每个指标必须绑定一个明确的权威数据来源。
7. I5 不复制 Goal、Finding、Proposal、Run、Delivery 等领域状态。
8. 聚合读模型优先从现有数据组合；是否新增 API 由 I5-A 核验结果决定。
9. 允许不同数据块独立加载、独立表达数据新鲜度。
10. 所有写操作仍回到原领域服务，I5 不成为新的业务写入口。
11. 归档 Project 可查看历史，但不得继续产生新的项目活动。
12. I5 在 I1～I4、I6 的数据契约明确后最后实施。

## §14. 待裁决事项

以下事项不应在缺乏代码事实时直接定稿：

- Q1：总控台首屏是否采用一个项目级聚合端点，还是多个数据块端点？
- Q2：最近活动是否直接复用审计事件，还是需要单独的项目活动读模型？
- Q3：Goal 的摘要和状态是否已有可直接消费的查询接口？
- Q4：环境就绪的成功条件由哪些权威字段决定？
- Q5：风险严重程度是否已有统一枚举，还是只在展示层做映射？
- Q6：各区块是否需要统一的数据更新时间字段，还是按数据块分别返回？

这些问题应先由 I5-A 代码核验给出事实，再决定是否需要用户裁决。

---

**I5 的最终目标：让项目负责人一进入项目，就能看清目标、进展、执行、风险和需要自己处理的事项；而总控台展示的每一个结论，都能追溯到真实业务事实。**
