# I4 · Project Goal（Knowledge + project-goal）设计稿 V1.0

> **文档性质**：S01 设计稿——Project Goal 领域模型与 Knowledge 管理规则  
> **版本**：V1.0  
> **状态**：待代码核验、待用户最终确认  
> **所属范围**：S01  
> **核心原则**：Project Goal 是项目的权威目标性知识资产，复用现有 Knowledge + `project-goal`，不另建平行存储；Agent 可以提出修改，但项目目标的正式变更由人类负责确认。

---

# §0. 设计目标与基本裁决

## 0.1 要解决的问题

一个 Project 在长期研发过程中，会持续产生：

- 项目目标与愿景；
- 业务需求；
- 需求变更；
- 技术决策；
- 架构约束；
- 实施过程中的发现；
- 阶段性成果；
- Agent 的分析与建议。

这些内容都可能进入 Knowledge，但它们的重要性和权威性并不相同。

其中，Project Goal 有特殊地位：

1. 它描述项目为什么存在、希望实现什么。
2. 它是人类对项目方向的正式表达。
3. 它是 Agent 理解项目目标、判断任务方向的重要上下文。
4. 它可能随着项目发展发生变化，但不能被 Agent 的普通知识写入随意覆盖。
5. 它需要保留历史变化，能够追溯谁在什么背景下改变了项目目标。

因此，本设计需要明确：

- Goal 和普通 Knowledge 的区别；
- Goal 的唯一性；
- Goal 的创建、修改和确认规则；
- Agent 如何提出 Goal 变更；
- 多 Agent 并行时如何避免相互覆盖；
- Goal 如何进入 Agent 上下文；
- Project 归档后 Goal 如何处理。

## 0.2 核心裁决

| 编号 | 裁决 | 说明 |
|---|---|---|
| I4-D01 | 复用现有 Knowledge | 不建立独立的 Goal 文档存储系统 |
| I4-D02 | 使用 `project-goal` | 作为 Goal 的 Knowledge 类型标识 |
| I4-D03 | 每个 Project 一个正式 Goal | 不允许多个互相竞争的正式项目目标 |
| I4-D04 | Goal 是项目级权威知识 | 普通 Knowledge 不能覆盖 Goal |
| I4-D05 | Agent 可以提出修改 | Agent 不得自行批准项目目标变更 |
| I4-D06 | 人类负责最终确认 | Goal 的正式变更必须有可信的人类确认行为 |
| I4-D07 | Knowledge 写入统一协调 | 多 Agent 并行不能直接互相覆盖 |
| I4-D08 | 保留 Goal 历史 | 正式变更必须能够追溯 |
| I4-D09 | Agent 默认读取正式 Goal | 未确认的提案不能冒充正式项目目标 |
| I4-D10 | 归档后禁止修改 | 已归档 Project 的 Goal 只读 |

## 0.3 不在本设计范围内

本设计不负责：

- 普通需求文档的完整生命周期；
- Discovery Finding 的人工确认机制（由 I2 负责）；
- Git 仓库读写权限；
- Task 生命周期；
- Agent 的角色与调度；
- 整个 Knowledge 系统的底层索引算法；
- Markdown 解析、Embedding、全文检索的具体实现；
- 项目归档生命周期本身（由 I1 负责）。

本设计只定义 Project Goal 在现有 Knowledge 体系中的领域语义和管理规则。

# §2. Project Goal 的领域定义

## 2.1 定义

Project Goal 是一个 Project 唯一的正式目标性 Knowledge 资产。

它描述：

- 项目要解决什么问题；
- 项目希望达到什么结果；
- 项目的核心使用对象；
- 项目范围；
- 项目明确不做什么；
- 项目成功的判断标准；
- 项目当前阶段的主要目标。

Goal 不等于完整需求文档，也不等于 Task 列表。

它是整个 Project 的方向性约束。

## 2.2 Goal 与普通 Knowledge 的区别

| 对比项 | Project Goal | 普通 Knowledge |
|---|---|---|
| 作用 | 定义项目方向 | 记录项目知识 |
| 归属 | 一个 Project | 一个 Project 或其他现有知识空间范围 |
| 权威性 | 项目正式目标 | 根据来源、审核状态和内容类型决定 |
| 创建 | 人类建立或确认 | 按 Knowledge 现有流程 |
| 修改 | 必须经过人类确认 | 按现有 Knowledge 规则 |
| Agent 行为 | 可以提出修改建议 | 可以按授权流程创建或补充 |
| 并发 | 严格协调 | 按 Knowledge 通用并发机制 |
| 历史 | 必须可追溯 | 遵循现有版本策略 |
| Agent 上下文 | 默认加载正式版本 | 按任务相关性检索 |

## 2.3 Goal 的建议内容结构

Goal 的正文采用 Markdown。

建议结构如下：

```markdown
# Project Goal

## 1. 项目背景
为什么启动这个项目？

## 2. 核心问题
项目希望解决什么问题？

## 3. 项目目标
最终希望达到什么结果？

## 4. 目标用户
项目主要服务于哪些对象？

## 5. 项目范围
明确本项目需要完成的范围。

## 6. 非目标
明确本项目暂时不做或明确不做的内容。

## 7. 成功标准
如何判断项目达到目标？

## 8. 关键约束
业务、技术、合规、资源等约束。

## 9. 当前阶段目标
当前阶段最重要的交付目标。
```

以上是建议的内容模板，不意味着数据库中已经存在对应的结构化字段。

**裁决：Goal 正文以 Markdown 为主，不将其拆成大量 `core.project` 字段。**

原因：

- Goal 具有较强的自然语言表达需求；
- 项目目标会持续演进；
- Markdown 方便人类和 Agent 共同理解；
- 不应为了结构化读取而重复存储一份权威内容；
- 可以通过解析和索引获得检索能力。

如果未来需要统计某些结构化信息，应优先考虑从正式 Goal 中提取派生数据，而不是形成第二份可独立修改的目标事实。

# §3. Goal 的唯一性与归属

## 3.1 唯一性规则

一个 Project 在任意时刻只有一个正式生效的 Project Goal。

这里的唯一性是业务语义，不意味着现有数据库已经存在唯一索引。

实施前需要核验是否已有对应约束。

如果没有，应补充必要的数据库约束或通过现有 Knowledge 服务实现事务级唯一性。

## 3.2 Goal 的归属

Goal 必须属于一个明确的 Project。

不得出现：

- 一个 Goal 同时作为多个 Project 的正式目标；
- 一个 Agent 创建 Goal 时没有明确 Project；
- 一个 Project 因并行 Agent 执行而出现多个正式 Goal；
- 普通 Knowledge 通过修改类型标识而直接变成正式 Goal，绕过确认流程。

如果需要从其他 Project 复制 Goal 内容，应创建新的提案或新的 Goal 内容，不应共享同一个可变权威文档。

## 3.3 Goal 与 Project 元数据

Goal 的正文不应与 `core.project` 的基础元数据重复。

`core.project` 负责项目身份、生命周期等平台管理事实。

Project Goal 负责项目的目标性知识。

两者职责如下：

| 内容 | 权威位置 |
|---|---|
| Project ID | `core.project` |
| Project 生命周期 | `core.project` |
| Project 目标正文 | Knowledge / `project-goal` |
| Goal 的正式版本 | Knowledge 现有版本机制或本设计要求补充的版本机制 |
| Goal 修改提案 | 现有 Proposal / DocumentProposal 流程 |
| 人工确认行为 | 可信服务端确认记录及审计 |
| Agent 执行状态 | Task / Run 体系 |

不应在 `core.project` 中额外保存一份可独立编辑的 Goal 正文。

# §4. Goal 生命周期

## 4.1 生命周期原则

Goal 的生命周期分为两个层次：

1. Goal 正式内容的生命周期；
2. Goal 修改提案的生命周期。

正式 Goal 与待确认提案不能混为一谈。

## 4.2 正式 Goal 的生命周期

建议业务语义：

```text
not_created
    |
    v
active
    |
    v
archived (Project archived)
```

说明：

- `not_created`：Project 尚未建立正式 Goal。
- `active`：正式 Goal 存在并可被读取、修改。
- `archived`：所属 Project 已归档，Goal 只读。

这里的 `not_created / active / archived` 是领域状态描述，不代表现有 Knowledge 表中已经存在这些状态字段。

如果现有 Knowledge 有自己的文档状态机，应映射到现有模型，而不是为了 Goal 再增加一套重复状态机。

## 4.3 修改提案的生命周期

Agent 或人类提出修改时，应使用现有 Knowledge Proposal / DocumentProposal 流程。

不能另建一套与现有状态机平行的 GoalProposal 状态机。

已知：

`ai.document_proposal` 八态：

```text
draft
  |
  v
quality_gates_passed
  |
  v
redline_pending
  |
  v
confirmed
  |
  v
commit_pending
  |
  v
committed
```

异常或终止状态：

```text
rejected
rolled_back
```

这套流程可以作为 Goal 修改的承载基础，但必须先核验：

- `project-goal` 是否已经可以进入该管线；
- `confirmed` 的实际含义；
- `committed` 是否意味着正式 Knowledge 内容已经更新；
- 确认行为是否具备可信人类身份；
- 是否能够保证旧版本和新版本的关系；
- 是否能够防止未确认内容被 Agent 当作正式 Goal。

**不得直接假定 `confirmed` 和 `committed` 在所有业务场景中完全等价。**

## 4.4 创建正式 Goal

建议流程：

```text
Project 创建
    |
    v
建立 Goal 初稿
    |
    v
人类检查
    |
    v
确认 Goal
    |
    v
进入正式 Knowledge
    |
    v
Agent 可读取正式 Goal
```

如果 Project 创建时没有 Goal：

- 可以允许 Project 先存在；
- 但在正式 Goal 建立前，应向 Agent 明确标记 Goal 缺失；
- Agent 可以协助生成初稿；
- 不允许 Agent 自动将初稿发布为正式 Goal。

是否强制 Project 创建时同步建立 Goal，需要结合现有项目创建流程决定。本设计不强制引入额外的 Project 中间态。

## 4.5 修改正式 Goal

建议流程：

```text
人类 / Agent 提出修改
          |
          v
创建修改提案
          |
          v
解析和质量检查
          |
          v
生成差异（Redline）
          |
          v
人类审核
          |
          v
人类确认
          |
          v
提交 Knowledge 正式版本
          |
          v
更新 Agent 读取的正式 Goal
```

其中：

- Agent 可以生成修改提案；
- Agent 可以提供修改理由和证据；
- Agent 可以生成 Redline；
- Agent 不得替代人类完成最终确认；
- 只有成功提交的版本才能成为正式 Goal。

## 4.6 修改不等于覆盖

修改 Goal 必须形成新版本。

禁止：

- Agent 直接覆盖正式 Goal 文件；
- Agent 直接删除旧 Goal 内容；
- Agent 绕过 Proposal 直接修改正式版本；
- 两个 Agent 同时以旧版本为基础分别提交，后提交者静默覆盖前者；
- 只保存最新内容而无法还原历史目标。

# §5. 人类与 Agent 的职责边界

## 5.1 人类职责

人类负责：

- 创建和确认项目目标；
- 判断目标是否合理；
- 决定目标是否变更；
- 确认目标变更的影响范围；
- 决定项目是否偏离原始目标；
- 对重大目标变化做最终裁决。

人类是 Project Goal 的最终决策者。

## 5.2 Agent 职责

Agent 可以：

- 读取正式 Goal；
- 分析当前 Task 是否符合 Goal；
- 发现需求与 Goal 冲突；
- 提出 Goal 修改建议；
- 生成 Goal 修改草稿；
- 解释修改原因；
- 生成新旧版本差异；
- 提供证据和影响分析；
- 检查其他 Knowledge 是否与 Goal 冲突。

Agent 不可以：

- 自行确认 Goal；
- 自行拒绝人类提出的 Goal 变更；
- 将自己的分析结论直接写入正式 Goal；
- 将某个 Task 的临时目标升级为 Project Goal；
- 因为发现了新事实而自动改变项目方向；
- 使用伪造的用户身份完成确认。

## 5.3 Agent 的 Goal 偏离处理

如果 Agent 发现 Task 与正式 Goal 不一致，应：

1. 停止将冲突内容当成既定目标继续扩展；
2. 记录冲突点；
3. 提供相关证据；
4. 向人类提出问题或建议；
5. 等待人类决策。

这里的“停止”指停止擅自改变项目目标，不代表所有无关 Task 都必须停止。

如果冲突只影响当前 Task，可以由 Task 管理流程处理；如果冲突涉及整个项目方向，则需要进入项目级人工决策。

# §6. 多 Agent 并行与 Knowledge 写入协调

## 6.1 基本原则

Project 可以有多个 Agent 并行执行任务。

但 Project Goal 是共享的权威知识。

因此：

**Agent 并行读取，Knowledge 统一协调写入。**

不能让多个 Agent 直接持有 Goal 正式文件的写权限并自由覆盖。

## 6.2 写入协调模型

```text
                 Project Goal
                      |
              正式版本（只读）
                      |
        +-------------+-------------+
        |             |             |
      Agent A       Agent B       Agent C
        |             |             |
     修改建议       修改建议       修改建议
        |             |             |
        +-------------+-------------+
                      |
              Knowledge 协调入口
                      |
                Proposal 流程
                      |
                人类确认
                      |
                 正式提交
                      |
                 新版本生效
```

这里的统一协调入口是逻辑职责，不预设必须新增某个独立服务或微服务。

应优先复用现有 Knowledge 写入服务。

## 6.3 Agent 并发提案

允许多个 Agent 同时提出 Goal 修改。

例如：

- Agent A 认为目标范围需要扩大；
- Agent B 发现当前目标存在技术不可实现性；
- Agent C 认为成功标准不够明确。

这些建议可以同时存在。

但它们不能直接修改正式 Goal。

## 6.4 基于基础版本的修改

每个修改提案必须能够识别其基于哪个正式 Goal 版本产生。

例如：

```text
正式 Goal V3
    |
    +--- Agent A 提案 P1（基于 V3）
    |
    +--- Agent B 提案 P2（基于 V3）
    |
    +--- Agent C 提案 P3（基于 V3）
```

当 P1 被确认并提交，正式版本变为 V4。

此时 P2、P3 不能直接提交。

它们必须重新检查：

```text
Proposal 基础版本 = V3
当前正式版本 = V4
```

发生不一致时：

- 标记为需要重新校验或存在冲突；
- 不允许自动覆盖 V4；
- 可以基于 V4 重新生成提案；
- 由人类决定是否继续采用原建议。

## 6.5 并发控制要求

实施时应采用现有 Knowledge 版本机制。

如果现有机制不具备条件更新能力，则新增必要的并发控制。

建议逻辑：

```text
提交提案时：

1. 确认 Project 仍为 active
2. 读取当前正式 Goal 版本
3. 比较提案基础版本
4. 不一致则拒绝直接提交
5. 一致则执行原子提交
6. 保存新版本
7. 保存审计记录
```

具体锁顺序、数据库事务和版本字段以代码核验结果为准。

不要仅依赖应用层先读后写，因为并发提交可能在检查和写入之间发生。

## 6.6 一个关键裁决

**统一协调不等于所有 Agent 串行执行。**

Agent 的任务执行、分析、文件修改仍然可以并行。

只有共享 Knowledge 的正式写入需要经过协调。

这样既保留并行执行效率，也避免共享知识被覆盖。

# §7. Goal 版本、历史与审计

## 7.1 版本原则

正式 Goal 每次发生有效变更，都必须留下可追溯的历史。

至少能够回答：

- 当前正式 Goal 是什么？
- 上一个正式版本是什么？
- 谁提出了修改？
- 为什么修改？
- 谁确认了修改？
- 何时确认？
- 哪些 Agent 或 Task 参与了修改？
- 修改前后差异是什么？

## 7.2 不重复建设版本系统

首先核验现有 Knowledge 版本机制。

如果现有机制已经支持：

- 版本标识；
- 正式版本；
- 历史内容；
- 差异查看；
- 来源追踪；

则直接复用。

如果没有，应补齐必要能力。

不要为了 Goal 额外建立一套独立版本表，除非现有模型确实无法承载。

## 7.3 审计

Goal 的正式变更必须能够关联可信审计记录。

审计至少应能识别：

| 内容 | 说明 |
|---|---|
| Project | 所属项目 |
| Goal | 被修改的目标 |
| 操作类型 | 创建、确认变更、拒绝提案等 |
| 操作者 | 真实服务端身份 |
| 提案 | 对应 Proposal |
| 变更前版本 | 原正式版本 |
| 变更后版本 | 新正式版本 |
| 时间 | 服务端记录时间 |
| 变更原因 | 人类确认时的说明 |

确认人和确认时间应以可信审计记录为依据。

不得通过 Agent 自行填写的 Markdown 字段作为身份确认依据。

已知 `governance.audit_log` 是当前项目审计体系的一部分，实施时应核验它能否承载上述关联，不要无必要地另建审计系统。

## 7.4 审计原子性

Goal 正式版本提交与审计记录必须具备一致性。

建议：

```text
同一事务：

1. 校验 Project 状态
2. 校验正式 Goal 当前版本
3. 校验 Proposal 状态
4. 更新正式 Goal
5. 记录新版本关系
6. 写入审计记录
7. 更新 Proposal 最终状态

全部成功后提交。
```

如果审计写入失败，正式 Goal 变更应整体回滚。

实际事务边界需要结合现有 DocumentProposal 实现核验。

# §8. Agent 上下文读取规则

## 8.1 正式 Goal 是默认权威上下文

Agent 开始执行 Project Task 时，应能够读取当前正式 Goal。

不应要求每个 Task 的创建者重复粘贴项目目标。

## 8.2 读取优先级

建议上下文优先级：

| 优先级 | 内容 | 使用方式 |
|---|---|---|
| 1 | 当前正式 Project Goal | 项目方向的权威依据 |
| 2 | 已确认的项目决策 | 项目约束和明确裁决 |
| 3 | 与 Task 相关的正式 Knowledge | 当前工作所需知识 |
| 4 | 已确认的 Finding | 有证据支持的事实 |
| 5 | 未确认的 Proposal / Finding | 只能作为待核验信息 |
| 6 | Agent 临时分析 | 不得作为正式项目事实 |

该表定义的是上下文解释优先级，不是要求每个 Agent 一次性加载全部项目文档。

## 8.3 Goal 缺失

如果 Project 没有正式 Goal：

- Agent 应能识别 Goal 缺失；
- 不得自行编造一个正式目标；
- 可以协助生成初稿；
- 应提醒人类完成项目目标确认；
- Task 是否允许继续执行由任务类型和项目管理策略决定。

不建议因为 Goal 缺失就全局禁止 Agent 工作。

例如，仓库环境初始化、基础代码扫描等任务可能不依赖正式 Goal。

## 8.4 Goal 变更后的上下文一致性

正式 Goal 更新后：

- 新创建的 Run 应读取新版本；
- 正在运行的 Run 不应被静默修改其已获取的上下文；
- 如果新 Goal 与正在执行的 Task 存在重大冲突，应通知人类；
- 是否取消或重新执行相关 Task，由项目管理流程决定。

建议 Run 的执行上下文记录本次实际读取的 Goal 版本或稳定内容标识，以便事后追溯。

这是建议新增的上下文追踪能力，不代表当前 `task_run` 已有对应字段。

## 8.5 防止提案污染正式上下文

未确认的 Goal 修改提案：

- 不得替代正式 Goal；
- 不得进入 Agent 的权威 Goal 上下文；
- 可以作为明确标注的待审信息提供给相关 Agent；
- Agent 必须知道它是提案，而不是正式目标。

# §9. Project 归档后的 Goal 规则

本节继承 I1 的 Project 归档规则。

## 9.1 归档规则

Project 进入 `archived` 后：

- Goal 正式版本只读；
- 不允许创建新的 Goal 修改提案；
- 不允许确认新的 Goal 修改；
- 不允许 Agent 继续修改 Goal；
- 允许查看正式 Goal；
- 允许查看历史版本；
- 允许查看历史提案与审计记录。

## 9.2 归档时存在未完成提案

如果 Project 归档时存在未完成 Goal 修改提案：

- 不允许它们在归档后继续提交；
- 不允许异步处理任务绕过 Project 状态继续发布；
- 可以保留原始提案和审计信息；
- 具体终止状态应复用现有 Proposal 状态机，不得随意增加不兼容状态。

## 9.3 与 I1 的一致性

I1 负责：

- Project 归档；
- Project 活动门禁；
- Run 取消；
- 执行凭据撤销。

I4 负责：

- Goal 只读；
- Goal 修改入口关闭；
- 未完成 Goal 提案不能继续发布。

不能出现 Project 已归档，但异步 Knowledge Worker 仍然能够把 Goal 新版本提交为正式版本的情况。

因此，Knowledge 正式提交入口必须检查 Project 是否仍然 active。

# §10. 建议接口与服务逻辑

本节是新增设计建议，不代表现有 API 已经存在。

实施前先核验现有 Knowledge API，优先扩展现有服务。

## 10.1 读取接口

建议具备以下能力：

```text
读取 Project 当前正式 Goal
读取 Goal 历史版本
读取 Goal 修改提案
读取 Goal 版本差异
```

具体 URL、RPC 名称和返回结构由现有 API 风格决定。

不要求为了每项能力建立独立服务。

## 10.2 创建与修改接口

建议具备：

```text
创建 Goal 初稿
创建 Goal 修改提案
提交 Goal 修改提案审核
确认 Goal 修改提案
拒绝 Goal 修改提案
```

Agent 和人类可以有不同调用入口，但最终必须经过统一的 Knowledge 领域服务。

## 10.3 Agent 写入约束

Agent 调用 Goal 修改入口时：

- 必须明确 Project；
- 必须明确修改目标；
- 必须提供修改原因；
- 必须能够识别基础版本；
- 必须保留来源信息；
- 不得调用正式发布入口冒充人类确认。

## 10.4 人类确认约束

人类确认时：

- 必须使用可信服务端身份；
- 必须检查 Tenant 和 Project 权限；
- 必须检查 Project 未归档；
- 必须检查 Proposal 当前状态；
- 必须检查基础版本仍然有效；
- 必须写入审计记录；
- 必须保证业务变更和审计一致性。

不得接受客户端自行传入的 `confirmed_by` 作为真实确认人。

## 10.5 不建议新增的内容

本设计不建议：

- 新建 `project_goal` 独立存储表；
- 在 `core.project` 再增加一份 Goal 正文；
- 新建独立 Goal 版本系统；
- 新建独立 Goal 审批状态机；
- 为每个 Agent 建立一份独立的 Goal 副本；
- 为 Goal 单独建设一套文档检索系统。

如果现有实现确实无法支持某项必要能力，才考虑增加最小化扩展。

# §11. 数据一致性与异常场景

## 11.1 重复创建

两个 Agent 或人类同时尝试创建正式 Goal：

- 最终只能有一个正式 Goal；
- 不能通过应用层先查后写来保证唯一性；
- 必须由事务或数据库约束保证；
- 失败的一方应得到明确冲突结果。

## 11.2 同时修改

两个 Agent 基于同一版本提出修改：

- 两个提案都可以保存；
- 不能直接同时提交；
- 第一个成功提交后，第二个必须重新校验基础版本；
- 不允许静默覆盖。

## 11.3 确认与归档竞争

人类确认 Goal 和 Project 归档可能并发发生。

必须有明确的事务顺序和线性化结果：

- 如果 Goal 变更先成功，之后归档，则新 Goal 成为归档时的最终版本；
- 如果归档先成功，Goal 确认必须失败；
- 不允许归档完成后再出现新的正式 Goal 版本。

具体锁顺序继承 I1 的 Project 活动门禁设计。

## 11.4 提案提交失败

如果 Proposal 已经确认，但正式 Knowledge 提交失败：

- 不得假装正式 Goal 已更新；
- 必须保留可恢复的提交状态；
- 重试必须幂等；
- 不得重复产生多个正式版本；
- 必须能够识别最终是否已经提交。

应复用现有 `commit_pending` / `committed` 等状态语义，不重新发明另一套状态。

## 11.5 正式 Goal 内容损坏

如果当前正式 Goal 无法读取：

- 不允许自动回退到某个未确认提案；
- 应报告正式 Goal 读取失败；
- 可以尝试从历史正式版本恢复；
- 恢复行为必须可审计；
- 不得将历史版本静默当成当前版本。

# §14. 最终设计裁决

本设计最终确定以下规则：

1. Project Goal 是 Knowledge 体系中的一种特殊项目级知识资产，类型标识为 `project-goal`。
2. 不建立独立的 Goal 文档存储，不在 `core.project` 重复保存 Goal 正文。
3. 一个 Project 只有一个正式生效的 Goal。
4. Goal 使用 Markdown 表达，允许自然语言描述项目背景、目标、范围、非目标和成功标准。
5. Agent 可以读取 Goal、分析 Goal、提出 Goal 修改建议。
6. Agent 不得自行确认或发布正式 Goal。
7. Goal 修改复用现有 Knowledge Proposal / DocumentProposal 流程，不另建平行状态机。
8. 正式 Goal 的修改必须保留历史版本和可信审计记录。
9. 多 Agent 可以并行提出修改，但正式 Knowledge 写入统一协调。
10. 提案必须基于明确的正式 Goal 版本；基础版本过期时不得静默覆盖。
11. Agent 默认读取当前正式 Goal，不能把待确认提案当成正式目标。
12. Project 归档后 Goal 只读，所有 Goal 正式写入入口必须遵循 I1 的 Project 活动门禁。
13. 实施前必须完成 Knowledge、`project-goal`、DocumentProposal、版本机制和写入入口的代码核验。
14. 所有新增字段、接口、约束和实现必须在实施任务中明确标注，不得伪装成现有代码事实。

# §15. 待用户最终确认的问题

> **本次用户裁决（2026-11-03，S01-0 基线阶段）**
>
> | 问题 | 裁决 | 与本文推荐的关系 |
> |---|---|---|
> | **Q1** Goal 是否必须在 Project 创建时建立 | **是——随 Project 创建时一并建立**（每 Project 一条正式 Goal） | **推翻本稿推荐**（本稿推荐"不强制同步建立"）。裁决理由：Project 由人类创建，人类在创建时即应明确项目目标；Goal 事后补建会让 Agent 在无正式目标的情况下先跑一段，违背"人类负责项目"原则 |
> | **Q2** Agent 是否允许直接修改正式 Goal | **不允许——Agent 只能提出修改提案，由人类确认后正式发布** | 与本稿推荐一致（**确认**） |
>
> **Q3～Q6 保持本稿推荐口径**（走完整 DocumentProposal 管线；允许多 Agent 并行提案但正式提交串行 + 基础版本校验；暂不做结构化字段；Agent 默认读取正式 Goal）。实施时若与代码事实冲突，须回审本节，不得默默偏离。
>
> **对实施的直接影响**：I4-B 的「初次创建规则」按 Q1 落为「创建 Project 时建立」；
> I4-C 的「确认与提交真实语义」按 Q2 落为「Agent 永不直接写正式 Goal」；
> I4-A 需在核验中确认 Project 创建链路（`pm_lists::create_project_handler` →
> `bootstrap_project*`）能承载 Goal 的同步建立。

以下问题影响最终实施边界。

**Q1：Goal 是否必须在 Project 创建时建立？**

推荐：不强制同步建立。Project 可以先创建，Goal 可以随后由人类建立；在正式 Goal 建立前，Agent 必须知道 Goal 缺失。

**Q2：Agent 是否允许直接修改正式 Goal？**

推荐：不允许。Agent 只能提出修改提案，由人类确认后正式发布。

**Q3：Goal 修改是否必须经过完整 DocumentProposal 管线？**

推荐：是。优先复用现有管线，不为 Goal 创建单独审批系统。

**Q4：Goal 是否允许多个 Agent 同时提出不同修改？**

推荐：允许并行提案，但正式提交必须串行协调，并检查基础版本。

**Q5：Goal 是否需要结构化字段？**

推荐：暂时不需要。正文以 Markdown 为权威内容；后续如果有统计、过滤或自动校验需求，再从正式内容派生结构化数据。

**Q6：Agent 是否默认读取正式 Goal？**

推荐：是。Project 级 Agent 上下文默认包含正式 Goal，Task 级 Agent 按需加载相关 Knowledge。

---

**最终建议：** I4 不应该演变成一套新的文档系统。它应该是现有 Knowledge 体系之上的一组领域规则：明确哪个文档是项目目标、谁有权改变它、修改如何确认、多个 Agent 如何协作，以及所有 Agent 如何读取同一个权威版本。

这套规则稳定后，Project Goal 就成为整个 AI 研发管理平台的方向性依据。
