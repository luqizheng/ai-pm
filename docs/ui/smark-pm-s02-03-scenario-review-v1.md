## §1. 修改意见明细

**C-1 · 缺第五来源「存量/冷启动导入」。**
来源枚举须补「存量/冷启动导入」（`CreateRequirements` 命令，现系统**唯一的**需求创建路径），并声明导入与运行时新建共用同一身份/类型/生命周期语义——否则第五来源的需求在模型里无出生地。

**C-2 · 验收双链悬空。**
任务级验收链（`delivery.task_acceptance_criterion` + D5 证据）已存在；需求级验收（CAND-8）尚待建。场景稿两链都提及但未写明**汇合点**：两链须在交付确认（Delivery acceptance）处汇合，由交付确认同时背书任务级与需求级验收结论。

**C-3 · 版本变化→Task 影响须展开三步。**
§6.3-4 中需求版本变化对已关联 Task 的影响应展开为：**识别**（哪些 Task 关联了旧修订）→ **提示**（向 Task 责任人/Agent 发变更信号）→ **裁决**（人决定 Task 是否跟新修订/维持快照/解除关联）。隐含"按需求反查 Task"的反向查询能力依赖，稿中未列。

**C-4 · 异常场景缺零 Task NFR 验收失败。**
NFR 可合法关联零个 Task（约束②是"可以"非"必须"），其验收失败的裁决路径（CAND-10 / Q-14）是异常场景之一，稿中异常枚举漏列。

**C-5 · 「确认」术语三分。**
稿中「确认」一词三用，建议三分：**采纳**（accept，draft 修订的采纳）、**定稿**（approve，revision 定稿）、**Finding 确认**（confirm，I2 语义）。三个动作的权限主体与红线各不相同。

**C-6 · §4.1 与 §5.3 缺交叉引用。**
两节描述同一权限/红线主题但互不引用，读者无法确认是否同一套规则。

**C-7 · BR 表漏两条。**
业务规则表建议补 BR-07（需求正文权威唯一，Q-3 关联）与 BR-08（禁止无痕删除——修订链不可跳脱）。

**C-8 · §5.1 权限前置加现状锚点。**
权限前置条件应标注现状：V-4 已实证「读受保护（404/空列表）但写全开（201+200）」，即稿中前置在现状**不满足**，防读者误以为已具备。
