# PM-AI 五阶段业务体系 V1.0（核定基线）

- **版本**：V1.0
- **核定日期**：2026-11-08
- **状态**：已核定（用户批准作为 PM-AI 一级业务架构基线）
- **定位**：后续所有需求、数据库设计、服务划分和 UI 导航都必须能够映射到这五个阶段。

---

## 一、五阶段业务体系总览

| 阶段 | 名称 | 核心问题 | 一句话定位 |
| --- | --- | --- | --- |
| **S01** | Project Initialization（项目初始化） | 我们正在做什么项目？项目目前是什么状态？ | 项目初始化与项目认知建立 |
| **S02** | Requirement Engineering（需求工程） | 这个项目究竟需要实现什么？ | 需求工程与需求治理 |
| **S03** | Analysis, Design & Technical Decisions（分析、设计与技术决策） | 应该采用什么技术方案，如何实现？ | 需求转化为技术分析、设计方案、ADR 和可实施的设计基线 |
| **S04** | Task Management & Planning（任务管理与执行规划） | 需要完成哪些工作，如何组织和安排？ | 将已批准的设计和实施基线转化为可执行任务 |
| **S05** | AI Agent Execution（AI Agent 执行） | 如何让 AI Agent 真正完成工程任务？ | 调度外部工程 Agent，执行、验证与交付协调 |

### 核心关系

```
S01 建立项目认知 → S02 确认做什么 → S03 决定怎么做 → S04 规划谁来做、如何做 → S05 真正执行并交付
```

---

## 二、各阶段核心职责

### S01：项目初始化（Project Initialization）

**核心问题**：我们正在做什么项目？项目目前是什么状态？

**主要内容**：

1. 项目创建、基本信息和项目目标。
2. Git Repository 接入与多仓库管理。
3. 代码库自动发现与项目现状分析（Code Discovery）。
4. Project Cognition：建立项目技术认知。
5. AI-PM 项目负责人初始化。
6. 开发环境、Runner 配置与管理。
7. 项目初始化状态和待人工确认事项。

**最终产出**：一个具备项目目标、项目认知、代码上下文和 AI-PM 管理能力的项目。

---

### S02：需求工程与需求治理（Requirement Engineering）

**核心问题**：这个项目究竟需要实现什么？

**主要内容**：

1. 需求收集：用户输入、项目目标、历史文档、Discovery Findings。
2. AI 需求分析、识别、归纳和结构化。
3. Functional / Non-functional Requirements。
4. 需求优先级、分类和依赖关系。
5. 需求澄清与问题管理。
6. 需求评审和人工正式确认。
7. 需求版本、变更和需求基线。
8. 需求追踪：需求与设计、ADR、任务之间的关联。
9. 外部 Commit 变更接管与需求归属识别（S02-I7）。

**最终产出**：经人工确认、可追踪、可管理变更的正式需求体系。

**特别强调**：正式需求确认权属于人，AI 负责分析、建议和维护。

---

### S03：分析、设计与技术决策（Analysis, Design & Technical Decisions）

**核心问题**：应该采用什么技术方案，如何实现？

**子阶段**：

| 子阶段 | 主要内容 |
| --- | --- |
| S03-01 | 需求技术分析 |
| S03-02 | 架构与代码分析 |
| S03-03 | 技术方案设计 |
| S03-04 | ADR 技术决策 |
| S03-05 | 设计评审与批准 |
| S03-06 | 实施基线与交接 |

**关键领域模型**：

- **Design**：设计实体，可以关联多个 Requirement。
- **Design Revision**：每次设计修改产生新版本，不覆盖历史。
- **ADR**：独立的架构决策实体。
- **Design Review**：设计评审和人工批准。
- **Implementation Baseline**：正式实施依据。

**最终产出**：已经经过人工批准、技术决策明确、实施范围和验收标准完整的技术设计基线。

**正式准入条件**：设计批准、必要 ADR 已解决、实施范围和验收标准齐备。

---

### S04：任务管理与执行规划（Task Management & Planning）

**核心问题**：需要完成哪些工作，如何组织和安排？

**主要职责**：

1. 从需求和实施基线生成任务。
2. AI 辅助任务拆分（Task Decomposition）。
3. 建立任务与 Requirement、Design、ADR 的追踪关系。
4. 任务依赖关系和执行顺序。
5. 任务优先级、工作量和执行计划。
6. 多 Repository 任务分配。
7. 任务状态、阻塞和风险管理。
8. 为外部工程 Agent 准备执行上下文。
9. 任务交付要求和验收标准。

**最终产出**：可执行、可追踪、有明确交付标准的任务计划。

**重要边界**：S04 负责项目管理和执行规划，**不应该把代码执行本身混入任务管理领域**。

---

### S05：AI Agent 执行（AI Agent Execution）

**核心问题**：如何让 AI Agent 真正完成工程任务？

**主要职责**：

1. Agent 执行任务的调度。
2. MCP 与外部工程工具集成。
3. Codex、Claude Code、Trae 等执行端接入。
4. 执行上下文和知识注入。
5. Agent 执行过程管理。
6. 多 Agent 并行执行与协调。
7. Git 代码变更、Commit 和交付证据收集。
8. 自动测试与执行结果验证。
9. 执行失败、重试、阻塞和人工介入。
10. 人工介入后的会话恢复与继续执行。
11. 执行结果回传 PM-AI。
12. 交付审核、验收和知识库更新。

**最终产出**：真实的代码变更、测试结果、Commit 记录、交付证据，以及更新后的项目知识。

**职责区分**：

- S04 决定任务是什么、执行顺序和交付要求。
- S05 负责调度和协调工程 Agent 完成任务。
- MCP 是通信接口，**不是执行运行时**。
- 工程 Agent 的执行能力可以来自外部工具，**不要求 PM-AI 自己实现代码执行引擎**。

## 三、阶段之间的数据和责任关系（PM-AI 完整业务闭环）

```
S01 项目初始化        S02 需求工程          S03 技术设计          S04 任务规划          S05 Agent 执行
项目目标、项目认知  →  正式需求、需求版本  →  Design、Revision   →  任务、依赖、优先级  →  代码变更、测试、
代码上下文             需求基线              ADR、实施基线          执行计划              Commit、交付证据
                                                                                              │
                                    ← ← ← ← ←  反馈到需求、设计与项目知识，形成持续迭代  ← ← ←
```

## 四、架构原则

**这五个阶段不应该只是五组菜单，也不应该是五个互相独立的子系统。**

它们必须构成一个**有明确领域边界、上下游交付契约和追踪关系的完整体系**。

### 五方责任矩阵

| 维度 | 主要责任 |
| --- | --- |
| **人类** | 负责目标、正式确认、重要决策和最终验收 |
| **AI-PM** | 负责项目管理、分析、协调、治理和知识维护 |
| **工程 Agent** | 负责实际工程执行 |
| **KB / PC** | 负责项目知识与产品认知的权威管理 |
| **PostgreSQL** | 负责状态、身份、版本引用、审批和审计等事务性数据 |

这与既定产品原则一致：**人类负责项目，AI Agent 协助执行**。
