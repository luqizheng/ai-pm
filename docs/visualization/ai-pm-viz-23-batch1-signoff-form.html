本单是领域语义授权，不是架构选型确认。 专家已裁决「允许分批激活」，但架构裁决不代替领域 Owner 对具体关系的签名。
  • Registry 是映射与校验机制，不是业务关系权威——本单不定义新业务事实，只确认既有库内关系的语义是否被准确表达。
  • 每条关系独立会签、独立 Active、独立生效：同批其他条目已签，不会自动激活本条。

  • 否决不是失败——错误的词条比没有词条更危险（会让影响分析、覆盖检查失真）。
R-01 design.covers_requirement 责任 Owner：design-owner
源表
design.design_requirement
方向
directed（design → requirement）
端点
design_revision → requirement_revision
治理级别
L2

语义：Design Revision 覆盖、实现或约束某一特定 Requirement Revision。

请确认以下三点：
  1. 语义确实是「覆盖 / 实现 / 约束」，而非仅「提及」或「弱关联」。
  2. 图边读取绑定修订（requirement_revision_id），不回退到 Requirement 当前版本。
  3. 两端版本归属一致（由源数据保证或读取时校验）。

R-04 task.implements_requirement 责任 Owner：delivery-owner
源表
delivery.task_requirement
方向
directed（task → requirement）
端点
task → requirement_revision
治理级别
L2

语义：Task 被正式关联为实现某一特定 Requirement Revision 的交付任务。

请确认以下三点：
  1. 这是「实现范围绑定」，不是普通任务参考或弱关联。
  2. 历史绑定不得自动改写为 Requirement 当前 Revision。
  3. 不得仅凭该关系推断 Task 已完成或 Requirement 已验收（交付关联 ≠ 完成事实）。

R-05 task.depends_on_task 责任 Owner：delivery-owner
源表
delivery.task_dependency
方向
directed（dependent → prerequisite）
端点
task → task（CHECK 防自依赖）
治理级别
L2

语义：Task A 依赖 Task B，表示 B 是 A 的前置任务。Registry 方向 = task_id（依赖方）→ depends_on_task_id（前置方）。

请确认以下三点：
  1. task_id = 依赖方，depends_on_task_id = 前置方（沿用库内定义）。
  2. Registry 语义方向与 DAG 展示方向是两个约定——DAG 显示 prerequisite → dependent，不得为统一图形方向而改 Registry 语义。
  3. 影响分析与依赖闭包遍历方向相反（闭包沿 Registry 方向；影响分析沿反向），两处代码各自显式声明。
