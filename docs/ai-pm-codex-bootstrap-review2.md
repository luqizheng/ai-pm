## 二、P0：必须修正的问题

### P0-1：`X-AI-PM-Device-Id` 不能被当成设备身份

这是当前方案最需要明确的一点。

V1 的组合是：不发放设备凭据 + MCP 使用现有真人 API Key + `X-AI-PM-Device-Id` 用于 `executor_id` 归因 + Header 自报不可信。

这四条组合起来意味着：**V1 的 Device 不是经过认证的可信设备，而是一个经过登记、可供请求关联的开发环境实体。**

因此必须区分三种身份：

| 身份 | 来源 | 可信程度 | 用途 |
| --- | --- | --- | --- |
| Principal | 真人 API Key | 可信 | 认证、授权、审计主体 |
| Device ID | 请求 Header | 不可信声明 | 环境归因、关联记录 |
| Runner ID | V2 设备凭据 | 经认证 | 设备级执行身份 |

建议把下面这段作为设计稿的硬约束：

> V1 Device ID 仅作为客户端声明的开发环境标识，不构成设备身份认证，也不构成任何权限凭据。服务端不得仅凭 `X-AI-PM-Device-Id` 建立设备信任、扩大项目权限、仓库权限或执行权限。
>
> 所有 MCP 工具调用必须先完成真人 Principal 认证与现有权限校验。Device ID 仅用于辅助归因；当其不存在、无效或不属于当前 Principal 可访问的租户范围时，应按未登记设备处理，不得影响 Principal 的授权结果。
>
> V2 引入设备凭据后，才允许将经过认证的设备身份用于设备级授权与执行控制。

还有一个需要落实到数据库和审计模型的细节：**不要让 Device ID 覆盖真人 principal 的审计身份。**

审计记录应至少能够区分：

- `actor_principal_id`：谁发起了调用。
- `claimed_device_id`：客户端声称使用哪个开发环境。
- `run_id`：如果存在，属于哪次执行。

否则以后查问题时，容易把「哪个人操作」与「哪台机器发起请求」混为一谈。

### P0-2：Device Project Binding 不能成为权限授予机制

「Binding 不扩大 Repository 权限」这个原则正确，但还需要写清楚服务端执行规则。

例如：用户 A 是 Project 成员；Project 关联 Repository R1、R2；Device D 绑定了这个 Project；用户 A 通过 D 调用 MCP，但 A 对 R2 没有对应操作权限——此时不能因为 D 绑定了 Project，就允许 A 操作 R2。

建议明确：

```text
MCP 请求
  │
  ├── 1. 认证真人 Principal
  │
  ├── 2. 校验 Principal 的 Tenant / Project 成员资格
  │
  ├── 3. 校验目标 Repository 的访问权限
  │
  ├── 4. 解析 Device ID（仅归因）
  │
  ├── 5. 记录 Device / Project Binding 关系
  │
  └── 6. 执行 MCP Tool
```

注意，Device 解析可以在权限校验前后进行，但不能成为权限校验的替代品。

建议把这条写入 **T-088 的服务端验收标准**，而不只是放在架构原则中。

### P0-3：T-081 必须成为真实部署验收门禁

裁定 T-081 并入 V1 前置是对的。但需要注意：`curl http://server/mcp` 能返回响应，并不代表 Codex 已经能够正常使用 MCP。

T-081 至少应该验收：

1. Windows 开发机能够访问服务器 `/mcp`。
2. MCP 认证链路能够使用现有真人 API Key。
3. MCP 工具能够获得正确的真人 Principal 上下文。
4. T-051 的 Project Member 校验仍然有效。
5. T-059 的审计归因仍然有效。
6. MCP 长连接或协议交互不会被反向代理错误截断。
7. 未认证请求和越权请求被正确拒绝。

特别是第 3、4、5 条。**跨机连通只是网络验收，不能代替身份链路验收。**

## 三、P1：建议补充的设计约束

### P1-1：Device 的生命周期需要明确

V1 虽然不需要设备凭据，但 Device 仍然是一个持久化对象。至少需要定义：

| 状态 | 语义 |
| --- | --- |
| Active | 可正常用于环境归因 |
| Revoked | 已撤销，不再接受为有效登记设备 |
| Disabled（如需要） | 管理员暂时停用 |

其中最重要的是：

- 重新初始化时复用未撤销 Device。
- 已撤销 Device 不得通过相同 ID 自动恢复。
- Device 被撤销不应撤销真人 Principal。
- Device 被撤销不应改变 Repository 自身权限。
- Device Project Binding 的有效性必须受 Device 状态约束。

如果 V1 不需要 Disabled，就不要为了状态完整性提前引入。

### P1-2：重新初始化必须具有幂等性

复用未撤销 Device 的方向合理，但需要把初始化过程定义为幂等操作：

```text
Bootstrap
  │
  ├── 已有有效 Device
  │     └── 复用 Device
  │
  ├── Device 不存在
  │     └── 创建 Device
  │
  └── Device 已撤销
        └── 不得自动恢复
```

尤其需要明确：

- 同一 Device 重复执行 Bootstrap 不会产生重复记录。
- 重复绑定不会产生重复 Binding。
- 原有有效绑定不会被无意清除。
- 用户主动解除绑定和重新绑定应有明确操作语义。

### P1-3：Ready 不能等同于安装成功

建议把 Ready 定义为一个可验证的状态：

| 检查项 | Ready 条件 |
| --- | --- |
| Skill | 文件存在，版本与 manifest 一致 |
| MCP | Remote MCP 配置存在 |
| Authentication | 真人 API Key 能通过认证 |
| Device | Device 已登记且有效 |
| Project | 至少有一个有效 Project Binding |
| Repository | 所绑定的仓库信息可被服务端识别 |
| Tool | 核心 MCP 工具可正常调用 |

同时应当区分：

- **Installed**：本地文件和配置安装完成。
- **Connected**：Remote MCP 可以连接。
- **Authenticated**：真人身份认证成功。
- **Ready**：必要能力全部通过自检。

不要把四者合并成一个布尔值。这也意味着 **Ready 应当是一个检查结果快照，而不是永久有效的设备属性**——认证过期、绑定撤销、MCP 不可用时，都可能让环境从 Ready 退化。

### P1-4：Manifest 的 SHA-256 校验需要明确信任根

SHA-256 + 同源 manifest 比单纯下载后校验文件要好，但注意：如果 ZIP 和 manifest 都来自同一个被篡改的服务器，那么攻击者可以同时替换 ZIP 和 manifest。

所以 SHA-256 只能保证「文件与 manifest 声明一致」「下载过程没有发生非预期内容变化」，**不能单独证明发布者身份**。

建议设计稿明确写成：

> V1 使用同源 manifest 与 SHA-256 校验实现文件完整性验证，不将其描述为独立的发布者身份认证机制。

V1 可以先保持简单，但不要把完整性校验写成供应链安全保证。

## 四、V1/V2 边界：应当坚持现有裁定

本部分基本赞成，不建议现在增加功能。

| 能力 | V1 | V2 |
| --- | --- | --- |
| Skill 安装 | 是 | 复用 |
| Remote MCP 配置 | 是 | 复用 |
| 真人 API Key | 是 | 可兼容 |
| Device 登记 | 是 | 复用 |
| Project Binding | 是 | 复用 |
| 本地 Runner | 否 | 是 |
| 设备凭据 | 否 | 是 |
| 授权码 | 否 | 是 |
| 无人值守调度 | 否 | 是 |
| CodexExecutor | 否 | 复用 D3/T-031 |

尤其不要在 V1 中提前做：本地 Runner 安装器、设备凭据签发、设备心跳、设备级任务领取、无人值守执行、Runner 进程管理。

**V1 的价值是：让一个真实开发环境能够快速接入 PM-AI，并通过真人身份使用 MCP。不要为了给未来的 V2 铺路，把 V1 做成一个半成品 Runner。**

## 五、任务拆分评审

当前任务关系总体合理。建议补充三个任务验收约束：

| 任务 | 必须验收的内容 |
| --- | --- |
| T-081 | 真实 Windows → Server MCP 通信，而非服务器内部自测 |
| T-088 | Principal 权限与 Device 归因完全分离；Binding 不扩大权限 |

T-090 对 T-082 的硬依赖赞成。初始化后的 Codex 如果连任务列表都无法正常获取，那么所谓 Ready 的实际意义很有限。
