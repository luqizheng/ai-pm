# 文档治理规范

- **状态：** 当前文档维护规范
- **生效日期：** 2026-11-21
- **适用范围：** 本仓库 `docs/` 下的产品、架构、实施、审查、验收和运维文档

## 1. 目标

建立一套低成本、可理解、可持续维护的文档体系，解决多轮人工同步造成的重复、过期、相互矛盾和入口不清晰问题。治理规则应适合小团队，不引入复杂审批流程。

## 2. 文档权威层级

文档目录只表达主题归属，不直接决定权威性。出现冲突时按以下顺序判断：

1. **用户明确确认的业务决策与授权边界**：最高优先级；任何技术文档不得覆盖。
2. **当前正式架构基线 / ADR**：定义系统目标模型、业务规则、职责边界和明确非目标。
3. **当前实施规范 / 技术设计**：在架构基线范围内定义 schema、API、事件、事务、代码实现和测试契约；不得反向改变业务决策。
4. **代码事实与审查报告**：描述某个 commit / migration / 代码快照的真实状态，用于识别差距，不自动覆盖目标架构。
5. **验收记录**：证明某一范围在特定时间、特定代码版本上的验收结果，不代表后续版本仍然成立。
6. **实施计划 / 工作任务**：说明计划做什么；除非有明确验收证据，不表示已经完成。
7. **研究材料、讨论稿和历史版本**：保留背景与演进依据；与当前基线冲突时标记为历史，不作为实施依据。

如果同一层级文件冲突，先在决策索引或冲突台账登记，再由有权主体裁决。不得默默选择更晚的文件或更高的版本号。

## 3. 必须标明的文档状态

新建或实质修订文档时，在标题附近标注状态、版本、日期和适用范围。推荐状态：

| 状态 | 含义 | 能否作为实施依据 |
|---|---|---|
| `BASELINE` / 正式基线 | 已确认的目标架构或正式规则 | 是 |
| `APPROVED` / 已批准设计 | 在正式基线内已批准的详细设计 | 是，限于声明范围 |
| `IMPLEMENTATION` / 实施规范 | 工程实现契约和验收要求 | 是，不能改变业务基线 |
| `EVIDENCE` / 事实证据 | 代码、数据库、测试或验收事实 | 仅作为事实依据 |
| `PROPOSAL` / 提案 | 推荐方案，尚未批准 | 否 |
| `OPEN` / 待决 | 明确需要进一步决定的问题 | 否 |
| `HISTORICAL` / 历史 | 已被新基线替代或仅用于追溯 | 否 |

避免仅用文件名中的 `v1`、`final`、`latest` 推断状态。

## 4. 决策来源必须可区分

架构文档中涉及决策的内容，应区分：

- **用户明确确认**：用户作出的业务、产品或授权决定。
- **授权范围内的架构裁决**：用户已明确委托助手自主收敛的技术设计，由助手按既定约束作出的决定。
- **推荐 / 提案**：尚未获得确认或尚未纳入授权范围的方案。
- **待人类决定**：涉及业务目标、正式需求、重大业务取舍、权限边界或不可逆授权的事项。

不得将助手建议静默写成用户已确认，也不得把“技术上可实现”写成“已获业务授权”。

## 5. 文件组织规则

推荐按文档的主要用途归档：

- `architecture/`：长期有效的架构原则、领域边界、正式基线和架构技术设计。
- `adr/`：跨文档影响较大、需要单独记录原因和后果的架构决策。
- `product/`：产品定位、目标用户、产品需求与 PRD。
- `scenarios/`：按产品场景组织的用户流程、功能规格、UI 与 QA。
- `tasks/`：跨场景的领域专项设计和实施契约。
- `executor/`：Runner / Executor 接入、安装和运维资料。
- `audit/`：代码事实、数据库盘点、差距审查和影响分析。
- `acceptance/`：验收结果和签署记录。
- `runbooks/`：可操作的开发、部署和运维步骤。
- `reference/`：无法归入上述稳定主题的参考材料。

同一主题只保留一个明确的当前入口；历史材料可以保留在原处，但必须从当前入口标注其历史属性和替代关系。

## 6. 更新流程

文档同步按以下顺序进行：

1. 收集用户明确决策、已授权裁决、代码事实和现有文档。
2. 识别重复、冲突、过期假设和缺失主题。
3. 确定本次变更影响的权威基线、实施规范和索引。
4. 更新当前文档；历史材料仅在必要时添加状态说明或替代链接。
5. 更新目录 README、交叉引用和相关任务清单。
6. 检查链接、编号、版本、日期、术语和决策来源。
7. 将同一轮相关变更作为一个清晰的 Git commit 提交，并记录 commit / 变更摘要。

禁止只新增一份“最新汇总”而不更新正式索引；也禁止仅移动文件却不修复交叉引用。

## 7. 冲突与历史版本处理

- 不删除有审查、验收、代码事实或决策过程价值的历史材料。
- 旧设计与当前基线冲突时，在旧文档或索引中标明 `HISTORICAL` 和替代文档。
- 如果旧文档仍有有效子结论，应提取并纳入当前基线后再标记整体历史。
- 对无法确定是否已废弃的内容，登记为 `OPEN`，不得擅自删除或宣称已解决。
- 文件重命名或迁移必须同步修复全仓链接。

## 8. PA-06 / PA-07 专项规则

- PA-06 定义人类与 Agent 的协作授权边界；PA-07 展开 Agent Team、执行运行时和 Task 执行编排，不得改变 PA-06 的业务授权原则。
- AI-PM 可以在已确认目标和授权范围内自主规划、分派、调整和交付；正式业务目标、需求含义和重大业务取舍仍由人类决定。
- 平台正式 Task / Run / Delivery / Review 状态必须经平台受守卫的命令通道维护；外部 Harness 不因执行任务而取得直接修改权威业务状态的权限。
- Runner 管理外部执行进程与运行环境；Harness 是被调用的工程执行系统；MCP 是通信/工具接口，不是 Runner 或执行 Runtime。
- 多 Agent 可以并行执行，但项目级目标、优先级冲突和正式知识写入由唯一逻辑 Project AI-PM 统一协调。
- Workstream 和 Agent Work Unit 的概念不得被误解为新增一套独立 Task / Run 生命周期或平台自有 Agent 身份系统。

- [ ] 是否区分用户决定、授权内技术裁决、提案和待决事项？
- [ ] 是否把目标架构与当前代码事实分开？
- [ ] 是否注明代码 / 数据库 / 测试结论对应的 commit 或日期？
- [ ] 是否更新相关 README 与交叉引用？
- [ ] 是否保留仍有价值的历史证据？
- [ ] 是否检查术语、编号、版本和路径？
