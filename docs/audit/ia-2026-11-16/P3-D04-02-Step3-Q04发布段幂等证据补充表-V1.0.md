### 3. 相同 operation_id + 不同 fingerprint 是否确定返回 409 — CODE FACT：**否**

- completed 行：短路分支**无条件**返回原 receipt（:147-163）——即使本次请求意图与原发布不同（若可构造），也**不会 409**；
- pending/failed 行：走继续发布路径，409 仅由提案状态守卫/CAS/锚失配触发——同样不是指纹级 409；
- **结论**：Q-04 条件「同 op+异 fp→409」在发布段**未实现**。结构性缓解=现状键派生自 proposal_id+提案提交后内容锚不可变（成员锚定触发器），使「同键异指纹」在现有调用面难以构造——但这不构成显式比对，**不得据此标已满足**；
- **实施归属**：由 **GAP-27** 的指纹列+命中比对（同 op 同 fp 确认/异 fp 409）承载，**不新增重复 GAP 编号**（总账 V1.2 §五 T4）。

### 4. 不同 operation_id + 相同 Proposal 内容是否允许并存 — SCHEMA FACT：**允许**

- proposal.proposal_content_hash **无唯一约束**（SCHEMA FACT 0001:3240-3264：仅 NOT NULL）→ 不同 op_id/不同提案行同内容可并存，无 DB 层合并；
- 分析链侧另有候选排除（已入版本∨开放提案的修订跳过）=链路内防重，非全局约束；
- **测试**：发布段「异 op 同内容并存」**无专门用例**（TEST FACT 缺位登记；D6.6 场景 5 已列，随 GAP-29/30 配套批补，不新增编号）。
