## 二、要点归档（详细论证见专家来文，此处仅登记处置口径）

1. **引用面 UNIQUE 边界规则（专家建议入正式审计文档）**：FK 引用面 UNIQUE 不属于业务身份约束清单，而属 FK 结构完整性所要求的最小支撑约束；附三检查（每条至少被一条实际 FK 引用/列序匹配/不借此扩大业务身份范围）。
2. **NO ACTION 口径确认**：历史记录解释价值优先；未来清理需求走业务层显式依赖识别+顺序删除，不赋予 DB 自动删除历史的权限。
3. **DB Guard 边界声明（专家建议）**：DB Guard 是针对正常数据库写入路径及非特权绕过写入的纵深防御机制，不替代数据库权限体系、服务层授权及运维审计；建议未来分维护 Constraint Registry 与 Trigger Registry 两清单。
4. **GAP 边界防混淆（专家额外发现）**：GAP-35≠解决全部并发竞争；GAP-31-A（确定性发布键）≠严格幂等完整闭合（Q-04 对同 op+完整 fingerprint 重放与异 fp 冲突有独立要求）；GAP-32 须独立闭合证明；GAP-36（expire/decide 行竞争）不与 close/decide 混同。
5. **专家六问**（§七，唯一要求补充的材料=《Q-10/GAP-32 现状竞态闭合证明 V1.0》）：①close/decide 是否获取完全相同的项目级 advisory lock；②锁获取时机是否覆盖候选读取/判定/写入；③批量 publish 独立子事务与外层 close 事务间是否存在状态不一致窗口；④部分失败时报告状态/成功/失败计数语义；⑤是否存在不遵循锁协议的写入路径；⑥是否有真实多连接 close×decide 并发测试。
6. **专家不建议清单**：不回退 0030/0035/0036、不重做 0037、不复制 PC 全部 28 条冗余身份 UNIQUE、不增 CASCADE、不把业务规则写入触发器、不为 Q-10 重设计并发架构。
7. **实施授权边界**：本次审阅不产生新的实施授权。
