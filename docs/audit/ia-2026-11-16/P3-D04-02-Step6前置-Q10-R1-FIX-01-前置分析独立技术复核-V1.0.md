## R1：终态不可变性（applied 与 ledger completed 全路径追踪）

### R1-a `proposal.status='applied'`

- **写入路径（CODE FACT，全服务层唯一）**：pc/publish.rs:630 与 projc/publish.rs:630 `UPDATE … SET status='applied' … WHERE … AND status='approved'`——WHERE 限定 approved，applied 行结构上不可能被再次命中。
- **更新/翻转路径**：服务层无 applied→X 写点（grep 全服务层 `'applied'` 写点仅上述两处+project_import 的**异表** repo_import）。**Schema 级兜底（CODE FACT）**：0034 触发器 allowlist 中 applied 无出边——即使未来出现未知写路径，DB 直接拒绝（`illegal transition applied -> X`）。双重不可变。
- **回滚路径**：applied 写点位于 publish_inner 事务内，事务回滚=行回 approved（不留 applied）。
- **异常路径**：applied UPDATE `rows_affected != 1` → Err（:636-640），不产生半态。

### R1-b `write_operation.status='completed'`

- **写入路径（CODE FACT）**：pc/projc publish.rs:644（发布段）+ 起草段两处（proposal.rs 起草账本完成锚定）——均为 `SET status='completed' … WHERE id=$1`。
- **关键问题：该 UPDATE 不限当前 status，是否存在 completed 后被翻转？——否（CODE FACT，:169-207）**：`completed` 行在 publish 入口短路分支（`if row.0 == "completed" { … return Ok(replayed) }`，:169-194）**先于一切 UPDATE 执行并返回**；能走到 :644 的行必然非 completed（INSERT 新行，或既有 pending/failed 行——failed→completed 重试翻转是设计内路径〔故障消除后重试，测试 pc_proposal 注入场景族〕，**不触及"completed 之后"命题**）。
- **既有 pending/failed 行处理（CODE FACT，:197-207）**：非 completed → 继续走发布（注释明示"提案状态与版本号唯一约束兜底"）。
- **回滚路径**：同事务，回滚则 completed 消失。
- **结论**：completed 之后无任何 UPDATE 写点（短路先返回+无其他 UPDATE 语句以 completed 行为目标）。

**R1 判定：✅ 成立（且 0034 为 applied 提供 Schema 级第二重保证——强于前置分析原文表述）。**

## R2：事务原子性（两项事实是否同事务产生并提交）

**CODE FACT**：`UPDATE proposal SET applied`（:628-636）与 `UPDATE write_operation SET completed`（:642-650）位于**同一 `tx`**（publish_inner 事务），中间无 COMMIT；随后生命周期推进/审计/outbox 同事务，最终单点 COMMIT。→ 两事实**原子同生**，不存在"applied 而账本未 completed"的已提交中间态（除非二者皆无）。一致性保证=单事务原子性，无需跨事务推理。

**R2 判定：✅ 成立（比前置分析隐含表述更明确：判定式的两个谓词同事务诞生）。**

## R3：TOCTOU（重读与实际发布之间的时间窗口，逐行）

- **状态读取发生在哪里**：拟新增于 close 循环 Err 分支（analysis_report.rs:598-604 pc / projc 对应段），经 **pool 独立连接**执行无锁 SELECT（READ COMMITTED，每语句新快照）。
- **读取使用什么锁**：无锁（纯 SELECT）。**不参与任何锁序**（与 advisory/行锁无交互）。
- **读取后哪些事务可能改变相关状态**：
  - `proposal.status`：applied 无出边（R1-a 双重保证：服务层 WHERE 限定+0034 触发器）——**无可变事务**；
  - `ledger.status`：completed 后无 UPDATE 写点（R1-b 短路先返回）——**无可变事务**；
  - 账本行本身：同键（`{domain}-decision:{id}` 服务端派生）无并发插入面；起草段命令键（`-analyze:`/`-identity:`）与发布键不相交。
- **实际发布如何处理并发竞争**：publish_inner=advisory('pc_publish:'+project)→账本 INSERT ON CONFLICT→proposal FOR UPDATE（守卫 approved）——并发同提案发布在 advisory 处串行化，后者走 completed 短路。
- **是否存在重读后仍误分类的情况（穷举 Err 来源）**：
  | Err 来源 | 重读时提案状态 | 分类 | 正确性 |
  |---|---|---|---|
  | 守卫：`is 'applied'; requires 'approved'`（R-1 本体：显式补发布先 COMMIT） | applied + 账本 completed | replay | ✅ |
  | 守卫：其他非 approved 态（withdrawn/expired/rejected——close 外层或并发终态化） | 非 applied | failed | ✅（确未发布） |
  | CAS 失配（publish.rs:305-317，提案→failed 同事务 COMMIT） | failed | failed | ✅ |
  | 发布事务失败回滚（Db 错等） | 仍 approved（或账本无行） | failed | ✅ |
  | 指纹失配 409（GAP-27） | approved | failed | ✅（ANALYSIS：close 面 fp 恒=同提案内容锚，该 Err 实际不可达；即使可达分类亦稳） |
  | NotFound/Forbidden | 不变 | failed | ✅ 保守 |

  **误分类反例穷举：无**。重读时点的状态即终态（R1），且分类只依赖终态事实、不依赖 Err 文本。

**R3 判定：✅ 成立（窗口存在但窗内无可变事务=判定不可失效；未发现误分类路径）。**

## R5：锁序与事务边界（实际调用链）

**CODE FACT 调用链（pc 侧；projc 同构）**：

```
close_report (analysis_report.rs:548, 外层 tx A)
 ├─ A: SELECT report … FOR UPDATE            [:554-563]（全程持有→双 close 互斥）
 ├─ 循环: publish_version(pool, …)            [:596-605]（独立连接，每提案独立 tx B）
 │    tx B: pg_advisory_xact_lock('pc_publish:'+project)   [pc/publish.rs:117]
 │         → INSERT write_operation … ON CONFLICT DO NOTHING [:123-131]
 │         → (既有行) SELECT status… → completed 短路返回    [:151-194]
 │         → SELECT proposal … FOR UPDATE                    [:195-204]
 │         → SELECT approval … FOR UPDATE                    [:211-218]
 │         → …成员/版本/审计/outbox…
 │         → UPDATE proposal applied (WHERE status='approved')[:628-636]
 │         → UPDATE write_operation completed                 [:642-650]
 │         → COMMIT B
 │    [拟新增] Err 分支: pool 无锁 SELECT 重读（不进 tx A/B，无锁参与）
 ├─ A: SELECT draft/submitted … FOR UPDATE    [:610-612]（publish 段之后）
 │    → UPDATE withdrawn + 审计（tx A 内）
 └─ A: COMMIT（报告 closed）
```

- **锁序**：tx A 仅持 report 行锁于 publish 循环期间（withdraw 段行锁在 publish 段后获取→同向）；tx B 内序=advisory→账本行→提案行→审批行（§17.3 既登记）；**A 与 B 锁集不相交**（B 不触 report 行；A 在 B 存续期不持提案行锁）→ 无死锁面（与 E-31/E-33 登记一致）。
- **拟新增重读**：无锁 SELECT 于两事务之外——**锁序图零变更**。

**R5 判定：✅ 成立（无新锁边；未采方案 A；约束遵守）。**
