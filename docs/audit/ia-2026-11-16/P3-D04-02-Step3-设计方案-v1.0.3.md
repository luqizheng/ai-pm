## 0. 设计立场与总原则

1. **参考实现关系**：PC 是状态机与事务语义的参考实现；ProjC 满足共同契约，保留六项登记领域差异（+本轮登记第 7 项：ProjC 无身份综合链，提案产生=分析链单一路径，E-38）与独立测试要求；不削弱 A-3。
2. **五概念不压缩**：提案状态/对象生命周期/Revision 归属/审批决策事实/发布结果五个正交概念五载体表达。
3. 时间语义遵循 R38（§D7.1 字段表）。
4. **账本行=单一权威指纹**；禁止阶段指纹。
5. 〔v1.0.3 新增〕**裁决并入纪律**：五项 A 级裁决（归档记录 V1.0）为本版最高设计输入；凡裁决已定处，本设计只落实不重议；现状实现与裁决不一致处一律登记为实现差距（GAP-35/36），不回改裁决。

## D1. PC/ProjC 目标状态机

### D1.1 五概念分层

| 概念 | 载体 | 状态值域 | 目标裁定 |
|---|---|---|---|
| 提案状态 | `proposal.status` | draft / submitted / approved / rejected / withdrawn / expired / applied / failed | **值域全保留（Q-03 裁决：expired 保留为终态）**；合法转换集见 D1.2 转换表（五裁决定稿） |
| 正式对象生命周期 | `lifecycle_status` | identity / draft / active / deprecated / superseded | 终态保护维持 |
| Revision 归属 | 双投影（current_revision_id+version_member） | —（不设 status 列） | 维持 |
| 审批决策事实 | `approval` 行 | pending / approved / rejected | 行级不可变；**重决互改废止（Q-02b）**——决策事实一经落定不可翻转 |
| 发布结果 | `cognition_version.status` | published / archived | 单向维持 |

### D1.2 提案状态机（五裁决定稿；PC 参考实现，ProjC 同契约）

**状态语义与终态性**：

| 状态 | 业务含义 | 终态性 |
|---|---|---|
| draft | 已起草未送审（成员已锚定） | 非终态 |
| submitted | 待人工决策；pending 审批行在位 | 非终态 |
| approved | 已获真人批准；等待发布（close 批量或显式补发布） | 非终态 |
| **rejected** | 已被真人驳回 | **终态（Q-02b）**——不允许重决为 approved、不允许 resubmit；重新治理=新 Proposal（新 op_id）+保留与原 Proposal 关联+原拒绝记录保留 |
| withdrawn | 撤回（提案方或 close 批量） | **终态** |
| **expired** | 过期未决 | **终态（Q-03）**——不允许恢复；原 Proposal 保留过期时间、过期原因和审计记录（承载=GAP-36） |
| applied | 已正式发布进版本 | **终态** |
| failed | 发布 CAS 失配 | **终态**（重做=re-propose） |

**合法转换表（目标定稿——凡未列入者均为非法转换）**：

| # | 当前态 | 动作 | 执行主体 | 前置条件 | 目标态 | 事实与副作用 |
|---|---|---|---|---|---|---|
| T-01 | （无） | create | AI 服务链/人工（入口后置） | 成员规范化+目标解析+F-05 并入+等级下限+基线+闭合预检 | draft | proposal+members+审计 |
| T-02 | draft | submit | AI 服务链（提案面）/人工 | FOR UPDATE+成员完整+hash 一致+L3+基线 CAS | submitted | status+pending approval 行+审计 |
| T-03 | submitted | approve | **真人+A3** | FOR UPDATE 双行+三方哈希+L3 | approved | approval 终态行+proposal 翻转+审计 |
| T-04 | submitted | reject | **真人+A3** | 同 T-03（L3 不阻断驳回） | **rejected（终态）** | approval 终态行（拒绝记录必须保留）+翻转+审计 |
| T-06 | approved | publish | **真人+A3** | 发布十四步 | applied | version+members+审计+Outbox+账本 completed+生命周期推进 |
| T-07 | approved | 发布 CAS 失配 | 系统 | 基线迁移 | failed | 同事务内置 failed+审计+账本 failed+COMMIT+409 |
| T-08 | draft / submitted | withdraw | 创建者（非创建者须 A3） | FOR UPDATE+draft/submitted 守卫 | withdrawn | status+审计 |
| T-09 | 同态 | 重复决策/重复提交/重复发布 | 同原主体 | 同 op_id+同指纹+同 proposal+同意图 | 不变 | 幂等返回既有 receipt（Q-04） |
| **T-10** | submitted | expire | **管理/运维动作（非 AI、非自动巡检；实施澄清项=备注 R-04）** | 管理决策+过期原因 | **expired（终态）** | status=expired+**过期时间/过期原因承载（GAP-36）**+审计 |

**非法转换（目标语义明示）**：

| 禁止转换 | 裁决依据 | 现状差距 |
|---|---|---|
| rejected → submitted（resubmit） | Q-02a | 现状 submit 仅 draft——已合规 |
| rejected → approved（重决翻案） | Q-02b | **现状 decide 允许=GAP-35**（实现批收敛） |
| approved → rejected（批准后翻驳） | 统一状态规则未列此转换→非法（推论 R-03，见归档记录 §五；如意图不同须补充显式裁决） | 现状 decide 允许=**并入 GAP-35** |
| expired → submitted / approved | Q-03 | 现状无 expired 路径——合规 |
| approved → withdrawn | 统一规则未列（approved 的唯一出路=publish 或 CAS 失配 failed） | 现状 withdraw 守卫仅 draft/submitted——已合规 |

**withdraw 守卫补充证据**：非创建者 withdraw 须 A3（proposal.rs:1153-1156：created_by 匹配免门、否则 ensure_formal_authorized）——withdraw 权限=创建者或 A3 审批人。【E-41】

**同态幂等（T-09）**：重复决策（approved→再 approve）=幂等返回既有审批事实；重复提交/重复发布=按 Q-04 四条件幂等；跨态翻转一律 409（GAP-35 收敛后）。

### D1.3 审批决策事实状态机

pending→approved/rejected 单向（触发器强制）；已决行不可变；**重决互改废止（Q-02b）**——v1.0.2 的「重决=新插 pending 行」机制不再需要（无跨态重决场景），保留机制本身作为实现余量不构成违规。每条决策事实=append-only 终局记录（R36 同构）。

### D1.4~D1.6

对象生命周期/发布结果/统一抽象与差异——维持 V1.0.2；领域差异清单增第 7 项：**ProjC 无身份综合链**（提案产生=分析链单一路径；identity 链 PC 独有，E-38）。

## D2. 人工确认机制与权限矩阵

四主体矩阵维持 V1.0.1/V1.0.2 结论。〔v1.0.3 按 Q-02a/b/Q-04 更新〕决策语义定稿：

- **重复审批请求**：同态（approved→再 approve）→幂等返回既有审批事实；跨态→拒绝（GAP-35 收敛后一律 409）。
- **已审批对象再次提交或修改**：不允许——approved 出路仅 publish（applied）或 CAS 失配（failed）；重新治理=新 Proposal（Q-02a/b 重新治理原则）。
- **审批撤销/重新决策**：无撤销语义；**重新决策（跨态翻转）废止**——原拒绝/批准记录永久保留，审计全历史；变更意图=新 Proposal+新 op_id+新审批流程（重新治理原则）。
- 审计要求：每条决策事实独立落审计（同事务），历史不可改写。

### D6.6 身份模型与完整指纹（Q-01/Q-04 裁决落实）

**身份模型（V1.0.2 三裁定，经 Q-01 批准方案 A 正式生效）**：起草+提交=一项逻辑操作；op_id 结构=`{domain}-analyze:{task_id}` / `{domain}-identity:{round_id}:{slot}`；基数=1 task→≤1、1 round→≤2（profile/vision）；四层身份分明；不以 content_hash 代替逻辑身份。

**Fingerprint 完整性核验结果（Q-04 关键约束落实）**：

| 核验项 | 结果 |
|---|---|
| `proposal_content_hash` 覆盖范围（现状代码） | title/rationale/origin_kind/governance_level/expected_version_no+成员集 pins（publish.rs:705-725） |
| 缺口 | **risk_level / confidence / source_id 三要素未被覆盖**——不能充当 Q-04 要求的「完整、规范化的请求意图」指纹 |
| 完整 request_fingerprint 定义（目标） | 规范化哈希覆盖**九要素**：{title, rationale, origin_kind, source_id, governance_level, risk_level, confidence, expected_version_no, 成员集 pins} |
| 双指纹职责分离 | `proposal_content_hash`=提案**内容**锚（提交/裁决/发布三处锚点比对，语义不变）；`request_fingerprint`=账本行**幂等指纹**（九要素完整意图）——**并存、职责分离、不可互代** |
| 发布段指纹 | (proposal_id, expected_version_no)——内容已由 approval 锚定，维持 |
| 存储 | 账本行指纹列（GAP-27 实施批；启动占位、完成回填权威值） |

**Q-04 六情形行为表（裁决原文落位）**：

| 情形 | 行为 |
|---|---|
| 同 op_id+同完整 fingerprint | 幂等返回原操作 receipt |
| 同 op_id+不同 fingerprint | 拒绝 409 |
| 异 op_id+同 Proposal 内容 | 允许并存，不自动合并 |
| 同一请求重复投递 | 不重复创建产物（账本短路） |
| 同 op_id 但 source/target/slot 等意图不同 | 拒绝，不得误判为重放 |
| 内容或预期基线变化 | **使用新的逻辑操作身份**（新 op_id；不得复用旧键改指纹） |

**账本行启动/完成的两值关系（非阶段指纹）**：启动时指纹列为占位（请求指纹可先记调用方输入哈希），**完成时回填九要素权威指纹并此后不可变**；重放校验只对权威指纹比对——同一账本行不存在两个有效指纹。

### D6.7 账本事务与恢复模型

维持 V1.0.2（同事务 all-or-nothing；恢复锚=调用方 operation_id 重放；唯一键等待互斥；业务校验失败回滚 vs 发布段 CAS-failed-COMMIT 特例）。**Q-01 裁决确认**：账本与 Proposal 产物、审批、审计、Outbox 同事务；advisory 仅并发协调、不承担幂等权威职责。
