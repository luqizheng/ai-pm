## 二、逐项正式记录

### Q-01：幂等账本实现——选择 A

- **方案**：扩展现有 write_operation，作为逻辑操作幂等的权威记录。
- **理由**：无补充意见（采纳设计方案 V1.0.2 §D6.6/D6.7 方案 A 论证）。
- **设计要求（裁决原文）**：复用现有账本；扩展命令类型、产物关联和指纹能力；操作账本与 Proposal 产物、审批、审计及 Outbox 遵循同事务设计；advisory lock 可继续用于并发协调，但**不独立承担逻辑操作幂等的权威职责**。
- **影响范围**：GAP-01/02/23/27 闭合方向确定；设计方案 §D6.6/D6.7 身份模型（一项逻辑操作/单一权威指纹/基数与 slot 判别）随本裁决确立为正式模型；实施=GAP-27（Schema/API 实施批）。

### Q-02a：rejected 是否允许 resubmit——选择 A

- **方案**：不允许；rejected 为终态。
- **理由**：无补充意见。
- **裁决规则**：①rejected 为终态；②不允许原 Proposal 从 rejected 回到 submitted；③重新提出=创建新 Proposal；④新 Proposal 使用新的逻辑操作身份，并**保留与原 Proposal 的关联**。
- **影响范围**：状态机 T-02 定稿（draft-only）；审阅流「决定暂记互改」中 rejected 侧复活路径废止。

### Q-02b：rejected 是否允许直接重决 approved——选择 A

- **方案**：不允许；rejected 保持终态。
- **理由**：无补充意见。
- **裁决规则**：①不允许 rejected→approved；②不允许通过重复调用审批接口改变原拒绝结论；③重新治理=创建新 Proposal、重新提交并经人工审批；④**原拒绝记录必须保留**。
- **影响范围**：状态机 T-05（重决互改）**从目标转换集删除**；现状实现（decide 允许 approved↔rejected 互改）登记为**实现差距 GAP-35**（实现批收敛，非设计缺陷）；审阅流 v2「决定暂记」语义由裁决废止。

### Q-03：expired 处置——选择 A

- **方案**：不允许恢复；expired 保持终态。
- **理由**：无补充意见。
- **裁决规则**：①expired 为终态；②不允许 expired→submitted；③不允许 expired→approved；④继续推进=创建新 Proposal（新逻辑操作身份）；⑤**原 Proposal 保留过期时间、过期原因和审计记录**。
- **影响范围**：**expired 保留在状态值域**（V1.0.2 推荐「移除」未被采纳——以本裁决为准）；新增合法转换 `submitted → expired`（触发主体=管理/运维动作，实施澄清项）；**GAP-28 作废重立**：由「CHECK 移除 expired」改为「expired 终态转换+过期时间/原因承载」=**GAP-36**（新登记，Schema/API 实施批）；审计要求=过期动作落审计。

### Q-04：重复提交与幂等重放——选择 A

- **方案**：严格幂等重放。
- **理由**：无补充意见。
- **裁决行为表（原文）**：

| 请求情形 | 裁决行为 |
|---|---|
| 相同 operation_id + 相同完整 fingerprint | 返回原操作 receipt |
| 相同 operation_id + 不同 fingerprint | 拒绝，返回 409 |
| 不同 operation_id + 相同 Proposal 内容 | 允许并存，不自动合并 |
| 同一请求重复投递 | 不重复创建产物 |
| 相同 operation_id 但 source/target/slot 等意图不同 | 拒绝，不得误判为重放 |
| 内容或预期基线变化 | 使用新的逻辑操作身份 |

- **关键约束（原文）**：operation_id 标识逻辑操作身份；request_fingerprint 标识**完整、规范化的请求意图**；proposal_content_hash 标识 Proposal 内容，**不能未经证明就替代完整请求指纹**；必须完成 D6.6 Fingerprint 完整性核验。
- **影响范围**：D6.6 指纹定义按核验结果修订（见 §四）；GAP-07 闭合方向确定。

## 三、五项裁决形成的统一状态规则（原文归档）

**Proposal 生命周期**：
- 正常审批路径：`draft → submitted → approved`（具体发布及 Revision 双投影仍遵循既有设计契约）；
- 拒绝终态：`submitted → rejected`——不允许重新提交，不允许直接重决 approved；
- 过期终态：`submitted → expired`——不允许恢复，继续推进须创建新的 Proposal；
- 重新治理原则：rejected/expired 之后需要重新治理=**新 Proposal + 新 operation_id + 新审批流程**；原 Proposal 和历史审计保持不变。

## 四、D6.6 Fingerprint 完整性核验结果（任务要求 3）

**核验问题**：`proposal_content_hash` 能否充当 Q-04 要求的「完整、规范化的请求意图」指纹？

**核验证据（E-42）**：`canonical_proposal_hash_from_rows`（pc/publish.rs:705-725）的哈希输入=**title / rationale / origin_kind / governance_level / expected_version_no + 成员集 pins**（共 5 元数据列+成员）。

**核验结论：不完整——存在三列覆盖缺口**：

| 请求意图组成 | 是否被 proposal_content_hash 覆盖 |
|---|---|
| title / rationale / origin_kind / governance_level / expected_version_no | ✓ |
| 成员集（change_kind+identity+revision pins） | ✓ |
| **risk_level** | **✗ 未覆盖** |
| **confidence** | **✗ 未覆盖** |
| **source_id** | **✗ 未覆盖** |

**修订裁定（设计层闭合，实施=GAP-27）**：完整请求指纹（`request_fingerprint`）定义=规范化哈希覆盖 **{title, rationale, origin_kind, source_id, governance_level, risk_level, confidence, expected_version_no, 成员集 pins}** 九要素；`proposal_content_hash` 保留其现有语义（提案**内容**锚，用于提交/裁决/发布三处锚点比对），**与 request_fingerprint 并存、职责分离**——后者才是账本行的幂等指纹。二者不可互相替代（Q-04 关键约束「proposal_content_hash 不能未经证明就替代完整请求指纹」的核验落点）。
