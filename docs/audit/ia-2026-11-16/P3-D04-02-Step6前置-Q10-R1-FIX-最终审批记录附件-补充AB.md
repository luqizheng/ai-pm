## 补充 A：F2 清理错误可观测性说明

**场景**：advisory 获取语句失败（F2）时，事务清理采用 drop 路径。若连接在 advisory 执行期间已发生 IO 故障，drop 清理是否成功**不可预设**。

**如实记录（sqlx 0.8.6 行为边界）**：
1. `Transaction` 的 drop 触发回滚发送，但**不 await 完成**——清理阶段的错误（含连接已断时的发送失败）**无法被同步捕获**，亦不进入 `FailedTech`；
2. 因此 F2 的日志与计数仅描述**原始故障**（`kind:"advisory", error=<advisory 语句错误>`）——**不声称已确认回滚成功**；
3. 兜底事实（PostgreSQL 服务端保证）：会话中断时 backend 自行回滚未决事务并释放全部会话级资源（含 advisory）——即使 drop 清理失败，**锁最终释放由服务端保证**，正确性不受影响；
4. **计数口径不变**：F2 清理成败均 `failed + warn(advisory)`（清理失败不产生第二种计数）；
5. 限制声明（修复报告沿用）：F2 清理错误不可观测=接受的限制；如需可观测清理须显式 `rollback().await`——但 advisory 失败后连接状态未知，显式回滚同样可能失败且引入 F5 双故障路径——维持 drop（简单）+服务端兜底（充分）的组合，不扩大。

### B.2 T8-e 经实际 Pool 归还路径的实测设计（实施期执行，按审阅方五步）

```
1. 从被测 Pool 获取连接 C，执行 SELECT pg_backend_pid() 记录 PID；
2. 经独立管理连接执行 pg_terminate_backend(PID)；
3. 在 C 上走真实事务结束路径（commit/rollback 或 drop 归还）；
4. 再次从同一 Pool 获取连接 C'（可循环获取断言不命中已终止句柄）；
5. 断言：C' 查询成功且 PID ≠ 已终止 PID——即 Pool 归还路径确实剔除坏连接。
```

**证据归属声明**：仅 L3/本设计产出可作为「sqlx 0.8.6 连接淘汰」的证据；在其实测通过前，**任何材料不得声称"连接池一定能自动恢复"**（与 V1.2.2 §1.2 降级口径一致——正确性不依赖之，恢复性需实测背书）。
