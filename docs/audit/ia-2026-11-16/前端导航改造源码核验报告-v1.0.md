## 2. 十二问核验（§2.2）

格式：结论 → 证据（文件:行号，本轮实测）→ 改造含义/风险。

### Q1 导航是否仍由 navigation.ts 单源派生？——**是**

- `navigation.ts:84-271` `navGroups` 四组 16 项（personal 2 / workspace 2 / modules 8 / admin 4）；`navigation.ts:274` `flatNavItems`（命令面板消费）。
- `router/index.ts:89-96` `buildRoutes()` 遍历 `navGroups` 派生；`:559-563` `createRouter({ routes: buildRoutes() })`。
- 含义：拆 Global/Project/Settings 三 config 后，`buildRoutes` 必须改为遍历三个配置源；`flatNavItems` 与 `SideNav.vue:15-21` 的导入要跟随。
- **风险**：`isManagementPath`（`navigation.ts:305-314`）从 admin 组**动态派生**——admin 组解散即返回 false（全量失守），这是 R-7 同 commit 约束的实证。

### Q2 NavItem/NavGroup 是否支持嵌套？——**类型支持，数据未用**

- `NavItem.children?: NavChild[]` + `expandable`（`navigation.ts:53-56`）；`NavChild`（`:60-67`）。`navGroups` 无任何 `children` 赋值。
- `SideNav.vue` 有子菜单渲染分支（当前数据下不可达）。
- 含义：项目导航树（设置子树、开发环境三层）可直接用 `children` 扩展，无需新类型；但 `navItemRoutes` 的「父项 redirect 首子项 + 子项平铺」策略（`router/index.ts:62-77`）要决定嵌套层级是否保持平铺路由（**建议保持平铺**，激活判定 `isNavItemActive`（`:282-288`）已按平铺语义写）。

### Q3 路由如何从导航配置生成？——**派生 + 手工补充双轨**

- 派生：`navItemRoutes`（`router/index.ts:59-86`）：有 children → 父 redirect 首子 + 子平铺；无 → `component ?? PlaceholderView`（`:82`）。
- 手工补充（`:98-543`）：cognition/baseline/create/assistant/command-center（`:106-140`）、execution 子页 6（`:148-184`）、design 子页 5（`:191-222`）、tasks 子页 7（`:231-278`）、project settings 12（`:284-356`）、旧路由重定向 5（`:359-382`）、requirement 4（`:387-439`）、visualizations（`:426-431`）、notifications（`:443-447`）、settings 域（`:452-536`）、404（`:538-543`）。
- 守卫：`router.beforeEach` 仅查 token（`:618-643`）；`PUBLIC_LAYOUTS={auth,bare,design}`（`:600`）；design 仅 DEV 动态注册（`:581-592`）；**登录成功 redirect 落 `/dashboard`**（`:625`）——团队总览改名时须核对（Q-08 建议 A=只改名不改路径，则此处不动）。
- 含义：说明书 §5.1「不允许路由存在但无入口」当前已违反（cognition/baseline 零入口），Phase 1/2 修复。

### Q4 project_id 如何传递与保持？——**三通道，store 为运行时单源**

- 通道 A（壳恢复）：`WorkspaceShell.vue:44-47` `urlProjectId()`；`:57-91` `bootstrapProjectContext()` 恢复优先级 **URL > localStorage(`aipm.current-project`) > 首个项目**；`:55-63` mock 分支（`VITE_USE_MOCK=1` 时 `demo.ts` 注入项目清单）。
- 通道 B（业务范围）：`api/scope.ts:46-48` `scope.currentProjectId` **派生自** `shell.currentProjectId`（不再是独立第二源）；业务页仍可 query 优先自判。
- 通道 C（设置域）：`views/project/settings/shared.ts:26-28` query 优先 + scope 回退。
- 一致性 watch：`WorkspaceShell.vue:138-142` 路由 `?project_id=` 变化 → `shell.setCurrentProject`。
- 含义：说明书 §5.2 的「统一 shell.currentProjectId」目标与现状方向一致；改造点是**把「各页 query 优先」收敛为壳层统一恢复**，页面只读 store。

### Q5 项目切换如何影响页面状态？——**两阶段 + 守卫 + 不暴露旧数据**

- `stores/shell.ts:345-357` `switchProject`：switching 态 → resolve → 落地；`:148-158` 切换中 `currentProject=null`（Figma「07」no stale data）；`:365-372` `requestProjectSwitch` 有活跃会话先确认（`:333` `pendingProjectSwitch` + `ProjectSwitchGuardDialog.vue`）。
- 切换联动：`WorkspaceShell.vue:121-134` watch → localStorage 持久化 + `loadRepositoryContext` 重载；`SideNav.vue:49-55` watch → reviewCenter 徽标聚合重拉。
- 含义：Phase 1 新增「进入项目工作区」模式时，切换链必须复用 `requestProjectSwitch`（不得绕过守卫）；助手上下文快照（`:56-72` `AssistantContextSnapshot`）机制不受导航分层影响。

### Q6 isManagementPath 的真实用途？——**仅控制 AI 助手可见性，非权限**

- `navigation.ts:298-314`：判定 admin 组全部导航项+子路径；注释明示「租户级运营面…AI 助手不出现」。
- 消费方唯一：`use-shell-chrome.ts:25-27` → `assistantVisible`/`contextVisible`/`focusAvailable`（`:33-55`）。
- 含义：它是 **UX 门不是安全门**（说明书 §7.3 口径正确）；迁移时保持「判定=纯路径函数」，新增 `/settings/team` 前缀即可，禁止引入角色判断。

### Q7 ASSISTANT_HIDDEN_PREFIXES 实际判定规则？——**管理组派生 + 硬前缀数组**

- `navigation.ts:321` `ASSISTANT_HIDDEN_PREFIXES = ["/project/settings"]`；`:326-331` `isAssistantHiddenPath = isManagementPath || 前缀命中`（exact 或 `path/` 开头）。
- 含义：团队设置迁入 `/settings/team/*` 后，四个现 admin 项中迁出的 3 项（members→`/settings/team/members`、ai-providers→已在 `/settings/team/ai-providers` 但将脱离 admin 组、announcements 待定）会脱离判定——**须把 `/settings/team` 追加进前缀数组**（若产品确认团队设置页全部无 AI），或按页面粒度细化。

### Q8 AGENTS 规则 5 具体要求？——见 §1，四处由 useShellChrome 自动派生，人工动作 = 前缀 + 测试用例 + 两命令。

### Q9 use-shell-chrome 如何控制四列？——**单源派生 5 个 computed → v-if + data-属性**

- `use-shell-chrome.ts:20-64`：`isAssistantHiddenRoute` / `isAssistantRoute`（`=ASSISTANT_PATH "/project/assistant"`，`:7`）/ `assistantVisible`（总开关×专注×会话页×隐藏页）/ `contextVisible`（不含会话页特例）/ `focusAvailable`。
- 消费：`WorkspaceShell.vue:219-247` 壳根 `data-sidebar/data-context/data-ai-panel/data-focus` + `AssistantColumn v-if` + `ContextPanel v-if`；TopBar 助手按钮同源。
- 含义：Phase 1 新增列（ProjectNavigation）时必须**新增 grid 模板分支 + 对应 data-属性**，并保持「v-if 移除列 ⇒ data-* 同步收列」纪律（否则重现管理页空带缺陷）。

### Q10 Context Panel 是否依赖路由？——**依赖**

- `ContextPanel.vue:188-206` `availableObject` 从 `route.path` 推导当前页业务对象（detail id 正则 + design/requirements/tasks 分支）；`:126-132` TABS 五枚（context/sources/results/actions/**graph**）；`:216-229` History 为 **Drawer 分类**（非页签）。
- 含义：①V1.1 右栏清单把 History Drawer 写进页签槽位、丢了 Graph——`/project/visualizations` 唯一直达入口即 Graph 页签（`router/index.ts:424-431` 注释「入口=右栏 Graph 页签与对话卡」），R-5 未裁决前不得删；②路由分层后 `availableObject` 的路径分支要适配新路由结构。

### Q11 Baseline 是否有可复用状态 API？——**有**

- `api/baseline.ts`：`loadBaselineOverview` / `confirmBaseline` / `createBaselineProposal` / `decideBaselineItem`（`BaselinePage.vue:12-19` 导入实证）；`BaselineOverview{proposal, items[]}`，页面已做 `proposedCount`/`canConfirm` 派生（`BaselinePage.vue:45-50`）。
- 含义：NAV-0201 BaselineStatusCard 可直接复用 `loadBaselineOverview`（状态/待确认数/阻塞数均可从 items 派生），**无需新后端端点**；注意未决条目阻塞确认的语义（canConfirm = 有 proposal 且 proposed=0）。

### Q12 /project/devenv 是否有设备以外能力？——**没有，纯设备页**

- `BootstrapView.vue:14-24` 仅导入 `api/devices`（bind/get/list/register/revoke/unbind 六端点，pm_devices.rs）；readiness=服务端计算快照只读展示；MCP 连接状态无后端源、页面不渲染假状态（`:26-35` 注释，G-09 挂账）。
- 含义：NAV-0301~0303 迁移时整页可平移为「Devices」子页；Executors 无任何现成 UI（后端 executor 概念存在于导入/执行通道），PLANNED 兜底正确；Runners 页（`/project/settings/runners` + `:deviceId` 详情）独立存在，不与 Devices 混合。
