## 0. 设计立场与总原则

1. **现状即目标态的验证起点**：依赖核查已证实 PC/ProjC 服务层状态机与事务机制同构且成熟。本设计定稿现有机制为目标设计；凡现状已满足冻结契约之处标注「已满足」。
2. 〔v1.0.1 修订 §10〕**参考实现关系**：PC 是状态机与事务语义的**参考实现**（机制语义的验证载体）；ProjC 必须满足**共同契约**（同一状态机语义、事务边界、幂等模型、审计纪律），同时保留**明确登记的领域差异**（§D1.6 六项）与**独立测试要求**（`projc_formal_chain.rs` 6 用例独立存在，不得以「PC 已测」替代 ProjC 验证）。本表述不削弱 A-3 的不对称裁决（PC L3 数据源 Legacy / ProjC 冲突源在役）。
3. **五概念不压缩**（D1 红线）：提案状态、正式对象生命周期、Revision 归属、审批决策事实、发布结果五个正交概念，分别由五个载体表达，不引入统一 status 字段。
4. 时间语义遵循 R38（§D7.1 字段表逐项定义）。
5. 证据标注 E-xx；证据不足显式标记。凡「待裁决」处不得作为既定目标。

## D1. PC/ProjC 目标状态机

### D1.1 五概念分层

| 概念 | 载体 | 状态值域 | 目标裁定 |
|---|---|---|---|
| 提案状态 | `proposal.status` | draft / submitted / approved / rejected / withdrawn / expired / applied / failed | 语义采用现值域为状态机基础；**`expired` 处置待裁决 Q-03**（§D1.2-R1-c）；T-05 重决语义**待裁决 Q-02b**（§D1.2） |
| 正式对象生命周期 | `cognition_object.lifecycle_status` / `relationship.lifecycle_status` | identity / draft / active / deprecated / superseded | 采用现值域；deprecated=终态，superseded=终态须带 successor（触发器强制） |
| Revision 归属 | `current_revision_id` + `version_member` 双投影 | —（不设 status 列） | 裁定：不引入 revision status 字段；修改正文恒产生新 Revision（G-06） |

### D4.9 close_report 跨事务协调（专节）〔v1.0.1 扩展：锁与并发分析〕

**结构**（维持）：外层事务 A（report FOR UPDATE→approved 提案清单→子事务 B_i 逐提案发布→未决 withdraw FOR UPDATE+审计→COMMIT）；B_i=完整十四步独立事务（确定性 operation_id，见 §D6.5-修订）；失败计数不阻断。**不是一个原子事务**。

**当前实现事实 / 目标建议 / 待裁决三分（配合 §11）**：

| 事实（现状，E-18） | 目标建议（本设计，待裁决） | 待裁决项 |
|---|---|---|
| ① close 无域级 A3 门；publish 段逐提案过 ensure_formal_authorized（真人+A3） | 建议=维持（withdraw 未决提案属流程动作，正式认知变更已由 publish 段守住） | **Q-05**：close 主体是否须 A3 |
| ② 未决提案 withdraw 于外层事务逐条审计 | 维持 | 随 Q-05 |
| ③ 子发布失败计数不阻断（CAS 失配→提案内置 failed） | 维持（批量收口语义） | 无（已确认设计裁定，登记 GAP-12 建议列） |
| ④ approved 清单选取**无 FOR UPDATE**；与并发 decide 存在窗口竞态（见下） | 建议清单加 FOR UPDATE 或 close 后残留在途提案走显式补发布兜底 | **Q-10（新增，不阻塞）** |
| ⑤ 发布失败补救=提案 failed 终态→re-propose；非 CAS 失败→同 operation_id 重放 | 维持 | 无 |

**锁与并发分析（任务书 §9 指定）**：

| 事务 | 锁获取顺序 |
|---|---|
| A（close 外层） | report 行锁 → （子事务 B 并行期间 A 挂起等待）→ proposal×N（withdraw FOR UPDATE） |
| B（publish 子事务） | advisory(`pc_publish:{project}`) → proposal FOR UPDATE → approval FOR UPDATE → 插入/更新族 |
| C（decide/approve/reject） | proposal FOR UPDATE → approval FOR UPDATE；**report 仅无锁普通读**（record_decision 前置检查，proposal.rs:920-930） |

- **反向锁顺序**：不存在——全仓库无「先锁 proposal 再锁 report」路径（C 对 report 无锁；E-16/E-18 取证）。
- **死锁风险**：无环。可能等待链 A→B→C（A 持 report 等 B；B 等 C 持有的 proposal 锁；C 不等任何 A 持有资源）→链尾 C 必然完成→链解。B 之间由 advisory 串行。
- **锁等待**：A 持 report 行锁贯穿整个批量（含全部 B_i）→并发第二个 close 在 report 行上排队（串行化，符合设计）；并发 decide 在 proposal 行上与 B_i 竞争（短暂）。
- **竞态窗口（新发现，GAP-32+Q-10）**：close 在 A 内先**无锁读** approved 清单（analysis_report.rs:586-591），后 withdraw FOR UPDATE（:613-619）。若 decide 在两步之间把某提案 submitted→approved：该提案不在 approved 清单（漏发布）也不在 draft/submitted 集（不撤回）→报告已关闭、提案滞留 approved。补救路径存在：**显式补发布**（publish 不检查报告状态，approved 即可发布；见 §D6.5 operation_id 统一）→ 窗口窄+有兜底 → Q-10 不阻塞，处置方式（FOR UPDATE 清单/显式补发布文档化/告警）待裁决。

## D5. 并发控制设计

### D6.5 审批与发布

审批同态幂等/异态竞争维持。〔v1.0.1 修订（配合 §6）〕**发布 operation_id 统一规范**：

- **目标规则（确定性派生）**：`operation_id = {pc|projc}-decision:{proposal_id}`——**由提案身份确定性派生，禁止调用方任意给定**。close 批量与显式补发布使用**同一规则**→同一提案的同一次发布意图（含失败后重放）恒为同一账本键。
- **理由**：一个提案至多一次 applied（终态）→确定性键使「close 发布」与「显式补发布」天然共享幂等防重：同提案第二个不同键的发布请求在入口即拒绝（INVALID_CONTRACT 类校验），防止两账本键并发推进同一提案发布（advisory 只串行不防重）。
- **现状差距**：`PublishVersionInput.operation_id` 为调用方传入（close 固定 `pc-decision:{id}` 格式、显式补发布任意）→**GAP-31**（入口校验缺失）；目标校验归 Schema/API 实施批。
- **已发布但调用方未收到响应**：重放同键→幂等返回既有 version（replayed=true）——跨入口路径均成立（键统一后）。

### D6.6 统一幂等模型

两级锚架构维持（L1 事实级已满足/L2 意图级方案 A）。〔v1.0.1 修订（配合 §2）〕**operation_id × request_fingerprint 语义**：

| 组合 | 结果 |
|---|---|
| 同 operation_id + 同 fingerprint | **幂等重放**：返回既有产物（账本短路/同态返回） |
| 同 operation_id + **不同** fingerprint | **拒绝（409 mismatch）**：同一逻辑操作 id 不得携带不同内容——防 operation_id 被复用到不同请求 |
| 不同 operation_id + 相同 content_hash | **不视为同一逻辑操作**：允许并存（各自独立审批；折叠提示为可选产品优化，不编号） |

- **fingerprint 定义**：请求逻辑内容的规范化哈希——propose 段=canonical_proposal_hash 同构输入（title/rationale/origin/governance/expected_version_no/成员集）；submit 段=(proposal_id, proposal_content_hash, expected_version_no)；publish 段=(proposal_id, expected_version_no)（内容已由 approval 锚定）。存储=账本行 `expected_content_hash` 列复用（现发布段已存，扩展后起草/提交段存 fingerprint）。
- **四层身份分明**：

| 身份 | 锚 | 载体 | op_id 复用规则 |
|---|---|---|---|
| 逻辑提案身份（产生意图） | operation_id=`{domain}-analyze:{task_id}` / `{domain}-identity:{round_id}` | 账本 L2 行 | 一次逻辑提案一个 op_id；重试必复用 |
| 物化操作身份（草稿对象/修订） | object_key + content_hash（+evidence identity） | 业务表唯一约束（L1） | 不使用 op_id——内容级天然幂等 |
| 提交操作身份 | proposal_id + pending approval 行 | proposal/approval | 复用逻辑提案 op_id（起草提交一体链）或 submit 子键 `{op_id}:submit`（实施定，Q-06） |
| 发布操作身份 | `{domain}-decision:{proposal_id}` | 账本（现有） | **独立于起草 op_id**——发布是独立业务动作，不复用上层 op_id |

- operation_id 生命周期：调用发起方生成→账本 INSERT→pending→completed（回填 artifact_id）/failed（last_error）/abandoned（人工，Q-08）→清理策略 Q-07。

### D6.7 〔v1.0.1 新增（任务书 §三.1）〕账本事务与恢复模型

**裁定：pending 账本行与业务物化处于同一事务**（与发布段十四步同构；不得引用十四步作为「起草段已闭合」的证据——十四步只证明该模式在发布段可行，起草段模型在此显式定义）：

| 维度 | 语义 |
|---|---|
| 事务边界 | `BEGIN → 账本 INSERT（ON CONFLICT DO NOTHING）→ fingerprint 校验 → 业务物化（draft/proposal/submit）→ 账本终态化 → COMMIT`——账本行与业务行**同生共死** |
| 事务回滚 | 账本行随业务回滚=**无孤儿 pending**；operation_id 未消费→同 op_id 重放安全重执行（L1 内容去重保证不产生重复草稿） |
| 进程崩溃 | 未 commit=等同回滚（同上）；已 commit=账本 completed+产物完整→重放幂等返回。**恢复锚=调用方持有的 operation_id 本身**（账本缺席=未完成，账本在场=已完成/可查） |
| 失败分类 | ①业务校验失败（成员非法/hash 失配/L3 冻结/基线迁移）→**回滚**+409/403（账本无痕，修复后可重试）——发布段 CAS 失配的「事务内置 failed COMMIT」**不推广**到起草段（起草段失败状态无领域可见性需求，回滚更简单且无死锁约束）；②基础设施失败（连接/超时）→回滚，重放恢复 |
| 并发推进防护 | 唯一键等待互斥（D5 补充 1）+ completed 短路 + fingerprint 校验——三重保证同一 operation 至多推进一次 |
| 账本-产物一致性 | 同事务=不可能半边（账本 completed 必有产物；产物在必有账本）；对账巡检=Q-09 后置 |
| 与发布段的关系 | 同一模型（账本+advisory+CAS+唯一约束），各自独立事务；**发布段的 CAS-failed-COMMIT 特例**源于其「提案行锁已在手」的补偿约束，起草段无此约束故不复制 |

**端到端时序（修订版，方案 A+确定性发布键）**：

```
正常：分析任务 → L1 物化（source/evidence/draft）→ 账本 pc-analyze:{task_id}(pending)
  → create+submit → 审计+outbox(pc.change_proposed) → 账本 completed → COMMIT
  → 真人A3 审批（approval 终态行）→ 真人A3 close → publish(pc-decision:{id})
  → advisory→账本(pending)→CAS→十四步→账本 completed→COMMIT
重复请求：同 op_id+同指纹 → 账本命中 → 幂等返回既有产物（无第二提案/版本/事件）
部分失败：业务校验失败 → 全回滚（账本无痕）→ 修复后同 op_id 重试
          发布 CAS 失配 → 提案/账本内置 failed + 审计 → COMMIT → 409 → re-propose
超时重投递：调用方超时/服务端已成功 → 重放同 op_id → 幂等返回
          outbox 重复投递 → 消费侧终态短路+写侧键去重；5 次失败 → dead_letter
```

## D7. 审计、事件与 Outbox

### D7.1 〔v1.0.1 新增（任务书 §三.7）〕R38 时间语义逐字段表

| 字段/时点 | 语义 | R38 归类 | 现状与备注 |
|---|---|---|---|
| `approval.decided_at` | 人工审批决策发生的时刻 | **决策时间**（审批决策事实 R36 五元组组成部分，append-only 行各自携带） | 重决=新行各自携带 decided_at；与状态翻转（proposal.status）概念分离 |
| `cognition_version.confirmed_at` | 发布**确认决策**发生的时刻（真人 A3 执行发布确认动作） | **决策时间**（该版本确认决策事实的组成部分，与 confirmed_by 配对） | 现状与发布生效时间**同事务压缩承载**——概念上是两个语义（R38 先例同 KB published_at），不得据此声称二者均可独立追溯 |
| 实际发布生效时间 | 发布事务 COMMIT、状态翻转与正式化生效的时刻 | **发布生效时间**（决策的**结果应用时点**，即状态翻转与正式化生效） | 概念分离已按 R38 冻结；字段级分离（独立物理列）归 Schema/API 实施批=**GAP-33** |
| 流程元数据时间 | `proposal.submitted_at/created_at/updated_at`、审计行时间戳、报告 close 时间、账本 created_at/updated_at、报告分析时段等 | **流程元数据**——不属决策事实组成部分，不得与决策时间或发布生效时间混为同一语义 | 与冻结效力边界二同口径：未来域内流程时间语义归该域自行裁决 |

**红线重申**：不得将决策时间（decided_at/confirmed_at）与发布生效时间混为一谈——决策事实的追溯能力依赖前者，结果应用的可观察性依赖后者；现状共用物理值不改变概念边界（与 §D1.2/D6.5 引用的 R26~R38 口径一致）。

〔v1.0.1 修订（配合 §12）〕**提案产生事件（`pc.change_proposed`）的准确事务语义**：

- **写入时机与边界**：起草链（propose_from_analysis）**同事务尾部**（proposal+submit+账本[方案A后]与事件同一事务）——事件与领域事实同生共死：事务回滚→事件不存在；不存在「无领域事实的事件」，也不存在「事件先行」。
- **失败回滚**：随事务全回滚；重试时由幂等键（analysis_outcome_key）写侧去重。
- **重放语义**：同键再写→ON CONFLICT DO NOTHING→返回既有事件 id。
- **消费者链路状态（已确认，修正 v1.0 的「未逐一核对」）**：`pc.change_proposed` / `projc.change_proposed` / `projc.cognition.version_published` 在运行时目录 **has_handler=true, enabled_by_default=true**（outbox.rs:319-325/:351-361；消费面=Platform 留痕 ProjChangeProposedHandler / ProjcVersionPublishedHandler）——**链路已登记闭合**。「目录定义≠消费者链路闭合」原则保留：本例为已闭合实例，未来新事件仍须遵循「未启用禁止生产」。
- 事件重复/乱序/延迟/失败处理维持 v1.0（at-least-once+消费幂等+退避→dead_letter）。

其余维持 v1.0（九类事实权威/审计/事件对照表；四身份列静态守卫；payload 引用纪律）。
