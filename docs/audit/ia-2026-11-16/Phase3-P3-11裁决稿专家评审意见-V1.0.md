## 二、四项必须修订

### 2.1 R-07（P0）：DomainRef 不得复用 owner_domain 语义

0007 已冻结 `relationship_type.owner_domain` = **该关系类型实例的确认权威域**；裁决稿 R-07 的 `(owner_domain, …)` 会混淆「关系的权威归属」与「被引用对象的归属」（ProjC 维护的跨域关系可引用 PC 对象，目标对象身份是 PC）。

修订：DomainRef 明确区分——

| 字段 | 回答的问题 |
|---|---|
| target_domain | 被引用对象属于哪个领域 |
| target_object_type | 被引用对象是什么类型 |
| target_object_id/key | 被引用对象是谁 |
| revision_context | 引用哪个版本/版本上下文 |

`RelationshipType.owner_domain` 继续独立表示关系确认权威。**必须禁止把关系所有权和目标对象所有权合并为一个 Domain 字段**。此为领域契约表达，不要求立即建数据库字段。

### 2.2 R-04：停止条件从「代码合入」升级为「能力就绪+验收通过」

代码合入 master ≠ 发布链可承担生产职责。停止条件至少满足七条就绪项：

1. projc.* schema 与对象字典就绪；
2. ProjC 独立 Revision/Version 发布链就绪；
3. 人工确认权限与正式发布硬门就绪；
4. DomainRef 解析及引用权限检查就绪；
5. 审阅流 v2 可将提案路由到正确领域；
6. 相关测试、注册表、迁移记录完成；
7. 旧路径有明确停用开关和验证结果。

同时消除 R-04/R-09 表述不一致，明确过渡动作为：审阅 v2 决定暂记继续；close_report 可完成关闭；snapshot 提案保留审核结果与历史；**但 ProjC 发布链就绪前不允许发布为 PC 正式认知版本；不能为维持端点行为而继续产生错误领域的正式版本**。

### 2.3 R-03：区分 Product Module 与 Repository Module

| 类型 | 领域 | 含义 |
|---|---|---|
| Product Module | PC | 产品功能、业务能力的组织单元 |
| Repository Module | ProjC | 仓库代码结构中的技术模块 |
| Technical Component | ProjC | 技术架构中的组件 |
| Business Capability | PC | 产品或业务能力 |

相似自然语言名称 ≠ 相同对象身份；字典定义各自独立。Repository Module 实现了某 Product Module 时：两域各自维护认知，经显式关系引用；**ProjC 不能因代码扫描发现某功能就自动创建 PC 的 Product Module**。另：D-4 身份综合留 PC 认可，但**只有经业务语义判断确属产品身份的候选才进入 PC**，不能把所有仓库身份扫描结果归入 PC。

### 2.4 R-06：跨域冲突归属原则

所有权原则：**冲突对象的所有权由主要冲突认知所属领域决定；涉及其他领域时通过 DomainRef 引用对方对象，双方各自履行确认责任**。

例：产品业务规则要求某处理方式但技术架构无法满足——PC 不擅自改技术架构；ProjC 不擅自改产品业务规则；ProjC 可提技术侧替代方案；PC 可重新评估业务规则；双方确认后各自更新本域正式认知。**暂不新增 Global Conflict 领域或统一冲突中心**；跨域协调经引用与待处理事项完成。

## 三、其他确认意见

- **R-01 附注**：projc.source 若保留，只能是 ProjC 自己的证据来源登记/领域引用记录，**不得成为与 kb.source 同权威含义的第二正式来源资产**；对正式来源的引用走 DomainRef（不形成两个 Source 权威）。
- **R-02**：五条原文保留建议冻结；「不允许两个领域同时成为同一知识正文的权威」是四域架构重要红线。
- **R-05**：从 PC/ProjC 正式认知字典移除；Analysis 保留与否由 Analysis 产品设计定；不为兼容历史 snapshot 继续作为正式认知类型。
- **R-08 附注**：统一检索每条返回结果必须可识别**原始领域、原始对象身份、版本上下文、访问权限判断结果**，不能只返回合并文本片段。
- **R-09**：按领域分流发布方向确认；审阅 v2 UX 与决定语义不变。
- **R-10**：保留原始记录；数据确为零则重跑分析，不为不存在的存量建复杂迁移机制。

## 四、新增两条架构红线（进四域通用治理规范，不限于 PC/ProjC）

**红线一：共享技术基础设施不得产生共享业务权威。**
可共享：DDL 模式、CAS 与幂等机制、发布事务模式、通用基础设施代码、DomainRef 契约、检索基础设施。
不可共享：正式对象身份、未定义的状态机、正式确认权、正文权威、领域业务字典。

**红线二：跨域引用不构成跨域授权。**
引用他域对象不意味着：可直接修改目标对象；可替目标领域确认；可绕过目标领域审核；可自动继承目标对象的全部访问权限。

## 六、最终意见

支持整体方向，以 V1.1 修订稿进入正式逐项裁决。三个最重要决定：① ProjC 独立 projc.*，不经 pc.* owner_domain 双领域混载；② 仓库分析结果按业务含义分流，Finding 仅候选；③ 跨域引用与统一检索可共享基础设施，但绝不改变领域权威与人工确认责任。V1.1 修订并正式冻结后，P3-11 解除 P0 阻塞，进入 P3-D03/D04。
