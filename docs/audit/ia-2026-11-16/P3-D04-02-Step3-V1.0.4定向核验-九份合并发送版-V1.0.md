# 第二部分：D6.6 Request Fingerprint 与 Operation Identity 完整性核验 V1.0

（原文=《P3-D04-02-Step3-D66指纹与操作身份完整性核验-V1.0.md》）

## 1. 三概念分离（不得混用）

| 概念 | 定义 | 载体 | 唯一性 |
|---|---|---|---|
| operation_id | **逻辑操作身份**：一次逻辑操作（propose/publish）的全局名字 | write_operation 账本行 | UNIQUE(tenant_id, project_id, operation_id) |
| request_fingerprint | **完整、规范化的请求意图指纹**（九要素，§4） | 账本行指纹列（GAP-27 实施） | 行内唯一权威值（完成时锚定后不可变） |
| proposal_content_hash | **Proposal 内容锚**：内容五元组+成员集哈希 | proposal.proposal_content_hash | 提交/裁决/发布三处锚点比对用 |

DESIGN REQUIREMENT：三者职责分离——operation_id 回答「哪次操作」，request_fingerprint 回答「这次操作要什么」，proposal_content_hash 回答「提案内容是什么」。proposal_content_hash 不经证明不得替代 request_fingerprint（Q-04 关键约束）。

## 3. operation_id 组成规则（DESIGN REQUIREMENT）

```
propose（起草+提交一体）：
  分析链：{pc|projc}-analyze:{task_id}
  身份链：{pc}-identity:{round_id}:{slot}   slot ∈ {profile, vision}
发布：
  {pc|projc}-decision:{proposal_id}          （确定性派生，禁调用方任意——GAP-31 校验）
```
- 生成方与所有权：analyze 键空间=分析链消费者（kb_pc_handlers）；identity 键空间=身份综合服务（须透传 round_id——GAP-02 前置）；decision 键=close/显式补发布确定性派生。
- 作用域：租户+项目（账本唯一约束三元组）+键空间前缀（域+链）+业务锚+槽位。

## 4. 账本唯一性与作用域规则

- SCHEMA FACT：`write_operation_tenant_id_project_id_operation_id_key UNIQUE (tenant_id, project_id, operation_id)`（0001:5746；0026 projc 侧补齐）。
- DESIGN REQUIREMENT：跨 tenant/project 的同名字符串 op_id=不同账本行（约束三元组天然隔离）；键冲突语义=同租户同项目内才可能发生→冲突即同逻辑操作→进入指纹校验流程。
- 并发规则：唯一索引插入等待互斥→先者 commit(completed)→后者幂等返回；先者 rollback→后者继续（D5.1 补充 1）。
