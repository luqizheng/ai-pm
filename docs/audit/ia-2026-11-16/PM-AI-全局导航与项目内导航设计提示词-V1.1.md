# PM-AI 全局导航与项目内导航设计提示词 V1.1

> 日期：2026-11-16
> 依据：《PM-AI 全局导航 IA 基线 V1.1》，遵循已正式确认的 P-01～P-10 裁决
> 性质：Figma AI 设计提示词（导航框架层）

## 一、设计任务

请为 PM-AI（AI R&D / Project Management Platform）设计一套专业、克制、高信息密度的桌面端导航系统。

本次设计依据《PM-AI 全局导航 IA 基线 V1.1》，必须遵循已经正式确认的 P-01～P-10 裁决。

本任务重点不是重新设计所有业务页面，而是建立统一的应用导航框架，包括：

1. 全局导航。
2. Team 上下文切换。
3. Project 上下文切换。
4. 项目总控台入口。
5. 项目内二级导航。
6. 四域独立导航入口。
7. 项目设置导航。
8. 顶栏和右侧 Context Panel 的协调关系。

## 二、产品定位与视觉要求

PM-AI 是 AI 辅助研发与项目管理平台。

产品采用以下工作模式：

- 人类负责项目决策和管理。
- AI Agent 协助需求分析、任务分析、风险识别、架构一致性检查和工程执行。
- AI 可以提出建议、生成分析结果和执行任务。
- 正式确认、关键审批和受保护操作由人类完成。

视觉方向：

- 专业的 B2B SaaS 产品。
- 现代、简洁、克制。
- 高信息密度，但避免拥挤。
- 强调信息层级、当前上下文和操作状态。
- 使用清晰的图标、文字标签、选中态和状态提示。
- 不使用游戏化视觉。
- 不使用过度装饰性渐变。
- 避免大面积彩色卡片。
- 以桌面端 1440px 作为主要设计基准。

## 三、必须采用的导航架构

### 1. 全局导航层

全局导航只承担 Personal、Team、Current Project 三个范围的入口和上下文切换。

Personal：

- 个人主页
- 通知中心

Team：

- 团队总览
- 项目列表
- 团队设置
  - 团队常规
  - 成员与邀请
  - AI Provider
  - 团队公告（适用时）

Current Project：

- 当前项目
- 项目总控台
- 进入项目工作区

注意：

- 不要把所有项目模块平铺在全局导航。
- 不要建立 Platform Administration 固定分区。
- 不要增加 Workspace Switcher。
- Team Switcher 和 Project Switcher 必须明确区分。
- 个人设置放在账户菜单中。
- 新建项目作为明显但不过度突出的快捷操作。

### 2. 项目内导航层

进入项目工作区后，显示独立的项目内二级导航。

项目导航树：

- 项目总控台
- 需求
- 技术设计
- 任务管理
- AI 执行中心
- 代码发现
- 分析
- 知识库
- 产品认知
- 项目认知
- 人工审核中心
- 项目设置
  - 基础设置
  - 成员（规划项）
  - 仓库
  - 开发环境
    - Devices
    - Executors
    - Runners
  - AI 配置与执行策略

项目导航要求：

- 顶部清晰显示当前项目名称。
- 显示项目状态或必要的上下文标识。
- 当前选中模块必须明显。
- 支持分组和折叠。
- 不要将所有项目设置子页面都放在第一层。
- 不要将开发环境、仓库等一次性配置能力提升为全局一级导航。
- 项目切换后，项目导航结构保持一致。

## 四、四域独立导航设计

必须将以下四个领域设计为独立入口：

### Analysis（分析）

负责分析执行和分析结果。

页面入口：分析。

需要体现：

- 分析运行记录。
- 分析报告。
- Report Revision。
- Findings。
- Conclusions。
- Recommendations。
- 报告审阅与关闭。

Analysis 拥有报告审阅页面和报告审阅操作。

### KB（知识库）

页面入口：知识库。

负责：

- Source。
- Document。
- Document Revision。
- Memory。
- Memory Proposal。
- Knowledge Review。

不得将 KB 页面设计成其他认知领域的总入口。

### Product Cognition（产品认知）

页面入口：产品认知。

负责正式产品认知，例如：

- 产品定位。
- 产品目标。
- 业务领域。
- 产品能力。
- 模块。
- 角色。
- 场景。
- 流程。
- 业务对象。
- 业务规则。
- 认知对象及其关系。

### Project Cognition（项目认知）

页面入口：项目认知。

负责项目技术认知及其生命周期，例如：

- 项目技术认知。
- 架构约定。
- 技术决策。
- 认知冲突。
- 证据。
- 确认与冻结状态。

四域在视觉上可以采用一致的页面框架，但不能设计成同一个页面里的四个普通 Tab。

必须让用户明确知道自己正在操作哪个领域。

## 五、关键页面设计

### 页面 A：Personal / Team 全局入口

展示：

- 个人主页入口。
- 通知中心入口。
- 当前 Team。
- Team Switcher。
- 团队总览。
- 项目列表。
- 团队设置。
- 新建项目按钮。

重点表现 Team 与 Project 的层级关系。

### 页面 B：项目总控台

设计项目进入后的默认总控页面。

首屏优先展示：

1. 待人工处理。
2. 当前执行。
3. 风险。
4. 项目基线状态。
5. 初始化进度。
6. 最近活动。

不要使用四个 KPI 数字卡片作为主视觉。

项目基线状态必须常驻可见，展示：

- 当前基线状态。
- 待确认事项数量。
- 已完成的基线内容。
- 阻塞事项。
- 进入基线确认的操作入口。

基线正式确认必须体现人工确认要求，不能设计为 AI 自动确认。

### 页面 C：项目工作区

展示全局导航与项目内导航之间的关系。

要求：

- 全局导航保持轻量。
- 项目内导航承担全部项目模块入口。
- 当前项目名称始终可见。
- 页面标题、面包屑和项目上下文一致。
- 右侧 Context Panel 与项目内导航保持独立。

### 页面 D：Analysis 报告审阅

设计独立的 Analysis 页面。

展示：

- 报告列表。
- 报告状态。
- 报告详情。
- Revision 历史。
- Findings。
- 人工审阅操作。
- 报告关闭操作。

报告审阅操作只能在 Analysis 页面执行。

### 页面 E：人工审核中心

这是跨领域待处理事项聚合入口。

展示不同领域提交的待处理事项：

- Analysis 报告待审阅。
- KB 知识确认。
- Product Cognition 提案审批。
- Project Cognition 冲突或确认事项。
- 其他需要人工处理的事项。

每条记录必须显示：

- 来源领域。
- 对象名称。
- 待处理类型。
- 优先级。
- 当前状态。
- 简要说明。
- 进入原领域处理的操作。

重要：人工审核中心只聚合和跳转，不重复实现各领域的审批操作。

### 页面 F：项目设置

采用独立的项目设置子导航。

分区：

- 基础设置
- 成员（规划项）
- 仓库
- 开发环境
- AI 配置与执行策略

开发环境内部明确区分：

- Devices：设备注册、设备身份、设备连接与健康状态。
- Executors：执行器配置和执行能力。
- Runners：Runner 管理和运行环境。

不要把 Devices、Executors、Runners 合并成一个没有语义区分的设置页面。

## 六、顶栏设计

顶栏应包含：

- PM-AI Logo。
- Team Switcher。
- Project Switcher。
- 全局搜索 / 命令面板。
- 通知入口。
- AI 助手入口。
- 新建项目快捷入口（适当位置）。
- 账户菜单。

不要加入 Workspace Switcher。

## 七、右侧 Context Panel

右侧上下文面板保留以下结构：

- Context
- Sources
- Results
- Actions
- History Drawer

Context Panel 负责展示当前 AI 工作上下文、来源、结果和可执行动作。

它不是项目模块导航，也不是领域正式页面。

## 八、交互状态

请至少设计以下状态：

1. 未选择项目。
2. 已选择项目，但尚未进入项目工作区。
3. 已进入项目工作区。
4. 项目导航展开。
5. 项目导航折叠。
6. 项目模块选中。
7. 项目设置展开。
8. 开发环境展开。
9. 当前存在待人工处理事项。
10. 项目基线待确认。
11. 项目基线已确认。
12. 当前项目存在风险。
13. AI 助手打开与关闭。
14. Context Panel 展开与收起。

## 九、设计输出要求

请输出：

1. 全局导航组件。
2. Personal / Team 导航页面。
3. 项目总控台页面。
4. 项目内二级导航组件。
5. 四域独立入口的导航表现。
6. Analysis 报告审阅页面。
7. 人工审核中心页面。
8. 项目设置导航页面。
9. 开发环境 Devices / Executors / Runners 子导航。
10. 顶栏与右侧 Context Panel 的组合状态。

请建立可复用的导航组件和统一设计规范。

组件至少包括：

- GlobalNavigation
- TeamSwitcher
- ProjectSwitcher
- ProjectNavigation
- ProjectNavigationGroup
- NavigationItem
- NavigationBadge
- ContextPanel
- BaselineStatusCard
- ReviewQueueItem

## 十、不可违反的架构约束

1. KB、Analysis、Product Cognition、Project Cognition 必须保持四域独立。
2. Analysis 拥有 Report 和 Report Revision。
3. Analysis 报告正文以 Git 为权威，DB 保存 Revision 身份、状态和 Git 引用。
4. KB、PC、Project Cognition 不得被设计成同一种知识对象。
5. 人工审核中心只聚合，不接管领域审批语义。
6. 项目基线确认必须保留人工确认门。
7. Team 成员与 Project 成员必须区分。
8. Devices、Executors、Runners 必须分开。
9. 全局导航与项目内导航必须分层。
10. 不引入未经定义的 Workspace 业务实体。
11. 不设计 Platform Administration 固定导航分区。
12. 设计稿不能暗示尚未实现的功能已经上线。

最终设计应让用户始终清楚三个问题：

- 我当前在哪个 Team？
- 我当前正在管理哪个 Project？
- 我当前操作的是哪个业务领域？

导航系统应服务于领域边界、项目上下文和人工决策流程，而不仅仅是页面跳转。

## 附：交付与实施注意事项

建议将 Figma 设计拆成两个交付层次：

- 第一批：全局导航、Team/Project 切换、项目总控台、项目内二级导航、项目设置。
- 第二批：四域独立入口、Analysis 审阅页面、人工审核中心的聚合跳转交互。

这样可以先冻结导航框架，再逐步补齐四域页面，不必等待所有业务页面完成后才验证整体导航。
