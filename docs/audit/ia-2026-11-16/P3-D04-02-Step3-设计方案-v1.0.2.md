### D5.1 〔v1.0.2 新增（任务书 P1-1）〕close/publish/decide 锁与并发分析——证据化与结论收窄

**已验证路径与锁序**（全部含代码证据）：

| 路径 | 连接/事务 | 锁获取顺序（按时间） | 证据 |
|---|---|---|---|
| close 外层 A | 池连接 1，单事务 | `integration.repo_analysis_report` 行 FOR UPDATE → （子事务 B_i 全部结束后）→ proposal×N FOR UPDATE（withdraw 段）→ 审计写入 | analysis_report.rs:554-563（FOR UPDATE）、:613-619（withdraw FOR UPDATE） |
| publish 子事务 B_i | **池内另取连接**，独立事务 | advisory(`{pc\|projc}_publish:{project}`) → proposal FOR UPDATE → approval FOR UPDATE → 插入/更新族（version/member/生命周期/账本/审计/outbox） | pc/publish.rs:102-108/:182-215 |
| decide（approve/reject） | 独立事务 | proposal FOR UPDATE → approval pending FOR UPDATE；**report 仅普通 SELECT（无锁）** | pc/proposal.rs:938-995/:920-930 |
| 显式补发布 | 独立事务 | 同 B_i（advisory→proposal→approval） | pc/publish.rs 同入口 |

**专项核查结论**：

1. **advisory→report 顺序**：不存在于任何单一事务——advisory 仅在 B（publish 连接）获取，report 锁仅在 A（close 连接）获取，二者分属不同事务连接，不构成锁序对。
2. **report→advisory 顺序**：跨事务等待链存在（A 持 report 锁、B 子事务取 advisory），但因分属不同事务，**不构成同事务锁序反转**；A→B→C 等待链的链尾 C（decide）不等待任何 A/B 持有资源→链必然收敛。
3. **proposal→report 顺序**：不存在——decide 对 report 为无锁普通读（proposal.rs:920-930）；全仓库无「先 proposal 锁后 report 锁」路径。
4. **隐式锁/触发器/外键**：
   - 外键=0（pc/projc 全 schema 无 FK，0001/0025/0026 取证）——无 FK 级联锁；
   - 约束触发器（活库清单 E-33）：`trg_*_vm_closure`（AFTER INSERT，DEFERRABLE INITIALLY DEFERRED，COMMIT 时评估，内部为普通 SELECT——READ COMMITTED 下不加行锁）、`trg_*_pm_anchored(_ins)`（AFTER INSERT/UPDATE/DELETE，普通 SELECT proposal.status）——**均为纯读触发器，不引入额外行锁**；
   - 唯一索引逐行检查：`uq_*_vm_*` 多行插入存在经典唯一索引插入死锁面，但发布事务被 advisory 项目级串行化→同项目不存在并发多行 version_member 插入→面消除。
5. **事务隔离级别**：**READ COMMITTED**——运行时实证 `SHOW transaction_isolation`='read committed'（aipm_mig_full，2026-11-17）+ 全仓库无 IsolationLevel/SET TRANSACTION 显式配置（grep 0 命中，E-31）。READ COMMITTED 下 FOR UPDATE 读最新已提交行+普通读不加锁——与上述分析前提一致。
6. **连接关系**：close 外层与 publish 子事务使用**同一池的不同连接**（publish_version 内 `pool.begin()`）——两层事务无嵌套关系，A 的回滚不影响已提交的 B_i，反之亦然。

**结论收窄**：以上四条已验证路径**锁序无环、无死锁**；**本结论仅覆盖已枚举路径，不构成全局无死锁保证**——未来新增涉及 report+proposal 双资源的写路径时须重新走查（登记为设计纪律，入 GAP-32 处置建议）。GAP-32（approved 清单无 FOR UPDATE 竞态窗口）与 Q-10 维持**非阻塞**性质，未发现新的直接阻塞证据。

### D6.6 〔v1.0.2 修订（任务书 P0-1/P0-2）〕身份模型与单一指纹

**裁定 1：起草与提交 = 一项逻辑操作（propose）**。
依据：分析链现状即同事务一体——`propose_from_analysis` 在同一事务内完成 create_proposal_in（提案+成员+审计）与 submit_proposal_in（状态翻转+pending 审批行+审计）（pc/proposal.rs:1466-1491，单 tx 两段调用）；「起草即提交」是该链的既定语义（草案期成员创建即齐备，无独立提交动作）。目标设计确认此语义为正式模型：**提案不存在独立的「提交」逻辑操作**，submit 子步骤是 propose 操作的组成部分。
物化（对象草稿 upsert、来源/证据登记）= **独立的 L1 内容幂等操作**（content_hash/object_key/evidence identity 锚定，不需要账本），与 propose 分属不同事务（上游完成后再起草提案）——两层操作两层锚，不共用 operation_id。

**裁定 2：账本行单一权威指纹 = `proposal_content_hash`**。
- propose 账本行的 fingerprint **只有一个**：`proposal_content_hash`（规范化哈希覆盖 title/rationale/origin_kind/governance_level/expected_version_no/成员集全集）。
- 它在操作**完成时一次性写入**账本行（成员集在创建时即锚定→全操作稳定，不存在阶段漂移）——**不是「启动指纹→完成指纹」的两段设计**；启动时该列以占位写入、完成时回填为权威值，重放校验只认权威值。
- 起草段与提交段**共用同一指纹**（同一账本行、同一逻辑操作）：成员锚定后内容即冻结，两段的「逻辑内容」相同。
- 调用方侧（未来 API 场景）请求指纹=调用方对自身载荷的哈希，仅用于**重放校验比对**（与账本权威指纹不一致→409 mismatch）；分析链消费者不携带指纹，其重放由 op_id 所有权规则约束（`{domain}-analyze:{task_id}` 键空间仅分析链可产生）。

**裁定 3：身份基数与 op_id 结构（任务书 P0-2）**：

| 链路 | 基数事实（代码证据） | op_id 结构 | 单键唯一标识一次逻辑提案？ |
|---|---|---|---|
| 分析链 | 一次调用=一个提案（全部候选合并为一个提案的成员集，单次 create_proposal_in，proposal.rs:1466-1482）| `{domain}-analyze:{task_id}` | **是**——一 task_id 生命周期内至多 1 提案（方案 A 账本强制；新分析=新 task_id，运营模型既定）|
| 身份综合链 | 一轮=**至多 2 个 PC 提案**（profile/vision 各一，propose_pc_object×2，identity.rs:228-247）+ 1 个 Goal 提案**经 knowledge_proposal 8 态管线（非 pc.proposal）**（identity.rs:256-259）| `{domain}-identity:{round_id}:{slot}`，slot∈{profile,vision} | **round_id 单键不唯一（v1.0.1 表述修正）**——必须含槽位判别；slot=对象键（product-profile/product-vision），轮内稳定 |

- **同一 task/round 重试复用**：同 (task_id) / (round_id,slot) 重试→同 op_id→账本语义（completed 短路回放/唯一键等待互斥/指纹校验）。
- **不同提案防错命中**：①op_id 结构判别（task/round/slot 三维不同键）；②不同 op_id+同 content_hash=不同逻辑操作（并存不合并，V1.0.1 已裁）；③指纹校验拒绝键复用错配。
- **不以 content_hash 代替逻辑提案身份**：content_hash 仅作 L1 内容去重与指纹材料；逻辑身份=op_id 结构键。

**裁定 4：Q-06 边界（任务书 P0-1.4）**：Q-06 仅裁决 wire 命名细节（命令名、submit 子键是否拆 `{op_id}:submit`）；**核心身份模型（本节三项裁定）不属于 Q-06 裁决范围**——本节为本设计的目标模型，Q-01 批准方案 A 即视同批准本节模型；若 Q-01 选 B/C 则本节随之失效重议。

**原子性关系表（任务书 P0-1.5，propose 操作单事务内）**：

| 对象 | 与账本行的原子性 | 说明 |
|---|---|---|
| proposal + proposal_member | 同事务（不可分） | 账本 completed ⇔ 提案存在 |
| approval(pending) | 同事务（submit 子步骤写入） | 账本 completed ⇔ pending 审批行存在 |
| 审计（create+submit 两条） | 同事务 | 随事务全回滚 |
| Outbox（`{domain}.change_proposed`） | 同事务尾部 | 随事务回滚；幂等键写侧去重 |
| 账本行自身 | 同事务（pending→completed 全在内） | 回滚=无痕；崩溃=未 commit 无痕 |

发布段原子性维持十四步（账本+version+members+生命周期+审计+事件同事务）。

**完整操作时序（v1.0.2 定稿，方案 A）**：

```
分析链（起草+提交=一项逻辑操作）：
  上游：derive → L1 物化（source/evidence/对象草稿，content_hash/object_key 幂等）
  propose 操作单事务：
    账本 INSERT {domain}-analyze:{task_id} (pending, ON CONFLICT 等待/幂等)
    → advisory(分析起草串行化) → 候选排除
    → create_proposal_in（提案+成员+审计）
    → submit_proposal_in（翻转+pending approval+审计）
    → outbox(change_proposed, key=analysis_outcome_key)
    → 账本 completed（回填 artifact_id=proposal_id，权威指纹=proposal_content_hash）
    → COMMIT
  重放：同 op_id → completed 命中 → 返回既有 proposal（无第二提案）
  失败：业务校验/L3/基线 → 全回滚（账本无痕）→ 修复后同 op_id 重试

身份链（每槽位一项逻辑操作，两个独立 propose 操作）：
  apply_identity_drafts → 报告 open 校验
  → propose(profile)：L1 草稿幂等 → 账本 pc-identity:{round}:profile(pending)
    → create+submit+审计 → outbox → completed → COMMIT
  → propose(vision)：同构（:vision 槽位）
  → goal：knowledge_proposal 管线（独立域，不在本设计范围）
  部分失败：profile 成功/vision 失败 → vision 槽位账本无痕 → 同 (round,vision) 重试，
  profile 不受影响（槽位键隔离——修正 v1.0.1「同轮重跑重复提案」缺口的具体闭合方式）

发布（独立逻辑操作）：
  真人A3 → publish(operation_id={domain}-decision:{proposal_id}，确定性派生)
  → advisory → 账本(pending) → proposal/approval FOR UPDATE → CAS → 十四步
  → 账本 completed(artifact_id=version_id) → COMMIT
```

### D6.7 账本事务与恢复模型

维持 V1.0.1 同事务模型；〔v1.0.2 精化〕恢复锚表述修正：**同事务模型下「事务回滚/进程崩溃后」不存在需要保留的 pending 恢复锚**——回滚=账本无痕、恢复=调用方重放同 operation_id 重执行（内容级 L1 去重保证不产生重复草稿）；崩溃在 commit 后=账本 completed+产物完整→幂等返回。「分离事务+孤儿 pending 巡检」路线**不被本设计采用**（其长期 pending/重复执行问题随之不存在），Q-08 的巡检对象相应收窄为「发布段账本非终态行」（唯一可能的长挂来源=事务挂死，DB 层面自愈于连接断开）。
