## 一、现状与 R-1 精确复现路径（CODE FACT）

两域 close 批量发布段同构（analysis_report.rs:583-605 pc / :648-671 projc）：

```
approved_ids = SELECT id WHERE source_id=$1 AND status='approved'   -- 无锁读（外层事务）
for id: match publish_version(pool, …) { Ok → applied+=1, Err(_) → publish_failed+=1 }
```

R-1 交错：并发显式补发布先 COMMIT（提案→applied、版本落库、账本 completed）→ close 的 publish_version 因 `required_status="approved"` 守卫返回 Err(Conflict) → **计 publish_failed+1**——库状态一致（版本在、审计全、对账差分=0），仅计数误导。

## 二、并发窗口核查（裁决步骤 2）

**方案 B 判定式**：Err 分支内重读 `status='applied' AND EXISTS(账本行 operation_id='{domain}-decision:{id}' AND status='completed')` → 计 replayed；否则维持 failed。

窗口逐项：

| 窗口 | 分析 | 结论 |
|---|---|---|
| 重读时刻 vs 显式发布 COMMIT | publish_version 返回 Err 前，对方事务已 COMMIT 或已回滚（连接级同步点）；重读经 pool 连接 READ COMMITTED 每语句新快照 → 必见 COMMIT 后状态 | **无窗** |
| 重读后状态再变（TOCTOU） | `applied` 在 0034 转换矩阵中**无出边**（终态）；账本 completed 行无状态回退写点（E-51 全集+同键短路只读） | **判定=终态事实，不可失效** |
| 重读后账本再变 | 同上：completed 后同键仅短路读，无 UPDATE | **无窗** |
| CAS 失配案例对照 | 提案→failed（0034 有向 approved→failed）→ 重读 status='failed' → 维持 failed 计数 | 语义不混 |
| 其他 Err（NotFound/Forbidden/Db） | 重读 status 仍 approved（或行缺）→ 维持 failed | 保守正确 |

**结论：方案 B 在现有锁协议下可保证正确性，无需新锁、无需方案 A（清单 FOR UPDATE）**——判定建立在两个不可变终态事实（applied 无出边+completed 不回退）之上，重读本身为无锁只读，不与 advisory/行锁交互（不构成锁序新边）。

## 三、事务边界与失败处理核查（裁决步骤 3）

- 重读使用 `pool`（独立连接，与 publish 子事务同层）而非外层 `tx`——**不延长外层事务持锁面**、不产生外层事务内的陈旧快照误判（外层 REPEATABLE? 否——PG 默认 READ COMMITTED，但外层 tx 语句快照仍取自其开始? 不：READ COMMITTED 每语句新快照；用 pool 则完全隔离于外层，语义最干净）；
- 失败处理：重读自身 Err（连接异常等）→ 维持原 Err 计 failed（保守降级，不引入新错误路径）；
- 锁序不变式：全程新增面=一次无锁 SELECT，零锁参与 → 既有锁序图（§17.3/E-31 族）不变。
