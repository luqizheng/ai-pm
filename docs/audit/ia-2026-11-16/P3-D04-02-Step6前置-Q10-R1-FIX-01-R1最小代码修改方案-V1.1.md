## 〇、勘误登记（先行如实）

1. **《竞态闭合证明 V1.0》§四 R-1 行**：「显式补发布先 COMMIT→close 的 publish_version 因 required_status 守卫 409→误计 publish_failed」——**推演错误**：忽略了 close 的 publish_version 与竞争者共享 advisory+同发布键，后者必先命中**账本 completed 短路**（:159）返回 `Ok(replayed)`，**永远到不了守卫**（:225）。守卫 Err 需要「提案 applied ∧ 账本无 completed 行」——同事务原子性（R2）排除该组合。
2. **《独立技术复核 V1.0》R4 场景 2**：「close 循环内 Ok(replayed) 不可达」——**推导同样错误**（漏了"清单读取在先、竞争在后"时序）；正确事实：竞争交错下 `Ok(replayed)` **可达**，且现实现将其计入 `applied_proposals`——**计数语义正确**（该提案确经发布完成，幂等重放确认）。
3. 影响评估：q10_race_closure 场景 C 测试断言（`applied+failed≤1`、publish 恒 Ok）与实测全绿**与新结论一致**（从未断言过 failed 分支——恰因该分支在竞争下不发生）。

## 一、修订要求 R-1：重读后竞争发布窗口（时序全序分析）

### 1.1 真实调用链与锁位置（CODE FACT，pc 侧；projc 同构）

```
close_report(外层 tx A，持报告行 FOR UPDATE)
 └─ publish_version(pool 独立连接，tx B)
     B1 pg_advisory_xact_lock('pc_publish:'+project)   [:117]（事务级：随 B 提交/回滚释放）
     B2 INSERT write_operation … ON CONFLICT(三元组) DO NOTHING [:123-131]
     B3 既有行 SELECT status → completed ⇒ 指纹校验 ⇒ 短路返回 Ok(replayed) [:151-194]
     B4 提案 FOR UPDATE + 守卫 required_status='approved'   [:195-228]
     … B5 发布主体 → applied+completed 同 tx COMMIT
```

**advisory 获取/释放时机**：tx B 首语句获取、B 提交或回滚即释放；**所有发布者（close 循环体/显式补发布）经同一入口同一键**。

### 1.2 close×竞争发布者的全部可能顺序（穷举）

| # | 顺序 | close 的 publish_version 结果 | 计数 |
|---|---|---|---|
| S1 | close 先获 advisory，竞争者排队 | close 正常发布 `Ok`（首次）；竞争者后到短路 `Ok(replayed)` | applied+=1 ✓ |
| S2 | 竞争者先获 advisory 并 **COMMIT 后** close 才进入 | close 在 B3 **短路** `Ok(replayed)` | applied+=1 ✓（语义正确：发布经幂等确认完成） |
| S3 | 竞争者持 advisory **进行中**，close 的 publish 排队 | 同 S2（advisory 释放后进入即短路） | applied+=1 ✓ |
| S4 | close 读取 approved_ids（清单）时竞争者尚未开始/进行中/已完成 | 不改变上述——publish_version 的结果由 S1-S3 决定 | 同上 |
| **审阅方时序**（Err 后 JOIN 见 approved+无行） | —— | **不可达**：守卫 Err 需「applied ∧ 无 completed 行」（B3 未短路）——R2 同事务原子性排除其服务层来源；且 Err 分支触发前提（到达 B4）要求 B3 未命中 completed——两者矛盾 | —— |

**结论**：在现有锁协议（项目级 advisory+服务端派生同键+账本短路先于守卫）下，**审阅方要求的"Err 后竞争提交"窗口不存在**——Err 分支的竞争性来源为零；Err 仅来自非竞争原因（CAS=failed、守卫其他态、Db 错），分类 failed 恒正确。

### 1.3 是否存在现有协议下的最小保证方式 / 是否停止

- 比最小处理更强：**无需任何处理**——正确性由既有机制（advisory 串行+同键短路+同事务原子）结构性给出；
- **R-1 原始问题（误计 failed）经证明不可达** → 修复的前提消失。按指令 §四停止，不自行选择处置（见 §四选项）。

## 二、修订要求 R-2：T-2 确定性测试重设计

V1.0 的 T-2（预置 applied+completed 再 close）确与 `approved_ids` 仅选 approved 的实现不符——**指正成立**。但按 §一 修正后的事实，正确的确定性交错预期**不是**"守卫 Err→replay=1"，而是：

```
① seed：approved 提案（账本无行）+ analyzed 报告
② close 启动，注入同步点：approved_ids 读取完成后、publish_version 调用前挂起
   （实现设计：测试内以 tokio::sync::Barrier/one-shot 信道驱动 close 的两阶段——
    须在实施时以最小测试钩子或拆两步调用实现；本版仅设计不实施）
③ 显式 publish_version 提交（applied+completed）
④ 放行 close 的 publish_version
⑤ 预期（§一 S2）：close 的 publish=Ok(replayed) → applied_proposals=1、
   failed=0、（若采纳选项 B'）replayed 字段仍=0——失败计数恒 0
⑥ 断言：版本恰 1；提案 applied；报告 closed；无任何 failed 计数
```

该测试**证明不可达性**（竞争下 Err 不出现、误计不发生）——比 V1.0 的 replay 路径测试更贴近被保护的真实性质。若负责人仍要求防御性分类测试（注入态），另附：构造「applied+账本无行」（直写删行）→Err→JOIN=(applied,无行)→**failed**（保守正确）——同样不产生 replay=1 的服务层路径。

## 三、修订要求 R-3：重读异常处理四分类（若 Err 分支重读仍被保留）

| 情形 | `unwrap_or(None)` 行为 | 问题 | 最小建议 |
|---|---|---|---|
| 未找到提案（行消失） | None→failed | 与"不满足 replay"同路——业务上均为 failed，可接受 | 合并归 failed（注明） |
| 不满足 replay 条件 | None→failed | 正确 | 保持 |

| 连接/库暂不可用 | 同上 | 同上 | 同上（sqlx 池重试语义不变） |
