## E-33 close/publish/decide 完整锁路径（任务书 P1-1）

| 路径 | 锁序（时间序） | 证据 |
|---|---|---|
| close 外层 A | report FOR UPDATE（analysis_report.rs:554-563）→【子事务 B_i 执行】→ proposal×N FOR UPDATE（withdraw，:613-619）→ 审计（append_audit_with_after，:627-636） | E-18 |
| publish 子事务 B_i（close 或显式） | advisory（pc/publish.rs:105-108）→ proposal FOR UPDATE（:182-192）→ approval FOR UPDATE（:200-210）→ 插入/更新族（:454-685） | E-15 |
| decide（approve/reject） | proposal FOR UPDATE（proposal.rs:938-946）→ approval pending FOR UPDATE（:986-995）→ 审批终态化+翻转+审计（:1047-1096）；**report=普通 SELECT 无锁（:920-930）** | E-16 |
| 显式补发布 | 同 publish（独立调用同一入口） | E-15/E-19 |
| **反向序（proposal→report）** | **不存在**——全路径 report 仅无锁读 | E-16 |
| **advisory↔report** | 分属不同事务连接（B=池内另连、A=close 连接），非同事务锁序对 | E-18/E-15 |
| 连接关系 | close 外层与 publish 子事务=同一池不同连接（publish_version 内 `pool.begin()`），非嵌套事务 | E-15 |

- 结论：**已验证四路径锁序无环、无死锁；不构成全局无死锁保证**（新增涉及 report+proposal 双资源写路径须重新走查——设计方案 §D5.1 纪律）。
- 确认度：已确认（路径枚举内）；全局性=不声明。

## E-35 提案基数与身份链结构（任务书 P0-2）

- **分析链基数**：`propose_from_analysis` 单次调用=单次 `create_proposal_in`（全部候选合并为一个提案的成员集，pc/proposal.rs:1466-1482）→ 1 调用=1 提案；重复调用防护=advisory+候选排除+事件幂等键（E-16/E-22）；候选排除测试=`propose_from_analysis_candidate_exclusion`（projc_formal_chain.rs:987）。
- **身份链基数**：一轮=**至多 2 个 PC 提案**——`IdentityApplyOutcome{profile_proposal_id, vision_proposal_id, goal_proposal_id}`（identity.rs:133-137）+ `propose_pc_object`×2（product-profile/product-vision，identity.rs:228-247，各自独立 upsert→create→submit 三段事务）；**Goal 走 `knowledge_proposal::submit_proposal` 8 态管线，非 pc.proposal**（identity.rs:256-262）→ PC 侧身份链 op_id 必须含槽位判别：`pc-identity:{round_id}:{profile|vision}`。
- **部分失败语义**：「三提案落地（单事务性不做强求……已落库的提案保留在各自审批面可人工处置）」（identity.rs:210-211 注释）→槽位键隔离与现状部分失败语义一致。
- 确认度：已确认。
