## 一、审阅方指出的缺口（如实复述）

若实现为**两条独立 SELECT**（先读 proposal 后读账本，或反向），READ COMMITTED 下每条语句独立快照：两条读取之间并发发布事务提交 → 观察到 `(approved, completed)` 或 `(pending|failed, applied)` **混合对**——同事务原子提交不自动保证两条查询看到同一快照。R3 原证明缺此条件。

## 二、四点核查逐项回答

### 1. 单条 SQL JOIN 还是两条独立 SELECT？

**方案裁定（本核查正式确定）：单条 JOIN**——

```sql
SELECT p.status AS proposal_status, wo.status AS ledger_status
  FROM {domain}.proposal p
  LEFT JOIN {domain}.write_operation wo
    ON wo.tenant_id = p.tenant_id AND wo.project_id = p.project_id
   AND wo.operation_id = '{domain}-decision:' || p.id::text
 WHERE p.id = $1
```

一次语句、一个语句级快照、两事实一次读取。**前置分析 f76829b 未明确读写法（缺口成立）；独立复核 05ae6c3 亦未裁定（审阅方指正正确）。本核查将其定为修改方案的**规范性约束**：实现必须逐字采用上述单语句形态，禁止拆成两条 SELECT。**

### 2. 若两条独立 SELECT，是否同一 REPEATABLE READ 事务？

**不适用**（已裁定单条 JOIN）。备位说明：即便未来有人改回两条 SELECT，REPEATABLE READ 事务确可消除混合观察，但**引入事务边界管理成本且改变读侧行为**——按裁决特别约束（不加新机制）不予采用；单语句是零机制增量的等价解。

### 3. 如何排除混合快照？

**MVCC 论证（ANALYSIS，基于 CODE FACT R1/R2）**：
- 两事实由**同一源事务**同 COMMIT 建立（R2：publish_inner 单事务，applied 与 completed 间无中间 COMMIT）；
- PG MVCC 可见性按**事务提交点**判定：任何其他连接的**单条语句**快照，对该提交要么全见、要么全不见——**结构上不存在"见半个提交"的语句快照**（同一提交内两行变更共享同一 commit 可见性）；
- 因此单条 JOIN 的结果域只含：提交前一致对 `(approved, 无行)` 或提交后一致对 `(applied, completed)`；审阅方时间线 T1-T4 的 `(approved, completed)` 组合**仅在两条 SELECT 各自取快照跨提交时才可构造**——单语句下不可达；
- R1 补强：即便出现任何理论混合（不可能），分类条件要求 `applied AND completed` **同时**成立才计 replay——`(approved, completed)` 落入 failed 分支=保守方向（宁误报失败、不误报 replay），不产生"真失败计 replay"的反向错误。

### 4. 真实多连接测试（两次读取之间提交发布事务）

**TEST FACT（新增 `tests/q10_r3_snapshot_check.rs`，2 用例 × 3 轮全绿）**：
- 交错构造：读侧循环 **2000 次**执行与修复将采用的**逐字相同**的单条 JOIN，与一次性 `publish_version`（把 approved+无账本行 → applied+completed）`tokio::join!` 真并发（独立连接、读侧无锁无等待=交错窗口最大化）；
- 断言：全部观测对 ∈ 合法域（`approved/submitted/draft/withdrawn/rejected/expired/failed × 任意账本态` ∪ `applied × completed`）；**混合对计数=0**（显式枚举非法对：`applied×pending`、`applied×failed`、`applied×无行`——覆盖审阅方两个方向的时间线）；末次观测收敛于 `(applied, completed)`；
- 两域各一（pc/projc 同构覆盖）。
