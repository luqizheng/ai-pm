# AI-PM 工期核算与报价单导出 · 产品需求文档（PRD）V1.0

> **一句话**：项目负责人把客户需求丢进来，系统用 LLM 拆成三级功能结构、逐项填人天、汇总出工期，导出 Excel 交给销售部填单价。

> **边界**：系统只回答「要做多少天」，**不回答「多少钱」**。金额一律由销售在导出的 Excel 里填单价后自动算出。

## 一、背景与目标

### 1.1 背景

售前阶段，项目负责人要根据客户需求判断「这个项目要做多久」，这个数字直接决定销售报价的底盘。当前做法是负责人凭经验在 Excel 里手工列功能、手工填天数，存在三个问题：

| 问题 | 后果 |
|---|---|
| 分解靠记忆，容易漏项 | 漏掉权限、数据迁移、联调、部署这类"不显眼但要命"的工作项，报出去的工期不够做，项目亏 |
| 天数是单点值，没有区间 | 实际必然超，超了只能自己扛；没有"这是 80% 置信度的工期"这种说法 |
| 分解结果不沉淀 | 下一个类似项目重新拍一遍，团队的历史偏差从不回流 |

### 1.2 目标

| 编号 | 目标 | 衡量口径 | 目标值 |
|---|---|---|---|
| G-01 | 缩短单份工期核算耗时 | 从建单到导出 Excel 的时长（含人工调整） | ≤ 30 分钟（现状：半天到一天，估算） |
| G-02 | 降低漏项率 | 导出时 12 类工作项核对清单的未覆盖项数 | 0（不覆盖不放行） |
| G-03 | 工期可承诺 | 输出 P80 置信工期而非单点值 | 100% 的导出单据含区间 |
| G-04 | 沉淀可复用数据 | 每个估算项的 LLM 原值 + 人工调整值双留痕 | 100%（为后续校准打底） |

> **不设**「估算准确率」作为 V1 目标——准确率要靠实际工时回流才能算，V1 还没有回流数据，现在设这个指标只会变成假数字。准确率是 V2 目标（见 §14）。

### 1.3 非目标（本期明确不做）

1. **不计算金额**。无单价表、无毛利率、无成本核算、无币种换算。
2. **不做对外报价审批流**。系统产出的是内部工时核算底稿，销售拿到 Excel 后的定价行为不在本系统内。
3. **不做实际工时回流与自动校准**。字段预留（`actual_days`），逻辑 V2。
4. **不做合同/发票/回款**。
5. **不做蒙特卡洛模拟**。V1 用 PERT + 正态近似 P80，够用且可解释。

## 二、名词与术语

| 术语 | 定义 |
|---|---|
| 估算单（Estimate） | 一次工期核算的完整产物，含 WBS 树、人天、汇总、假设清单，可多版本 |
| WBS | 工作分解结构。本系统固定三级：L1 功能模块 → L2 子功能 → L3 工作项 |
| 工作项（Item） | WBS 的叶子节点，唯一可填人天的层级 |
| 工作项类型（category） | 前端 / 后端 / 数据 / 联调 / 测试 / 部署 / 文档 / 设计 / 项目管理 / 其他 |
| 三点估算 | 每个工作项填乐观 O、最可能 M、悲观 P 三个值 |
| 期望人天 | PERT 公式 `(O + 4M + P) / 6`，工作项的标准人天 |
| P80 工期 | 有 80% 概率不超的工期，`Σ期望 + 0.8416 × √(Σσ²)`，σ = (P−O)/6 |
| 关键路径工期 | WBS 中依赖链最长的一条，决定最少日历天，不可通过加人压缩 |
| 日历天 | `max(总人天 ÷ 并行人数, 关键路径人天)` 后向上取整，再按工作日换算 |
| 漏项清单 | 12 类固定工作项核对表，任一未覆盖则不允许导出 |
| 需求覆盖率 | 已映射到工作项的需求条目数 ÷ 需求条目总数 |

## 三、需求范围

### 3.1 包含

- 估算单的新建、编辑、复制、版本化
- 三种输入来源：粘贴需求原文 / 关联已有需求条目 / 纯手工建树
- LLM 三级 WBS 分解（含不确定项、风险提示、排除项）
- 工作项三点估算与人工调整（保留 LLM 原值）
- 漏项检查与需求覆盖率校验
- 工期汇总（总人天 / P80 / 日历天 / 关键路径 / 分类占比）
- Excel 导出（3 个 sheet，预置单价空列与金额公式）
- 导出快照冻结与审计留痕

### 3.2 不包含

见 §1.3。

## 四、方案对比与选型

### 4.1 方案 A：只做手工 WBS，不接 LLM

| 维度 | 评价 |
|---|---|
| 成本 | 最低（纯 CRUD + Excel 导出） |
| 体验 | 与现状 Excel 差距不大，只是换了个地方填 |
| 风险 | 低 |
| 结论 | 不作为主方案。用户明确要求 LLM 生成功能模块，这是本需求的核心价值点 |

### 4.2 方案 B：LLM 一次生成完整 WBS + 人天，人工只做微调 ✅ 推荐

| 维度 | 评价 |
|---|---|
| 成本 | 中（新增 1 个 Skill + 1 套校验 + Excel 导出） |
| 体验 | 输入一段需求 → 30 秒出完整结构 → 人工改重点项 |
| 风险 | LLM 系统性乐观偏差、漏项、编造不存在的技术栈 |
| 结论 | **推荐**。风险用「强制核对清单 + P80 + 人工确认」三道闸口兜住 |

### 4.3 方案 C：LLM 只给建议，人工从零填

| 维度 | 评价 |
|---|---|
| 成本 | 中 |
| 体验 | 慢，LLM 价值基本浪费 |
| 结论 | 不采用 |

### 4.4 Excel 生成位置选型

| 方案 | 实现 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| 后端 Rust `rust_xlsxwriter` | `GET /v1/pm/estimates/{id}/export.xlsx` | 导出内容与库内快照严格一致；天然可审计；前端零增重；纯 Rust 无 C 依赖 | 需加 1 个 crate | ✅ **推荐** |
| 前端 exceljs | 浏览器生成并下载 | 即时、可预览 | 与库内快照可能不一致；前端 +1 个大依赖；导出行为不可审计 | 备选 |
| CSV | 后端拼字符串 | 零依赖 | **无法带公式和格式**，销售拿到还得手工加列，不满足需求 | 否决 |

## 五、用户角色与使用场景

### 5.1 角色

| 角色 | 是谁 | 在本功能中的动作 | 能力水平 |
|---|---|---|---|
| 项目负责人（PM） | 售前/交付负责人 | 建单、跑分解、改天数、导出、发给销售 | 熟练，懂技术边界 |
| 技术负责人（可选） | 研发 TL | 复核高风险模块的天数 | 熟练 |
| 销售 | 商务 | **不进系统**，接收导出的 Excel，填单价算最终报价 | 新手（对系统无感知） |
| 观察者 | 其他成员 | 只读查看历史估算 | — |

> **画像假设（待确认）**：项目负责人通常同时管 2–5 个售前机会，需要快速出数；对"再填一遍表单"容忍度极低。此画像为基于需求描述的推断，非调研结论。

### 5.2 核心场景（主流程）

**场景 1：新客户需求，从零估算**
1. PM 打开项目 → 工期核算 → 新建
2. 粘贴客户需求原文（或上传需求文档文本）
3. 点「生成分解」，30 秒内得到三级 WBS + 人天初值
4. 扫一眼标红的「不确定项」和「风险提示」，逐条处置
5. 改几个明显不准的项，加两个 LLM 漏掉的项
6. 看汇总：总人天 128、P80 165 人天、3 人并行约 55 个工作日
7. 导出 Excel，发给销售

**场景 2：需求变更后重新出数**
1. 打开已有估算单 → 复制为新版本
2. 只改受影响的模块（局部重新生成，不推翻已改过的部分）
3. 系统高亮「本次变更影响」：+12 人天
4. 导出 v2，附带 v1→v2 差异说明

**场景 3：LLM 不可用**
1. 分解失败或超时
2. 系统提示「转换手工模式」，已有的输入原文保留
3. PM 手工建树，人天照填，其余功能（汇总、校验、导出）完全可用

### 5.3 分支与异常

| 场景 | 期望行为 |
|---|---|
| 需求文本为空或 < 50 字 | 拒绝生成，提示补充（信息量不足无法分解） |
| 需求文本 > 20,000 字 | 提示分段，或按章节摘要后分解（标注「基于摘要估算，可能偏差」） |
| 已有需求条目但未全选 | 覆盖率按已选条目计算，导出前提示未覆盖项 |
| 某个工作项 > 5 人天 | 标黄提示「建议拆分」，不硬拦（有些项确实拆不动） |
| 所有项都是 LLM 生成、零人工调整 | 导出前二次确认「未经人工复核，确认导出？」 |
| 关键路径为空（没填依赖） | 日历天退化为「总人天 ÷ 人数」，页面标注「未设置依赖，日历天为粗略值」 |

## 六、功能需求

### FR-01 创建估算单

| 项 | 内容 |
|---|---|
| 描述 | 在指定项目下创建估算单，支持三种来源 |
| 规则 | ① 单号规则 `EST-{YYYY}-{NNN}`，项目内自增不重复；② 标题必填 ≤ 100 字；③ `source_kind` 三选一，落库后不可改；④ 关联需求时保存 `requirement_id` |
| 验收 | **Given** 项目 P 下无估算单，**When** 创建标题「XX 系统一期」并粘贴需求，**Then** 生成单号 `EST-2026-001`，状态 `draft`，原文入库可回溯 |
| 验收 | **Given** 标题为空，**When** 提交，**Then** 阻断并定位到标题字段提示 |

### FR-02 LLM 三级 WBS 分解

| 项 | 内容 |
|---|---|
| 描述 | 输入需求文本，调用 LLM 生成 L1/L2/L3 三层结构，每项带三点估算、类型、复杂度、依据、置信度 |
| 规则 | ① 分解为异步任务，前端轮询/SSE 显示进度，超时 120s 判失败；② 输出必须通过 §15.2 契约校验，字段缺失整单失败不回写；③ `missing_info` / `risk_flags` / `excluded` 三组必返（可为空数组）；④ 关联需求时，每个叶子项须带 `requirement_ref`；⑤ 记录 `llm_model` + `prompt_version` 供追溯 |
| 验收 | **Given** 一段含 5 个功能点的需求，**When** 触发生成，**Then** 得到 ≥5 个叶子项，每项 category 在枚举内，三点值满足 O ≤ M ≤ P |
| 验收 | **Given** LLM 返回非法 JSON，**When** 解析，**Then** 整单失败并提示重试，库内不产生半截数据 |
| 验收 | **Given** 需求提到"对接微信支付"，**When** 生成，**Then** `risk_flags` 非空且被展示 |

### FR-03 分解结果编辑

| 项 | 内容 |
|---|---|
| 描述 | 三级树全量可编辑 |
| 规则 | ① 支持改名、改类型、改三点值、增删项、调整顺序、同级拖动；② 叶子项可下钻变父节点（自动生成子项）；③ 支持「仅重新生成本模块」，已有子项按名称模糊匹配保留人工修改；④ 任一字段被人工改过，`source` 置 `human`，`llm_expected_days` 保留原值不再覆盖 |
| 验收 | **Given** LLM 给某项目 3 人天，**When** PM 改为 5 人天，**Then** 该项 `source=human`、`llm_expected_days=3`、`expected_days=5` |
| 验收 | **Given** 一次「重新生成本模块」，**When** 完成，**Then** 人工改过的项数值不被覆盖，仅新增/删除项变化 |

### FR-04 三点估算与人天计算

| 项 | 内容 |
|---|---|
| 描述 | 工作项填 O/M/P，系统自动算期望人天与总人天 |
| 规则 | ① 期望 = (O+4M+P)/6，保留 2 位小数；② 总人天 = 期望 × 数量；③ 校验 O ≤ M ≤ P，违反即报错；④ 单位人天下限 0.25，超过 5 人天标黄提示拆分（不阻断）；⑤ 父节点人天 = 子节点求和，父节点不可直接填 |
| 验收 | **Given** O=2, M=4, P=9, qty=1，**When** 保存，**Then** 期望 = 5.17 人天 |
| 验收 | **Given** O=5, M=3，**When** 保存，**Then** 报错「乐观值不得大于最可能值」 |

### FR-05 漏项检查与覆盖率校验

| 项 | 内容 |
|---|---|
| 描述 | 导出前强制核对 12 类工作项与需求覆盖情况 |
| 规则 | ① 12 类清单见 §15.3，任一类型无对应工作项则标为「未覆盖」；② 未覆盖项必须由 PM 二选一：新增工作项 / 勾选「本项目确实不涉及」并填原因；③ 关联需求时，覆盖率必须 100% 才能导出，否则列出未覆盖需求条目；④ 校验结果随快照一起冻结 |
| 验收 | **Given** WBS 中无任何 `deploy` 类型项，**When** 点导出，**Then** 弹窗列出「部署与环境未覆盖」，不填原因不允许继续 |
| **这是本需求最重要的一条防线**，漏项比估不准更贵 | |

### FR-06 工期汇总

| 项 | 内容 |
|---|---|
| 描述 | 实时汇总总人天、P80、日历天、关键路径、分类占比 |
| 规则 | ① 总人天 = 全部叶子项总和；② σ_total = √(Σσᵢ²)，σᵢ=(Pᵢ−Oᵢ)/6；③ P80 = 总人天 + 0.8416×σ_total；④ 日历天 = ceil(max(总人天÷人数, 关键路径人天))，再按每周 5 工作日折算；⑤ 关键路径 = 按 `depends_on` 求 DAG 最长路径，无依赖时该项为空并降级提示；⑥ 分类占比按 category 汇总人天 |
| 验收 | **Given** 总人天 100、σ_total 20、3 人，**When** 查看汇总，**Then** P80 = 116.8，日历天 = ceil(max(33.3, 关键路径)) |
| 验收 | **Given** 无任何依赖关系，**When** 查看，**Then** 日历天按总人天÷人数计算，并显示「未设置依赖」提示 |

### FR-07 Excel 导出

| 项 | 内容 |
|---|---|
| 描述 | 一键导出 `.xlsx`，交销售填单价 |
| 规则 | ① 三个 sheet：汇总 / 明细 / 假设与排除（结构见 §15.4）；② 明细表含「单价」「金额」两个**空白列**，金额列预置公式 `=合计人天*单价`，小计与总计同样预置 `SUM` 公式；③ 导出内容来自库内冻结快照，不受导出瞬间页面状态影响；④ 文件名 `{项目名}-工期核算-{单号}-v{版本}-{YYYYMMDD}.xlsx`；⑤ 导出耗时 ≤ 3s |
| 验收 | **Given** 一份含 40 个子项的估算单，**When** 导出，**Then** 得到 3 sheet 文件，明细 40 行，单价列为空，金额列有公式 |
| 验收 | **Given** 销售在 Excel 里给某行填单价 1500，**When** 打开，**Then** 该行金额自动 = 合计人天 × 1500，小计随之更新 |

### FR-08 版本与快照

| 项 | 内容 |
|---|---|
| 描述 | 导出即冻结，变更起新版本 |
| 规则 | ① 首次导出生成 `snapshot`（完整 WBS + 汇总 + 校验结果 + 假设清单的 JSON）；② 已导出单据转 `exported`，只读；③ 需改动时「创建新版本」，`version+1`，状态回 `draft`，保留上一版快照可对比；④ 版本对比至少展示：新增/删除项、人天变化、总工期变化 |
| 验收 | **Given** v1 已导出，**When** 尝试直接编辑，**Then** 阻断并提示「已导出，请创建新版本」 |
| 验收 | **Given** v1 总人天 120，v2 改后 132，**When** 对比，**Then** 显示 +12 人天及受影响项清单 |

### FR-09 不确定项与风险提示

| 项 | 内容 |
|---|---|
| 描述 | LLM 返回的不确定项、风险、排除项必须在页面显著位置呈现并可处置 |
| 规则 | ① 不确定项可转为「假设」（进假设清单）或「待客户确认」（进导出文件的客户待办页）；② 风险提示可转为工作项（自动带出预估人天）或标记「已知悉」；③ 未处置的不确定项在导出前提示，不强制阻断（有些确实要先报价后澄清） |
| 验收 | **Given** 3 条不确定项仅处置 1 条，**When** 导出，**Then** 提示「2 条未处置」，可选继续或返回 |

### FR-10 审计

| 项 | 内容 |
|---|---|
| 描述 | 全部关键动作留痕 |
| 规则 | 记录：创建、触发生成、单项人工修改（含改前后值）、删除项、重新生成、导出、版本创建。复用现有 `governance.audit_log` 与 SSE 审计流 |
| 验收 | **Given** PM 改了 5 个项并导出，**When** 查审计，**Then** 可见 5 条 item.update 与 1 条 estimate.export |

### FR-11 列表与检索

| 项 | 内容 |
|---|---|
| 描述 | 项目下估算单列表 |
| 规则 | 列：单号、标题、版本、状态、总人天、P80、日历天、创建人、更新时间；支持按状态筛选、按标题搜索；默认按更新时间倒序 |

## 七、非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | LLM 分解 P95 ≤ 60s（异步，前端可见进度）；汇总接口 P95 ≤ 500ms（200 项内）；导出 P95 ≤ 3s |
| 容量 | 单估算单 ≤ 200 个叶子项；单项目 ≤ 500 份估算单 |
| 可用性 | LLM 不可用时降级为手工模式，编辑/汇总/导出全部可用（对齐架构原则 §4「先可靠保存，再分析」） |
| 一致性强 | 汇总值由服务端计算，前端不自行核算（防口径漂移） |
| 并发 | 编辑走乐观锁（`revision`），冲突返回 409 并提示刷新 |
| 安全 | 无 PII 存储需求；需求原文可能含客户信息，按项目隔离，跨项目访问 404 |
| 兼容 | 导出的 xlsx 须在 Excel 2016+ / WPS 打开无告警（公式与格式兼容） |
| 可访问性 | 树形编辑支持键盘展开/折叠；所有可点项有 focus ring（沿用 PRISM 门禁） |

## 八、业务流程与状态流转

### 8.1 主流程

```
① 新建（选来源）
      ↓
② 输入需求（粘贴 / 关联需求条目 / 空）
      ↓
③ LLM 分解（异步） ──失败──→ 手工模式（不阻断）
      ↓
④ 人工审阅   ←─── 局部重新生成 ───┐
   ├─ 处置不确定项 / 风险          │
   ├─ 改天数 / 增删项              │
   └─ 填依赖（可选）               │
      ↓                            │
⑤ 漏项校验（12 类 + 覆盖率）        │
   └─ 未覆盖 → 补项或填豁免原因 ────┘
      ↓
⑥ 汇总（总人天 / P80 / 日历天）
      ↓
⑦ 导出 Excel → 快照冻结 → 状态 exported
      ↓
⑧ 交销售填单价（系统外）
```

### 8.2 估算单状态机

| 当前状态 | 触发事件 | 下一状态 | 允许操作 |
|---|---|---|---|
| `draft` | 提交评审 | `in_review` | 编辑、生成、导出（导出直接跳 `exported`） |
| `draft` | 直接导出 | `exported` | 只读、创建新版本 |
| `in_review` | 打回 | `draft` | 编辑 |
| `in_review` | 通过并导出 | `exported` | 只读、创建新版本 |
| `exported` | 创建新版本 | `draft`（version+1） | 编辑新版本 |
| `exported` | 归档 | `archived` | 只读 |

> 状态单向流转，`exported` 不可回退到 `draft`——回退靠新建版本，避免"客户手里的 v1 被偷偷改了"。

### 9.1 数据模型（新增 schema `estimation`，迁移 0007）

### 9.2 埋点（服务端记录，非前端埋点）

| 事件 | 触发时机 | 关键属性 |
|---|---|---|
| `estimate.create` | 建单 | source_kind, has_requirement |
| `estimate.generate` | 触发生成 | model, prompt_version, duration_ms, item_count, missing_count |
| `estimate.item.override` | 人工改天数 | item_id, from, to, llm_expected |
| `estimate.item.add` / `.remove` | 增删项 | category |
| `estimate.check.waive` | 豁免漏项 | category, reason |
| `estimate.export` | 导出 | version, item_count, total_days, p80_days |

### 9.3 指标口径

| 指标 | 计算式 | 用途 |
|---|---|---|
| 人工调整率 | 被人工改过天数的项数 ÷ 叶子项总数 | 衡量 LLM 初值可用度，>50% 说明 prompt 需要改 |
| 漏项补录率 | 人工新增项数 ÷ LLM 生成项数 | 衡量 LLM 分解完整度 |
| 单均耗时 | 建单到导出的时间差中位数 | 验证 G-01 |
| 估算偏差率（V2） | (实际人天 − 估算人天) ÷ 估算人天 | 校准系数来源 |

## 十、权限与安全

| 操作 | project_owner | 项目成员 | 观察者 | 备注 |
|---|---|---|---|---|
| 查看估算单 | ✅ | ✅ | ✅ | 跨项目 404 |
| 新建 / 编辑 / 生成 | ✅ | ❌ | ❌ | 成员可申请升权 |
| 导出 | ✅ | ❌ | ❌ | 导出即对外交付物，需 owner 级 |
| 删除（草稿） | ✅ | ❌ | ❌ | 已导出不可删，只能归档 |

- 权限码建议：`PM_ESTIMATE_READ` / `PM_ESTIMATE_WRITE` / `PM_ESTIMATE_EXPORT`。
- **是否需要走现有 `external_commitment` 红线**：**否**。系统不生成金额、不对外发送，红线针对"对外承诺金额"，本功能边界止于内部工时底稿。导出行为记审计但不阻塞。此判断列为待裁（§13-1）。
- 需求原文可能含客户敏感信息：仅项目内可见，导出文件中**不含**原文全文（只在假设页引用必要片段）。

## 十一、异常处理清单

| 编号 | 场景 | 处理 |
|---|---|---|
| E-01 | LLM 返回非法 JSON / 缺字段 | 整单失败，不写半截数据，提示重试 |
| E-02 | LLM 超时（>120s） | 标记失败，转手工模式，原文保留 |
| E-03 | LLM 返回 0 个叶子项 | 视为失败，提示「需求信息不足，请补充或手工建树」 |
| E-04 | 需求文本 < 50 字 | 建单允许，生成拒绝 |
| E-05 | 需求文本 > 20,000 字 | 提示分段；选择继续则先用摘要分解，页面标注偏差风险 |
| E-06 | O > M 或 M > P | 阻断保存，定位到字段 |
| E-07 | 叶子项 > 5 人天 | 标黄提示拆分，不阻断 |
| E-08 | 叶子项 < 0.25 人天 | 提示合并，不阻断 |
| E-09 | 父节点被直接填人天 | 阻断，提示只能填叶子 |
| E-10 | 删除有子项的节点 | 二次确认，级联删除并记审计 |
| E-11 | 12 类工作项未覆盖 | 阻断导出，要求补项或填豁免原因 |
| E-12 | 需求覆盖率 < 100% | 阻断导出，列出未覆盖条目 |
| E-13 | 已导出单据被编辑 | 阻断，提示创建新版本 |
| E-14 | 并发编辑冲突 | 409，提示刷新后重试 |
| E-15 | 导出时快照生成失败 | 导出失败，状态保持 `draft`（不留半冻结状态） |
| E-16 | 关键路径计算发现环（A 依赖 B、B 依赖 A） | 阻断保存依赖，指出环路 |
| E-17 | 时间/人数为 0 | 阻断，提示人数至少 1 |
| E-18 | 项目被删除/归档 | 估算单只读保留，导出仍可用 |

## 十二、上线计划、依赖与验证

### 12.1 分期

| 期 | 范围 | 产出 |
|---|---|---|
| **P0** | 建单 + 手工 WBS + 三点估算 + 汇总 + Excel 导出 | 可用的手工版，先验证 Excel 是不是销售真正要的格式 |
| **P1** | LLM 分解 + 不确定项/风险处置 + 局部重新生成 | 核心价值上线 |
| **P2** | 漏项校验 + 覆盖率 + 版本对比 | 质量防线 |
| **P3（V2）** | 实际工时回流 + 校准系数 + 偏差报表 | 长期护城河 |

> P0 先出的理由：Excel 格式是最大不确定性——销售部实际怎么填、要不要分角色、要不要含税列，只有拿到真文件才知道。先用手工版把格式试对，再上 LLM，避免"LLM 很好但导出的表销售不用"。

### 12.2 依赖评估

| 依赖项 | 所属 | 分级 | 最晚就绪 | 影响与替代 |
|---|---|---|---|---|
| 现有 `pm-ai` 模型适配器 | 本仓 | ✅ 已就绪 | — | 直接复用 `openai_adapter` |
| 现有命令通道与审计 | 本仓 | ✅ 已就绪 | — | 写入走 `command_executor`，审计自动落 |
| Excel 生成库 `rust_xlsxwriter` | 新增 crate | 并行 | P0 开发前 | 不可用则退前端 exceljs |
| 需求条目读取接口 | 本仓 `/v1/pm/requirements` | ✅ 已就绪 | — | — |
| 销售侧 Excel 格式确认 | 销售部 | **阻塞** | P0 验收前 | 未确认则 P0 无法验收；替代：先用内部模板，后续改 |

### 12.3 上线后验证

1. 用 3 个真实历史项目做回测：不看实际结果先估，再对比历史实际工时，记录偏差（不入库，仅验证）。
2. 让销售实际用导出的 Excel 报价一次，收集格式反馈。
3. 检查审计链路完整（生成、改项、导出均有记录）。

### 14.2 LLM 输出契约

```json
{
  "modules": [
    {
      "name": "用户认证",
      "children": [
        {
          "name": "手机号验证码登录",
          "items": [
            {
              "name": "登录页 UI 与交互",
              "category": "frontend",
              "complexity": "M",
              "o": 1, "m": 2, "p": 4,
              "qty": 1,
              "rationale": "含表单校验、倒计时、错误提示三态",
              "confidence": "high",
              "requirement_ref": "REQ-003"
            }
          ]
        }
      ]
    }
  ],
  "missing_info": ["未说明是否需要微信一键登录"],
  "risk_flags": ["短信服务商需企业资质审核，可能影响排期"],
  "excluded": ["不含 UI 视觉设计稿与品牌物料"],
  "tech_stack_assumed": ["Vue3", "Spring Boot", "MySQL"]
}
```

**校验规则（任一不满足整单失败）**：
1. `modules` 非空；每个 module 至少 1 个 child；每个 child 至少 1 个 item
2. `category` ∈ {frontend, backend, data, integration, test, deploy, doc, design, pm, other}
3. `0.25 ≤ o ≤ m ≤ p ≤ 40`
4. `confidence` ∈ {high, medium, low}
5. `rationale` 非空（禁止无依据数字）
6. `missing_info` / `risk_flags` / `excluded` 三个 key 必须存在（可为空数组）
