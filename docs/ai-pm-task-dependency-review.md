## 2. P0：并发正确性（必须修复或证明已防护）

### 2.1 并发建边可能绕过环检测

**性质：设计缺口，从设计稿 §4.2 的校验顺序即可推演，不需要看代码。这是本次评审最重要的问题。**

反例时序——当前 A、B 之间**没有任何依赖**，两个事务并发：

| 步骤 | 事务 T1：添加 A → B | 事务 T2：添加 B → A |
|---|---|---|
| 1 | 锁定 A（`FOR UPDATE`） | 锁定 B（`FOR UPDATE`） |
| 2 | 查询 B 的祖先，发现没有 A | 查询 A 的祖先，发现没有 B |
| 3 | 检查通过，插入 A → B | 检查通过，插入 B → A |
| 4 | 提交 | 提交 |

**最终结果：形成依赖环 A ⇄ B。**

为什么现有设计无法阻止：

1. `FOR UPDATE` 锁定的是**下游任务行**。T1 锁 A、T2 锁 B，两边**不会互相阻塞**。
2. 递归 CTE 的快照读**看不到对方尚未提交的边**，无法解决两个并发事务之间的图结构一致性问题。

**建议修正：增加项目级依赖图写锁。**

```sql
SELECT pg_advisory_xact_lock(hashtextextended($project_id::text, 0));
```

所有依赖边的新增、删除，在**检环和修改之前**先获取同一个项目级事务锁，使同一项目的图结构修改串行化。

两条约束：

1. **锁的唯一性**：所有建边/删边入口必须使用**同一把**锁（同一 `project_id` 派生键），不能存在绕过路径。若未来新增任何写边入口（管理脚本、批量导入等），必须强制走同一入口。
2. **锁顺序**：如果终态迁移（解锁传播）也要与建边串行化，必须设计统一的锁获取顺序——advisory lock 必须在任务行锁**之前**获取，避免 advisory lock 与任务行锁之间出现锁顺序反转死锁（见 §2.2 的锁协议）。

### 2.2 建边与上游完成之间存在竞态，可能永久漏解锁

**性质：设计缺口。比环检测更隐蔽。**

前提：A 是上游，B 是下游，B 当前为 `blocked`，A 当前为 `running`。

| 时间 | 事务 T1：添加依赖 | 事务 T2：完成上游 |
|---|---|---|
| 1 | 插入 B → A | |
| 2 | 检查上游状态，发现 A 未完成 | |
| 3 | | A → `completed` |
| 4 | | 查询 A 的下游依赖 |
| 5 | | **看不到 T1 尚未提交的依赖边** |
| 6 | 提交 | 提交 |

**最终状态：**

```
A = completed
B = blocked，B 依赖 A
```

后果链条：

- A 已进入终态，**不会再次触发终态迁移**；
- B 没有被解锁；
- B 的依赖实际上已经全部满足。

**这是一个永久阻塞任务**，且没有任何报错——属于静默数据损坏，排查成本极高。

根因：建边事务与终态解锁事务之间**没有建立可证明的串行关系**。

**建议修正（二选一，或组合）：**

方案一：行锁协议

1. 建边时，先锁定**上游**任务行；
2. 再锁定下游任务行；
3. 检查上游状态；
4. 插入边并执行解锁判断；
5. 上游终态迁移必须持有**同一个上游任务行锁**，直到完成下游扫描。

注意：这要求严格设计所有入口的锁顺序（上游行 → 下游行，与 §5.3 既有「下游 `ORDER BY task_id` 加锁」需统一为全局一致的获取顺序）。

方案二：项目级 advisory lock 统一协议

让建边和终态传播共同遵循 §2.1 的项目级锁协议。锁必须在任何任务行锁获取**之前**完成获取，避免锁顺序反转。

**验收要求：把这个场景补入验收矩阵，做真正的并发集成测试**（两个真实并发事务/连接），而不是只测两个串行事务。见 §9.1 行动清单 #2。

## 3. P1：状态语义与调度

### 3.1 `blocked` 不一定代表等待任务依赖

**性质：设计缺口（业务语义）。**

现有解锁条件（设计稿 §5.3）：

```text
if status == Blocked && dependencies_satisfied {
    // Blocked -> Ready
}
```

但既有系统已有 `task_waiting.reason`：

- `needs_info`
- `needs_decision`
- `needs_approval`
- `external_dependency`

这些状态同样对应一个 `blocked` 任务。反例：

```
Task A:
    status = blocked
    waiting_reason = needs_approval

Task B:
    status = completed

A depends_on B
```

B 完成后 `dependencies_satisfied(A) = true`，系统会把 A 从 `blocked` 迁到 `ready`——**但 A 实际上还在等人工审批**。

结论：**任务依赖满足 ≠ 任务所有阻塞原因都已消除**。§5.3 的 `Blocked → Ready` 目前只判断任务依赖，没有判断其他等待条件。

**建议：不要让任务依赖解锁直接拥有 `Blocked → Ready` 的全部决定权**，至少增加一个明确条件：

```text
status == blocked
AND dependency_wait_condition == true
AND all_dependencies_satisfied
AND no_other_active_blockers
```

两个实现方向：

| 方案 | 内容 | 评价 |
|---|---|---|
| A | 在 `task_waiting` 中增加明确的依赖等待语义，区分其他等待原因 | 可行，但每种阻塞机制各自拥有解锁权 |
| B | 引入统一的 **Blocker 聚合判定**，任务只有所有阻塞条件消除后才能进入 `Ready` | **评审推荐** |

推荐方案 B 的理由：未来很可能继续增加阻塞来源——等待人工审批、等待外部系统、等待其他 Agent、等待资源、等待任务依赖。不应让每种阻塞机制分别拥有自己的状态解锁权（这与 §4.2 的统一解锁抽象互为表里）。

### 3.2 `dependency_unmet` 可能消耗完 Run 的重试次数

**性质：实现风险，需核实 `release_back` 的具体实现。**

设计稿 §5.2 的链路：

```text
依赖未满足
    ↓
release_back
    ↓
dispatch_attempts + 1
    ↓
指数退避
```

风险场景：

```text
Task A 依赖 Task B
A 已经 Ready，B 还在 Running

第 1 次扫描：dependency_unmet
第 2 次扫描：dependency_unmet
第 3 次扫描：dependency_unmet
...
若 dispatch_attempts 受最大尝试次数限制：
dependency_unmet → 达到最大尝试次数 → Run 被判定耗尽
```

**依赖未满足不是执行失败，不应该消耗执行重试预算。**

设计稿 §5.2 已声明「不把 Run 判失败、不写 `task_run_failure`」，但还不够，必须核实 `release_back` 的具体实现：

- [ ] 是否有最大尝试次数（`max_attempts`）？
- [ ] 是否会将 Run 转成 `dead` / `failed`？
- [ ] 是否会影响后续重新派发？
- [ ] 是否会产生失败审计？

**建议区分两类计数：**

| 计数 | 含义 |
|---|---|
| `dispatch_attempts` | 真正的执行领取尝试 |
| `dependency_defer_count` | 因依赖未满足而延迟的次数（仅观测用，不参与失败判定） |

更明确的目标语义：

```text
dependency_unmet
    ↓
Run 保持 queued
    ↓
设置 next_attempt_at
    ↓
不消耗执行失败预算
```

若当前 `release_back` 已允许无限退避且不触发最大尝试次数，则风险较低——**但必须由代码和测试证明**，不能靠声明。

## 4. P1/P2：终态语义与治理

### 4.1 `failed` 为什么不算依赖满足？后续如何恢复？

D5 把 `{completed, cancelled, superseded}` 算满足，`failed` 不算。当上游 `failed` 时，下游将**永久等待**——因为上游已进入终态，不会再触发一次正常的完成事件。

虽然可以删除依赖边，但这相当于人工修改工作流，不是产品化的恢复路径。

**建议明确四种上游状态的不同语义：**

| 上游状态 | 下游行为 | 含义 |
|---|---|---|
| `completed` | 满足 | 正常完成 |
| `cancelled` | 满足**或人工裁决** | 取决于业务规则 |
| `superseded` | 满足**或人工裁决** | 被替代是否意味着交付完成？ |
| `failed` | 不满足 | 前置任务执行失败 |

尤其是 `cancelled` 和 `superseded`，**不一定天然等价于交付完成**。反例：

```
A：设计数据库架构
B：实现数据库架构

A 被取消，并不意味着 B 可以直接执行。
```

**建议：**

1. 保留当前 D5 作为 **v1 的明确策略**，但把它视为**业务策略**，而不是状态机的天然属性（在文档中显式标注这一点）。
2. 为未来保留扩展空间（v1 不实现）：

```rust
enum DependencyCompletionPolicy {
    RequireCompleted,
    AnyTerminal,
    CompletedOrSuperseded,
}
```

3. **必须明确 `failed` 之后的人工处理路径**，否则永久阻塞只是被隐藏起来：
   - 重新执行上游；
   - 删除依赖边；
   - 人工豁免依赖；
   - 将上游替换成新的任务。

### 4.2 依赖解锁需要区分自动解锁与人工解锁

当前解锁行为是「上游进入终态 → 依赖满足 → `Blocked → Ready`」一条直路。但任务可能因其他原因进入 `blocked`（§3.1）。

**建议把解锁动作抽象为独立的领域操作：**

```rust
try_unblock_task(tx, task_id, trigger)
```

```rust
enum UnblockTrigger {
    DependencySatisfied,
    WaitingConditionResolved,
    ManualOverride,
}
```

内部统一检查：

1. 当前任务是否处于 `blocked`；
2. 所有依赖是否满足；
3. 是否还存在其他有效阻塞原因；
4. 是否允许进入 `ready`；
5. 是否需要产生 `TaskReady`。

这样未来增加审批、外部事件、人工干预时，不需要不断修改 `unlock_downstream`。

**边界建议：不要把 `unlock_downstream` 做成未来所有解锁场景的总入口**——它应该只负责「发现受影响的下游任务」，统一解锁判定交给 `try_unblock_task`。

### 4.3 终态迁移入口可能不止两个

实施记录（§10.2 偏差 1）已确认两个入口：

- `apply_task_transition`（命令通道）
- `pm_write::update_task`（UI 直写历史路径）

这是正确的偏差修正。但建议**进一步全量检查所有修改 `delivery.task.status` 的代码**，候选入口：

- [ ] UI PATCH（已覆盖）
- [ ] Agent 命令
- [ ] 系统自动迁移
- [ ] 管理员操作
- [ ] 任务导入
- [ ] 后台补偿任务
- [ ] 数据修复脚本

否则可能出现：

```
通过命令完成任务     → 正常解锁
通过 UI 完成任务     → 正常解锁
通过另一个后台入口完成任务 → 没有解锁
```

这类「某条路径漏了副作用」的问题非常难排查——症状（下游永久 blocked）与根因（入口漏接）在代码上相距很远。

**建议固化为架构约束：**

> 所有可能使 Task 进入终态的业务写入，都必须经过统一的终态副作用处理机制（依赖解锁、审计、Outbox）。禁止业务代码直接 `UPDATE status` 绕过。

并且**最好落实成代码层的约束**（如：终态 UPDATE 只允许出现在唯一模块、lint/测试断言其余路径不可达），而不只是文档约定。

### 4.4 删除依赖边的审计和语义还不够完整

当前 DELETE 幂等（不存在也返回 204）是合理的。但审计维度建议补齐：

- [ ] 删除边时是否记录**删除前的完整关系**（而非只有 `depends_on_task_id`）？
- [ ] 是否记录**操作者及删除原因**？
- [ ] 是否区分**人工删除与系统自动删除**？
- [ ] **删除边导致解锁时，解锁审计能否关联具体删除动作？**

最后一点最关键。反例：B 原本依赖 A、C；删除 A → B；B 因 C 已完成而解锁。未来追踪时应该能回答：

> **为什么 B 在这个时间点变成 Ready？**

建议解锁审计记录（字段示意，重点是让解锁具有可追溯性）：

```json
{
  "trigger": "dependency_removed",
  "changed_dependency": "A",
  "remaining_dependencies": ["C"],
  "satisfied": true
}
```

## 5. P1：租户隔离需核实 RLS

**性质：实现风险。** DDL 有 `tenant_id UUID NOT NULL` 与：

```sql
FOREIGN KEY (tenant_id, project_id) REFERENCES core.project (tenant_id, id)
```

这能保证**项目归属关系**，但**有 `tenant_id` 列 ≠ 自动具有租户隔离能力**。

核实清单（对照 T-021b 与 ADR-0001 的实际 RLS 约束）：

- [ ] `task_dependency` 是否启用了 RLS？
- [ ] 是否存在正确的租户隔离策略（policy）？
- [ ] 应用数据库角色是否能够绕过 RLS？
- [ ] 递归 CTE（§4.2 检环）是否严格限定 `project_id`？
- [ ] GET upstream/downstream（§4.1）是否同时限定 `tenant_id`？
- [ ] 直接访问边表时是否可能跨租户读取？

**特别提醒：新增边表不能只因为它加入了 `tenant_schema.rs` 的表清单（§10.1：39 → 40，XT-3 机械断言），就认为数据库隔离已经完整。** 表清单断言只证明「表被登记」，不证明「策略正确生效」。

## 6. P2：数据模型与接口演进

### 6.1 依赖边缺少业务级类型

当前边只有 `task_id` / `depends_on_task_id`，表达的是「**B 必须等待 A**」。**对 v1 足够。**

未来可能需要的类型：

- **强依赖**：上游必须完成；
- **弱依赖**：上游失败也可以继续；
- **条件依赖**：满足某个结果才继续；
- **替代依赖**：多个上游满足其中一个即可。

**不建议现在就增加复杂的依赖类型**，但可以考虑预留：

```sql
dependency_type TEXT NOT NULL DEFAULT 'required'
```

是否现在增加，取决于近期需求。若目前确定所有依赖都是 AND 关系，维持现有结构也没有问题。

### 6.2 缺少依赖图的整体查询接口

目前 GET 返回单任务视图：

```json
{ "task_id": "...", "upstream": [], "downstream": [] }
```

单任务查询没问题。但在 AI 研发管理平台中，依赖图通常需要：

- 查看整个任务依赖图；
- 查看某任务的完整上游链；
- 查看某任务的完整下游链；
- 查找阻塞某任务的根因；
- 查看任务是否处于可执行路径上。

建议未来增加：

```text
GET /v1/pm/projects/{project_id}/dependency-graph
GET /v1/pm/tasks/{task_id}/dependency-chain
```

不建议现在为这些需求修改 v1，但**数据查询层最好考虑递归查询的可复用性**——设计稿 §4.2 的检环 CTE、§5.1 的判定 SQL 与未来的链路查询共享递归骨架，宜抽取复用，避免各自复制一份图遍历。

### 6.3 缺少大规模解锁的处理策略

当前解锁链路：

```text
上游完成
    ↓
查询所有下游
    ↓
ORDER BY task_id 加锁
    ↓
逐个解锁
```

小规模依赖图没有问题。但假设：

```text
A
├── B1
├── B2
├── B3
...
└── B10000
```

完成 A 时需要一次性锁定并处理 10000 个任务，可能造成：

- 事务时间过长；
- 锁竞争；
- Outbox 大量写入；
- 其他任务领取延迟；
- 数据库连接占用。

**v1 可以保留同步事务解锁**——它有很好的原子性。但建议：

1. **设置明确的规模假设**（单个上游允许的下游数量上限），写入设计文档；
2. **监控三个指标**：`dependency_unlock_count`、`dependency_unlock_duration`、`dependency_unlock_failures`。

未来如果需要异步批量解锁，应该设计**可靠的补偿机制**（失败重试 + 最终一致核对），**不能简单把事务拆开**——拆开就放弃了「状态迁移与事件写入原子」这一既有保证（见 §8 保留原则）。

## 7. 测试增补建议（C59–C68）

现有 C43–C58 覆盖了基本功能，但**主要是正常流程测试**。真正需要补的是**并发与异常场景**：

| 编号 | 场景 | 预期 |
|---|---|---|
| C59 | 两个事务同时建立反向依赖 | 至多一个成功，不能形成环 |
| C60 | 建边与上游完成并发发生 | 最终下游必须解锁 |
| C61 | `blocked` 任务同时存在 `needs_approval` | 依赖满足后仍保持 `blocked` |
| C62 | `dependency_unmet` 超过普通重试上限 | 不消耗执行失败预算 |
| C63 | 上游 `failed` | 下游保持阻塞，存在明确恢复路径 |
| C64 | 多个上游并发完成 | 只产生一次有效解锁 |
| C65 | 删除依赖与上游完成并发 | 不发生漏解锁或错误状态迁移 |
| C66 | 不同租户访问边表 | 无法读取或修改其他租户的数据 |
| C67 | 大量下游同时解锁 | 事务耗时和锁竞争在约定范围内 |
| C68 | 所有终态写入入口 | 都触发一致的解锁副作用 |

**其中 C59、C60 是最重要的两个**——对应 §2 的两个 P0，现有验收记录完全没有覆盖。

**测试方法论要求**：使用**两个独立数据库连接 + 显式事务屏障（barrier）**来构造并发场景——两个事务各自开启、各自执行到关键点、用屏障对齐后再各自提交——**而不是依靠测试随机碰撞**。随机碰撞式并发测试不可重复、不可调试，无法作为验收证据。

## 8. 值得保留的设计（不要为修复而推翻）

并不是所有地方都需要修改。以下决策经评审确认正确，**不建议为了修复上述问题而推翻**：

| 设计 | 结论 | 原因 |
|---|---|---|
| 独立 `task_dependency` 边表 | 保留 | 关系与等待原因分离，职责清楚 |
| 禁止跨项目依赖 | 保留 | 避免项目之间出现复杂的生命周期耦合 |
| 数据库复合外键 | 保留 | 将项目归属约束下沉到数据库 |
| 写边时递归 CTE 检环 | 保留 | 比每次调度时检查图结构更合理 |
| 领取时动态检查依赖 | 保留 | 执行资格由调度层统一裁定 |
| 复用 `TaskReady` Outbox | 保留 | 不需要另外引入执行派发机制 |
| 解锁与状态迁移同事务 | 保留 | 避免状态已经 Ready，但事件没有投递 |
| Model A / Model B 分开处理 | 保留 | 指定任务领取和后台扫描的调度语义不同 |
| 终态集合统一定义 | 保留 | 避免多个地方各自定义依赖满足条件 |

特别是这个设计：

```text
TaskReady = 进入执行队列
Claim     = 真正获得执行资格
```

**值得作为整个 AI PM 执行系统的长期架构原则**。由此推论：不要把依赖判定塞进 `TaskReadyHandler`——执行资格归领取侧，与设计稿 §5.3 的既有裁定一致。
