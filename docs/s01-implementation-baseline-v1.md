> 文档性质：正式实施总基线

> 状态：实施基线裁决已确认；I6-B V1.1 合并及 Migration 冻结仍为实施前置门槛

## 0. 基线目的

S01 的目标是将 AI-PM 平台现有设计、代码事实、数据库结构、技术裁决和产品 UI 统一成可执行、可验证、可追溯的实施基线。

本基线不是重新设计平台，而是：

1. 保留已经确认的架构和业务决策。
2. 以真实代码和数据库为依据，纠正设计假设。
3. 将已确认的专家裁决落实到设计正文。
4. 明确需要新增的 Migration、API、Worker 和 UI。
5. 建立 TASK 与实施、测试、验收之间的追溯关系。
6. 防止 Codex 或其他 Agent 自行改变已经冻结的设计。

## 1. 基线优先级

发生设计冲突时，按以下顺序处理：

1. 用户已经明确确认的最终裁决。
2. 已确认的架构决策及 ADR。
3. 已确认的专项设计稿和专家裁决。
4. 实际代码、Migration 和生产调用链核验结果。
5. S01 正式实施基线。
6. 尚未确认的设计候选及实施方建议。

特别说明：

- 代码事实用于证明现状，不代表现状一定正确。
- 设计稿用于定义目标，不代表目标已经实现。
- Agent 的分析结论不自动成为正式事实。
- 未经用户确认的 P0/P1 业务规则不得由实施方自行决定。

## 2. S01 实施范围

S01 采用 I1～I6 六个既定设计工作域作为专项实施依据。

各工作域必须独立维护设计、代码核验、任务及验收证据，不得因为跨域依赖而混淆各自的业务责任。

实施要求：

- 先完成设计与代码对齐。
- 再完成数据模型和事务边界。
- 再完成应用服务与接口。
- 再完成 Worker、MCP 和前端接入。
- 最后完成跨域集成及验收。

具体 TASK 的顺序以任务依赖关系为准，不人为假定 I1～I6 必须完全串行。

## 3. 代码事实基线

### 3.1 I6-A 代码核验基准

核验对象：

- 仓库：`ai-pm`
- Git 基线：`master aaee6e5`
- Migration：0001～0028
- 核验报告：I6-A V1.0
- 核验清单：I6-A-001～115

重要事实：

1. `discovery.discovery_session` 已存在，不能重新设计为尚不存在的新表。
2. `discovery.discovery_finding_repository` 已存在且有真实读写。
3. `repo_import` 不存在 `source` 列，`WEB` 属于 `discovery_session.source`。
4. Source 不具备独立状态字段。
5. 多仓数据模型已支持，但现有执行流程存在首个仓库失败即中止的问题。
6. Import 失败、取消、驳回及 Worker 无人认领等路径存在 Project 初始化状态恢复缺陷。
7. Import 的取消状态存在被 Worker 后续写入覆盖的风险。
8. Repository、Finding 和跨项目归属存在需要数据库约束或业务修复的边界问题。

### 3.2 核验等级

所有实施事项必须标注：

- `[FACT]` 已由代码或 Migration 证实。
- `[PARTIAL]` 部分证实，仍有核验工作。
- `[MISSING]` 已确认不存在。
- `[DEFECT]` 已确认存在缺陷。
- `[NEW]` 需要新增实现。
- `[DECIDED]` 已经正式裁决。

I6-A 空库初始化仍有实测缺口，不能把目录级 Migration 核验等同于真实空库迁移验收。

### 3.3 现有能力保护原则

已有生产链路优先修复、扩展和复用。

不得仅因为新设计稿采用不同命名或抽象，就重复创建：

- Discovery Session
- Finding Repository 关联
- 现有 Import 和 Job 机制
- 已有知识提案状态机
- 已有 REST/MCP 服务入口

## 4. I6-B 最终技术裁决

### 4.1 D-1：重试与草案版本

正式决定：采纳 D-1a。

规则：

1. `draft_ready` 状态允许重试失败的 Source。
2. 重试成功后，必须重新生成草案。
3. `draft_revision` 增加 1。
4. 原有草案不得被覆盖，应保留版本和追溯关系。
5. Import 进入 `proposed` 后禁止重试。
6. 如果需要重新分析，必须按照已确认的终止及重新创建流程处理。

验收要求：

- draft_ready 下重试成功。
- 新草案包含最新成功 Attempt 的材料。
- 旧草案可追溯。
- revision 正确递增。
- proposed 状态下重试被拒绝。
- 并发重试不会产生多个有效草案版本。

### 4.2 D-2：Evidence 同项目约束

正式决定：采纳 D-2a。

采用数据库级约束，不仅依赖应用层检查。

涉及三处数据：

**discovery_finding**

- 增加 `project_id`。
- 从所属 Discovery Session 获取并回填。
- 增加 `UNIQUE (tenant_id, project_id, id)`。

**repo_import**

- 使用已有 `project_id`。
- 增加 `UNIQUE (tenant_id, project_id, id)`。

**Evidence**

- 增加 `project_id NOT NULL`。
- Finding 外键包含 `tenant_id, project_id, finding_id`。
- Import 外键包含 `tenant_id, project_id, import_id`。
- 两条外键分别引用对应的组合唯一键。

同时保留 Source 归属约束：

`UNIQUE (tenant_id, import_id, repository_id)`

该唯一键是 Attempt/Evidence 组合外键的前置条件。

验收要求：

- 同租户跨项目 Finding 引用必须失败。
- 不同租户引用必须失败。
- 缺失父记录必须失败。
- 正确项目归属的 Evidence 必须成功创建。
- 历史数据回填必须验证完整性。
- Finding、关联关系、Evidence 和审计记录必须保持同一事务。

### 4.3 I6-B V1.1 必须合并的内容

将专家裁决 C-1～C-4、N-1～N-5，以及边界评审 R-3-1～R-6-2 合并到 V1.1 正文。

特别要求：

- Project 初始化占有和释放检查影响行数。
- 删除测试专用的绕过操作归属路径。
- 单 Active 初始化操作由数据库部分唯一索引保证。
- generation 采用操作表权威与 Project 行锁。
- Attempt 保存每轮 facts、计数及错误信息。
- Source 保存固定 Commit 基准。
- 增加 Source 三列组合唯一键。
- Evidence 增加代码与非代码判别 CHECK。
- D-1、D-2 正式进入状态机、表结构和验收标准。
- 增加 I6-B-036～051 验收项。

### 4.4 Migration 冻结规则

I6-B V1.1 正文合并完成后，必须经过：

1. Migration 顺序审查。
2. 外键依赖审查。
3. 唯一键及 CHECK 审查。
4. 事务和并发审查。
5. 空库迁移测试。
6. 升级路径和环境一致性测试。

未通过以上检查，不得宣称 Migration 已冻结。

## 5. 跨域实施约束

### 5.1 数据库

- Migration 是数据库结构的正式变更依据。
- 不允许通过应用层假设代替数据库完整性约束。
- 多租户归属必须有明确的数据库和服务端保障。
- 并发控制优先使用数据库事务、行锁、唯一约束。
- 所有关键状态迁移必须具备明确的合法条件。
- 失败操作必须保证事务一致性。

### 5.2 API 与 MCP

REST 和 MCP 必须遵循相同领域业务规则。

禁止：

- REST 有权限检查而 MCP 没有。
- MCP 使用另一套状态机。
- 不同入口对同一操作产生不同业务结果。
- 通过 MCP 绕过人工审批和权限限制。

### 5.3 Worker 与 Agent

- Worker 是后台任务的执行者。
- Agent/Codex 是具体任务的执行者。
- MCP 是 Agent 与平台交互的通信接口。
- 平台负责授权、调度、状态、审批和正式记录。
- Agent 的自然语言输出不能直接成为正式业务事实。

多 Agent 可以并行执行，但知识正式写入必须经过统一协调。

### 5.4 状态与历史

必须区分：

- Project 与 Task。
- Task 与 Run。
- Run 当前状态与历史执行记录。
- Discovery Session 与 Import。
- Source 与 Attempt。
- 草稿、提案与正式知识。

重新执行不得覆盖历史 Run。

## 6. UI 正式设计基线

唯一视觉基线：

《AI-PM 高保真设计系统 V1.0》

### 6.1 全局规范

- 桌面端优先。
- 默认深色主题，支持浅色主题。
- 顶栏 52px。
- 左侧导航 232px，可折叠。
- 右侧上下文栏 320px，可隐藏。
- 中央工作区自适应。
- AI Workspace 模式使用底部 AI 指令栏。
- 传统 Page 与 AI Workspace 并存。

### 6.2 首批页面

1. Project Dashboard
2. Repository Management
3. Discovery Workspace
4. AI Execution Center
5. Knowledge Review Center
6. Development Environment

项目初始化属于 Project Dashboard 内的阶段流程，不新增独立 Import 一级菜单。

Repository Management 是持续存在的仓库管理页面，不是一次性初始化向导。仓库关联、用途、访问状态、分支及后续维护都需要在这里管理。

但它不应取代项目总控台成为整个工作台的核心入口。

### 6.3 页面实施顺序

首先交付 Project Dashboard。

随后沿用同一设计系统扩展其他页面，不允许每个 TASK 自行设计一套 UI。

所有页面必须明确：

- 当前业务对象。
- 当前业务状态。
- AI 建议与正式事实。
- 用户可执行的操作。
- 操作权限。
- 失败与冲突状态。
- 相关执行证据。

禁止将 Mock 数据包装成真实后端能力。

## 7. TASK 实施管理规范

每个正式实施 TASK 必须具有：

| 字段 | 要求 |
|---|---|
| TASK ID | 唯一编号 |
| 设计依据 | 关联正式设计稿 |
| 代码事实 | 说明现有实现 |
| 实施范围 | 明确新增、修改、删除 |
| Migration | 关联数据库变更 |
| API | 关联 REST/MCP |
| Worker | 关联后台执行 |
| UI | 关联页面及组件 |
| 测试 | 明确单元、集成和并发测试 |
| 验收 | 可复现的验收条件 |
| 依赖 | 明确前置 TASK |
| 证据 | 提交、测试报告、运行结果 |

### 实施纪律

1. 一个 TASK 有明确的业务边界。
2. 不允许一个 TASK 顺便修改无关模块。
3. 不允许跳过前置依赖。
4. 不允许未经裁决改变已冻结设计。
5. 发现代码事实与基线冲突，先提交差异。
6. 发现新的 P0/P1 问题，先暂停受影响范围。
7. 所有完成状态必须有测试或运行证据。

## 8. 统一验收体系

S01 采用五级验收。

**L1：代码验收**

- 编译通过。
- 静态检查通过。
- 代码结构符合架构约束。

**L2：数据库验收**

- Migration 执行成功。
- 外键、唯一键和 CHECK 生效。
- 事务回滚正确。
- 并发约束正确。

**L3：接口验收**

- REST 正常。
- MCP 正常。
- 权限与租户隔离正确。
- 错误码和业务错误映射正确。

**L4：业务流程验收**

- 正常流程。
- 失败流程。
- 重试流程。
- 取消流程。
- 恢复流程。
- 并发流程。

**L5：UI 与端到端验收**

- 页面符合统一视觉基线。
- 前后端状态一致。
- 真实数据可展示。
- 操作可以实际执行。
- 历史记录和证据可追溯。

不能以 L1 通过代替整个 TASK 完成。

## 10. 正式变更管理

S01 冻结后，任何变更必须提交：

- 变更原因。
- 影响的业务规则。
- 影响的数据库结构。
- 影响的 API/MCP。
- 影响的 Worker。
- 影响的 UI。
- 兼容性分析。
- 测试及迁移方案。

变更分为：

- P0：数据完整性、安全、租户隔离、状态机重大错误。
- P1：核心业务规则或执行链错误。
- P2：一般功能增强。
- P3：视觉、体验及非关键优化。

P0/P1 必须经过正式裁决，不能由 Codex 自行决定。
