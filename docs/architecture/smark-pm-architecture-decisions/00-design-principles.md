# 设计原则与架构边界

**文档编号：** ARCH-PRINCIPLES\
**状态：** 已确认基线\
**基线日期：** 2026-11-20

## 1. 产品定位

smark-pm 是面向小型、紧密协作的软件研发团队的 AI 研发项目管理平台。

平台的目标不是将传统大型企业项目管理流程完整数字化，而是为团队和 AI
Agent
提供共享上下文、清晰的信息路由、可追溯的决策记录，以及必要的通知与协作支持。

## 2. 团队协作假设

系统设计基于以下团队现实：

-   团队规模较小，成员之间沟通直接、协作紧密。
-   团队成员通常具备复合能力，同一成员能够承担项目管理、产品管理、需求分析、技术判断、开发和测试等工作。
-   成员可以通过线下或即时沟通直接协商，不需要系统为每个普通事项设置多层审批。
-   不应将人员僵化地划分为大量专业岗位，再通过复杂会签流程完成日常工作。

因此，系统应避免引入不必要的审批层级、多人会签、投票机制、委员会和形式化工作流。

### 2.1 小型紧密研发团队的设计原则

smark-pm 不照搬大型企业的项目管理体系。后续设计遵循：

1. **不按岗位切割能力**：一个成员可以同时承担项目管理、产品管理、需求分析、技术判断、开发和测试工作。（Product Owner 不是专业岗位，而是生命周期决策与末位保护的治理身份，见 PA 基线 §3/§4。）
2. **不建立不必要的审批层级**：不因为事项涉及多个 Product，就强制多人审批或跨 Product 会签（PA-03-03）。
3. **系统负责记录，不代替团队协商**：复杂讨论可以在线下完成，系统记录最终决定及其依据（PA-03-04：决策完成记录决策人/时间/内容，其他成员无需再确认）。
4. **AI 优先承担分析与授权范围内的执行**：发现问题、整理背景、分析影响、提出方案，并在已确认目标和约束内自主执行与交付验收（PA-06-01/04/05），而不是把大量分析工作转交给人类。
5. **人类处理真正需要人类判断的事情**：业务目标冲突、需求取舍和重要方向决策（PA-04-02），以及重大风险、不可逆操作、安全风险和数据丢失（PA-06-06 §8.4）。
6. **共享优先，重复最少**：需求、设计、任务和技术知识尽可能通过关联复用，而不是复制出多套管理对象（PA-04/PA-05）。

换言之，smark-pm 是一个帮助每个人高效管理和推进研发工作的 AI 协作系统，而不是一个要求员工按照组织流程逐级办事的审批系统。

### 2.2 待确认事项（OPEN）

- **客户侧参与未建模**：团队成员会直接跟客户谈需求并验证开发结果，但客户身份（外部参与者）、客户来源需求的录入与反馈通道，在本文件集与 PA 基线中均未定义。待产品裁决，不得擅自实现。

## 3. AI 与人类的职责原则

-   AI Agent 负责分析、提出建议，并在授权边界内自主执行工作。
-   人类主要在关键业务取舍、重大方向变化和确实需要人类判断的事项上介入。
-   应尽可能让 AI 自主完成常规分析、任务组织和执行工作。
-   不应为了"有人确认"而人为增加低价值确认步骤。
-   当事项涉及不同 Product
    的业务目标冲突、优先级取舍或重大范围变化时，Agent
    应提供分析和建议，并请求人类决策，不得擅自替人类作出业务取舍。

## 4. Product 与 Project 的职责边界

### 4.1 Product

Product 是人类业务协作、业务信息分发和日常业务决策参与的边界。

Product 主要维护：

-   业务目标；
-   业务需求；
-   业务规则；
-   Product 范围内的业务活动；
-   与业务取舍有关的人类决策参与关系。

Product Membership
用于确定相关业务信息的路由对象和决策参与者，不等同于普通 Project
知识读取权限。

### 4.2 Project

Project 是 AI Agent
执行研发工作的上下文，也是共享研发资产和技术知识的主要归属边界。

Project 主要维护：

-   研发任务；
-   统一技术知识；
-   技术设计和架构信息；
-   技术决策记录；
-   项目研发活动与执行历史。

技术设计不按 Product 复制。多个 Product 可以共同引用同一 Project
技术设计。

### 4.3 二者关系

-   Product 与 Project 可以多对多关联。
-   Product 维护业务上下文，Project 维护共享研发与技术上下文。
-   Agent 处理需求时，应同时读取相关 Product 的业务上下文和关联 Project
    的技术上下文。
-   Product 成员的业务参与身份，不应被误解为普通 Project
    知识的独立访问隔离机制。

## 5. 协作复杂度控制

系统优先采用简单、可理解、可追溯的规则：

-   能由 Agent 自动完成的常规工作，不要求人类逐项确认。
-   普通进展进入信息流，不默认发送即时通知。
-   决策请求和重要事项应清晰路由给真正相关的人。
-   一位具备相应参与资格的成员即可完成日常决策，不要求全员批准或跨
    Product 会签。
-   通过 Activity History 留下必要记录，而不是把每个动作都变成审批流程。

## 6. 设计审查准则

后续设计应回答：

1.  这项机制是否解决了真实的协作问题？
2.  是否可以由 Agent 自动完成，而不需要人为增加步骤？
3.  是否错误地把 Product 业务边界当成 Project 普通知识隔离边界？
4.  是否引入了不适合小团队的审批、会签或组织层级？
5.  是否保留了足够的决策依据和历史可追溯性？

若某项复杂机制不能带来明确价值，应优先采用更简单的方案。
