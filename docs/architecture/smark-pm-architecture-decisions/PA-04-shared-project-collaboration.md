# PA-04：共享 Project 的研发协作与事项归属

**决策编号：** PA-04\
**状态：** 已确认\
**基线日期：** 2026-11-20

## 1. 目标

定义多个 Product 共享同一个 Project
进行研发时，需求、任务和技术设计的归属方式，以及 Product
冲突、生命周期变化和研发优先级的处理规则。

核心原则是：业务上下文归 Product，研发执行与共享技术资产归
Project；共享实现只维护一份，不因 Product 数量而复制任务或技术文档。

## 2. PA-04-01：需求与任务归属

### 已确认规则

-   需求归属一个或多个 Product。
-   研发任务归属 Project，不强制直接绑定 Product。
-   任务可以关联一个或多个需求，通过需求关系识别任务服务的 Product。
-   允许没有需求关联的 Project 公共技术任务。
-   共享研发实现只建立一份任务，不按 Product 重复创建。

### 设计含义

一个任务可以同时实现多个 Product 的需求。任务的执行上下文属于
Project，业务目标和验收约束则来自其关联需求。

## 3. PA-04-02：多 Product 需求冲突

### 已确认规则

当多个 Product 的需求发生冲突时：

-   Agent 识别冲突；
-   Agent 分析影响、技术代价和可选方案；
-   如果冲突涉及业务目标、优先级或业务取舍，必须交由人类决策；
-   Agent 不得自行选择优先满足哪个 Product；
-   如果只是纯技术实现问题，且不改变已确认业务要求，Agent 可以自主处理。

### 边界

Agent
可以提出技术方案和影响分析，但不能把技术便利性擅自转化为业务优先级决定。

## 4. PA-04-03：Product Abandoned 对任务的影响

### 已确认规则

  ------------------------------------------------------------------------------------------------------
  任务情况                            Product Abandoned 后的处理
  ----------------------------------- ------------------------------------------------------------------
  只服务该 Product 的未完成任务       停止主动推进，保留任务和历史，等待人类重新评估；不自动关闭或取消

  同时服务 Active Product 的任务      可以继续执行，但需重新评估目标和验收标准；不再以已放弃 Product
                                      的目标作为当前约束

  Project 公共技术任务                不因单个 Product 放弃而直接受到影响
  ------------------------------------------------------------------------------------------------------

其他规则：

-   Product 重新启动，不意味着其历史任务自动恢复执行。
-   是否恢复历史任务，应根据当前目标和上下文重新评估。

## 5. PA-04-04：需求变更与共享任务验收

### 已确认规则

-   需求变更只修改对应需求，不自动修改其他 Product 的需求。
-   Agent 分析需求变更对共享任务及其他关联需求的影响。
-   共享任务完成时，必须满足所有关联 Active Products 的有效需求。
-   Abandoned Product 的需求不再构成当前验收约束。

### 设计含义

共享任务不能只因某一个 Product 的需求已满足就被判定完成；但已放弃
Product 的旧需求也不能继续无条件阻塞当前共享任务。

## 6. PA-04-05：技术设计归属

### 已确认规则

-   技术设计以 Project 为主要归属。
-   同一技术设计可以被多个 Product 的需求共同引用。
-   不按 Product 复制技术设计。
-   Product 维护业务目标、需求和业务规则。
-   Project 维护统一技术知识、架构设计和技术决策记录。
-   Product 引用 Project 技术设计，不建立 Product 私有技术设计副本。
-   Agent 同时读取 Product 业务上下文和 Project 技术上下文。
-   技术知识变化时，Agent 分析受影响的 Product。

## 7. PA-04-06：技术设计变更

### Agent 可自主处理

-   普通实现细节调整；
-   不改变需求约束的重构；
-   不影响其他 Product 有效需求的技术优化；
-   已批准设计范围内的实现调整。

### 需要人类决策

-   改变已确认的架构方向或设计约束；
-   影响多个 Product 的有效需求或验收标准；
-   涉及重要业务目标、成本或交付范围取舍。

### 组织与决策边界

-   不设置专职架构师审批角色。
-   Product Owner 不垄断技术决策。
-   不要求每个 Product 分别批准。
-   一位有资格的 Product Member 决策即可。
-   普通技术调整只需留下适当记录，不制造审批负担。

## 8. PA-04-07：技术知识共享

### 已确认规则

-   Project 统一维护技术知识、架构设计和技术决策。
-   Product 维护业务知识。
-   Product 通过关联关系引用 Project 技术设计，不复制正文。
-   Agent 分析需求时，同时读取 Product 业务上下文和 Project 技术上下文。
-   技术知识变化时，由 Agent 分析受影响的
    Product，不要求人工逐个维护副本。
-   不建立 Product 私有技术知识副本。

## 9. PA-04-08：研发优先级

### 已确认规则

-   Agent 可以自主安排普通研发任务。
-   调度时考虑依赖、风险、紧急程度、已确认交付目标和执行资源。
-   多 Product 出现实质性资源竞争时，Agent 分析并提出建议。
-   必要时，请相关成员中的任意一人决定优先级。
-   人类可以直接调整任务优先级，Agent 应遵循明确指示。
-   不设跨 Product 优先级委员会或复杂排期审批。

## 10. 端到端协作原则

1.  Product 提供业务目标、需求和业务规则。
2.  Project 提供统一研发上下文、任务执行环境和技术知识。
3.  Agent 将需求映射到共享研发任务，并维护明确关联。
4.  Agent 自主处理不改变业务约束的普通技术工作。
5.  对业务冲突、重大设计变化或实质性资源竞争，Agent
    提供分析并请求人类决策。
6.  任务验收以所有关联 Active Product 的有效需求为准。
7.  Product 生命周期变化不应破坏共享 Project 的其他有效工作。
