# 甲部分：Product / Project 成员权限模型

## 1. Product 成员与 Project 成员的权限关系 〔CONFIRMED〕

1. **Project 成员自动成为该 Project 所有关联 Product 的成员**（经 P4-02 Link active 关系传播；独立 Project 无此传播）。
2. **Product 成员可以只读访问该 Product 的全部直接关联 Project**。
3. 只读访问范围为**完整只读**，包括：
   - Project 详情；
   - 需求；
   - 设计；
   - 技术认知；
   - 任务；
   - 项目其他普通业务内容。
4. **Product 成员身份本身不授予**：Project 修改权、任务操作权、正式认知确认权。
5. **成员资格传播只允许单层，不递归**：
   - Project 成员 → 直接关联 Product 的成员；
   - Product 成员 → 该 Product 直接关联 Project 的完整只读访问；
   - **不得**通过只读访问的 Project 继续继承其他 Product 的成员资格。
6. 写权限、正式认知确认权、管理权仍维持既有冻结边界（P4-01 DR-06 第 2 条、P4-02 DR-03 交集、H8 人工确认门）——本轮只新增**读面**，不改任何写面。

## 2. Product 成员资格的来源与撤销 〔CONFIRMED〕

Product 成员资格可来自多个**独立来源**：

- **S1** Product Owner 自动来源；
- **S2** Product Owner / Tenant Admin 管理的直接添加来源；
- **S3** 每个关联 Project 的成员继承来源（每 Link 一个来源）。

规则：

1. **任一有效来源存在，用户即为 Product 成员**（来源之间并集，非覆盖）。
2. 用户退出某个 Project，只撤销**该 Project 提供的 S3 来源**。
3. **解除 Product–Project 关联（Link ended）时，自动撤销该 Project 提供的成员继承来源**（人工 end 与 team_dissolved 清扫两种 ended 路径同规则；与 P4-02 DR-02/DR-06 的 ended 语义衔接）。
4. 撤销直接添加来源（S2）或 Owner 来源（S1），**不得撤销**仍然有效的其他来源。
5. Product Owner / Tenant Admin 对 Product 成员名单拥有**直接管理权**（S2 的授予与撤销）。
6. **Tenant Admin 不自动成为 Product 成员**；其管理访问权来自 Tenant Admin 角色本身（对齐 P4-01 DR-06 现状）。
7. **权限取并集**：Product 原有权限与 Product 提供的只读权限取并集，不相互覆盖。
8. **来源失效后访问权立即撤销**；后续请求必须重新检查权限，不得依赖旧会话缓存（与 P4-02 DR-03 补充 B「实时有效授权」惯例一致）。

## 3. Product 成员的只读范围 〔CONFIRMED〕

Product 成员可以**查看**关联 Project 的：

- Agent 执行记录；
- Agent 分析结论；
- Agent 委派关系；
- Token 消耗；
- 预算使用；
- 工具调用记录；
- 执行结果；
- 人工讨论和评论；
- 设计评审；
- ADR 决策过程；
- 任务评论；
- 人工与 Agent 对话记录。

但**不能因此获得**：

- 任务编辑、执行、取消等操作权限；
- Agent 控制权限；
- 预算调整权限；
- 人工讨论或评论的编辑、删除、参与权限；
- 正式认知确认权限。

## 4. 显式可见性限制（默认完整只读的例外）〔CONFIRMED 框架 + 具体策略 OPEN〕

1. **定位**：允许对部分业务内容显式设置额外可见性限制。这是 §1「Product 成员默认完整只读」规则的**例外机制**，不是新权限体系的默认面。
2. **不过度设计**：不为普通业务对象引入过度复杂的权限体系（对齐 AGENTS.md 规则 1 与 P4-01 DR-06「角色爆炸」否决理由）。
3. 框架三要素：
   - **适用范围**：部分业务对象可显式设限〔CONFIRMED：机制存在；哪些对象类型可设限 → 〔OPEN〕〕；
   - **授权主体**：倾向由 Project Owner ∪ Tenant Admin 设置/解除（待裁决）〔OPEN〕；
   - **检查位置**：服务层读取守卫为唯一强制点，搜索 / 索引 / API / 导出同步过滤；禁止只在 UI 层设防（与敏感区 §8 入口检查同构）〔CONFIRMED：单一强制检查点原则〕。
4. 具体策略（对象类型白名单、粒度、继承行为、与敏感区的关系）→ 〔OPEN，见 §13〕。

# 乙部分：敏感区总体架构

## 6. Product 和 Project 分别拥有独立敏感区 〔CONFIRMED〕

1. **KB 和 PC 均支持独立敏感区**；Product KB 与 Project KB 分别拥有自己的敏感区。
2. 每个 Product / Project 敏感区独立管理：
   - 敏感资源；
   - 资源授权；
   - 访问审计；
   - 索引文件（`索引.md`）；
   - 索引生成和更新机制（Index Generator）。
3. **不得将 Product 与 Project 敏感区合并成 Tenant 全局敏感知识库**（保持 P3-11 双域独立权威边界；P3-11 冻结令第 1/11/12 项沿用）。

## 7. 环境分类与敏感等级：两个独立维度 〔CONFIRMED〕

**维度一：环境分类** = Production / Staging / Testing / Development。
**维度二：敏感等级** = Sensitive / Non-sensitive。

默认判断：

| 环境 | 默认敏感性 |
|---|---|
| Production | 默认敏感，**不允许自动降低** |
| Staging | 根据实际内容判断 |
| Testing | 默认非敏感 |
| Development | 默认非敏感 |

约束：

1. **环境不能决定最终敏感等级**：Testing 中存在真实客户数据或生产凭据仍需标记敏感；Development 中存在真实密钥仍需标记敏感；Production 默认敏感。
2. **Product Owner / Project Owner 可以标记或解除敏感标记**。
3. **解除敏感标记必须二次确认并审计**。
4. **Tenant Admin 可以管理授权机制，但不能随意代替领域 Owner 作业务敏感性判断**。
5. **普通 Modify 权限不包含敏感等级调整权**。
6. **降低敏感等级时必须重新检查访问范围**，防止原本受保护的信息因降级自动暴露。

## 8. 敏感资源独立存储与受控引用 〔CONFIRMED〕

**已选定方案：敏感信息独立存储；普通文档只通过受控资源入口引用，不在普通文档中嵌入敏感正文。**

1. 敏感正文写入**独立敏感存储区域**（Product / Project 各自敏感区内）。
2. 普通文档只能引用**稳定的敏感资源 ID**。
3. 普通文档通过**系统生成的受控资源入口**跳转。
4. 用户点击入口后，系统**重新检查该人类用户的 Read 权限**（访问时授权，非引用时授权）。
5. 未授权用户不得看到敏感正文。
6. 无权用户在普通文档中只能看到通用名称：**`受限敏感资源`**。
7. 无权用户**不得看到**原始文件名、服务器名称、文件路径、资源描述、摘要或其他敏感元数据。
8. **不允许**通过复制敏感正文到普通文档来绕过隔离（系统不提供把敏感正文写入普通文档的通道；复制粘贴类绕过属制度约束 + 审计，非主要技术机制）。
9. **不采用**敏感属性在所有复制、引用和衍生文档间传播作为主要安全机制；**以独立存储和访问时授权检查为核心**。

所有访问入口都必须执行权限检查：UI 跳转、搜索、API、下载、导出、及其他可获取敏感正文的系统入口。

**索引隔离**：敏感区不得进入普通 KB 全文搜索索引或普通 PageIndex 索引。Agent、搜索和上下文机制不能绕过敏感资源授权。

## 9. 人类敏感区授权机制 〔CONFIRMED〕

1. Product 和 Project **分别管理各自敏感区的授权人员**。
2. **Product / Project 普通成员资格不自动授予敏感区访问权**（敏感区授权独立于普通成员资格，两套机制不得混同）。
3. **Tenant Admin 拥有授权机制管理权限，但不自动获得敏感内容明文读取权**。

三种独立权限：

| 权限 | 含义 |
|---|---|
| **Read** | 查看敏感正文 |
| **Modify** | 创建、编辑、删除敏感资源 |
| **Use** | 授权系统在特定任务中调用敏感信息，但不向调用方暴露明文 |

规则：

1. 三种权限**独立授予，可组合**。
2. **Use 不等于 Read**。
3. **Modify 不自动包含 Read**。
4. **Modify 不自动包含 Use**。
5. 敏感信息的读取、修改、使用、授权和撤销**均应审计**。
6. 权限来源失效后**立即撤销**，后续请求重新检查权限。

**边界声明**：本轮已明确**普通 Agent 不读取敏感正文**。不得把人类 Use 权限解释成「普通 Agent 已可自动使用生产凭据或其他敏感信息」；Agent 是否能经受控 Use 参与特定自动化任务，另行讨论裁决（〔OPEN，见 §13-O4〕）。

## 10. 普通 Agent 对敏感区的访问边界 〔CONFIRMED，本轮核心架构决定〕

**已选定：敏感区正文不直接向任何普通 Agent 开放。Agent 只能提供受控链接，由人类用户自己点击查看。**

1. 普通 Agent **不读取**敏感正文。
2. 普通 Agent **不把敏感正文放入** Chat 上下文。
3. 普通 Agent **不在 Chat 中展示**敏感正文。
4. 普通 Agent **不创建、编辑或删除**敏感正文，只能提出建议。
5. Agent **不得将敏感正文复制到**：普通文档、任务记录、Agent Memory、普通知识库、对话输出。
6. **不得**通过委派、共享记忆、搜索摘要、其他 Agent 或上下文传递绕过限制。
7. 人类用户点击资源入口后，由系统独立检查**该人类用户**的 Read 权限（与 §8 第 4 条同一检查点）。
8. **不再为普通 Agent 配置敏感正文 Read 权限**（普通 Agent 永远不读取正文，权限对象不存在）。
9. Agent **可以知道敏感区存在**，并查看受控的目录基本信息。
10. Agent **可以搜索**敏感资源目录的受控元数据，但不得读取正文、摘要、文件路径或敏感字段。
11. Agent 搜索目录时**不得返回**敏感资源总数、未授权资源数量，或通过分页、统计等方式泄漏敏感资源分布。
12. **无匹配结果时，不得透露是否存在被隐藏的敏感资源**（防枚举）。
13. Agent 只能提供**系统生成的受控资源入口**，不能构造绕过授权的直接访问路径。

## 11. Sensitive Knowledge Index（`索引.md`） 〔CONFIRMED〕

### 11.1 定位与内容边界

每个 Product / Project 敏感区独立拥有一份 `索引.md`。

1. **定位**：敏感区的概括性目录，也是**普通 Agent 唯一允许读取的敏感区相关知识文件**。
2. 普通 Agent 不读取敏感正文；Agent 只能借助索引判断是否存在所需资源，并向人类用户提供受控入口。
3. **索引可以包含**：敏感资源的通用名称；资源类别；用途；适用环境；稳定资源引用 ID；其他经过脱敏检查允许公开给 Agent 的目录信息。
4. **索引严禁包含**：真实服务器地址；账号密码；Token；Secret；连接字符串；生产环境敏感配置；其他可直接暴露敏感正文或凭据的信息。
5. **索引不得成为敏感正文的摘要副本**。
6. `索引.md` 是目录性受控产物，**不是敏感正文的权威**；敏感正文权威仍在各敏感资源的独立存储及其所属领域规则之下。

### 11.2 Index Generator 〔CONFIRMED 机制定位；实现细节 OPEN〕

索引由**独立的受控机制 Index Generator** 生成和维护，与普通 Agent 严格隔离：

1. Index Generator 可以在**受控条件下**读取敏感正文，用于生成脱敏目录。
2. 普通 Agent **不可调用** Index Generator 获取敏感正文。
3. Index Generator **不得**把原始敏感正文写入普通 Chat、Agent Memory 或普通 KB。
4. Index Generator 的输出**必须经过独立脱敏检查**。
5. **不得**把 Index Generator 的读取能力赋予普通 Agent。

### 11.3 发布方式 〔CONFIRMED：自动发布 + 脱敏检查强制 + Owner 事后检查〕

**已选定：AI 自动生成或更新后直接发布，领域 Owner 事后检查，不要求事先人工审批。** 但自动安全检查为强制步骤：

1. Index Generator 生成候选索引。
2. 系统自动执行**脱敏检查**（发布前强制，不得因自动发布而取消）。
3. 检查是否存在疑似密钥、密码、服务器地址、Token、连接字符串等高风险信息。
4. 检查通过 → 直接发布。
5. 检查失败 → **阻止发布**。
6. 失败时**保留上一份有效索引**。
7. 产生**安全告警**，供领域 Owner 检查。

### 11.4 索引的独立性 〔CONFIRMED〕

- 每个 Product 敏感区独立维护自己的 `索引.md`；每个 Project 敏感区独立维护自己的 `索引.md`。
- Product Index **不自动包含**关联 Project 敏感资源；Project Index **不自动包含**关联 Product 敏感资源。
- **不合并**成跨领域索引。
- Agent 根据当前领域和任务读取对应索引。

### 11.5 版本管理 〔CONFIRMED：方案 B——只保留最新成功发布版本〕

1. 每个敏感区只保留**一份当前有效**的 `索引.md`。
2. 新版本成功生成并通过脱敏检查后，**直接覆盖**旧索引。
3. 不提供索引历史版本查看。
4. 不提供索引变更历史查看。
5. 不提供索引历史回滚。
6. 生成失败或脱敏检查失败时，保留上一份有效索引。

**边界澄清**：这里只是不保留**索引**历史版本；敏感资源**正文**自身仍按其所属领域规则管理版本，两者互不等同。

### 11.6 更新触发 〔CONFIRMED：方案 C——事件触发 + 定期完整扫描〕

**事件触发**：敏感资源新增、修改、删除，以及其他影响索引内容的变化，触发 Index Generator 更新索引。

**定期完整扫描**：系统按固定周期对敏感区执行完整扫描，核对当前资源与 `索引.md` 的一致性，修复遗漏或不一致。

两种机制遵守**同一发布规则**（§11.3）：生成候选索引 → 脱敏检查 → 通过后覆盖当前索引；失败则保留上一份有效索引并产生安全告警。

要求（机制级，〔CONFIRMED〕）：

- 定期扫描的**具体周期尚未裁决**——文档与实现均不得写死具体小时数或天数，标记为**待配置 / 待裁决**〔OPEN，见 §13-O1〕。
- 必须定义事件更新与定期扫描**同时发生时的并发控制**：不得因并发生成导致旧索引覆盖较新的有效索引（候选索引携带单调序，旧候选不得覆盖新有效索引）。
- 必须**幂等**；必须正确处理资源删除；必须定义失败重试与索引一致性要求。
- **不得**把失败的候选索引发布为当前有效索引。

（上述并发 / 幂等 / 失败恢复的**具体实现契约** → 〔OPEN，见 §13-O5〕。）
