## 2. 概念框架与术语

### 2.1 三个认知族（本设计的核心命名）

| 名称 | 载体（现状→目标） | 内容 | 权威 |
|---|---|---|---|
| **PC-P**（产品级正式产品认知） | 现状不存在 → 新建产品认知族，锚定 core.product.id | 产品定位、愿景、业务域、能力、业务规则、产品决策等**跨项目成立的产品真相** | 产品级人工门（Product Owner ∪ tenant admin，DR-08 裁决） |
| **PC-J**（项目级产品域认知） | 现状 pc.*（18 表，项目私有）→ 语义收窄：**保留项目级身份/版本/提案/人工确认/发布的基本机制**，增加来源关系、作用域标识、消费/派生边界约束与 identity 路由分流等增量（增量由独立实施任务包设计，§7.5/§11.1）——「基本机制保留」≠「零结构与契约变化」 | 项目上下文中的产品域知识：派生对象、项目特有对象、局部差异对象 | 项目级人工门（现 A3 闸不变） |
| **ProjC**（项目技术认知） | 现状 projc.* → **完全不动** | 技术架构、技术约定、仓库结构、技术组件 | 项目级人工门（P3-11 冻结链不变） |

命名说明：PC-P / PC-J 为本设计文档的**领域概念名**，非物理表名；物理 schema 形态（同 schema 双锚 vs 独立 schema）见 §11.3，随 DR 裁决。

关键语义：PC-P 与 PC-J 同属 pc 域（同一业务域、同一受控字典来源），但**身份命名空间按作用域分离**——PC-J 对象是独立身份（项目作用域），永远不是 PC-P 对象的项目内副本或代理；产品真相的唯一权威是 PC-P。

### 2.2 与既有术语的衔接

- P3-11 裁决稿的「PC（pc.*）」= 本文的 PC-J 前身 + 未来 PC-P 的机制母版；P3-11 五条权威边界约束的是**域间**（pc/projc/kb）关系，PC-P/PC-J 是**域内作用域分层**，不触犯五条（§9.1 逐条核验）。
- PC 领域模型基线 V1.0 §2.1「Product Cognition 是项目级产品认知管理领域」——本设计对该基线条款提出**显式修订建议**（若方案 C 获裁决）：Product Cognition 领域升级为「产品级权威 + 项目级产品域认知」双层结构。修订随 DR-01/DR-02 裁决生效，不静默覆盖。
- P4-01 DR-03 身份分离裁定原样保持：core.product（主体）≠ 任何认知对象；PC-P 对象以 product_id 为**归属锚**，不是主体身份的延伸。

### 2.3 五类关系分别建模（承审查防错 2，本节为全文纲）

| # | 关系 | 定义 | 方向 | 承载物 | 绝不意味着 |
|---|---|---|---|---|---|
| R1 | **权威归属** | 正式认知由哪个主体唯一维护与确认 | PC-P←Product / PC-J←Project / ProjC←Project | 族锚（product_id / project_id） | 权威不因被引用而转移或共享 |

### 2.4 业务领域 / 协议域标识 / 物理存储——三层概念分离（V1.1 新增，闭合审查 P0-1）

V1.0 将「PC-P/PC-J 同属 pc 域」（§2.1）与「注册表新增 PC-P 目标域枚举值」（§9.1-H2）并置，混淆了三个不同层面。三层定义与关系：

| 层 | 回答的问题 | PC-P | PC-J | 分离/一致关系 |
|---|---|---|---|---|
| **L1 业务领域** | 该认知属于哪个业务域、权威内容如何分类 | 同属 **Product Cognition 业务域**（pc 域） | 同左 | L1 两族**相同**——H1 五条权威边界与 R-03 分流判据在 L1 生效，不受 L2/L3 选择影响 |
| **L2 协议域标识** | DomainRef `target_domain` 如何寻址到该族对象 | **待裁决（DR-02）**，两案见下 | 同左 | **L1 相同 ≠ L2 必须相同**；L2 是协议寻址问题，不是领域归属问题 |
| **L3 物理存储** | schema/表落点 | F1 独立 schema（倾向）/ F2 同 schema 双锚（§11.3，待 DR-02） | 现有 pc.* | L3 跟随 L2 裁决；F1 时 L2/L3 一一对应，F2 时 L2 必须携带作用域判别 |

**L2 两案（均为候选，不预设双域或单域足够）**：

| 案 | 形态 | 对 H2 四字段契约的影响 | 优点 | 代价 |
|---|---|---|---|---|
| **α 双域值（倾向，PROPOSED）** | 新增 PC-P 目标域枚举值（如 `pc_product`）；现 `pc` 值语义校准为 PC-J（项目作用域产品认知） | **零结构变更**——四字段契约原样，仅枚举加值（additive，注册表登记） | resolver 路由 / 权限判定 / 身份唯一性按域值天然分离；PC-J→PC-P 派生引用=跨域 DomainRef（语义成立：DomainRef 描述被引用对象，与业务域归属无关） | 一业务域两个协议值的心智成本（靠注册表注释消解） |
| **β 单域值+作用域判别** | 保留 `pc` 单值，引用记录增加作用域判别（扩展四字段或复用 target_domain 取值如 `pc.product`） | **契约结构变更**——H2 冻结的四字段形态需扩字段或重载语义，涉 O-09 映射重议 | 协议值数量最小 | 与 H2 冻结契约摩擦；全部 resolver/授权/唯一性路径须处理判别符 |

**无论裁决为哪案，必须满足的五项闭合要求**（审查列明，作为 DR-02 的验收判据，直接影响 H2/H3/H6）：

1. **身份唯一性**：(协议域标识, 目标类型, 目标 id/key) 在全系统恰解析到一个对象；PC-P/PC-J 键空间不得产生歧义解析。
2. **Resolver 区分**：domain→schema 路由表（P3-11 裁决稿 §3 先例）必须能按引用记录无歧义路由到 PC-P 或 PC-J 的解析路径。
3. **权限闭环识别目标作用域**：授权判定（PC-P 产品门 vs PC-J 项目门）必须能从引用记录恢复目标作用域——授权检查的输入含作用域。
4. **注册表登记**：两族各自注册表条目与通道状态（PC-P 新条目登记、PC-J 现条目语义校准），协议级加法走注册表 V1.x。
5. **版本引用身份防混淆**：一切钉扎引用（消费/派生/证据）同时携带作用域标识与版本（revision_context），「规则 R v3」类引用不得出现跨族歧义。

## 3. 候选方案完整定义

三方案共用同一组评价维度（§4）与场景集（§5）。方案边界均以「PC-P 是否存在及 PC-J 是否存在」划分。

### 方案 A — PC 继续以 Project 为主体（Product 仅聚合）

- **定义**：不建 PC-P。产品域认知全部保持项目私有（现状 pc.* 原样）；Product（P4-01 主体）仅经 P4-02 Link 聚合关联项目，不承载任何认知权威。
- **「产品认知」语义**：N 个项目 = N 套互不认账的产品域认知集合；「某产品的正式认知」在系统内无单一答案。
- **跨项目一致性**：无机制保障；靠人工流程或产品外过程（如 P4-05 规划域人工协调）维持。
- **AI 多项目归纳**：无落点（无产品级候选承载）。
- **P4-05 Product Plan**：引用「产品正式认知」失义——只能引用某项目某版本，产品级引用模型无法建立。
- **权限**：零新增面。
- **迁移**：零。

### 方案 B — PC 正式认知整体上移 Product（无项目级产品域认知层）

- **定义**：建 PC-P 且**只建 PC-P**：现有 pc.* 的正式产品认知职责整体上移（身份锚 project_id→product_id，或按 §11.3 形态）；项目侧不保留产品域认知层。ProjC 不动。
- **「项目上下文中的产品域知识」**：产品认知域内的正式承载不成立——写入 PC-P 则项目局部内容污染产品权威（范围错位）；写入 ProjC 则违反 R-02/R-03 域界（业务规则属 pc 域）。间接表达（PC-P 反馈提案、交付工件）仍可能，但项目侧无可长期维护、持续演进的认知承载。
- **项目差异化**：无法在产品认知域内以项目为主体建立**独立、持续演进的正式认知对象**。项目差异并非绝对无法表达——仍可经 PC-P 反馈提案或项目交付工件（需求/设计）间接表达——但表达后项目侧无承载，不可作为项目级产品域认知长期维护与演进；任何项目与产品认知的不一致只能整体升级为产品级冲突 → 裁决瓶颈与噪音。
- **消费模型**：项目经授权读 PC-P（钉扎或跟随）；项目不持认知对象。
- **迁移**：pc.* 全面上移；identity 链、bootstrap、close pc 分支全部改锚。

### 方案 C — 分层：产品级权威 + 项目级引用/派生/局部认知（推荐）

- **定义**：建 PC-P（同 B 的产品级权威）；**保留并收窄** pc.* 为 PC-J：项目侧可创建 (a) 项目特有对象（无产品对应）、(b) 派生对象（derives_from PC-P 钉扎版本、内容自有）、(c) 差异表达（R4）；正式反馈经 R5 进 PC-P 确认链。ProjC 不动。
- **权威语义**：产品真相唯一权威 = PC-P；项目真相（项目上下文中的产品域知识）权威 = 项目（经 PC-J 对象承载）；两者是**不同内容**的权威，不存在同一身份双重权威。
- **项目差异化**：一等公民（R3/R4 显式建模，provenance 强制标注，防冒充规则 §7.4）。
- **消费模型**：同 B（钉扎引用 + 授权），另加 PC-J 本地承载。
- **迁移**：B 的全部动作 + PC-J 语义收窄（结构不变、语义与元数据增强）。

**方案取舍判据**（评估基准，非结论）：Phase 4 规划基线目标 4/6（认知权威边界、Product Plan 引用正式认知）；任务书 §二 六项区分是否全部可表达；P3-11 兼容成本；审查防错 1 的问题清单是否全部有解。

## 6. 方案论证与推荐

### 6.1 推荐：方案 C（PROPOSED）

**论证一：排除 A——Phase 4 目标链断裂。**
Phase 4 规划基线目标 6 与 P4-05 切片要求「Product Plan 引用正式产品认知」；任务书 §二 将「多 Project 下产品认知如何共享、派生、反馈、处理冲突」列为本切片根本问题。A 对四者全部给出否定回答，使 P4-01 冻结的 Product 主体沦为纯目录实体（Link + 未来资产关联），P4-05 引用模型失义，P4-00 审计指出的「同一产品 N 个项目 N 份互不认账单例」的语义冲突原样保留。A 是合法的基线保留项（DR 可裁），但与 Phase 4 立项目标不相容。

**论证二：排除 B——项目上下文产品域知识无法获得项目级认知承载。**
项目在实施中形成的产品域上下文知识（如「规则 R 在本项目场景下存在例外 E」「本项目交付的能力子集与产品基线的差异」）是真实、持续产生、有追溯价值的认知。B 下其三个可能去处均不成立（§3 方案 B 定义）：入 PC-P=范围污染；入 ProjC=违反 R-02/R-03 域界；入交付域=工件非认知。精确表述：B 并非使项目差异**完全无法表达**（反馈提案与交付工件仍可间接表达），而是使其**无法在产品认知域内以项目为主体建立独立、持续演进的正式认知对象**——表达即升级，项目侧不留存、不沉淀、不可追溯演进。同时 B 使一切项目↔产品不一致被迫整体升级为产品级冲突，裁决面噪音化（S3/S5/S9 场景 ⚠️）。

**论证三：C 的边际成本有界。**
PC-P 侧 B 与 C 成本相同（产品级族、产品级门、消费授权，一项都省不掉）；C 的唯一增量是 PC-J 语义层——而 PC-J 的载体就是**现有 pc.* 结构**（18 表、机制、测试全部复用），增量仅为 provenance 元数据与语义约束，无新表无新链。C 比 B 贵的部分，恰是 B 的结构性缺陷所在。

**论证四：与 P3-11 的兼容边界最清晰。**
ProjC 链零触碰；PC-J 沿用现有 close 发布链（范围收窄，契约机械语义不变）；PC-P 为独立新链；唯一深度改点=identity 链改锚（§9.3-I1）。相比 B 的「close pc 分支整体悬空」，C 的每处交互都可局部登记、局部裁决。

**独立性声明**：本推荐与 P4-00 §12 曾列的「(a)+(c) 混合」未确认推荐存在趋同，但本文论证独立基于 §5 场景分析与上述四条，不以 P4-00 推荐为依据（其明文不视为已确认）。

## 7. 目标领域模型（方案 C 展开；全部 PROPOSED）

### 7.1 主体与权威归属（答 Q1，DR-01/DR-02 输入）

- **产品正式认知权威 = Product 主体（经 PC-P 族承载）**。PC-P 身份锚 = (tenant_id, product_id)；core.product 为归属锚（P4-01 DR-02 形态），认知对象身份 ≠ 主体身份（P4-01 DR-03 分离裁定保持）。
- **项目上下文产品域认知权威 = Project（经 PC-J 族承载）**；**项目技术认知权威 = Project（projc.*，不动）**。
- 同一认知身份在全系统恰有一个权威；PC-J 派生对象是新身份（项目作用域），与 PC-P 源对象是 R3 派生关系而非同一身份的两个权威。

### 7.2 身份与版本（DR-02/DR-04 输入）

- PC-P 沿用 pc 机制：object（身份）→ cognition_revision（内容寻址修订）→ cognition_version（发布快照，predecessor 链，snapshot_hash 规范哈希）；提案 8 态 + 审阅流 v2 暂记语义 + 发布事务十四步同构（机制镜像，符合红线一「共享技术基础设施模式」）。
- PC-J 保留现有项目级身份、版本、提案、人工确认与发布的**基本机制**；增量=provenance 来源关系、作用域标识、消费/派生边界约束与 identity 路由分流（§7.4/§7.5/§11.1）——「基本机制保留」≠「零结构与契约变化」，具体增量由独立实施任务包设计。
- 版本不可变纪律全域保持；dissolved/archived 不改写任何版本行（§7.9）。

### 7.3 引用与消费模型（答 Q3，DR-03 输入）

- **消费引用 = 对 PC-P cognition_version 的钉扎**（version_no + 快照哈希 + 钉扎时间/执行者）。钉扎是消费的事实记录，不是 PC-P 对象的可变状态。
- 一 Product 多 Project：各项目独立钉扎、独立推进再基线进度；互不影响。
- **跟随最新不是消费形态**：任何读面可展示 PC-P 当前最新（展示≠消费），但以「项目已消费/已派生内容」为依据的一切下游（派生、证据、提案、一致性对比）必须钉扎具体版本。「始终跟随」作为每引用可选项 → DR-04 裁决点（默认否）。
- PC-J→PC-P 的派生钉扎与消费钉扎同一形态（DomainRef：target_domain/target_type/target_id/revision_context + revision_missing_reason 兜底，H2 契约原样）。

### 7.4 派生与局部差异边界（答 Q4，DR-05 输入）

**PC-J 对象三分类**（provenance 元数据强制，创建时定性、不可静默变更）：

| 类 | 定义 | 必备元数据 |
|---|---|---|
| project_original | 项目特有：无产品对应（项目场景独有约定/规则/能力切片） | 无 PC-P 引用 |
| derived | 派生：内容基于 PC-P 某版本，项目侧维护自有演进 | derives_from（DomainRef 钉扎版本）+ 源内容哈希 + 派生者/时间 |
| variant（派生特例） | 派生且内容存在有意差异（局部差异的载体） | derived 全部 + divergence_note（差异声明） |

**防冒充四规则**（答任务书 §3.2 Q7，审查防错 2 落地）：

1. PC-J 对象在任何读面必须携带 `scope=project` + `authority_level=project_context` 元数据；PC-P 读面永不聚合 PC-J 对象（R-08 结果元数据要求的域内执行）。
2. 对象键命名空间按作用域分离：PC-J 对象键不得声明 PC-P 身份（同字典、不同命名空间，身份比较必含作用域）。
3. PC-J 对象无论与 PC-P 内容多相似，**永不进入产品级视图、产品目录、产品检索聚合的产品真相面**（可经显式「项目认知」面检索）。
4. 派生对象的演进只发生在项目侧确认链（A3 门）；向产品的回流只有 R5 一条路。

**与 P4-DP-04「引用不复制权威」的关系**：消费同一资产 → 引用（R2，不复制）；创建项目上下文的新资产（内容自有）→ 新对象 + 来源钉扎（R3，不是「复制权威资产」——权威从未被复制，被创建的是不同作用域的新内容）。此区分写入 DR-05 裁决说明。

### 7.5 确认链与发布（答 Q2，DR-01/DR-08 输入）

**close 契约影响（关键登记）**：现状 close_report 批量发布全部 approved pc 提案（即产品认知）。方案 C 下：
- close pc 分支**继续发布 PC-J 提案**——契约机械形态不变（同表同链同幂等键族），发布对象语义收窄为项目上下文认知；
- **PC-P 发布与项目 close 脱钩**：产品权威的确认与发布必须由产品级权限主体执行（任务书 §3.5「正式认知确认仍由具有相应权限的人类执行」）；项目 Lead 的 A3 授权不足以确认产品真相。PC-P 发布形态（显式发布动作 / 产品级批量）→ DR-01/DR-08 裁决点。
- 此变更触及 P3-11 已验收工程契约的语义范围（非机械结构），按任务书 §5「区分目标领域模型与实施过渡态」原则登记为**实施期再裁决项**（§9.3-I3），不在本切片执行。

### 7.6 冲突处理与反馈机制（答 Q6，DR-06/DR-07 输入）

**六步全链**（任务书 §3.4 要求的步骤区分原样落地）：

| 步骤 | 承载 | 说明 |
|---|---|---|
| ① 冲突发现 | 三入口：a) 项目差异记录（R4）显式声明与 PC-P 基线不一致；b) PC-P 候选提案相互冲突（两项目对同一产品对象提交不同候选）；c) PC-P 新版本与项目钉扎基线的再基线评估中发现实施矛盾 | 发现是信号，不是合并 |
| ② 冲突记录 | **PC-P 族 conflict 对象**（新建，归属 PC 域——R-06 归属原则「主要冲突认知所在域持对象」：候选修订的目标是产品真相 → PC 域持有；涉及项目侧对象经 DomainRef 引用，项目侧各自履行确认责任） | 不是解冻 pc.conflict Legacy（R-06 对旧项目级表的原样保持）；是新族新对象，遵守同一归属原则；无 Global Conflict 域 |
| ③ 候选修订 | PC-P 提案（origin 标注来源项目与证据；evidence DomainRef 指向 PC-J/ProjC 项目对象） | AI 可起草；提案止于 submitted |
| ④ 人工裁决 | 产品级人工门裁决冲突（resolve/dismiss 带 note，projc 冲突语义同构）；项目侧差异由项目门处置 | AI 恒 403 |
| ⑤ 正式发布 | PC-P 发布事务产出新 cognition_version | 幂等账本 + CAS + 审计 + outbox 同构 |
| ⑥ 项目侧同步/再评估 | update-pending 感知（§7.7）→ 项目显式再基线 / 显式忽略（留痕）/ 提差异（回①） | 永不自动覆盖项目认知（任务书 §3.3） |

**反馈流（R5 正式化）**：项目实施发现 → PC-J 差异/候选记录 → 经反馈通道起草 PC-P 候选提案（人工或 AI 起草、人工提交）→ 产品门确认。证据随提案以**授权快照**形态提交（§7.8-E）：产品侧裁决基于快照，不依赖对项目对象的实时读取。**污染防护**：候选在获产品门确认前，永远只是 PC-P 提案面的 draft/submitted 行，不出现在任何产品真相读面（现状纪律「提案面产物不入 active」的域内重申）；项目侧原对象不受影响。

**AI 多项目归纳**：AI 可基于已进入 PC-P 链的多来源候选与证据归纳整理（聚合、去重、差异比对），产出**候选提案草稿**——起草≠确认；归纳输入限于显式进入 PC-P 链的内容与证据，不开放 AI 自由跨项目遍历读取（§7.8）。

### 7.7 感知机制（答 Q5，DR-04 输入）

- PC-P 发布 version N+1 → outbox 事件（现事件机制同构，新增事件族登记）→ 持有 N 及更早钉扎的**消费引用与派生引用**均进入 **update-pending** 态（派生基础过期必须可感知，S9/§5.1）。
- update-pending 是**感知态不是变更**：不改写项目任何数据；在项目视图与审阅中心供给待办（滞留留痕）。
- 项目三选一：再基线（钉扎推进到 N+1，必要时触发派生对象差异评估）/ 显式忽略（记录理由）/ 提差异（回冲突流①）。
- 解除关联后引用不再进入感知（授权已终止）；relink 后按新钉扎重置（§7.9）。

### 7.8 权限与授权模型（答 Q7，DR-08 输入）

**PC-P 读取授权**（任务书 §3.5 双向不自动穿透的落地）：

| 主体 | PC-P 读 | PC-P 写（正式） | 依据 |
|---|---|---|---|
| Product Owner ∪ tenant admin | 全量（含详情聚合） | 确认/发布/冲突处置 | P4-01 DR-06 冻结集 |
| 关联 Project 成员 | **经消费授权**（见下），限钉扎版本的已发布内容，只读 | 无（修改权仅在 PC-P 链） | 显式授权路径，非成员身份自动 |
| 未关联 Project 成员 / 普通租户成员 | 无（403） | 无 | DR-06 默认拒绝 |
| Product Owner 对项目认知（PC-J/ProjC） | **不自动**；只见显式提交进 PC-P 链的候选提案及其 evidence | 无 | 任务书 §3.5 反向对称 |

> 〔附录 B-2 影响标记（2026-11-19）：P4-09 成员权限补充设计〔CONFIRMED〕引入 Product 成员资格（Project 成员自动继承，单层）并确认 Product 成员对关联 Project 普通业务内容与技术认知的完整只读——与上表「Product Owner 对项目认知不自动读取」行存在显式冲突，须阶段 3 DR 重新裁决人类成员读面；同时「Product 成员是否自动获得本表 PC-P 已发布内容读取面」为新增待裁决点（P4-09 O8），在裁决前本表授权路径不变。本标记不改变本节 PROPOSED 状态。〕

**授权双语义分离（V1.1 闭合审查 P1-3）**：Link 写操作权限（P4-02 DR-03 交集）与「授予项目成员读取 PC-P」是**两个独立语义**——有权建立 Link ≠ 已授权认知读取。无论 G1/G2，PC-P 消费授权都必须是**可审计的显式授权决定**，不得由 Link 的存在隐含推导。

**消费授权形态两案**（DR-08 裁决点）：

- **G1（候选，重新定位）**：授权决定作为 Link 建立同一治理交互中的**独立显式决定**（独立确认项 + 独立审计事件，如 `product_cognition.consumption_granted / .revoked`），生命周期挂接于 Link。G1 只是**授权记录的承载方式**，不是把 Link 写权限升级为读取授权；若裁决认为挂接 Link 仍不足以表达授权独立性 → G2。
- **G2（候选）**：独立授权对象（per product×project：granted_by/at、scope、revoked_by/at），与 Link 状态解耦管理。最严格显式；代价：新对象 + 新管理面 + 与 Link 生命周期的一致性维护。

**显式授权契约六问（两案共同必须回答，V1.1 推荐答案，DR-08 裁决）**：

| 问 | 推荐答案 |
|---|---|
| 授权由谁作出 | **产品侧权限主体**（Product Owner ∪ tenant admin）——授权本质是开放产品资产读取，属产品侧权威；执行操作者须满足 P4-02 DR-03 交集（与 Link 同操作执行时天然满足） |
| 是否双侧分别确认 | V1 不强制第二 actor：产品侧主体显式决定 + 审计记录双侧执行者；更高治理（双侧互认）随 P4-02 DR-03 的双侧确认扩展路径另立 DR |
| 授权对象范围 | 限 **PC-P 已发布内容**（published cognition_version 的只读展示与钉扎）；不含 draft/proposal 面。粒度=授权级整域已发布内容；per-object 授权登记为扩展路径（V1 无场景） |
| 撤销是否需再确认 | 撤销=产品侧显式动作 + 审计，**不需 Project 侧确认**（授权是产品侧权利）；撤销后 PC-P 只读面即时 403 |
| Link ended 是否必然撤销 | **是**（授权活跃 ⊆ Link 活跃，ended 即终止）；显式撤销可更早发生 |
| 授权与 Link 状态一致性 | **子集关系而非完全一致**：授权不可长于 Link 存续；允许「Link active 但授权已撤销」态（项目保持关联但暂不消费产品认知） |

**证据访问授权边界（V1.1 新增，闭合审查 P1-4；H3 在数据读取层的落实）**：

| 证据形式 | 产品侧可读性 |
|---|---|
| 候选提案正文（差异说明、理由） | 提交进 PC-P 链后，产品门权限主体可读 |
| **证据快照**（提交时固化的内容副本：对象内容 + 来源钉扎 + 内容哈希，不可变） | 按快照授权范围可读——提交行为即项目侧对该内容的授权固化 |
| 原始 DomainRef（溯源指针） | **仅作溯源元数据展示**（目标存在性/版本号），不开通实时读取；实时读取须另行满足目标领域授权（产品侧对项目认知无自动读取权，§2.3 铁律 2） |
| 未授权的项目内部对象 | 不可读（无快照、无授权，无任何读取通道） |

推荐形态：候选提案携带**经授权的证据快照 + 原始 DomainRef（仅溯源）**——产品侧能理解反馈内容，项目内部对象不因反馈而自动开放。快照内容寻址不可变，与 revision 纪律一致；ProjC/交付域对象作为证据时同规则。

**AI Agent 边界**（任务书 §3.5 末项）：

1. AI 起草 PC-J/ProjC/PC-P 提案与草稿：沿用现状（项目作用域内 worker 已授权面）；PC-P 提案起草限于反馈流与归纳流（输入=显式进入链的内容）。
2. AI 确认/发布/冲突处置：恒 403（H8，全域不变）。
3. AI 自由跨项目遍历读取项目认知：**V1 不开放**。未来经统一检索（P3-10，R-08 权限元数据）作为受控通道另行裁决（O-01/O-07 承接）。
4. AI 对 PC-P 已发布内容的读取：随消费授权面（AI 主体服务项目时继承该项目的消费授权范围，只读）；AI 不得将未授权范围内容写入任何面。

### 7.9 生命周期处置矩阵（答 Q8，DR-09 输入；承审查防错 3）

**四分原则**：主体生命周期响应 / 关联生命周期响应 / 认知版本生命周期 / 认知正文传播——前两者允许「响应」（状态联动、授权终止），认知版本永远不可变，认知正文传播只经 §7.6 六步显式流。

| 情形 | PC-P 处置 | PC-J / 消费引用处置 | ProjC | 禁止事项（无传播） |
|---|---|---|---|---|
| Product **archived** | PC-P 链冻结：已发布版本**可读**（授权面内）；新提案/发布/冲突处置**停止**；进行中提案（draft/submitted/approved）**状态保留原样 + 主体态守卫冻结**（archived 期间命令面 403，**不引入「挂起」新状态、不做状态转移**；restore 后原状态原样继续，恢复后未决提案的处置策略 → DR-09） | 消费引用保留可读；update-pending 冻结；PC-J 对象不受影响 | 不受影响 | ❌ 不隐式归档任何认知版本/对象；❌ 不自动解除 Link（P4-01 DR-04：archived 禁新增关联，既有关联不自动解除）；❌ 不为冻结引入新状态值 |
