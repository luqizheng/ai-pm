## 2. 产品背景与核心问题

### 2.1 产品背景

在软件研发过程中，产品需求、业务规则、功能模块、页面交互、技术设计及历史决策会随着项目不断演进。

随着项目规模扩大，团队通常会遇到以下问题：

#### 问题一：缺少完整的产品全貌

团队掌握了大量局部需求，但无法准确了解：

- 产品整体定位和目标。
- 产品包含哪些业务能力。
- 功能模块之间如何关联。
- 用户角色和使用场景。
- 核心业务流程和状态流转。
- 页面、业务对象和业务规则之间的关系。
- 不同需求之间的依赖和约束。

结果是团队能够理解单个功能，却无法准确理解整个产品。

#### 问题二：历史知识分散且容易丢失

产品讨论可能发生在会议、邮件、即时通信、需求文档和其他协作工具中。

这些资料虽然被保存，却难以形成长期、可检索、可追溯的团队知识。

典型问题包括：

- 不记得过去是否讨论过某个问题。
- 不知道某个方案为什么被否决。
- 不知道某项业务规则的形成过程。
- 新成员无法了解历史讨论和决策背景。
- 新需求分析时重复讨论过去已经解决的问题。

#### 问题三：产品认知容易发生冲突

新需求不断增加，可能与历史需求、业务规则、流程、权限和页面交互发生冲突。

如果缺少统一的产品认知模型，团队很难发现这些问题。

AI 即使能够分析大量文档，也不能简单地把推断结果当作正式产品事实。

#### 问题四：文档不等于产品认知

文档只是知识来源之一。

- 文档中写了某个功能，不代表该功能已经实现。
- 代码中存在某个行为，不代表它已经成为正式产品规则。
- 会议中讨论过某个方案，不代表团队已经正式决定采用。
- AI 从多份资料推断出的关系，不代表该关系已经得到确认。

因此，PM-AI 必须明确区分资料、历史讨论、正式产品认知和实际产品状态。

## 3. 总体产品定位

PM-AI 建立两项相互独立、协同工作的原生业务能力：

### 3.1 Product Cognition

**Product Cognition 是 PM-AI 的产品认知管理能力。**

其目标是持续建立、维护和验证项目整体产品认知，使 AI 和人类团队能够理解：

- 软件是什么。
- 软件要解决什么问题。
- 软件具备哪些业务能力。
- 产品由哪些模块和功能构成。
- 不同业务对象、流程和规则如何关联。
- 需求和设计之间有哪些依赖。
- 产品认知如何随时间演变。
- 哪些认知已经正式确认，哪些仍然存在争议。

Product Cognition 不只是产品文档管理，也不是简单的知识检索系统。

它是项目级、关系化、可追溯、可治理的产品认知体系。

### 3.2 Knowledge Base

**Knowledge Base 是 PM-AI 的资料与知识管理能力。**

其目标是将团队分散的原始资料转化为可管理、可检索、可追溯的长期知识资产。

主要管理：

- 原始资料。
- 资料解析内容。
- 结构化知识提取。
- 历史讨论。
- 浅层记忆与深层资料。
- 来源、版本和关联关系。
- 知识提取和记忆更新的审核记录。

Knowledge Base 不负责决定正式产品是什么，也不负责直接确认正式产品规则。

它为 Product Cognition 提供知识依据。

### 3.3 两项能力的关系

两者在产品架构中并列，是独立的一级业务能力。

| 对比维度 | Product Cognition | Knowledge Base |
|---|---|---|
| 核心问题 | 我们如何理解整个产品？ | 团队过去积累了什么知识？ |
| 管理对象 | 产品认知及其关系 | 原始资料与提取知识 |
| 主要内容 | 产品定位、能力、模块、流程、规则、需求、决策 | 文档、会议记录、讨论、解析内容、历史记忆 |
| 核心价值 | 保持产品全貌、完整性和一致性 | 保留知识、还原历史、提供依据 |
| 主要输出 | 产品认知模型、认知变更建议、冲突和影响分析 | 可追溯知识、历史记忆、知识提取结果 |
| 确认机制 | 正式产品认知必须经过授权人员确认 | 浅层记忆内容变化必须人工审核 |

两者共享 Knowledge Coordination 协调能力，但不合并业务职责。

## 4. Product Cognition 产品模型

### 4.1 Product Big View

Product Cognition 的核心展示和分析目标是 Product Big View，即产品全貌。

Product Big View 包括三个层面：

1. 功能全貌：产品有哪些功能、模块和能力。
2. 业务全貌：产品服务哪些角色、场景和业务流程。
3. 产品全貌：产品定位、目标、边界、需求、设计和业务规则如何构成整体。

Product Big View 不是一张静态架构图，而是基于统一认知模型动态生成的产品全貌。

### 4.2 Product Cognition 的八个观察视角

Product Cognition 采用多视角关系模型，不设置唯一中心，也不建立八套互相独立的数据体系。

八个视角共享同一个 Product Cognition 模型。

#### 视角一：Product Vision

描述产品定位、目标和边界。

主要内容：

- 产品愿景。
- 产品目标。
- 产品价值。
- 产品服务对象。
- 产品范围。
- 产品边界和约束。

#### 视角二：Business Capabilities

描述产品需要具备的业务能力。

例如：

- 用户管理。
- 项目管理。
- 需求管理。
- 设计管理。
- 研发执行管理。
- 风险管理。

#### 视角三：Feature Modules

描述产品功能模块及其层级关系。

包括：

- 功能模块。
- 子模块。
- 功能点。
- 模块职责。
- 模块依赖。

#### 视角四：Actors & Scenarios

描述产品使用者和使用场景。

包括：

- 用户角色。
- 角色职责。
- 使用场景。
- 用户目标。
- 场景约束。

#### 视角五：Business Processes

描述业务流程和状态流转。

包括：

- 业务流程。
- 流程节点。
- 状态。
- 状态转换。
- 触发条件。
- 流程约束。

#### 视角六：Pages & Interactions

描述页面结构和用户交互。

包括：

- 页面。
- 页面区域。
- 导航。
- 交互行为。
- 页面权限。
- 页面与业务能力的关联。

#### 视角七：Domain Objects & Rules

描述业务对象及业务规则。

包括：

- 业务对象。
- 对象属性。
- 对象关系。
- 业务规则。
- 约束条件。
- 权限规则。

#### 视角八：Requirements & Decisions

描述产品需求、设计依据及历史决策。

包括：

- 产品需求。
- 需求约束。
- 需求依赖。
- 产品决策。
- 决策理由。
- 设计依据。
- 需求与设计之间的关联。

### 4.3 统一关系模型

八个视角不是独立模块，而是通过关系连接。

主要关系类型包括：

| 关系 | 含义 |
|---|---|
| Supports | 支持 |
| Realizes | 实现 |
| Triggers | 触发 |
| Involves | 涉及 |
| Displayed On | 展示于 |
| Depends On | 依赖 |
| Governed By | 受约束于 |
| Derived From | 来源于 |
| Supersedes | 替代 |
| Conflicts With | 冲突 |

关系本身也需要记录来源、确认状态和有效版本。

AI 可以识别并提出关系建议，但未经确认的推断不得成为正式产品约束。

### 4.4 Product Plan、Product Reality 和 Product Gap

Product Cognition 必须明确区分计划与现实。

#### Product Plan

团队希望软件具备什么能力，以及准备如何设计和实现。

主要依据：

- 正式需求。
- 已确认业务规则。
- 已批准设计。
- 正式产品决策。

#### Product Reality

软件实际具备什么能力。

后续可以通过以下证据逐步建立：

- Git Commit。
- 代码和工程执行记录。
- 测试结果。
- 发布记录。
- 实际运行情况。

代码中的行为不能自动成为正式产品规则。

#### Product Gap

Product Plan 与 Product Reality 之间的差距。

例如：

- 计划中存在某项功能，但尚未实现。
- 已实现功能，但未纳入正式产品计划。
- 实现行为与已确认业务规则不一致。
- 测试结果无法证明验收要求已经满足。

V1 优先建设 Product Plan。Product Reality 和 Product Gap 后续逐步扩展。

## 5. Knowledge Base 产品模型

### 5.1 核心资料层次

Knowledge Base 采用三层资料模型。

#### 第一层：Original Sources

原始资料层。

保存团队提交的原始信息，例如：

- Markdown。
- DOCX。
- PDF。
- 会议记录。
- 邮件。
- 即时通信记录。
- 设计资料。
- 录音及其他附件。

原始资料必须保留，不允许 AI 直接改写或覆盖原始内容。

#### 第二层：Extracted Content

解析内容层。

由 AI 或解析工具从原始资料中提取：

- 文档正文。
- 章节结构。
- 段落。
- 时间戳。
- 发言人信息。
- 邮件正文。
- 文档元数据。
- 其他可检索内容。

解析内容必须能够追溯原始资料及其具体位置。

#### 第三层：Structured Memory

结构化记忆层。

AI 从历史资料中提炼：

- 重要讨论。
- 团队观点。
- 关键方案。
- 被否决方案及原因。
- 未解决问题。
- 决策线索。
- 正式决策背景。
- 与产品认知有关的历史信息。

结构化记忆必须保留来源依据和确认状态。

### 5.2 Discussion Memory

Discussion Memory 是 Knowledge Base 中的重要能力，用于保存和还原团队的长期历史讨论。

它不是简单的聊天记录归档。

其核心价值是帮助团队理解：

- 某个问题过去如何讨论。
- 曾经有哪些不同方案。
- 为什么某个方案被否决。
- 哪些问题尚未解决。
- 某个决策为什么产生。
- 后续讨论如何改变原有认知。

历史讨论不等于正式产品事实。

AI 可以检索、总结和引用历史讨论，但不得将未确认讨论直接升级为正式产品需求、规则或决策。

### 5.3 Shallow Memory 与 Deep Memory

Discussion Memory 采用分层检索机制。

#### L1：Shallow Memory

浅层记忆。

保存经过价值筛选的长期重要信息，包括：

- 深入讨论及形成的方案。
- 重要未解决问题。
- 被否决的关键方案及原因。
- 正式决策的背景和理由。
- 重要业务约束。
- 历史争议。

浅层记忆不是所有资料的摘要，而是项目长期认知的高价值索引。

普通新需求分析默认检索浅层记忆。

浅层记忆未找到相关内容时，AI 只能说明当前浅层记忆中没有找到相关记录，不能断言过去从未讨论。

#### L2：Deep Memory

深层资料。

保存完整原始历史资料及其解析内容。

当用户要求还原历史、寻找具体讨论、核实决策依据，或者浅层记忆不足以回答时，AI 可以深入检索。

深层资料检索结果可以形成浅层记忆更新建议，但不能自动改变正式浅层记忆。

## 6. Knowledge Base 与项目的关系

### 6.1 Team Source Pool

资料首先进入团队级 Team Source Pool。

AI 可以分析资料内容并提出项目归属建议。

资料归属需要人工确认。

一份原始资料可以关联多个项目。

### 6.2 跨项目资料共享

当一份资料被确认关联项目 A 和项目 B 后：

- 两个项目的有效成员均可以按照权限阅读完整原始资料。
- 不对同一份原始资料进行片段隔离。
- 原始资料保持统一身份、统一版本和统一来源追踪。
- 两个项目分别建立自己的知识提取结果。
- 两个项目分别维护自己的 Product Cognition 关联。

没有关联该资料的其他项目不会自动获得访问权限。

### 6.3 动态访问权限

资料访问权限继承自已关联项目的成员关系和资料读取权限。

例如：

- 用户属于项目 A 和 B，可以访问关联 A、B 的资料。
- 用户退出 A，但仍属于 B，仍可通过 B 访问。
- 用户失去所有关联项目的访问资格后，不再具有项目访问权限。
- 上传者身份不产生永久访问特权。

原始资料统一保存，不因项目成员变化而复制。

## 7. Knowledge Coordination 协作架构

### 7.1 定位

Knowledge Coordination 是 Product Cognition 和 Knowledge Base 之间共享的知识协调能力。

它不是第三个知识业务模块，也不取代两者的职责。

主要负责：

- 知识提取结果协调。
- 来源追踪。
- 变更检查。
- 版本关系管理。
- 审核流程协调。
- 冲突检查。
- 统一审计。

### 7.2 职责分工

#### Knowledge Base 负责

- 接收和保存原始资料。
- 解析文档。
- 提取知识。
- 管理 Discussion Memory。
- 管理浅层记忆和深层资料。
- 管理资料版本和来源。

#### Product Cognition 负责

- 理解知识对产品全貌的影响。
- 检查需求、规则、流程和模块之间的一致性。
- 发现产品认知冲突。
- 提出产品认知变更。
- 分析认知变更的影响范围。
- 维护正式产品认知版本。

#### Knowledge Coordination 负责

- 协调知识流转。
- 维护变更链路。
- 确保来源和版本可追溯。
- 按治理规则执行审核与更新流程。
- 避免未经确认的知识直接成为正式认知。

### 7.3 文档变化感知

文档类变化首先由 Knowledge Base 感知和处理。

例如：

- Git 中 Markdown 文档变化。
- Git 中 PDF 文档变化。
- 新上传产品文档。
- 新上传会议记录。
- 新增外部资料。

Knowledge Base 解析文档并提取知识。

Product Cognition 再判断这些知识是否影响正式产品认知。

**普通代码文件不属于本阶段 Product Cognition 文档分析范围。**

对于 Git Commit：

- Markdown、PDF 等知识文档变化可以触发 Knowledge Base 分析。
- 普通代码变化不触发 Product Cognition 文档分析。
- 代码行为不能自动成为正式业务规则。

文档变化感知需要通过实际建立的 Git Provider Webhook、Repository App、平台事件或定期同步机制实现，不能假设 AI 能自然获知所有外部变化。

## 8. Product Cognition 治理原则

Product Cognition 必须保证正式产品认知的可靠性。

核心治理原则：

1. AI 可以分析和提出建议，但 AI 推断不能直接成为正式产品事实。
2. 正式业务规则必须由授权人员确认。
3. 未解决的产品认知冲突不能正式确认相关新需求。
4. 正式认知变更必须保留版本和决策历史。
5. 正式认知变更采用 Product Cognition Change Proposal。
6. 变更获批后，AI 必须进行关联对象影响分析。
7. 关联对象的正式更新仍需授权人员逐项确认。
8. AI 持续检查完整性、一致性、关联覆盖率和过时信息。
9. 未确认的推断、讨论和建议必须与正式产品认知明确区分。

### 8.1 认知变更提议

AI 发现产品认知需要调整时，创建 Product Cognition Change Proposal。

至少包含：

- 原认知。
- 新信息。
- 变化原因。
- 来源依据。
- 影响范围。
- 冲突分析。
- AI 建议。
- 关联对象更新建议。

建议状态：

- `DRAFT`。
- `PENDING_REVIEW`。
- `NEEDS_REVISION`。
- `APPROVED`。
- `REJECTED`。
- `SUPERSEDED`。

只有 `APPROVED` 才能触发正式产品认知版本更新。

### 8.2 优先级与待人工处理

需要人工处理的问题统一进入 Project Dashboard 的「待人工处理」。

采用 P0-P3 优先级：

| 优先级 | 定义 |
|---|---|
| P0 | 关键阻断，影响正式需求确认、核心业务规则或重大权限安全 |
| P1 | 重要问题，影响模块、流程、需求和设计一致性 |
| P2 | 一般问题，缺少关联、历史信息待核实、认知不完整 |
| P3 | 信息建议，优化建议、低风险整理和非紧急事项 |

优先级不代表 AI 获得修改权限。

### 8.3 AI 执行权限

按照风险区分：

- 低风险：AI 可以自动执行。
- 普通风险：AI 提出方案，人工授权后执行。
- 高风险：AI 只能提出方案，正式需求、业务规则、设计和决策必须人工确认。
- 重大冲突：暂停相关更新，必须人工裁决。

AI 的执行权限绑定具体批准事项和批准范围，不授予永久性的类别修改权限。

### 8.4 人工确认事项生命周期

Decision Status 与 Resolution Status 分离。

Decision Status：

- `PENDING`。
- `ACCEPTED`。
- `REJECTED`。
- `REVISION_REQUESTED`。
- `DEFERRED`。

Resolution Status：

- `NOT_STARTED`。
- `IN_PROGRESS`。
- `PENDING_VERIFICATION`。
- `VERIFICATION_FAILED`。
- `COMPLETED`。
- `CANCELLED`。

人工接受建议不代表问题已经解决。

只有更新完成并验证通过，才能闭环。

暂缓事项继续留在治理范围内；新资料到达、条件变化或定期检查发现重要进展时，AI 重新分析并视情况提醒。

## 9. Knowledge Base 治理原则

### 9.1 知识提取与人工审核

原始资料解析和深层资料整理允许 AI 自动执行。

但是：

**任何导致浅层记忆内容发生变化的操作，都必须经过人工审核。**

包括：

- 新增浅层记忆。
- 修改浅层记忆。
- 删除浅层记忆。
- 合并浅层记忆。
- 改变浅层记忆含义。

未经审核的结果只能保留在深层资料或待审核区，不得进入正式浅层记忆。

审核通过仅代表允许进入浅层历史记忆，不代表成为正式 Product Cognition。

### 9.2 浅层记忆版本管理

每条浅层记忆独立版本化。

核心规则：

1. 每次审核通过的内容变更产生新版本。
2. 旧版本不得覆盖或物理删除。
3. 新版本生效后，旧版本自动标记为 `SUPERSEDED`。
4. `WITHDRAWN` 和 `MERGED` 必须经过人工审核。
5. 所有版本保留完整内容、来源、变更原因、审核记录及版本关系。
6. 合并记忆时保留源记忆及其历史。
7. 历史检索支持当前状态和历史时间还原。
8. 浅层记忆版本更新不得自动改变正式 Product Cognition。

版本状态：

- `CURRENT`：当前有效版本。
- `SUPERSEDED`：被新版本替代。
- `WITHDRAWN`：人工确认撤回。
- `MERGED`：人工确认合并到其他记忆。

版本内容采用不可变原则，状态变化必须保留审计记录。

## 10. AI 角色与协作方式

Product Cognition 和 Knowledge Base 都是 AI-PM Platform 的原生能力，不依赖外部 Agent 才能工作。

### 10.1 Native AI-PM

Native AI-PM 负责：

- 产品认知分析。
- 需求影响分析。
- 知识提取和整理。
- 历史讨论检索。
- 冲突识别。
- 变更建议。
- 待人工处理事项生成。

### 10.2 External Agent Clients

外部 Agent Client 可以受托完成复杂任务，例如：

- 大型文档梳理。
- 复杂产品流程分析。
- 多资料交叉分析。
- 工程代码与实现证据分析（属于后续 Product Reality 范围）。
- 专项研究和分析。

外部 Agent 的分析结果必须经过 Knowledge Coordination 的来源检查、质量检查和治理流程，不能直接写入正式产品认知。

### 10.3 人类团队

人类负责：

- 确认资料项目归属。
- 审核浅层记忆变化。
- 确认正式业务规则。
- 确认正式需求和设计。
- 裁决重大认知冲突。
- 批准正式产品认知变更。

核心原则：

**人类负责产品，AI 协助建立和维护产品认知。**

## 13. 关键架构原则总结

本产品体系遵循以下原则：

1. Product Cognition 与 Knowledge Base 是两个独立的一级业务能力。
2. Product Cognition 管理正式产品认知，Knowledge Base 管理资料和知识。
3. Product Big View 是 Product Cognition 的核心全貌视图。
4. 八个 Product View 共享统一认知模型，不是八套独立数据体系。
5. 原始资料、解析内容、结构化记忆分层管理。
6. Discussion Memory 区分浅层记忆与深层资料。
7. 任何浅层记忆内容变化都必须人工审核。
8. 浅层记忆版本不可覆盖、不可物理删除。
9. 正式产品认知变更必须经过授权人员确认。
10. AI 可以自动分析和提出建议，但不能擅自将推断变成正式产品事实。
11. Knowledge Coordination 统一协调知识流转，但不合并业务职责。
12. 人类负责项目和产品，AI 协助执行、分析和维护知识。

---

## 文档结论

Product Cognition 与 Knowledge Base 共同构成 PM-AI 的长期产品认知和知识基础设施。

Knowledge Base 让团队能够保存、提取、检索和还原知识。

Product Cognition 让团队能够理解产品全貌、维护正式产品认知，并持续发现需求、业务规则、流程和设计之间的问题。

两者协同，使 PM-AI 不仅能够协助团队执行研发任务，还能够长期理解一个软件产品的整体结构、业务逻辑和演变历史。
