## 0. 给评审专家的现状背景（必读）

本方案基于一套已运行的 PM-AI 系统（Rust + PostgreSQL，axum REST + worker）。与本方案直接相关的既有事实：

1. **任务域能力已完备，且与执行解耦。** 系统已有一套正式研发任务体系：
   - 任务主表含 13 态状态机：`draft → ready → claimed → running → submitted → reviewing → completed`，含 `blocked / awaiting_decision / failed / changes_requested / cancelled / superseded`。状态转移有合法性校验（非法边直接拒绝）。
   - 任务依赖已实现为有向边表（自环禁止、递归 CTE 循环检测、依赖解锁判定），含 REST 接口。
   - 任务已支持：多仓库绑定（主/次/知识角色 + 路径范围）、验收标准条目、乐观锁并发控制、审计日志（变更前后快照）、任务取代链（supersession）。
   - AI 已能做"需求 → 任务批分解"：LLM 分解产物一律落为 `draft` 状态，AI 无任何批准权（系统红线），由人工整批确认后才进入 `ready`。
2. **审批底座已存在。** 系统有通用审批请求表（目标类型、所需角色、审批人授权表）+ 事务性 outbox 事件（`TaskReady / DeliverySubmitted / ReviewCompleted` 等 8 类已编目）+ 项目级/租户级双审计日志。现有审批实例目前 1:1 绑定"变更提案"，尚未覆盖任务计划。
3. **S03 设计成果尚未落库。** Design / Design Revision / ADR / Implementation Scope 在系统中**没有任何表**（契约层明确登记"通道未开放"）。S03 目前只有纸面设计文档（技术决策 Q1–Q5 已裁决：设计↔需求多对多、Revision 不可变、ADR 独立实体、AI 分析 + 人类批准、实施准入门禁）。这是 S4 最大的外部依赖缺口。
4. **新项目原则：不做迁移与兼容。** 直接改契约、重建表，不留旧格式过渡层。

因此本方案的核心立场是：**S4 不新建一套任务体系，而是新建「任务计划」这层聚合，并把现有任务域能力（状态机、依赖、验收、仓库绑定、审批底座）挂到计划上。**

## 1. 目标与范围

### 1.1 S4 做什么

- 读取 S03 已批准的设计成果（Design Revision / ADR / Implementation Scope / 验收条件），建立 Requirement → Design → ADR → Scope → Task Plan → Task 的全链追溯。
- 调用 LLM 将 Implementation Scope 拆解为任务计划（Task Plan）草稿，含依赖、仓库推荐、验收标准、执行约束。
- 人工审核 / 批准 / 退回任务计划；只有批准后任务才正式化为可执行任务。
- 支持人工修改后 AI 增量重拆（不覆盖人工修改）。
- 向 S05 提供执行资格检查与标准化执行上下文交接。

### 1.2 S4 不做什么（职责边界）

| 不做 | 归属 |
|---|---|
| 技术方案再设计、Design Revision 修改 | S03 |
| Runner / Codex 等执行运行时、Agent 调度 | S05 |
| Git commit、Delivery 实际执行 | S05 |
| 新建任务底层执行体系 | **禁止——复用现有 Task/Run/Delivery** |

### 1.3 三个架构问题的裁决建议

| 问题 | 建议裁决 | 理由 |
|---|---|---|
| **Q1 Task 与 Task Plan 的关系** | Task Plan 是一次任务组织方案的**聚合根**，有自己的 Revision；Task 是正式工作项，**复用现有任务表**，新增 `来源计划修订ID` 可空外键实现追溯。一个 Plan Revision 可产生多个 Task；未挂计划的独立任务允许存在（标记 out-of-plan）。 | 现有任务表已带状态机/依赖/验收/仓库绑定/审计，平行新建必然重复。 |
| **Q2 AI 重新拆解 vs 人工修改** | 重新拆解**永远产生新的 Plan Revision**，输出"新增 / 修改 / 删除"三类 diff 建议，由人逐项或整批确认后应用；已存在的任务不被 AI 原地覆盖，删除任务只能经"取代（supersession）"链路并留审计。 | 对齐系统既有"AI 提案 → 红线确认 → 版本化"范式；保证已批准内容不可静默丢失。 |
| **Q3 Task 是否独立于 S05 执行状态存在** | **是，且现状已满足。** 现有 13 态状态机与执行（Run）本就解耦：Run 是独立实体、有自己的 7 态状态机，Task 状态由统一应用服务拥有，S05 只能通过命令通道申请状态迁移。S4 无需为此新建机制。 | 事实已成立；本方案只需保证 S4 写路径也走同一命令通道，禁止双写。 |

### 1.4 附加裁决建议（提示词未列，但必须先定）

| 问题 | 建议裁决 | 理由 |
|---|---|---|
| **Q4 S03 设计成果载体缺失怎么办** | S4 与 S03 最小落地**同批实施**：先落 Design Revision / ADR / Implementation Scope 的最小表集（对标现有"需求修订"的不可变版本形态：`draft / pending_confirmation / approved / rejected / superseded` + 内容哈希），S4 才有可引用的输入。**不采用"把设计文档文本复制进任务描述"的过渡方案。** | S4 的核心价值是追溯链；没有正式设计实体，追溯链无从建立。参考既有裁决"不以通用文档修订冒充专用域实体"。 |
| **Q5 Task 是否需要内容版本历史表** | **S4 不新建 Task Revision 全量表。** 计划层版本由 Plan Revision 承担；任务内容变更由现有审计日志（前后快照）记录；已批准任务的重大修改走取代链路。 | 版本需求集中在"方案"层；任务级全量版本成本高、且与审计/取代机制重复。若评审认为必须，可作为 B4 增量项。 |
| **Q6 状态命名对齐** | 提示词中的 `PLANNED` 对应现有 `draft`（已规划、待人工确认），`READY` 对应现有 `ready`（人工确认、可执行）。**沿用现有 13 态，不新增 PLANNED 状态。** 依赖阻塞复用现有 `blocked` + 等待原因机制。 | 状态机已固化并有转移合法性守护；加同义状态只会制造两条进入 `ready` 的路径。 |

## 2. 领域模型设计

### 2.1 新增实体（全部新建）

| 实体 | 职责 | 关键字段 |
|---|---|---|
| **Task Plan** | 一次任务拆解方案的聚合根 | id、project_id、来源 Design Revision、状态（`draft / in_review / approved / superseded`）、当前 Revision 指针、乐观锁 |
| **Task Plan Revision** | 计划内容不可变版本 | revision_no、内容快照（任务清单草案 + 依赖边草案 + diff 摘要）、生成来源（AI 分析运行 ID / 人工）、内容哈希 |
| **Plan Approval** | 计划的人工审批记录 | 复用通用审批请求表，新增目标类型 `task_plan`；记录批准时的 Plan Revision、审批人、意见、时间 |
| **Task←Plan 关联** | 任务追溯来源 | 现有任务表加可空 `plan_revision_id`；同一任务可标注 out-of-plan |

### 2.2 复用实体（不新建）

| 能力 | 复用方式 |
|---|---|
| Task / 13 态状态机 / 转移校验 | 原样使用；S4 只负责把计划内任务建为 `draft` 并整批确认到 `ready` |
| Task Dependency 边表 + 循环检测 | 原样使用；S4 增加计划级拓扑排序 / 关键路径 / 可并行分组等**只读视图 API**，不改存储模型 |
| Task 仓库绑定 / 验收标准 | 原样使用；AI 拆解时写入推荐值，人可改 |
| 通用审批底座 + 审批人授权 | 扩展一个目标类型，不改审批引擎 |
| Outbox 事件 + 审计日志 | 新增事件类型：`TaskPlanGenerated / TaskPlanSubmitted / TaskPlanApproved / TaskPlanRejected / TaskPlanRevised` |
| Run / 执行契约 | S4 只产出"执行资格检查 + 上下文载荷"，交接动作复用现有 Run 创建与租约机制 |

### 2.3 设计基线最小表集（Q4 裁决项，与 S4 同批）

| 实体 | 形态 |
|---|---|
| Design / Design Revision | 对标现有需求修订：不可变 revision、状态 `draft→pending_confirmation→approved→rejected/superseded`、内容 jsonb + 哈希、approved_by |
| ADR | 独立实体 + 与 Design 的多对多关系（沿用系统已预埋的 ADR 关系类型种子） |
| Implementation Scope | Design Revision 内的结构化条目（模块、边界、涉及组件），供拆解按条目分派 |

## 3. 核心流程

### 3.1 主链：设计 → 计划 → 任务 → 执行

```
S03 已批准 Design Revision（Q5 实施准入门禁通过）
        │  前置校验：设计已批准、ADR 无未决冲突、Scope 非空
        ▼
发起拆解（人工触发）
        ▼
LLM 拆解（复用现有 LLM 接入层：项目级模型配置→租户默认→降级）
  输入：Design Revision + ADR + Scope + 现有任务清单（避免重复/冲突）
  输出：任务草案（标题/目标/约束/验收标准/依赖/仓库推荐/粒度自评）
        ▼
确定性校验（纯函数，不靠 LLM）：依赖成环检测、重复键、
  仓库归属校验（必须是本项目已验证仓库）、验收标准可测试性初检
        ▼
Task Plan Draft + Plan Revision #1   ← AI 产物一律 draft，AI 无批准权
        ▼
人工修改（可选，直接改草案，全部留审计）
        ▼
提交审核 → 人工批准（记录批准的 Revision）
        ▼
正式化：按计划批量创建正式任务（draft → ready 整批确认）
        ▼
S05 领取执行（执行资格检查 + 执行上下文交接）
```

### 3.2 AI 重新拆解（增量、不覆盖）

```
触发：人工"重新拆解"（携带人工修改意图说明）
        ▼
基于当前生效 Plan Revision + 人工修改记录 + 设计增量，
生成新 Plan Revision 草案 = diff（新增任务 / 修改任务 / 删除建议 / 依赖变更）
        ▼
人工逐项确认或整批确认
  ├─ 采纳 → 新 Revision 生效；删除任务走取代链路（不物理删除）
  └─ 拒绝 → 保留当前 Revision
```

### 3.3 执行交接（S4 → S05）

统一执行上下文载荷：

```
Task Execution Context
├── Task ID / Task Revision（审计锚点）
├── Project ID / Tenant
├── Repository 引用（含 base ref、路径范围、写权限声明）
├── 来源 Design Revision / ADR 引用
├── Implementation Scope 条目
├── 前置依赖及完成状态
├── 验收标准（可执行判定所需）
├── 技术约束 / 参考文档
└── 预期交付物
```

**执行资格检查**（全部通过才允许交接）：计划已批准、任务 `ready`、前置依赖全部 `completed`、仓库绑定有效且属于本项目、验收标准非空。

### 3.4 状态所有权（防双写）

- 任务状态唯一所有权：**统一任务应用服务**。S4 与 S05 均只能通过命令通道发起转移，转移合法性由状态机守护层校验。
- 计划状态（`draft/in_review/approved/superseded`）由计划服务独占；计划批准不直接改任务状态，而是触发"正式化"命令。

## 5. 权限、安全与审计

- 沿用既有链路：租户隔离（tenant_id）→ 项目可见性检查（不可见返回 404 不泄露存在性）→ 项目成员校验 → 审批人授权表裁决审批权。
- **AI 越权防线**：AI 产物只能落 `draft`/计划草案；所有 AI 写路径记录来源（分析运行 ID）；REST/MCP/执行器入口共享同一命令通道与状态守护，无旁路批准接口（专项测试覆盖）。
- 并发：计划与任务均有乐观锁；冲突返回明确错误码。
- 审计：计划生成/修改/提交/批准/退回/正式化/交接全链落审计日志，AI 与人工操作以 source 字段区分。

## 8. 开放问题（请评审专家裁决）

1. **Q4 同批落地 S03 最小表集**是否接受？（不落地则 S4 无输入，只能降级为"粘贴设计文本进任务描述"，追溯链断裂——本方案强烈反对降级。）
2. **Q5 不建 Task 全量版本历史**是否接受？还是要求任务级 revision 表？
3. 计划批准后，是否仍允许在计划外直接创建任务（out-of-plan）？本方案建议允许并标记，以满足日常零星任务。
4. 计划级"关键路径 / 并行分组"计算频率：建议事件驱动（依赖变更时重算，走 outbox），不做实时全图重算。是否接受？
5. 计划删除任务的语义：本方案建议只允许"取代"（旧任务 superseded、新任务接续、留审计），不允许物理删除已批准任务。是否接受？
