### 九项实施期裁定（详见设计稿 §9.2）

2. 事务所有权按值传给收尾函数：`finish_rejected(mut tx: Tx, …)` 自行 COMMIT，
   调用方 `return finish_rejected(tx, …)`。杜绝「半提交」路径。
3. **可写仓漏报不驳回**（`None => continue`）——D4 §5 明示 `submitted` ≠ 交付完整；

4. 落库 `commit_sha` 取**工作区实际 HEAD**（`rev-parse HEAD`），不取执行端声明。
5. `changed_files` 以 Git 现算为准（`diff --name-status base..commit`），上报只做比对。
6. 审计 actor 回退：项目 human 成员 → 平台 service principal（`DISPATCH_SERVICE_PRINCIPAL`）。
7. `request_fingerprint` 落 **Run 级列**（覆盖整单含 `integration_status`）。
8. 业务驳回**不是异常**：工具层回 200 + `outcome: "rejected"` + 机器可读 `code`；
   只有租约失效 / DB 错误才映射到 `ToolError`。
9. git 失败与超时统一走 `commit_not_descendant`，不扩张 §4.1 的九项错误码表。

### 踩过的坑

- 第二个 Run 用 `status='queued'` 会撞 `uq_task_run_active` → 改 `'succeeded'`。

### 关键结论
- **`WHERE NOT EXISTS` 不是并发安全的唯一性保证**——至少一次投递下两个 Worker 会
  「同查不存在 → 同插双写」；幂等必须靠**事务级 advisory lock**（键 = 幂等锚点）把
  「检查 + 写入」串行化，事务结束自动释放。
- **API 层的项目可见性检查不能替代底层 SQL 的项目约束**——调用方可构造别项目的
  `event_id`；`replay` 必须带 `project_id` 原子校验，且跨项目与不存在**同形返回**
  （否则成为事件 ID 探测 oracle）。
- **共享队列的消费者能力必须一致**——`pm-worker` 零 handler 空壳会把 `ai-pm-worker`
  能正常处理的事件经重试误判为死信（**假死信**，不是业务失败）。
  **「集合一致」≠「并发安全」**：并发靠 claim 的 `FOR UPDATE SKIP LOCKED` + 租约 +
  Handler 幂等，三者缺一不可。
- **事件目录是 Outbox 的契约中心**——`has_handler` 与 `enabled_by_default` 必须拆成两个
  字段，否则「有无消费者」与「默认是否生产」永远纠缠不清（env 变量是最大的漏洞来源）。
- **通知表的 `read_at` 不等于有清理机制**——本次只负责可靠写入，保留策略另行管理。
- **P0-4 连带修正 T-043 测试**：`review.rs` 的 `enable_notification_events()` 断言由
  「两事件产生」改为「**不产生**」——不为旧测试给事件目录开兼容口子（`AGENTS.md` 规则 1）。

- **P0-1b 审计三分**：真人 Actor（`actor_id`/`actor_identity_id`）/ `claimed_device_id`（**新增可空列**，与 T-059 的 `actor_client`/`actor_auth_mode` **同批迁移于 0027**）/ run（`target_type='task_run'`+`target_id`）。设备声明**绝不覆盖真人身份列**（§5.7）。
- **P0-2 授权流水线六步**成文（§5.4.1）：认证真人 → 校验成员资格 → 校验仓库访问权 → 解析 Device ID（仅归因）→ 记录 Binding → 执行工具；Device 解析**不得替代权限校验**；并入 T-088 验收。
- **P0-3 T-081 升级七项身份链路门禁**（§13.2），含「工具拿到正确真人 Principal 上下文」「T-051 成员校验有效」「T-059 审计归因有效」「反代不截断长连接」「未认证/越权被拒」，且**必须真实 Windows 发起**（C166）。
- **P1-1 唯一结构调整**：评审给的 Active/Revoked/Disabled 与 V1.2 的就绪态混在一列 → 拆 `status`（active/revoked）+ `readiness`（四层快照）两列；按评审明示**不引入 `disabled`**；撤销语义成文（不撤销真人 Principal、不改仓库权限、已撤销不得自动恢复、Binding 有效性受设备状态约束）。
- **P1-2 幂等三态**（§8.1）：复用 / 创建 / 已撤销不得自动恢复；重复绑定幂等（`UNIQUE(device_id, project_id)`）；原有绑定不被清除；解绑软删除 + 同 Project 重绑复活原行。

### 六条关键结论（入档）
1. **V1 是「真人通过一个已登记的开发环境接入 PM-AI」，不是「PM-AI 已经信任这台开发机器」**——贯穿 Device 表 / MCP 中间层 / 审计 / 权限校验。
2. **不做半成品 Runner**——Runner、凭据、心跳、设备级领取、无人值守、进程管理全属 V2。
3. **Binding 是声明与事实记录，不是授权授予**——成员无仓库权时即便设备已绑定也必须拒绝。
4. **Ready 是快照不是永久属性**——认证过期 / 绑定撤销 / MCP 不可用均可退化。
5. **SHA-256 只证文件完整性，不证发布者身份**。
6. **跨机连通 ≠ 身份链路可用**——T-081 须真实 Windows 完成七项身份验收。
