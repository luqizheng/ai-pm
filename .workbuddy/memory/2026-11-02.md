### 九项实施期裁定（详见设计稿 §9.2）
1. `task_repository_commit → task_repository` 组合外键**不成立**——`task_repository`
   主键是 `(task_id, repository_id)`，本表无 `task_id` 列（Task 身份经 `task_run`
   传递）。仓归属改由两条 `(project_id, …)` 组合外键保证。
2. 事务所有权按值传给收尾函数：`finish_rejected(mut tx: Tx, …)` 自行 COMMIT，
   调用方 `return finish_rejected(tx, …)`。杜绝「半提交」路径。
3. **可写仓漏报不驳回**（`None => continue`）——D4 §5 明示 `submitted` ≠ 交付完整；
   提交 2/3 个仓仍是有效 D4 事实，视图显示 `partial`，最终裁决归 D5。
   驳回权只留给事实冲突（只读仓有变化 / 基线漂移 / git 失败 / 仓不在契约）。
4. 落库 `commit_sha` 取**工作区实际 HEAD**（`rev-parse HEAD`），不取执行端声明。
5. `changed_files` 以 Git 现算为准（`diff --name-status base..commit`），上报只做比对。
6. 审计 actor 回退：项目 human 成员 → 平台 service principal（`DISPATCH_SERVICE_PRINCIPAL`）。
7. `request_fingerprint` 落 **Run 级列**（覆盖整单含 `integration_status`）。
8. 业务驳回**不是异常**：工具层回 200 + `outcome: "rejected"` + 机器可读 `code`；
   只有租约失效 / DB 错误才映射到 `ToolError`。
9. git 失败与超时统一走 `commit_not_descendant`，不扩张 §4.1 的九项错误码表。

### 踩过的坑
- `sqlx::Transaction` 的所有权：`tx.commit()` 消耗 tx，事务不能既传给 `&mut` 收尾函数
  又在调用方 commit。解法是 `type Tx = Transaction<'static, Postgres>` + 按值传递。
- 视图 CTE 写 `c.task_id`（`task_repository_commit` 无该列）→ 改为 `r.task_id` + JOIN
  `delivery.task_run r ON r.id = c.task_run_id`。
- `pg_get_constraintdef` 的 `confdeltype` 是 `"char"` 类型 → 用 `confdeltype::text`。
- `migration_0011` 的断言谓词 `LIKE '%status%'` 会把 0022 新增的 `integration_status`
  CHECK 也算进来 → 改为按 `conkey = ARRAY[status 列的 attnum]` 精确限定。
- 第二个 Run 用 `status='queued'` 会撞 `uq_task_run_active` → 改 `'succeeded'`。
- MCP 端到端测试：任务必须先 `report_progress(stage="started")` 进 `running`，
  否则 `claimed → submitted` 被状态机拒绝（合法边是 `running → submitted`）。
- 测试里用环境变量传工作区根会与同进程并行用例抢全局变量 → 加
  `submit_result_with(pool, args, &DeliveryOptions)` 注入。

### 关键结论
- **幂等识别必须在管线最前部**（⓪，先于 fencing）——成功提交后 Run 已非活跃，
  fencing 会直接拒绝重试，幂等若放在 UNIQUE 冲突分支就永远不可达。
- **校验范围 = 契约仓全集**，不是执行端上报集合（否则漏报只读仓即绕过）。
- 三层边界不可越：D3 证明执行过什么、D4 证明交付了什么、D5 才判断是否满足要求。
- `submitted` ≠ 交付完整 ≠ 任务完成。
